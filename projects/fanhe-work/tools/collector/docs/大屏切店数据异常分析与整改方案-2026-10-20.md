# 数据大屏切店数据异常 · 分析与整改方案

编制时间 2026-10-20 01:00  
分析对象 `preview/ops-dashboard-preview.html` 的 `#/screen` 路由及其关联的 6 个业务页、5 个抽屉  
分析方法 把内联脚本抽出为可执行模块，用 Node 直接调用 `pageOverview` / `metricsFor` / `quotaInfo` / `buckets` 等函数，逐店跑数对比，不靠目视

---

## 〇、先纠正一个前提

本项目**没有任何网络请求**。页面数据全部编译期内联在 `html:549-682`，`render()` 是同步函数，不涉及 fetch、Promise、并发。

所以「请求竞态」「接口返回乱序」在本项目里**不存在**，不需要排查。

但用户点名的其余环节全部存在，而且正是病因：

| 你提到的环节 | 本项目里的对应物                                          | 是否存在问题         |
| ------ | ------------------------------------------------- | -------------- |
| 参数传递   | URL hash 的 `s=` + `go()` / `navHref` / `applySet` | 基本正确，两处漏传      |
| 缓存     | `storeSeries` 把序列挂在 `s._cache` 上，**永不过期**         | 有隐患            |
| 状态复用   | 全局 `SER` + 模块级常量被 `pushDemoStore` 就地改写            | **主因之一**       |
| 请求竞态   | 无请求                                               | 当前不存在，代码阶段必然出现 |
| 接口返回   | 无接口；等价问题是「同一屏内选了不同的数据源」                           | **主因**         |

## 一、结论：不是「数据变了」，是「只有一半数据跟着变」

大屏切店时，屏幕上 17 个数字里只有 **4 个**会变，其余 13 个恒定为主店值，而且变的那几个没有任何「演示」标记。用户看到的是「切了店，数字一半对一半不对」。

更严重的是**同一个柱子，切店前后点它，抽屉给出两个不同的数**，而柱子高度一点没变。

三个根因：

1. **大屏不参与 `pushDemoStore`**（`html:2584` 明确 `if (st.route !== 'screen')`），所以模块常量、风险条恒为主店值；但模块卡第 1 张又用 `curM` 读聚焦店 → 同屏两套口径。
2. **堆叠柱与抽屉不同源**：柱子高度 = 五店合计（`html:1834` `sums`），抽屉金额 = 全局 `SER`（`html:2480` `buckets` → `slice`），而 `SER` 在大屏被设成「聚焦店」。
3. **分店金额有两个互不相干的生成源**：交易/大屏走 `storeSeries`（随机形状 + 大促脉冲），商品页走 `ITEMS × ratio`。同店同区间差最多 23.7%。

## 二、切店的完整加载与刷新链路

点一下店铺卡（`html:1803` 或 `html:1856`，都带 `data-set="s=s4"`）：

```
① document click 委托（html:2615）
   └─ e.target.closest('[data-set],...') → 命中 .store 或 <tr>
② el.dataset.set → applySet('s=s4')（html:2626 → 777）
   ├─ readState()            （html:736）从当前 hash 解析出完整状态
   │    · route/g/p/a/b/q 全部重算，a 由 presetRange 或 a1/a2 得出
   │    · s 校验：STORES.some(id) 命中才用，否则回落 'main'
   └─ 只改 st.s，其余字段原样带走
③ go(hashOf(st))             （html:805 → 769）
   ├─ closeDrawer()
   ├─ hash 已含 s= → 不追加
   └─ 若 location.hash 与目标一致 → 直接 render()；否则赋值触发 hashchange
④ hashchange → render()      （html:2680 → 2561）
   ├─ popDemoStore()         还原上一次的缩放（大屏场景是 noop）
   ├─ renderSidebar / renderTopbar   两者都读 storeOf(st.s)，会更新顶栏店名
   ├─ SER = storeSeries(s)    ★ 全局单店序列，大屏也被改了
   ├─ if (route !== 'screen') pushDemoStore(s)   ★ 大屏被排除
   └─ el.innerHTML = pageOverview(st)   整块重绘，无局部更新
```

**关键点**：刷新是「整页 innerHTML 重绘」，不存在局部 patch，所以「哪些数字变」完全取决于 `pageOverview` 内部读了什么。而它同时读了三种源：

| 源                                                  | 位置                                        | 是否随聚焦店变                   |
| -------------------------------------------------- | ----------------------------------------- | ------------------------- |
| `metricsFor(s, a, b)`                              | `html:1783` 五店卡、`html:1784` `curM`        | ✅ 变                       |
| 模块常量 `HEALTH / SERVICE / ADS / CONTENT_MORE / AGG` | `html:1819-1825` 风险条、`html:1866-1872` 模块卡 | ❌ 不变（大屏没缩放）               |
| 全局 `SER`                                           | `html:1832` `buckets` → `slice`           | ⚠️ 变了但只用于取日期骨架，数值未用（侥幸正确） |

## 四、按环节逐一核查

### 4.1 参数传递：基本正确，两处漏传

| 位置                              | 情况                                                                          | 判定        |
| ------------------------------- | --------------------------------------------------------------------------- | --------- |
| `hashOf`（`html:769`）            | 9 个参数全量写出，含 `s`                                                             | ✅         |
| `navHref`（`html:1041`）          | 侧栏、面包屑、模块卡跳转都带 `s`                                                          | ✅         |
| `applySet`（`html:777`）          | 只改指定字段，其余原样带走                                                               | ✅         |
| `go`（`html:805`）                | hash 缺 `s=` 时自动从 `readState()` 补                                            | ⚠️ 兜底而非显式 |
| `openBucket` 的跳转按钮（`html:2502`） | `'#/trade?g=day&p=custom&a1=..&a2=..&cmp=0&q=' + st.q` **不带 s**，靠 `go()` 兜底 | ⚠️        |
| `openRefund` 的跳转按钮（`html:2442`） | 同上，不带 `s`                                                                   | ⚠️        |
| `readState` 对非法 `s`（`html:763`） | 回落 `main`，但**不改写 URL** → 地址栏留着 `s=s9`，页面是主店，刷新后仍是主店                         | ⚠️ 隐性不一致  |

兜底逻辑目前能兜住，但任何绕过 `go()` 直接改 `location.hash` 的新代码都会丢店。属于「靠约定而非靠接口」的写法。

### 4.2 缓存：`_cache` 永不过期

```js
function storeSeries(s){
  if (s.real) return DAILY;
  if (s._cache) return s._cache;   // html:864，没有版本判断
  ...
  s._cache = rows;                 // 挂在 STORES 对象上，活到页面关闭
}
```

- 当前数据是常量，所以无害。
- **接入真实采集后必出问题**：每天数据更新，`_cache` 仍是首次生成的旧序列，切店看到的是旧数据，必须刷新页面才更新；而且 `s._cache` 挂在 `STORES` 上，任何模块都能改它，没有失效入口。

### 4.3 状态复用：三个全局可变状态

| 变量                       | 作用域                   | 风险                                                           |
| ------------------------ | --------------------- | ------------------------------------------------------------ |
| `SER`（`html:820`）        | 全局单店序列，`render()` 每次改 | 大屏也被改成聚焦店；`buckets()` 隐式依赖它，`openBucket` 因此读错源               |
| `FORCE_DEMO`（`html:975`） | 全局布尔                  | 大屏恒 false，所以分店聚焦时模块卡没有「演示」标记                                 |
| `_demoSnap`（`html:2523`） | **单槽快照**              | 若在未 pop 时二次 `pushDemoStore`，前一次快照被覆盖 → 常量永久缩放，`pop` 只能还原最后一次 |

`_demoSnap` 单槽当前不触发（只有 `render()` 一处调用），但 P0-1 那个排序 bug 已经证明「绕过 render 的局部重绘」是现实路径。一旦有人给排序、筛选加二次 push，就会出现复合缩放（0.4×0.4=0.16），且无法还原。

### 4.4 请求竞态：现在没有，代码阶段必有

`render()` 是同步的，没有请求序号、没有 AbortController、没有「最后一次请求获胜」的判定。按交接文档第九节的规划，接口层落地后 `render()` 会变成异步，届时：

- 快速连点 5 个店铺卡 → 5 个请求并发 → 慢响应后到会覆盖快响应，页面显示的不是最后点的那家店。
- 切店 + 切区间同时发生 → 两组参数交叉，可能渲染出「s4 的店 + s2 的区间」。

**建议现在就在文档里定死**：接口层必须带 `requestId`，响应回来比对当前 `hashOf(readState())`，不一致直接丢弃。这是唯一能根治的写法。

### 4.5 接口返回：等价问题是「数据源选择」

无接口，但同一屏里选了三套源（见第二节表格）。更细一层，**分店金额有两个独立的生成算法**：

```
storeSeries:  amt = round(3600 × ratio × (0.35 + 1.5×随机) / 10) × 10
              且 ratio ≥ 0.4 时第 20 天额外加 round(26000 × ratio)
商品页:        amt = ITEMS.amt × ratio   （即 108,000 × ratio）
```

两者的合计对不上：

| 店    | ratio | 交易页 / 大屏（storeSeries 求和） | 商品页（ITEMS×ratio） | 差值                  |
| ---- | ----- | ------------------------ | ---------------- | ------------------- |
| main | 1.00  | 108,000                  | 108,000          | 0                   |
| s2   | 0.22  | 24,880                   | 23,760           | +1,120（+4.7%）       |
| s3   | 0.14  | 13,700                   | 15,120           | **−1,420（−9.4%）**   |
| s4   | 0.40  | 53,450                   | 43,200           | **+10,250（+23.7%）** |
| s5   | 0.09  | 9,750                    | 9,720            | +30                 |

s4 的 10,250 主要来自大促脉冲（`html:871` 只给 `ratio ≥ 0.4` 的店加 `26000×0.4=10,400`）。

## 六、整改方案

### 6.1 先定一个语义问题（需你拍板）

大屏到底是「五店总览」还是「当前店的放大版」？这决定改法：

**方案 A（推荐）：大屏只做五店总览，聚焦店只影响高亮**

- 符合 v3 已定的信息架构（「数据大屏只做跨店总览，单店明细下沉到业务分析」）。
- 模块卡数字改成五店合计 / 主店占比，风险条明确标「主店」。
- 抽屉改成五店合计 + 分店明细，与柱子同源。
- 代价：切店后大屏几乎没有数字变化，只有高亮移动——但这**正是正确的行为**。

**方案 B（过渡）：大屏上所有单店数字都跟随聚焦店**

#### P1-4 分店金额单源化

**修改点**：`storeSeries`（`html:862`）生成后做一次归一化，使合计精确等于 `108000 × ratio`

```js
function storeSeries(s){
  if (s.real) return DAILY;
  if (s._cache && s._cacheV === DATA_VERSION) return s._cache;
  const target = Math.round(108000 * s.ratio);
  const rows = DAILY.map((r,i) => { /* 现有随机逻辑不变 */ });
  // 最大余数法摊平差值，保证合计精确
  const sum = rows.reduce((t,r) => t + r.amt, 0);
  const diff = target - sum;
  if (diff !== 0) {
    const step = diff > 0 ? 10 : -10;
    let left = Math.abs(diff) / 10;
    for (let i = 0; i < rows.length && left > 0; i++, left--) rows[i].amt += step;
  }
  s._cache = rows; s._cacheV = DATA_VERSION;
  return rows;
}
```

### 6.5 代码阶段必须预留（接口化之后）

`render()` 现在是同步的，改成异步后必须做三件事，否则「快速切店」必然出错：

```js
let _reqSeq = 0;
async function render(){
  const st = readState();
  const seq = ++_reqSeq;
  const data = await fetchOps(st);          // 带 shop_id / 区间
  if (seq !== _reqSeq) return;              // 后发先至的响应直接丢弃
  if (hashOf(readState()) !== hashOf(st)) return;  // 参数已变，丢弃
  paint(st, data);
}
```

三条断言：① 响应序号必须是最新的 ② 参数快照必须与当前 hash 一致 ③ 渲染前再读一次 `readState()`，不要用发起请求时的 `st` 直接画。

### 9.1 实施中发现一个比原分析更严重的问题

原分析认为「大屏主店卡不变、只有模块卡第 1 张变」。实际动手改的时候发现相反：

**大屏主店卡读的是全局 `SER`，而 `SER` 在大屏被设成了当前高亮店。**

链路：`pageOverview` → `metricsFor(主店)` → `metrics(a,b)` → `slice(a,b)` → `SER`。

| 主店占比 | 54.1% | **106.4%**（主店卡被替换后算出来的） |

所以用户说的「仅切换店铺数据就发生变化」，最刺眼的就是**主店卡和五店合计**在变——这两个本该是全场最不该动的数字。
