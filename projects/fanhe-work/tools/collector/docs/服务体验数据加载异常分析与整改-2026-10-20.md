# 服务体验板块数据加载异常 · 排查与整改

排查时间 2026-10-20 01:20
排查对象 `preview/ops-dashboard-preview.html` 的 `#/service` 路由及其依赖的数据层
排查方式 把内联脚本抽出为可执行模块，Node 里逐店调用 `pageService` 并解析输出 HTML 对比数值，再配合 Edge headless 实截页面

---

## 一、结论

服务页有 **4 处独立异常**，全部集中在「数据从常量到页面」这一段。没有网络请求，所以不是接口或竞态问题，是**取值路径重复计算**和**控件与数据能力不匹配**。

| # | 异常 | 严重度 | 用户感知 |
| --- | --- | --- | --- |
| 1 | 分店计数类指标被**二次缩放**，实际是 ratio² 量级 | P0 | 切到分店，咨询量只有理论值的 1/3 到 1/2，且各店比例不成体系 |
| 2 | 待处理工单 `TICKETS` 既不缩放也不按店过滤 | P0 | 分店页 KPI 说「1 条待回复」，下面工单却写「5 条评价待回复」，同页自相矛盾 |
| 3 | 时间条可点、可改 URL，但改完什么都不变 | P1 | 以为刷新失效 |
| 4 | 页头区间与「平均每天」写死 30 天 | P2 | 选了 7 天，页头还写 30 天 |

另外连带发现：**推广投放、内容运营两页有第 3 条的同款问题**（时间条纯装饰），一并修了。

---

## 二、逐处排查

### 异常 1 · 分店计数类指标二次缩放（P0）

**现象**：切到分店 3，咨询量显示 10；而主店 216、倍率 0.14，按设计应该是 30。

**定位**：`pageService` 第 2012-2019 行（整改前）

```js
const rows = STORES.map(s => ({
  s,
  rate: demoRatio(s, SERVICE.threeMinRate, 'svc'),
  sec:  demoNum(s, SERVICE.firstRespSec, 'sec'),
  cnt:  demoNum(s, SERVICE.consultCnt, 'cnt'),   // ← 这里
  ...
```

```js
function demoNum(store, base, salt){
  if (store.real) return base;
  const n = seedOf(store.id + salt);
  return Math.max(0, Math.round(base * (0.35 + store.ratio * 0.9) * (0.7 + n * 0.6)));
}                                                   // ← 又乘了一次 ratio
```

**成因**：两套缩放机制并存，没有清理。

- `demoNum` 是**切店机制之前**的写法。那时 `SERVICE` 是常量、不含分店倍率，所以函数内部自己乘 `ratio` 是对的。
- 后来加了 `pushDemoStore`，`SERVICE` 已经在 `walk` 列表里被整体缩成 `主店 × ratio`（`html:2580` 附近）。
- 两者叠加后，实际值是 `216 × ratio × (0.35 + 0.9×ratio) × (0.7~1.3)`，即 **ratio² 量级**，还带一个各店不同的随机因子。

**实测（整改前）**：

| 店 | ratio | SERVICE 已缩放值 | 页面显示 | 应为 |
| --- | --- | --- | --- | --- |
| 主店 | 1.00 | 216 | 216 | 216 ✅ |
| 分店 2 | 0.22 | 48 | **23** | 48 |
| 分店 3 | 0.14 | 30 | **10** | 30 |
| 分店 4 | 0.40 | 86 | **72** | 86 |
| 分店 5 | 0.09 | 19 | **10** | 19 |

主店正常、分店全错，所以只在切店时才暴露——这也是为什么之前几轮验收没发现。

**整改**：

1. 删掉 `demoNum` / `demoRatio`，换成只做小幅抖动的 `jitter`（**不乘 ratio**）。
2. 新增 `scaleSvc(s, v)`，计数类统一从**不可变基准** `SERVICE_BASE` 按店计算：

```js
const SERVICE_BASE = Object.freeze({ ...SERVICE });   // 放在常量区，pushDemoStore 之前

const scaleSvc = (s, v) => s.real ? v : Math.round(v * s.ratio);
```

3. 约定写进注释：**比率 / 时长不随店铺规模变**（只抖动 ±5% / ±25%），**计数类严格按 ratio**。

**为什么不直接用 `SERVICE`**：`SERVICE` 只反映「当前聚焦店」的缩放值，而「各店服务指标」表格要同时显示 5 家。读 `SERVICE` 会让 5 行全部等于当前店的值——这是比二次缩放更隐蔽的错误。

**影响范围**：仅服务页。大屏风险条读 `SERVICE`（不缩放，主店口径），不受影响。

### 异常 2 · 待处理工单不随店铺变化（P0）

**现象**：主店和分店 4 的「待处理」区，三条工单文字一模一样，且写死「5 条评价待回复」；而分店 4 的 KPI 显示「2 条」。

**定位**：`pageService` 第 2100 行（整改前）

```js
${TICKETS.filter(t => t.type === '评价' || t.type === '问大家' || t.type === '商品素材').map(...)}
```

**成因**：两个问题叠在一起。

1. `TICKETS` **不在** `pushDemoStore` 的 walk 列表里（`[ITEMS, BUYERS, SERVICE, ADS, CONTENT, CONTENT_MORE, CHANNELS, AREAS, KEYWORDS, FLOW_SPLIT, ACTIVITIES]`），所以它的数字不随店缩放。
2. 即使放进 walk 也没用——它的条数是**写死在字符串里的**（`'5 条评价待回复，最早一条已挂 4 天'`），缩放改不了文字。
3. 过滤条件只看 `t.type`，没看 `t.store`，所以主店工单会漏到分店页。

**整改**：按店铺分支，不再假装分店有工单。

```js
${cur.real
  ? TICKETS.filter(t => t.store === 'main' && (...类型...)).map(...)
  : `<div class="diag"><span class="badge">未接入</span>
     <p>${cur.short} 的工单数据尚未采集。主店当前：评价待回复 ${SERVICE_BASE.rateUnreplied} 条、
        问大家待答 ${SERVICE_BASE.wendaPending} 条、素材待优化 ${HEALTH.materialExpired + HEALTH.materialIncomplete} 个。</p>
     </div>`}
```

分店页现在显示一条「未接入」说明，并给出主店数字做参照——**参照值必须读 `SERVICE_BASE`**，因为此时 `SERVICE` 已经被缩放成分店值了。

**影响范围**：仅服务页。`TICKETS` 没有其它调用方。

### 异常 3 · 时间条是假控件（P1）

**现象**：点「近 7 天」或「单日」，时间条自己高亮变了、地址栏也变了，但 KPI、表格、页头全部不动。

**定位**：`pageService` 第 2053 行（整改前）

```js
${timeBar(st, false, '本页 6 项指标尚未接入采集，区间选择只改筛选条件，演示值不变')}
```

**成因**：这页的数据是 **30 天整段值**，没有逐日序列，`pageService` 里**没有任何一处读 `st.a`**——区间参数进来后无人消费。但控件照样渲染成可点的分段按钮，用户点了只会看到高亮移动。

文案「区间选择只改筛选条件」也不成立：页面里根本不存在筛选逻辑。

**整改**：换成不可交互的**快照条**。

```js
function snapshotBar(note){
  return `<div class="timebar">
    <div class="tb-item"><span class="tb-label">口径</span><span>30 天整段快照</span></div>
    <div class="tb-item"><span class="tb-label">覆盖</span><span>${DATA_START} ～ ${DATA_END}</span></div>
    <span class="tb-note">${note || '...不按区间聚合，故本页不提供区间选择'}</span>
  </div>`;
}
```

**为什么不是「让它生效」**：响应率、评价待回复、问大家待答本质是「当前状态」类指标，业务上就没有区间维度。真实接入后也应该是一个快照，而不是区间聚合。所以去掉控件比硬造一个筛选更接近正确形态。

**连带整改**：推广投放（`html:2160`）、内容运营（`html:2256`）用的是同款假时间条，同样处理。这两页的指标也全是整段口径，`pageAds` / `pageContent` 里同样没有读 `st.a`。

### 异常 4 · 页头区间与日均口径写死（P2）

**现象**：`me.cnt / 30` 硬编码；页头区间写死 `DATA_START ～ DATA_END`，不看用户选择。

**成因**：早期只有 30 天一种口径，直接写死。加了时间条之后没跟着改，于是「控件可改、文字不变」。

**整改**：
- 日均改用常量 `SAMPLE_DAYS`，文案从「平均每天」改成「30 天日均」，明确口径。
- 页头保留 30 天区间文字——**这是正确的**，因为数据覆盖就是这 30 天，且页面已不再提供区间控件，不存在「选了别的区间」的可能。

---

### 附带修掉的一处：服务保障卡

**现象**：分店 4 也显示「已开通 · 有效期至 2027-03-31」。

**成因**：`SERVICE.protection` 是字符串，`pushDemoStore` 只缩数字，字符串原样保留；服务保障属于店铺资质，分店未必开通。

**整改**：分店显示「未接入 / 分店保障状态尚未采集」，主店读 `SERVICE_BASE`。

## 五、遗留

| 项 | 说明 |
| --- | --- |
| 服务指标接入真实数据 | 6 项仍是演示值。B 批只需把 `qos-core` 的 `dateType=1d` 改 `recent30` 重跑，前 3 项就能变真实值 |
| 分店工单 | 需要分店授权后单独采集，当前用「未接入」空态兜住 |
| `ADS` / `CONTENT_MORE` 的同类风险 | 这两组常量仍在 walk 列表里正常缩放，未发现二次计算；但它们的 KPI 文案里若有写死数字，接入真实数据时要复查 |
