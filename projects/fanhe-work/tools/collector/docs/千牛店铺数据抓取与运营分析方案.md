# 千牛店铺数据抓取与运营分析方案

> 编写日期：2026-10-19
> 适用对象：全屋定制类淘宝/天猫店铺（单人主导运营）
> 目标：把店铺后台的经营数据变成可持续追踪、可做归因的本地数据资产

---

## 一、结论先行

GitHub 上不存在一个开箱即用的「千牛后台运营分析 Skill」。现有项目是三类零散产物：官方报表下载插件、生意参谋接口脚本、商家后台 MCP 服务。它们的共同问题是只解决单点采集，没有数据模型，也没有分析口径。

所以这件事的正确做法是组合三层，自建一层：

| 层 | 用什么 | 解决什么 |
| --- | --- | --- |
| 采集底座 | 官方报表定时导出 | 保证口径权威、稳定不断档 |
| 采集补充 | 登录态接口直取 | 补齐报表拿不到的明细粒度 |
| 数据层 | 本地 SQLite + 建模 | 让不同来源的数据能对齐比较 |
| 分析层 | 静态 HTML 看板 + 周报 | 回答业务问题，产出结论 |

优先级建议：先做采集底座（低风险、三天内见效），跑通后再补接口明细。反过来做，容易在风控上反复卡壳，拿不到稳定产出。

---

## 二、动手前必须澄清的三个事实

### 1. 千牛客户端抓不了，要抓的是网页后台

千牛 PC 端是 Windows 客户端，界面数据走私有协议，抓取成本极高且极易被判定异常。真实的运营数据在三个网页后台里：

- `myseller.taobao.com` 卖家中心，订单、商品、评价
- `sycm.taobao.com` 生意参谋，流量、成交、商品效果、市场
- `one.alimama.com` 阿里妈妈，直通车、万相台花费与 ROI

另有 `qianniu.taobao.com` 网页版工作台，作为入口。方案里说的「千牛后台」一律指这几个网页域名。

### 2. 官方开放平台能拿到数据，但门槛不在技术

淘宝开放平台（`open.taobao.com`）对商家有「自研类应用」通道，官方文档明确写了仅给自己使用、可直接发布上线、不需要审核。这条路合规性最好。

但有三道实际门槛：

- 订单、消费者等敏感数据接口要求应用部署在**聚石塔**（阿里云电商专用环境）内调用，普通本地机器调不通
- 未上线应用的调用流量被限制在 5000 次/天，三个月未上线会被清除
- 生意参谋的流量结构、竞品、关键词数据**不在**开放 API 体系里

结论：官方 API 适合作为长期合规通道，对单人店铺投入产出比偏低。除非后续要接 ERP 或做订单自动化，否则不建议从这里起步。

### 3. 店铺类型决定数据颗粒度

淘宝个人店与天猫店的生意参谋版本不同，能看到的指标和可导出的报表数量差别明显。天猫店通常有更完整的人群、竞品、内容数据。这一步需要登录后实际确认，方案里的报表清单必须按实际可见项裁剪。

## 三、四条通道的横向对比

| 通道 | 数据覆盖 | 稳定性 | 准入门槛 | 风控风险 | 结论 |
| --- | --- | --- | --- | --- | --- |
| 官方开放平台 API | 订单、商品、评价为主，无生意参谋数据 | 最高，平台承诺接口兼容 | 商家主体 + 应用创建 + 聚石塔部署 | 无 | 长期正确，短期过重 |
| 官方后台报表导出 | 生意参谋日报、商品数据、阿里妈妈报表、联盟概览 | 高，走平台自有导出流程 | 只需要登录账号 | 低 | 推荐作为采集底座 |
| 登录态接口直取 | 几乎全量，含报表不提供的明细字段 | 中，依赖接口签名与页面版本 | 需要已登录浏览器 | 中 | 推荐作为明细补充 |
| 页面 DOM 自动化 / RPA | 取决于能点到哪 | 低，改版即失效 | 无 | 中高 | 只在前三条都走不通时使用 |

关键判断依据在稳定性这一列。前两条依赖平台主动提供的出口，平台改版对它们影响小。后两条依赖页面结构，生意参谋历史上每年都有改版，任何基于 DOM 的采集脚本平均寿命在几个月量级。

## 四、推荐架构

```
┌─────────────────────────────────────────────────────────┐
│  采集层（本地 Windows，每日定时）                        │
│                                                          │
│  A. 报表下载器  ──►  raw/reports/YYYY-MM-DD/*.csv        │
│     走官方导出，口径权威                                  │
│                                                          │
│  B. 接口采集器  ──►  raw/api/YYYY-MM-DD/*.json           │
│     CDP 复用已登录 Chrome，页面内 fetch 后台 XHR         │
└──────────────────────────┬──────────────────────────────┘
                           │
┌──────────────────────────▼──────────────────────────────┐
│  数据层（SQLite，单机足够）                              │
│                                                          │
│  标准表：dim_date / dim_item / dim_channel               │
│  事实表：fact_trade_daily / fact_item_daily              │
│          fact_flow_daily / fact_service_daily            │
│          fact_ad_daily / fact_lead                       │
│                                                          │
│  原始数据只增不改，清洗结果可重算                          │
└──────────────────────────┬──────────────────────────────┘
                           │
┌──────────────────────────▼──────────────────────────────┐
│  分析层                                                   │
│                                                          │
│  · 日报：昨日核心指标 + 异常提示                          │
│  · 周报：渠道结构、单品贡献、询单转化、退款归因           │
│  · 看板：本地 HTML + ECharts，可追溯 90 天趋势            │
└─────────────────────────────────────────────────────────┘
```

设计要点说明。

**A 与 B 并存的核心原因是对账。** 同一天的支付金额，报表口径与接口口径可能相差几个百分点，原因通常是退款归属日、跨店优惠分摊、预售定金处理不同。每周拿 A 的汇总去校验 B 的明细，偏差超过 2% 就报警，这样能第一时间发现接口改版或字段变更，避免在错误的数上做分析。

**原始数据只增不改。** 后台数据会回溯变化，退款在次日冲减，昨天的数字今天再抓就不一样。所以每次抓取都存一份带抓取时间戳的原始快照，清洗层按快照时间重建，历史可复现。

## 五、GitHub 现有资源盘点

以下按可用性排序，均标注实际状态，不做美化。

### 值得直接用的

**1. dstmg/taobao-data-download-helper**
`https://github.com/dstmg/taobao-data-download-helper`

Chrome / Edge 的 MV3 扩展，本地运行，不经过第三方服务器。支持生意参谋店铺经营日报与商品数据、阿里妈妈营销场景与商品推广明细、淘宝联盟商家端推广概览。支持自选日期、逐日历史补采、每日定时。

- 协议：MIT
- 状态：2026-10-16 仍在更新，版本 1.2.3
- 边界：作者明确写了不保证免风控、不保证无人值守，验证码与登录失效需人工处理；单次历史补采最多 31 天
- 适用：作为本方案的采集底座 A，几乎不用改代码就能用

**2. jinguichen21-cloud/sycm-analysis-skill**
`https://github.com/jinguichen21-cloud/sycm-analysis-skill`

Skill 形态，通过浏览器会话调用生意参谋的 AI 问数接口（`sycm.taobao.com/ucc/next/message/send.json` 发起，`getReportResult.json` 轮询），拿到一份 Markdown 格式的经营周报，内容含核心结论、访客分析、竞店动向。

- 适用：直接产出「周报」这一层结论，可以嵌进分析层，省掉自己写汇总逻辑
- 边界：只能拿平台已经写好的报告文本，拿不到结构化明细；依赖登录态与接口稳定

### 有参考价值但要自己改

**3. Ecvelnter/sycm 与 mrzeng/sycm**
`https://github.com/Ecvelnter/sycm` / `https://github.com/mrzeng/sycm`

两个同源项目。思路是 Charles 抓包拿到生意参谋的 JSON 接口，把 Chrome cookie 塞进请求头直接请求，再用 tkinter 做界面导出 CSV。抓的是竞品入店搜索词的引流词与成交词。

- 参考价值：演示了「cookie + 后台 JSON 接口」这条路可行，比 DOM 解析稳定
- 局限：代码较老，cookie 手动粘贴，接口参数已可能变化，不能直接跑
- 协议注意：抓的是竞店数据，风控敏感度高于抓自己店铺

**4. wangshan9870/sycm-chrome-plugin**
`https://github.com/wangshan9870/sycm-chrome-plugin`

MV3 插件，在「市场 → 竞店分析」页面自动切换四周、抓取所有卡片商品。适合看它的 content.js 怎么处理分页与卡片遍历。

- 局限：纯 DOM 采集，页面改版即失效；同样涉及竞店数据

**5. TonyWang-hub/mcp-cn-commerce**
`https://github.com/tonywang-hub/mcp-cn-commerce`

中国电商平台商家经营数据的 MCP Server 套件，覆盖抖店、淘宝、京东、快手、小红书等，声称 155 个工具。

- 重要提醒：作者在 README 里自己写明各 SDK 的 `live_verified` 均为 `false`，真实商家验收和后台对账未完成。这意味着它更适合当接口设计的参考，不适合直接接生产
- 价值：它的工具命名与参数设计可以作为你自建采集器的接口抽象参考

**6. jdh1229/tmall-seller-mcp**
`https://github.com/jdh1229/tmall-seller-mcp`

Playwright 驱动的商家后台登录 MCP，支持会话保持、多店铺账号管理、页面导航与截图。

- 价值：会话保持的实现方式值得借鉴
- 不建议：它要求提供账号密码自动登录，与「人工登录、不代填凭据」的安全原则冲突，风控上也更容易被识别

**7. pythonrt/TSDK / fatelei/pytaobao / XiBao/pyTOP**
`https://github.com/pythonrt/TSDK` / `https://github.com/fatelei/pytaobao` / `https://github.com/XiBao/pyTOP`

开放平台 SDK 的 Python 封装，支持签名、请求、常见交易与商品接口。若后续走官方 API 通道，这几个是现成的客户端基础。注意 pyTOP 年代较早，签名方式需核对是否支持 hmac-sha256。

买家视角的商品详情抓取，拿的是前台商品页的价格、评价、问答。与后台经营数据无关，方向不对。

## 六、数据模型与指标口径

这一节是方案的技术核心。采集方式可以换，口径一旦定错，后面所有分析都要推翻重做。

### 表结构

**维度表**

| 表 | 关键字段 | 说明 |
| --- | --- | --- |
| dim_date | date_key, 是否大促, 是否周末 | 大促日单独标记，否则活动期数据无法剥离 |
| dim_item | item_id, 标题, 类目, 上架日, 是否定制 | 定制与非定制要分开，二者的转化逻辑不同 |
| dim_channel | channel_code, 一级来源, 二级来源 | 统一手淘搜索、推荐、直通车、内容、店铺内的口径 |

**事实表**

| 表 | 粒度 | 核心字段 |
| --- | --- | --- |
| fact_trade_daily | 日 | 访客数、支付买家数、支付金额、退款金额、退款笔数、客单价 |
| fact_item_daily | 日 × 商品 | 曝光、点击、加购、收藏、支付件数、支付金额、退款金额、单品转化率 |
| fact_flow_daily | 日 × 渠道 | 访客、支付买家、支付金额、渠道转化率 |
| fact_service_daily | 日 | 咨询人数、有效询单数、询单成交数、平均首响时长、询单转化率 |
| fact_ad_daily | 日 × 计划 | 花费、展现、点击、成交金额、直接 ROI |
| fact_lead | 线索级 | 来源、户型面积、预算区间、跟进阶段、结果、流失原因 |

`fact_lead` 是本方案区别于通用电商分析的关键。全屋定制的决策周期以周甚至月计，客单价高，客户在咨询阶段流失的量远大于下单后流失。生意参谋的漏斗止步于支付，看不到「聊了但没成」这一段的真实原因。这张表只能从客服聊天记录和跟进备注里人工或半自动沉淀，价值高于其他所有表。

### 指标口径（建议固定下来，写进配置）

| 指标 | 定义 | 注意点 |
| --- | --- | --- |
| GMV | 支付金额，含未发货、未确认收货 | 与平台「支付金额」对齐，不自行加减 |
| 净收 | 支付金额 − 退款金额 | 退款按退款成功日归属，与支付日可能跨天 |
| 客单价 | 支付金额 ÷ 支付买家数 | 用买家数不用订单数，定制行业一客多单常见 |
| 询单转化率 | 询单成交人数 ÷ 有效询单人数 | 有效询单需剔除「在吗」无应答；口径要写清 |
| 退款率 | 退款金额 ÷ 支付金额 | 按金额算，按笔数算会失真 |
| 单品贡献 | 支付金额 − 退款 − 广告花费分摊 | 广告分摊建议按点击占比，不用平均分摊 |
| 内容/搜索占比 | 各渠道支付金额 ÷ 总支付金额 | 用于判断流量结构是否健康 |

口径纪律：任何一张图上的数字，必须能追溯到某张表的某个字段和某个过滤条件。做不到就先别上图。

## 七、分阶段实施计划

### Phase 0 口径盘点（预计半天）

登录三个后台，完成三件事：

1. 确认店铺类型与生意参谋版本，列出实际可见的报表和可导出项
2. 列出你想回答的 5 个业务问题，后续所有表结构围绕这 5 个问题设计
3. 手工导出最近 30 天的核心报表，作为后续自动化的校验基准

**验收标准**：产出一份 `docs/报表清单.md`，含报表名、路径、字段名、可导出粒度、历史可回溯天数。

### Phase 1 采集底座（预计 1 天）

安装 `taobao-data-download-helper`，配置每日定时，把生意参谋店铺经营日报与商品数据下载到固定目录。

配套写一个轻量归档脚本，把浏览器默认下载目录里的文件按日期重命名并移动到 `raw/reports/YYYY-MM-DD/`，同时记录一份 manifest。

**验收标准**：连续 3 天早上检查，文件齐全、日期正确、无重复。中途手动重登一次，确认定时任务在登录恢复后能继续。

### Phase 2 接口明细采集（预计 2 至 3 天）

复用本机已有的 CDP 通道（`web-access` skill），在你已登录的 Chrome 里打开生意参谋页面，通过页面上下文的 `fetch` 直接请求后台 JSON 接口，拿商品级与渠道级的日明细。

工程结构建议：

```
qianniu-shuju/
├─ config/
│  ├─ metrics.yaml        指标口径定义
│  └─ collectors.yaml     采集任务清单与频率
├─ collectors/
│  ├─ report_download.py  官方报表归档
│  ├─ sycm_api.py         生意参谋接口
│  └─ common.py           登录态检查、重试、限速
├─ raw/
│  └─ YYYY-MM-DD/
├─ etl/
│  ├─ schema.sql
│  └─ transform.py
├─ warehouse/qianniu.db
└─ reports/
```

关键工程约束：

- 单日单接口只请求一次，请求间隔加 3 至 8 秒随机抖动
- 遇到 302 跳登录页立即停止并提示，不做自动重登
- 每个接口响应落一份原始 JSON，带 `fetched_at` 时间戳
- 接口签名参数若来自页面全局变量，运行时从页面读取，不硬编码

**验收标准**：连续 5 天自动跑通，商品级明细与官方报表的商品数据偏差在 2% 以内。

### Phase 3 落库与清洗（预计 1 至 2 天）

建立 SQLite 库，按第六节的表结构建表。清洗逻辑独立成模块，输入是 `raw/` 下的原始文件，输出是标准表，可随时全量重算。

**验收标准**：清空数据库，一条命令能从 raw 全量重建，结果与上次一致。

### Phase 4 分析与看板（预计 2 天）

先做日报，再做周报，最后做看板。顺序不能颠倒，因为日报能最快暴露数据质量问题。

日报内容建议固定为六行：支付金额、支付买家数、客单价、询单转化率、退款金额、广告 ROI，每项附同比与环比，异常项标红。推送方式用本地 Markdown 文件，配合现有的自动化任务每天定时生成。

周报回答四个问题：本周钱从哪来、哪些单品在贡献、询单在哪一步流失、退款集中在哪类订单。

**验收标准**：周报里每个结论都能点回对应的数据表；连续两周的周报不出现「数据缺失」导致的结论空缺。

### Phase 5 校验与维护（持续）

- 每周一次 A/B 双源对账，偏差超 2% 报警
- 每月检查一次接口是否改版，检查方式是看响应字段数是否突变
- 建一份 `docs/field-changelog.md`，记录每次字段变更与应对

## 八、风险与合规边界

这一节建议逐条遵守，出问题的代价远大于收益。

**合规边界**

- 只采集自己店铺、自己账号有权查看的数据。竞店数据平台只提供加工后的指数，绕过展示层去取原始数据，风险等级完全不同
- 不破解验证码，不伪造设备指纹，不使用代理池切换 IP
- 不代填账号密码。登录一律由本人扫码完成，脚本只复用已建立的会话
- 数据只存本地，不上传任何第三方服务器

**技术风险**

| 风险 | 表现 | 应对 |
| --- | --- | --- |
| 登录态过期 | 接口 302 跳登录页 | 停任务、本地提示、人工扫码后恢复 |
| 接口改版 | 字段缺失或结构变化 | 字段数突变检测 + 双源对账兜底 |
| 风控触发 | 滑块、限流、要求二次验证 | 降低频率、拉长间隔、暂停当日任务 |
| 数据回溯 | 昨日数字今日变化 | 原始快照 + `fetched_at`，清洗按快照重建 |
| 电脑关机 | 定时任务未执行 | 补采机制，检测到缺口自动补最近 7 天 |

**一个必须接受的现实**：任何基于登录态自动化的方案，都不存在真正意义上的无人值守。验证码、异地登录、平台大促期间的风控加严，都需要人工介入。方案设计上要把「人工介入」纳入正常流程，视为系统的一部分。若把它当成异常，很容易因为一两次失败就否定整套系统。

## 九、需要你先确认的五件事

在开工前，这五项信息决定了 Phase 0 的具体动作：

1. **店铺类型**：淘宝个人店还是天猫店。这决定生意参谋能看到哪些模块
2. **日均订单量级**：日均 10 单以内和 100 单以上，采集频率与存储设计不同
3. **最想回答的三个问题**：例如「哪个价格带的咨询转化最高」「直通车该不该继续投某款」「退款集中在哪个环节」
4. **是否接受每天手动扫一次码**：若不能接受，采集底座只能退化到官方报表下载这一条路
5. **分析产出的消费方式**：自己看本地文件、发给合伙人、还是要手机随时看。这决定看板形态
