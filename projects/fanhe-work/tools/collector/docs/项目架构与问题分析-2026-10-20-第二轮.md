## 一、结论速览

**一句话结论** 采集链路与数据口径是可用资产，展示层是负债。全部新发现的错误都指向同一个根因，即「为演示分店而生的常量缩放机制」，它是一副应当拆除的脚手架，不应带进代码阶段。

| 维度 | 评价 | 本轮实测依据 |
| --- | --- | --- |
| 采集链路 | 稳 | CDP 旁路录制是当前唯一可行路径，17 页可一次跑完，盘符与运行时全部自动探测 |
| 数据转换 | 中 | 三种结构识别准确，66 张表全部可回溯到源接口；但接口名靠 28 条硬编码映射，噪音靠 26 条正则排除 |
| 数据口径 | 强 | 四处交叉校验全部等于 108,000，本轮复核未漂移 |
| 展示层 | 弱 | 2803 行单文件，数据块是 CSV 的手工副本，无生成脚本、无数据断言 |
| 演示分店机制 | 高风险 | 3 处新发现的错误全部由它引起，且其中 1 处已潜伏成同类事故的复现条件 |
| 工程规范 | 中偏弱 | git 已建（4 次提交，工作树干净）；仍有 10 个探测脚本与主链路混放，663 MB 死重量未清 |

**优先级判断** 页面层继续打磨的边际收益已接近零，但转代码阶段之前必须先补一道数据契约，否则「手抄数据」这个缺陷会被直接带进数据库设计。

## 四、核心代码逻辑

### 4.1 采集层：为什么必须旁路录制

生意参谋有 baxia 风控，页面内注入的 `fetch` 与 `XMLHttpRequest` 一律返回 `TypeError: Failed to fetch`，隔离世界同样失败。新标签直接导航到 `.json` 接口地址会 `DNS_PROBE_FINISHED_NXDOMAIN`。唯一可行路径是让页面自己发请求，在 CDP 的 Network 事件上截取响应体。

`collect.mjs` 的实现要点：

1. `PUT /json/new?<编码后的完整 URL>` 建标签并直接导航，不做二次 `Page.navigate`（二次导航返回值稳定是 `about:blank`）。
2. 连接 `webSocketDebuggerUrl` 后先 `Network.enable`，并把 `maxTotalBufferSize` 提到 200 MB，否则大响应体拿不到。
3. `responseReceived` 时按三条规则筛出业务接口，即类型为 XHR/Fetch、域名含 `sycm.taobao.com`、命中 `DATA` 白名单且不命中 `NOISE` 黑名单。
4. `loadingFinished` 时才调 `getResponseBody`，保证响应完整；小于 30 字节或以 `<` 开头的直接丢弃。
5. 文件名由接口末段与截断的 query 拼成，`_manifest.json` 记录页面 URL、body 前 200 字与每个文件的来源 URL，后续 `build_csv.py` 靠它还原中文表名。
6. 每页固定等待 `WAIT`（默认 40 秒），17 页全量约 11 分钟。

**设计上的两处硬编码** 端口 9222 与 `WAIT` 都不可在运行中调整，多实例并行或换端口需要改代码。

### 4.2 转换层：三种结构的识别优先级

`convert()` 的判定顺序决定了同一份 JSON 会落到哪张表：

1. 先试 `convert_series`。若 `data` 含 `lastDay` 且有元素为字典的列表，按「序列末端对齐 `lastDay`」倒推日期，输出 `__逐日.csv`。这是唯一能产出逐日序列的路径。
2. 再判 `is_metric_map`。若字典中至少 60% 的值的结构含 `value` 键，输出 `__指标长表.csv`，把 `cycleCrc` 与 `value` 拆成两列。
3. 最后递归 `scan` 所有记录列表，每个列表单独出一张 `__<路径>.csv`，嵌套对象用 `a.b` 展开，`x.value` 与 `x.cycleCrc` 压平成 `x` 与 `x_环比`。
4. 三者都没命中才退化到 `__单行.csv`。

去重逻辑是全局 `seen_url`，以 `url.split('&_=')[0]` 为键，同一接口只保留第一次出现的那份。这解释了为什么 `flow-shopsource` 落盘了两份同名接口却只出一类表。

### 4.3 展示层：五个分层与两个全局状态

页面按「数据 → 工具 → 状态 → 计算 → 片段 → 页面 → 事件」七段组织，`st`（状态对象）贯穿全链路。全局可变状态只有两个。

**`SER`（当前店铺日序列）** 是全部区间计算的隐含输入。`slice` / `metrics` / `buckets` / `quotaInfo` 默认读它。这正是历史事故的病根，主店在大屏上被当成「当前高亮店」算出 43,200。修复方式是给 `metrics` 与 `buckets` 增加显式的 `ser` 参数，主店一律传 `DAILY`。

**`FORCE_DEMO`（整页强制演示标记）** 与 `_demoStack` 快照栈配对使用。`pushDemoStore(s)` 按 `ratio` 就地缩放 11 组常量的计数类字段，`popDemoStore()` 按栈还原。缩放白名单 `DEMO_KEEP` 只有 `status` / `kwCtr` / `firstRespSec`，另加 `crc$` / `rate$` / `ratio$` 三个后缀规则。

**计算层三档口径** 是本项目最重要的设计约束，也写在每个 KPI 卡右上角的徽标上。

| 档位 | 含义 | 适用指标 |
| --- | --- | --- |
| 逐日 | 区间内逐日数据精确求和 | 支付金额 |
| 折算 | 按覆盖天数等比折算（日均法） | 买家数、访客数、加购、收藏 |
| 整段 | 不随区间变化 | 跳失率、停留时长、退款、地域、搜索词 |
| 演示 | 尚未接入采集 | 其余 16 项新增指标 |

### 4.4 状态层：URL hash 是唯一状态源

`#/<route>?g=&p=&a1=&a2=&cmp=&b1=&b2=&q=&s=` 九个参数承载全部界面状态。`readState()` 做四件事，即路由白名单校验、预设区间换算、日期 clamp 到数据范围、非法 `s` 回落主店并用 `replaceState` 同步地址栏。所有交互最终都走 `go(hash)` 或 `applySet(expr)`，不维护第二份内存状态。

这套设计的好处是分享链接口径一致、刷新不丢状态；代价是每次点击都要重新解析并重渲染整页，无法做局部更新。

### 4.5 门禁：把口径写成断言

`check_store_switch.mjs` 把 HTML 的内联脚本抽出来，给 `document` / `window` / `location` / `history` 打桩，在 Node 里直接调纯函数断言。这是当前唯一能防回归的机制。

本轮实跑结果 17 条断言全部通过，退出码 0。

```

PASS  任意聚焦下主店卡恒 108,000、页脚恒 199,800
```

## 八、分析结论

### 8.1 三个根因，一个来源

三条 P0 里，第 1 条与第 3 条的直接原因都是「常量被就地缩放」这套机制，第 2 条与它无关但同属计算层。

这套机制的本质是用**可变全局状态模拟多店**。它的实现是巧妙的，栈式快照解决了嵌套还原，`DATA_VERSION` 指纹解决了缓存失效，`keepKey` 后缀规则解决了比率不缩放。但它有三个结构性代价。

1. **覆盖不完备无法在编译期暴露**。`walk` 的列表是手写的 11 项，新增常量忘了加进去就静默出错，`REFUND` 就是这么漏的。
2. **调用顺序成了隐式契约**。`metricsFor` 在缩放态下会二次乘 ratio，正确性依赖「大屏路由不缩放」这个约定，而这个约定只存在于注释里。
3. **基准会分叉**。`SERVICE` 与 `SERVICE_BASE` 并存就是分叉的结果，修一次事故就多一份基准，长期必然读错。

### 8.2 辩证看待「原型已饱和」这个判断

前一轮的结论是「继续打磨原型收益很低，应转采集与 git」。这个判断对了一半。

**成立的部分** 剩余 16 项指标的缺口全部卡在跨后台登录态与分店授权，属采集侧问题。页面再怎么改也变不出真实数据，这个瓶颈是硬的。

**需要修正的部分** 现在直接转代码阶段，会把「手抄数据」和「可变全局状态模拟多店」两个缺陷原样带进 `ecom_metric_daily` 的设计。后果是数据库里出现一套为演示而生的缩放逻辑，而真实分店数据接入后它必须整体拆除。拆除成本远高于现在补一道数据契约。

所以正确顺序是**先补数据契约，再转代码**。数据契约的产物（CSV 字段到页面字段的映射）可以直接复用为 `ingest.ts` 的 schema 草案，属一次投入两处收益。

### 8.3 一个需要明确的架构决策

`pushDemoStore` 这套机制**不应在梵禾 Work 里复刻**。真实分店数据接入后，五店指标应当各读各的序列，缩放机制整体删除。这一点建议写进代码阶段的设计约束，否则很容易被当作「已验证可用的方案」照搬。

## 十二、流量分析页区间不联动专项（2026-10-20 10:35，提交 `bd4eb0f`）

### 12.1 现象与定位

用户反馈切换时间区间后，流量分析页所有数字都不变。

实测确认，`pageFlow` 对 `st.a` 只有两处引用，都在非数值位置，页头日期文字与一张跳转链接的 `a1`/`a2` 参数。六张 KPI、渠道拆分三项、渠道结构三行、内容访客四项、新老买家两项，全部直接读模块常量。

| 区块 | 原实现 | 是否随区间变 |
| --- | --- | --- |
| 页头日期文字 | `st.a[0]` / `st.a[1]` | 变（仅文字） |
| 时间条高亮 | `timeBar(st)` | 变（仅高亮） |
| 六张 KPI | `AGG.uv.v` / `itmUv.v` / `pv.v` / `bounceRate.v` / `stayTime.v` / `uvValue.v` | 不变 |
| 渠道拆分 | `FLOW_SPLIT.rec` / `search` / `flowOther()` | 不变 |
| 渠道结构 | `CHANNELS.map(c => c.uv)` | 不变 |
| 内容访客 | `CONTENT.map(c => c.uv)` | 不变 |
| 新老买家 | `BUYERS.newCnt` / `oldCnt` | 不变 |
| 地域 / 搜索词 | `AREAS` / `KEYWORDS` | 不变 |

这与服务体验页、推广投放页、内容运营页此前的问题是同一类，但那三页已经改成 `snapshotBar()` 静态说明，控件消失。流量页保留了完整时间条却没有数据响应，形态上更隐蔽，用户会以为页面卡住。

### 12.2 根因

缺少一个把 `(a, b)` 映射成流量指标的中间层。交易页有 `metrics()`，商品页有按 `ITEMS × ratio` 的折算，大屏有 `metricsFor()`，唯独流量页直接从常量渲染。

### 12.3 修复

新增 `flowMetrics(a, b)`，按三组口径输出，页面逐块标注。

| 分组 | 指标 | 处理 |
| --- | --- | --- |
| 折算 | 全店访客、商品访客、PV、推荐 / 搜索 / 其他、渠道 UV、新老买家、内容访客 | 按 `cov / 30` 等比 |
| 整段 | 跳失率、停留时长、人均浏览、渠道转化率与同行基准 | 保持 30 天原值 |
| 固定口径 | 地域 Top 10、引流搜索词 | 不随区间变，卡片标题标注 |

三个关键设计点。

1. **「其他」取残差**。`other = uv - rec - search`，保证三项之和恒等于折算后的全店访客。若三项各自四舍五入，会出现差 1 的情况。
2. **访客价值改成派生值**。`uvValue = 区间支付金额 / 折算访客`。30 天时 108,000 / 3,890 = 27.763496，与接口原值逐位相等，所以整段视图不受影响；7 天时是 13,500 / 908 = 14.87，这才是有意义的区间指标。

## 十三、访客 / 买家改为逐日真值（2026-10-20 11:00，提交 `44bfa45`）

### 13.1 起因

页面单日视图有一行红字「支付金额为当日真实值，买家 / 访客只能按 30 天日均折算」。用户要求页面直接体现抓取到的真实值，不要对支付金额做任何折算。

先说清一件事：支付金额本来就没有被折算。`metrics()` 里只有一个 `reduce` 求和，单日就是当日原始值，多日就是逐日相加，没有任何系数。红字把「支付金额为真值」和「买家 / 访客要折算」写在同一行，读起来像是支付金额也被处理过。

真正需要解释的是买家 / 访客为什么折算。答案在接口能力上，但这个答案在本次核查中被推翻了。

### 13.2 推翻既有结论

项目文档和前两轮评审都断言「只有支付金额有逐日序列」，理由是 `getTendency` 的 URL 里写着 `indexs=payAmt`。这句话前半段对、后半段错。

```
data.my = { statDate: ['09-19', ...30 项], uv: [...], payByrCnt: [...], itmUv: [...] }
```

逐日访客、逐日支付买家、逐日商品访客一直就在这份 JSON 里。数据早在 `data/raw30/flow-overview/04_trend.json` 躺着，从来没有缺失过。

### 13.9 本次踩的两个坑

**第一，Python 文本模式写文件会改换行符。** 我用 `io.open(p,'w',encoding='utf-8')` 做批量替换，Windows 上默认把 `\n` 转成 `\r\n`，三个文件各有几百到三千处被改，git 里表现为整文件重写。改成 `io.open(p,'wb')` 处理字节，或显式 `newline=''`。

**第二，同一个仓库里换行符并不统一。** `preview/*.html` 是 CRLF，`scripts/*` 是 LF。`* -text` 让 git 按字节存，所以任何一侧被改动都会产生整文件 diff。修改前先确认目标文件的原有换行符，别假设全局一致。

### 14.2 一个必须先解决的量纲问题

四个指标的量级差两个数量级。

| 指标 | 区间范围 | 单位 |
| --- | --- | --- |
| 支付金额 | 0 ～ 49,000 | 元 |
| 访客数 | 16 ～ 568 | 人 |
| 买家数 | 0 ～ 7 | 人 |
| 转化率 | 0 ～ 10.20% | 百分比 |

放进同一个线性坐标轴，金额会把其余三条压成贴底的直线，等于只画了一条。常见的三种处理各有代价。

1. **双 Y 轴**：只能容纳两个量纲，四条指标里必然有一条被牺牲。
2. **对数轴**：能压住跨度，但 0 值无法表示，且运营人员读不懂刻度。
3. **各自归一化**：四条都看得见，但绝对值不可读。

本项目选了第三种，理由是这张图的用途是看趋势与拐点，绝对值在上方五店卡、跨店对比表、页脚合计三处都有。归一化按每条曲线在本区间的峰值，图注写明「只比趋势不比高低」，页脚给出区间合计，悬停给当日真值。这样读者有三条路径拿到绝对值，不会误读。

- `lineChartSVG(rows, on)`：纯 SVG 绘制，网格 5 条、折线、悬停热区、X 轴标签。`on` 是当前勾选的指标列表。
- `openStackTrend(st)`：原堆叠图移入抽屉。

图例勾选状态存进 URL 的 `ls` 参数，与「地址栏是唯一状态源」的既有约定一致。参数缺省表示四项全开，显式空值表示全关，所以分享链接能带上勾选组合。

## 十五、折线图切店不刷新（2026-10-20 11:30，提交 `a65c6a0`）

### 15.1 现象

点上方的店铺分段控件，五店卡、跨店对比表的当前行、页头文案都跟着变，右侧折线图一条曲线也不动。

### 15.2 根因：数据绑定漏了参数

排查顺序是先排除监听与缓存，再查数据源。

- **事件监听没问题**。切店走 `data-set="s=xxx"` → `applySet` → `go(hash)` → `hashchange` → `render()`，整页重渲染，折线图也被重画。
- **没有缓存问题**。折线图没有记忆化，每次 `render()` 都重新计算。
- **数据源有问题**。四个地方各自把店铺钉死：

| 位置 | 原写法 | 后果 |
| --- | --- | --- |
| `trendRows` 的金额循环 | `for (const r of DAILY)` | 只读主店日序列 |
| `trendRows` 的访客/买家循环 | `for (const r of DAILY_FLOW)` | 只读主店逐日流量 |
| 调用处 | `trendRows(st.a[0], st.a[1], st.g)` | 根本没有店铺参数可传 |
| 页脚合计 | `metrics(st.a[0], st.a[1], DAILY)` | 显式指定主店序列 |
| 卡片标题 | 硬编码「主店」 | 切店后标签也不变 |

结论：函数签名缺一个参数，导致整条数据链路拿不到当前店铺。重渲染发生了，但重算的结果和上一次完全一样。

这类缺陷的特征是「看起来像没刷新」，实际每次都在算，只是输入没变。它比缓存失效更难发现，因为没有任何报错，也没有旧值残留的迹象。

### 15.3 修正

`trendRows(a, b, g, store)` 增加店铺参数，内部改两处取数。

- 金额走 `storeSeries(store)`。主店返回真实 `DAILY`，分店返回缓存的生成序列，与交易页、五店卡同源。
- 访客与买家只有主店有逐日真值，分店按 `ratio` 缩放。转化率由缩放后的两者相除得出，因此不随倍率变化，与既有约定一致。

调用处传 `cur`，页脚改用 `metricsFor(cur, a, b)`（这个函数本来就处理了分店的倍率与基准问题），标题改为 `${cur.short} 四指标趋势` 并挂「真实」或「演示」小标。

### 15.4 顺带炸出来的取整事故

第一版按简单方式缩放，逐日 `Math.round(r.byr * ratio)`。切换分店 5 之后曲线几乎贴地，一查发现买家数只剩 1 人。

原因是分店买家每天只有 0 到 7 人。分店 5 的倍率是 0.09，`Math.round(4 × 0.09) = 0`，绝大多数日子被抹成 0，30 天累加只剩 1，而正确值应该是 `92 × 0.09 ≈ 8`。

逐日取整对小整数是灾难性的：误差不随机抵消，而是系统性向 0 收缩。

改成最大余数法（`scaleAlloc`）：先按比例摊成小数并向下取整，再按小数部分从大到小把剩下的单位补回去，保证合计严格等于 `round(总量 × 倍率)`。

| 店铺 | 倍率 | 逐日 round 的买家 | 最大余数法 | 应有值 |
| --- | --- | --- | --- | --- |
| 分店 2 | 0.22 | 23 | 20 | 20 |
| 分店 3 | 0.14 | 21 | 13 | 13 |
| 分店 4 | 0.40 | 44 | 37 | 37 |
| 分店 5 | 0.09 | 1 | 8 | 8 |

访客数因为基数大（16 到 568），逐日取整影响较小，但同一套方法一并处理，避免两套逻辑。

### 15.5 一个约定需要开例外

项目此前有一条硬约定：`#/screen` 是五店总览，切店只移动高亮，任何数字都不许变。这条约定的目的是防止「聚焦分店 4 时主店卡掉到 43,200」那类事故重演。

折线图改成单店视图之后，与这条约定直接冲突。处理方式是把例外写清楚，而不是悄悄破坏约定。

- 折线图是整屏唯一的单店区块，标题带作用域小标说明当前是哪家店、是真实还是演示。
- 门禁断言 ① 在比较前剔除 `.chart-card` 块，其余区块（五店卡、跨店对比、模块卡、页脚）继续受「切店不变」保护。
- 新增 7 条断言专门校验折线图确实跟着店铺变，防止以后为了「回到旧约定」把参数又去掉。

## 十七、交互后页面跳回顶部（2026-10-20 11:55，提交 `a27c7fe`）

### 17.1 现象

页面滚到下方后，点时间条、店铺切换、表头排序、图例勾选中的任何一个，视口立刻回到顶部。

### 17.2 根因：一行无条件的归零

`render()` 末尾写着：

```js
el.scrollTop = 0;
```

`el` 是 `#content`，页面真正的滚动容器（`.content{flex:1;overflow-y:auto}`，外层 `.app` 是 `height:100vh;overflow:hidden`，所以 window 不滚）。

这行代码在原型阶段是合理的：每次换页面都从头看。问题是整页只有一个渲染入口，换页和同页改筛选共用它。切区间、切店铺、排序、图例勾选全部走 `render()`，于是也被一起归零。

### 17.3 排除的三种可能

- **不是锚点跳转**。页面里没有 `<a href>`，所有交互都是 `button` 加 `data-set`，hash 是 `#/route?...` 这种形式，不对应任何元素 id，浏览器不会做锚点滚动。
- **不是表单提交**。日期输入用的是 `<input type="date" data-date>` 加 `change` 事件，没有 `<form>`，不会触发默认提交与跳转。
- **不是路由跳转的副作用**。hash 变化本身不会滚动，因为 hash 不匹配元素 id。真正的滚动来自 `render()` 里那一行。

### 17.4 最小修法

只动 `render()`，改两个位置。

```js
let _lastRouteRender = null;

function render(){
  const st = readState();
  const el = document.getElementById('content');
  /* 重写 innerHTML 会清空 scrollTop，所以必须在写之前读出来 */
  const sameRoute = _lastRouteRender === st.route;
  const keepTop = sameRoute ? el.scrollTop : 0;
  ...
  el.scrollTop = keepTop;
  _lastRouteRender = st.route;
}
```

三个要点。

1. **必须在写 `innerHTML` 之前读**。写 innerHTML 会让浏览器把 scrollTop 归零，写完再读只会拿到 0。
2. **只比较路由，不比较参数**。同路由不同参数（切区间、切店铺、图例）要保留位置；换路由才归零。
3. **不动 `go()` 与事件委托**。按钮的原有功能一行没改，只是渲染结束后的落点变了。

### 17.5 验证方式

静态检查发现不了滚动问题，必须真跑。做法是复制一份页面，在 `</body>` 前注入一段脚本，模拟滚动、点击、再读回 scrollTop，把结果写进一个带 id 的 div，然后用 `msedge --headless=new --dump-dom` 输出 DOM 并 grep 那个 id。hashchange 是异步的，脚本里每个动作后面要 `await sleep(200)`。

实测六种交互。

| 交互 | 滚动前 | 滚动后 | 期望 |
| --- | --- | --- | --- |
| 切区间（30 天 → 7 天） | 600 | 600 | 保留 |
| 切店铺（主店 → 分店 4） | 420 | 420 | 保留 |
| 商品页表头排序 | 520 | 520 | 保留 |
| 大屏图例勾选 | 300 | 300 | 保留 |
| 打开抽屉 | 260 | 260 | 保留（本来就不重渲染） |
| 换页到商品分析 | 380 | 0 | 归零，hash 变为 `#/items` |

这套方法比截图更可靠：截图只能看顶部有没有回去，注入脚本能直接断言数值。

### 17.6 门禁补充

新增 3 条，总数 55 增至 58。用 Node 造一个模拟浏览器的 `#content`：`innerHTML` 的 setter 会把 `scrollTop` 清零，与真实浏览器行为一致，然后连续调 `render()` 观察落点。

```
PASS  同页切区间保留滚动位置  → 实测 500
PASS  同页切区间没有渲染失败
PASS  换页回到顶部  → 实测 0
58 passed, 0 failed
```

第二条断言是必要的。`render()` 里有 try/catch，渲染失败时也会写 innerHTML（从而把滚动清零），只测滚动位置会让「渲染挂了」也显示为通过。

## 十八、截图脚本改为无头模式（2026-10-20 12:05，提交 `4717a7b`）

### 18.1 原脚本的三个问题

`scripts/shots-all.ps1` 是 CDP 时代的产物，沿用至今已经不合适。

1. **拍的是旧基线**。对比模式那张图的 URL 写死 `b1=2026-09-19&b2=2026-10-03`，正是第七节修掉的错误区间（B 落在 A 内部）。脚本不改，每次重跑都会把这个错误重新固化到截图里。

| 项目 | 改动前 | 改动后 |
| --- | --- | --- |
| 启动方式 | 调试端口 9222 + CDP 驱动 | 无头直截，一次性进程 |
| 依赖 | Edge + Node（`shot.mjs`） | 只需 Edge |
| 收尾 | `Stop-Process` 关掉全部 Edge | 进程自行退出，不动别的窗口 |

### 18.3 一个 PS 5.1 的坑

改完第一版跑起来立刻中断：

```
msedge.exe : 314321 bytes written to file ...screen-30d.png
    + FullyQualifiedErrorId : NativeCommandError
```

截图其实已经生成了，但脚本把它当成了致命错误。原因是 Edge 把「N bytes written」写到 stderr，而 PS 5.1 会把 native 程序的 stderr 包装成 error record，配上 `$ErrorActionPreference = 'Stop'` 就直接终止。

第一次运行只出了第一张就退出，其余十张没跑。

解法是把调用包起来，临时把偏好降为 `Continue`，调用完再改回 `Stop`。

```powershell
$prev = $ErrorActionPreference
$ErrorActionPreference = 'Continue'
& $edge @cliArgs 2>&1 | Out-Null
$ErrorActionPreference = $prev
```

值得记的一点：这类「命令成功但被判定为失败」的情况，在 PowerShell 调 native exe 时很常见，判断依据要看产物是否存在，不能只看退出码或错误流。

## 十九、数据对账门禁（2026-10-20 12:10，提交 `c17a258`）

### 19.1 为什么先做对账而不是生成

前三轮评审反复指出「CSV → 页面数据靠手抄」是整条链上唯一不可复现的一环。合理的下一步是写生成脚本，但直接写生成脚本有个隐患：**没有任何东西能证明生成结果和现状一致**。

### 19.2 脚本做了什么

`node scripts/check_data.mjs` 把 `csv30` 重新推导一遍，与页面里的同名常量逐项比对。

| 常量 | 来源 | 项数 |
| --- | --- | --- |

### 19.3 精度策略：两档而不是一档

首跑结果是 5 组通过、3 组失败。三类差异全部是**手抄时截断的位数**，不是数据漂移。

| 常量 | 页面值 | CSV 值 | 性质 |
| --- | --- | --- | --- |
| BUYERS.newCrc | -0.5417 | -0.5416666667 | 存了 4 位小数 |
| CONTENT[0].crc | 7.227 | 7.2268656716 | 存了 3 位小数 |
| AREAS[0].ratio | 0.1857 | 0.18571428571428572 | 存了 4 位小数 |

这些字段只用于格式化显示（`pct(x,1)`、`signed()`），不参与任何计算或锚点校验，截断无害。

但一刀切放宽容差会让脚本失去意义。所以分两档：

- **整数与金额逐位比**。1 元的漂移在 108,000 上是 9e-6 相对误差，远超 1e-9 的容差，一定被抓。
- **浮点给 1e-9 相对容差**，比率类再额外给 1e-3 绝对容差，并且**把实测最大偏差打印出来**。

第二档的关键是「打印偏差」。放行不等于无视，每个带容差的常量都会显示 `最大偏差 1.3e-8（显示精度截断，在容差内）`，读者一眼能看出它是真的对齐还是靠容差糊过去的。

```
PASS  BUYERS        4 项  最大偏差 3.3e-5（显示精度截断，在容差内）

PASS  KEYWORDS      8 项  逐位一致
8 组常量通过，共 8 组 / 0 处失败
```

### 19.4 检测能力的自证

一个永远返回 PASS 的检查等于没有。这次运气好：首跑就抓出 3 组差异，说明比较逻辑确实在工作，而不是空跑。

四个金额锚点也一并校验并通过：逐日求和、`AGG.payAmt`、10 个商品金额相加、退款率反算，全部 108,000。商品加购合计 111,000 作为 INFO 打印，不参与锚点，因为它本来就比支付金额多 3,000（漏损空间）。

### 19.5 覆盖边界

诚实地说清哪些没被覆盖。

- **CHANNELS**：推荐 / 搜索藏在渠道树 CSV 的 `children` 字段（JSON 字符串）里，需要解析嵌套结构，本轮未做。
- **FLOW_SPLIT**：同样来自渠道树，两个数，漂移风险低，暂留手写。
- **STORES / HEALTH / SERVICE / ADS / TICKETS / ACTIVITIES**：演示值或非 CSV 来源，本来就不该由 CSV 生成。
- **REFUND**：`trade-refund` 里有原始数据，但字段映射还没确认，本轮未接。

这五项是下一轮的增量。

### 19.6 下一步：生成脚本

对账已经能当裁判，接下来写 `build_preview_data.py`（或 .mjs）就有底气了：生成完立刻跑一次 `check_data.mjs`，数字只要动一个就会报出来。

## 二十、页面数据改为生成（2026-10-20 12:25，提交 `85681f5` + `d51ce74`）

### 20.1 本步目标

前三轮评审反复标记的「CSV → 页面数据靠手抄」，在这一步闭合。目标是让那 11 组常量由脚本从 `csv30` 生成，并且**在生成之后仍然可以证明数字没变**。

### 20.2 三层结构

```
scripts/lib/preview-source.mjs     取数：csv30 → 11 组常量（唯一一份）
        ↑                    ↑
check_data.mjs          build_preview_data.mjs
（对账，只读）            （生成，--write 落盘）
```

关键决定是**取数逻辑只留一份**。如果对账和生成各写一套，那么「生成后对账通过」只能证明两边一致地错，这种自证没有意义。

### 20.3 推导范围从 8 组扩到 11 组

新增三组，都来自渠道树 `flow-shopsource/03_..._data.csv`：

| 常量 | 来源 | 说明 |
| --- | --- | --- |
| CHANNELS | 顶层三行 | name/uv/ratio/crc/avg/good/byr/rate/amt 九列齐备 |
| FLOW_SPLIT | `children` 里的 推荐 / 搜索 | 2721 / 468 |
| TREE_PARENT | `children` 汇总 | total 3679、browse 83、live 9、sum 3281、gap 398 |

`children` 是个坑：它是**字符串形式的 JSON**，节点字段又各自包了一层 `{ value }`，还可能出现嵌套子节点。解析要递归，并兼容 `children.value` 为字符串或数组两种情况。

### 20.4 标记策略

没有把 11 组常量搬到一个连续区块，因为那样会打乱数据段的阅读顺序。改成给每个 `const` 单独包一对标记：

```
/* DATA:BEGIN AGG */
const AGG = { ... };
/* DATA:END AGG */
```

生成器只替换 `BEGIN...END` 之间的内容，标记外的人工注释（比如「渠道树父子不平，差 398 是口径差」那段）原样保留。

标记插入用花括号配平扫描定位 `const` 边界：从 `const NAME =` 之后开始走字符，跟踪 `()[]{}` 深度与字符串状态，深度归零遇到的第一个 `;` 就是结束位置。不能简单用正则，因为数组里含 `];` 这种组合。

### 20.5 生成器的实时校验

`build_preview_data.mjs` 默认只预演，打印每组是「不变」还是「更新」，加 `--write` 才落盘。落盘前后都能看到具体改动了几组。

预演第一次就显示 11 组全部「更新」，这在预期内：手抄值是截断过的（AGG 10 位有效数字、AREAS 4 位小数），生成器输出全精度，所以必然有差异。

### 20.6 一个把页面打白的 bug

第一版写进去之后页面直接白屏，报 `undefined is not iterable`。

原因是 `rowsJoined` 拼接多行数组时，行与行之间只加了换行、漏了逗号：

```js
  ['2026-09-19',1760],['2026-09-20',1760]      ← 行尾无逗号
  ['2026-09-23',0],['2026-09-24',0]
```

JS 把 `[..]` 换行 `[..]` 解析成**下标访问**，整个数组的每个元素都变成了 `undefined`，`DAILY.map(([d,a]) => ...)` 解构时崩掉。

修法是把行间连接符从 `nl` 改成 `',' + nl`。

值得记的是发现路径：先提交了一个只加标记、不改内容的检查点，所以出问题可以直接 `git checkout` 回到干净状态，而不是在坏的页面上修补。

### 20.8 影响范围

**会变的**：改数据的习惯。以后要改 `csv30` 再生成，不能直接改 HTML 里的常量，否则下次生成会被静默覆盖。

**不变的**：页面行为、所有显示数字、闸门断言、单文件特性。`REFUND`、`CONTENT_MORE`、`STORES`、`HEALTH`、`SERVICE`、`ADS`、`ACTIVITIES`、`TICKETS` 八组仍是手写常量，与生成体系并存，互不干扰。

**风险点**：如果有人删掉标记，生成器会报 `SKIP` 而不是静默跳过，需要留意预演输出。
