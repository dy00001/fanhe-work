## 五、当前存在的问题与风险

### 5.1 验收未闭环

**R1 阶段一遗留一项验收未勾选。** 「关键操作在 `audit_logs` 有记录」要求覆盖登录、授权变更、删除三类。当前登录链路已接入，授权变更与删除两类事件的接口尚不存在，因为账号与角色管理功能未实现。这不是缺陷，是依赖倒置。补齐的时机在账号管理功能排期之后。

### 5.2 安全相关遗留

**R2 改密后旧令牌不失效。** `users.passwordChangedAt` 字段在 T1-01 建表时已留，但签发访问令牌时没有把它写进载荷。目前改密不会让已签发的访问令牌失效。

**R3 改名可能绕过唯一约束。** 账号创建与登录查询已统一走 `normalizeUsername`，改名路径尚未覆盖。将来做改名时若不先用归一后的值查冲突，会出现「只差大小写」的重名漏网。

两项都属于改密与账号管理功能的一部分，等该功能排期时一并处理。

### 5.3 环境与运维

**R4 数据库不随介质移动。** 数据在宿主机命名卷上，换机必须重建。当前没有导出与恢复方案，若需要保留实验数据，需要另做安排。

**R5 忽略规则分散三处。** `.gitignore`、`eslint.config.js` 的 `ignores`、`.prettierignore` 各管一段，新增目录容易漏改。本日已经实际发生过一次，`node_modules.old/` 未被任何一处覆盖，导致 lint 报出 8803 条误报。

**R6 依赖备份未清理。** 四处 `node_modules.old/` 仍占空间。忽略规则已隔离其危害，但目录本身还在。

**R7 助手对远端的写入通道受限。** WorkBuddy 的 GitHub 连接器为只读，写入返回 403 且 GitHub 侧无设置项可调。所有远端写入必须经由本地 git 完成。

### 5.4 过程与质量

**R8 文档时效性滞后。** `WORK-STATUS.md` 生成于本日 03:05，其后有多项事实变化：仓库由私有改为公开、新增 `dev` 分支、数据库补齐两个迁移、新增四份文档、门禁由两项失败转为全绿。该文档目前与事实有偏差，需要回填。

## 六、下一步优先任务与理由

### 6.1 结论

**优先执行 T3-05 纪要模型与接口。** 在它之前，先完成两项准备，合计约半小时。

### 6.2 准备动作

**准备一，回填文档时效。** 更新 `WORK-STATUS.md` 中已过时的三个事实点：远端仓库可见性、`dev` 分支、数据库与门禁状态。理由是这些内容会被当作开工前的事实基础，带着错误快照开工容易做出误判。

**准备二，创建首个用户账号。** `users` 表当前为空。浏览器级端到端脚本能自建自清测试账号，所以自动化验证不受影响；但人工验收界面需要可用账号。执行 `pnpm db:create-owner` 即可。

### 6.3 选择 T3-05 的理由

**理由一，它在关键路径上。** T3-06、T3-07、T3-08 三项都依赖它。推迟它会连带推迟三项，共四项任务的启动时间。事件链同样有一个起点 T3-09，但两条链互相独立，先做哪条不影响另一条的时间，所以选择应基于其他标准。

**理由二，阶段出口条件要求三板块齐备。** 阶段三的出口是「启动通道、工作纪要、事件记录」三者都可用。启动板块已交付，纪要板块零起步。纪要与事件同为零起步，但纪要属个人工作台的核心场景，且它的下游链更长。

**理由三，前置条件已全部就位。** 权限点 `personal.note.read` 与 `personal.note.write` 已在共享包中定义完毕，四个内置角色的授权展开也已覆盖，种子脚本会读取共享包，无需重复定义。可复用的现成结构有四处，分别是数据表的归属隔离写法参照 `apps/api/src/launch/profiles.ts`、界面三态参照 `components/StateView.tsx`、前端两层数据层参照 `apps/web/src/lib/launch.ts`、辅助信息与主列表分离的做法参照 T3-04 的状态接口。这些结构都已在阶段三的前四项中被验证过。

**理由四，改动性质最安全。** 新增一张表、一组接口与一个页面，不触碰既有模块的行为。相比先做账号与角色管理去补 R1 的验收缺口，T3-05 的回归风险低得多。

### 6.4 需要留意的两点

**迁移顺序。** 新增 `notes` 表迁移时，要检查它对既有对象的依赖。现有四个迁移的目录名字典序与实际创建顺序并不完全一致，当前恰好满足依赖关系。新增迁移若引用更晚创建的对象，会出现依赖倒置。

**令牌与主题约定。** 界面侧有三条既有约定需要遵守。颜色令牌的唯一来源是 `index.css` 的两层结构，不要写死颜色。新增界面一律从 `components/ui/` 取组件，不要手写等价元素。新增颜色令牌要同时在 `:root` 与 `.dark` 两块里各写一份。

### 6.5 备选路径

如果要先处理风险而非推进功能，优先级排序如下。

第一，补 R1 的验收缺口需要先做账号与角色管理，那是一项未列入当前任务表的新功能，工作量大于 T3-05，不建议在此刻插入。

第二，R2 与 R3 依赖改密与账号管理功能，同样不宜单独提前。

第三，R8 文档回填已列入准备动作，成本半小时。

第四，R6 清理依赖备份属维护动作，可随时执行，不占开发节奏。

综合判断，功能推进与风险处置两条路中，推进 T3-05 的收益更高，风险处置的多数项目受制于尚未排期的功能，强行插入会打乱依赖顺序。
