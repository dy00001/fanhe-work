# 版本迭代方案 `0.3.0`

一版**把运营链路接到人手上**。此前接入一家店要手工改 `shops.config.json`、跑脚本、手工导入；现在在工作台里填四个字段完成绑定，之后由本机的常驻进程自动同步，面板上能看到每一步停在何处、为什么停。

## 一、为什么是 `0.3.0` 而不是 `0.2.2`

| 候选 | 判断 |
| --- | --- |
| `0.3.0`（次版本） | **采用**。新增用户可见能力（店铺绑定面板、采集器三态、打开登录入口），且升级需要额外动作：两条迁移、重跑种子、重建镜像、重打安装包 |
| `0.2.2`（补丁） | 不合适。本版主体是新能力而不是修复，且 0.2.1 的判据是「0.3.0 不合适，因为那批改动不在安装包里」，这批恰恰在安装包的前端产物里 |
| `0.2.1` 原地重打 | 不合适。服务端与桌面端都有行为变化，同号重发会让「装的是哪一份」无法判断 |

按项目既有的 0.x 约定，「破坏性变更」指升级需要额外动作。本版额外动作共五项，见 §3.1。

## 二、内容

### 2.1 店铺绑定入口

运营看板顶部新增折叠面板，仅持 `ops.shop.bind` 可见。填代号、名称、端口、掌柜即可登记一家店。

绑定做三件事：写 `ecom_shops`、尝试写采集槽位、置 `sync_requested_at`。**不做采集**，因为 API 可能跑在容器里，碰不到宿主机 Edge 与调试端口。

| 约束 | 原因 |
| --- | --- |
| 代号正则与采集器 `CODE_RE` 同源 | 放宽会让「绑定成功但永远没数据」这种半成功状态出现，且零报错 |
| 端口在启用中的店铺间唯一 | 两店共用一个调试端口，采到的必然是同一个账号 |
| 解绑是软删 | 逐日指标与维度快照都以 `shop_id` 为外键，删行等于级联删历史 |

### 2.2 绑定后自动同步

`tools/collector/scripts/sync-shops.mjs` 轮询待办、跑既有采集与入库、回写登录态与失败原因。

关键取舍有两条：

- **触发信号是一个时间戳，不是消息队列。** 采集器必须能在平台不可达时照常跑，丢了就等下一次定时，不会因为一次投递失败而卡住。
- **容器化之后走 DB 直连。** 采集入口的回环校验在容器里看到的源地址是 docker 网关，HTTP 那条路必然 `403 forbidden_origin`。`--transport auto` 先试 HTTP，被拒自动降级。这与既有 `db:ops-import` 是同一个思路：计划任务不该被 HTTP 可用性绑架。

失败原因逐条对应一个可行动作（端口不通 / 退出码 3 登录失效 / 退出码 4 页面没加载 / 导出失败 / 入库被拒 / 槽位缺失），回写 `last_sync_error` 后显示在界面上，不用翻脚本日志。

### 2.3 采集器心跳

面板顶部显示「采集器在线 / 离线 / 从未启动」。

心跳不设独立接口：**拉待办这个动作本身就是存活证明**，HTTP 与 DB 直连两条路各写一次。窗口 180 秒，判定函数 `isCollectorOnline` 在共享包，阈值只写一处。

三态分开是有意的：「离线」要重启进程，「从未启动」要注册计划任务，合并成一句会让人去重启一个不存在的东西。

### 2.4 打开登录

每行店铺可一键打开采集浏览器的登录窗口。桌面外壳走 IPC 起脚本，浏览器态退化成复制命令，安装态返回 `collector_missing` 并把命令显示出来。

代号在主进程二次校验，脚本以独立实参接收，不做字符串拼接。安装包不含 `tools/collector`，所以安装态这条通道不可用，靠命令文案兜底。

### 2.5 链路自检

`node scripts/doctor.mjs` 把「没有数」的五种可能拼成一张表，判定分阻断（退出码 1）与提示（退出码 0）。

### 2.6 常驻任务

`install-sync-task.ps1` 注册计划任务，登录触发 + 每分钟重复 + 不启动新实例。用重复触发当看护，是因为「失败时重启」对外部杀进程不生效（实测 `state=Ready`、无进程）。

## 三、影响与风险

### 3.1 升级时必须做的动作

1. 跑两条迁移（`add_ops_shop_binding`、`add_ops_collector_heartbeat`），`migrate` 镜像必须重建。
2. **重跑 `db:seed`**。新增权限点 `ops.shop.bind`：不重跑时 owner 仍有权限（走代码常量），内置「管理员」角色没有该点，表现是界面上少一个入口且零报错。
3. 重建 `api` 与 `web` 镜像并 `--force-recreate`。
4. 重打并分发安装包。桌面端的打开登录 IPC 只在新包里。
5. 在采集机上注册常驻任务，否则绑定不会自动同步，面板显示「采集器从未启动」。

### 3.2 会被用户感知的变化

- 运营看板顶部多一块「店铺绑定与管理」（仅持权限者可见）。
- 店铺列表显示登录态与同步状态，失败时直接给出原因与下一步。
- 每行可打开采集浏览器登录。
- 顶部一行采集器状态，能看出「点了立即同步有没有人接单」。

### 3.3 仍然存在的风险

| 风险 | 现状 |
| --- | --- |
| 按人归属未做 | `ecom_shops` 无 owner 列，所有持 `ops.shop.read` 的账号看到同一批店铺 |
| 首次登录仍需人工 | 登录态绑在本机浏览器 profile，服务端代劳必触发风控 |
| 安装态打开登录不可用 | 安装包不含 `tools/collector`，降级为显示命令 |
| 采集器中断 | 每分钟重复触发可自愈，最长中断约一分钟（实测两次非正常退出均被拉起） |
