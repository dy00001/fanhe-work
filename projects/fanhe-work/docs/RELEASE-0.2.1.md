# 版本迭代方案 `0.2.1`

一版收口。0.2.0 把运营看板立了起来，从采集到看板的路是通的，但路上有若干「看起来成功」的失败形态：维度被清空后仍记成功、采集中断在库里不留痕、锚点取错了店、接口卡住就无限等。这一版不做新板块，只把这些口子逐个堵上，并给三段各配一个能说清「哪一步没成」的校验器。

## 一、为什么是 `0.2.1` 而不是 `0.3.0`

| 候选 | 判断 |
| --- | --- |
| `0.2.1`（补丁） | **采用**。无新增迁移、无权限点变化、无页面增删。用户能感知的变化都是「原来错的地方现在对了」或「原来卡住现在有结果」 |
| `0.3.0`（次版本） | 不合适。多店采集与校验器属于工程链路，不在安装包里，不构成对用户的新能力 |
| `0.2.0` 原地重打 | 不合适。服务端与桌面端都有行为变化，同号重发会让「装的是哪一份」无法判断 |

按项目既有的 0.x 约定，「破坏性变更」指升级需要额外动作。本版唯一的额外动作是**重打安装包**，与权限、迁移无关。

## 二、内容

### 2.1 更新段：三态与维度保留

`ingestOpsSnapshot` 原先只有「成功」与「抛错」两种结局，两者之间有一片空白地带：

| 场景 | 原来 | 现在 |
| --- | --- | --- |
| 逐日有行、维度零行 | 记成功，采集时间被推进 | 记 `partial`，不推进 |
| 维度某类零行 | 整类 `deleteMany` 清空旧行 | 不动库，保留已有行 |
| 事务中途失败 | 运行记录随事务回滚，库里查不到这次尝试 | 运行记录移出事务，补写 `failed` |

第三行是最隐蔽的：采集中断时，`ecom_collect_runs` 里连一条失败记录都没有，看板的新鲜度面板会显示「上次采集是几天前」，看起来像「今天还没跑」，实际是「跑了但炸了」。

### 2.2 抓取段：必采接口判定表

新增 `required-endpoints`，把「每页必须拿到什么」写成一份表，采集脚本与校验脚本共用。缺页时 `collect-daily` 单列打印 `missing`，但**不改退出码**：改成非零会让它天天红，告警随即失效。

### 2.3 跨段：两个校验器与一条串行链

| 工具 | 校验对象 | 用途 |
| --- | --- | --- |
| `verify-daily.mjs` | 采集产物与上报契约 | 入库前确认字段齐、日期对 |
| `ops-verify.ts` | 库内数据与契约 | 入库后确认落库值与契约一致 |
| `run-pipeline.mjs` | 五步串联 | 整体退出码 0 / 2 / 1 三级 |

三级退出码的含义：`0` 全成、`2` 有告警但数据可用、`1` 有阻断。这样计划任务能区分「该重跑」与「该看人」。

### 2.4 推送段：超时、ETag、回前台重取

| 改动 | 位置 | 解决什么 |
| --- | --- | --- |
| 三个运营接口 15s 超时 | `apps/api/src/routes/ops.ts` | 库慢时请求挂住，前端永远在骨架态 |
| 反代 GET/HEAD 20s 上游超时返回 504 | `apps/desktop/src/server.ts` | 桌面端请求没有上限，窗口像死了 |
| 三个读接口加 ETag | `apps/api/src/routes/ops.ts` | 切换区间与店铺时重传整块 JSON |
| `visibilitychange` 静默重取 | `apps/web/src/lib/use-ops-dashboard.ts` | 窗口放一天再回来，看到的还是旧数 |
| `useNow` 每分钟推进 | `apps/web/src/lib/use-now.ts` | 新鲜度文案在渲染时取一次就定格 |

静默重取刻意**不进数据指纹**：进了指纹就会触发整页重绘，滚动位置与悬停状态一起丢。失败时保留旧数据，不把屏幕清空。

### 2.5 多店采集（工程链路）

一店一份浏览器 profile 是硬约束。同一 profile 切账号时，采集器看到的是「已登录」，但店铺已经换了，数据会顶着别人的名字入库且不报错。配套加了串店防护：`--shop` 与目录推断出的店铺不一致时直接 `exit 1`，因为串店的表现只是「主店数字翻倍」，不报错。

### 2.6 店铺名统一

四个写入点原来各写一份：`ecom_shops.name`、`tools/collector/shops.config.json`、`apps/api/src/tools/ops-seed-shops.ts`、`tools/collector/scripts/export-ingest.mjs`。只改库不改代码时，重建库或重跑回填会把名字改回去。现统一为「梵禾」「雅素」「简作」，四处逐字一致。

## 三、影响与风险

### 3.1 升级时必须做的动作

1. `docker compose build api web` 后 `up -d --force-recreate api web`。判据是带 `shop` 的请求其 `range.to` 跟着店铺走，且响应头里有 `etag`。
2. 重打并分发安装包。推送段改动在客户端，服务端更新不到已安装的机器。
3. **不需要**跑迁移、**不需要**重建 `migrate`、**不需要**重跑种子（权限点与角色授权都没动）。

### 3.2 会被用户感知的变化

- 看板切店后，区间的末日跟随该店自己的数据；此前可能显示别家的日期。
- 窗口长时间放着再回来，数字会自己更新一次，不再需要手动刷新。
- 采集失败时，新鲜度面板会显示「失败」而不是「几天前」。
- 店铺名从「分店 2」「分店 3」变为「雅素」「简作」。

### 3.3 仍然存在的风险

| 风险 | 现状 |
| --- | --- |
| 日增未接计划任务 | 仍要人工触发，忘了看板就不更新 |
| 千牛直采未做 | 维持不做的判断，现有 Edge 每店 profile 够用 |
| s2 / s3 未跑完整日增 | 多店代码已就位，真实账号上只完成了登录 |
| 服务体验 / 推广投放 / 内容运营 | 仍无数据源，显示缺数说明 |

### 7.1 推送与打 tag

`main`、`dev` 同时推到 `c268bee`（`dev` 先 `git branch -f dev main` 对齐，否则推 dev 必被拒）。随后打**注解 tag** `v0.2.1`（解引用 `c268bee`）并单推。

### 7.2 发布命令

```bash
cd apps/desktop
GH_TOKEN=<GCM 取出的令牌> ./node_modules/.bin/electron-builder publish \
  -f release/fanhe-work-setup-0.2.1.exe \
  -f release/fanhe-work-setup-0.2.1.exe.blockmap \
  -f release/latest.yml \
  -v 0.2.1 -p always
```

两点注意：`-v` 在 `publish` 子命令里是**版本号**不是 `--version`；`-f` 必须三个文件成套点名，漏一个不报错但后果静默。

### 7.3 草稿转公开

`publish` 建出来的是**草稿**（`draft:true`、`published_at:null`），此时未认证 by-tag 返回 404 —— 那是「不可见」不是「没发上去」。用一次 `PATCH /releases/419625037` 带 `{"draft":false,"body":...}` 关掉草稿，`published_at` 才落值。

### 7.4 追加的第四条核对（本轮新增）

前三条只证明「清单与本地一致」，**不能证明传上去的字节就是本地那份**。GitHub 资产对象带 `sha256` 摘要，与本机三件套逐一比对：

| 资产 | 线上 sha256 | 结果 |
| --- | --- | --- |
| `fanhe-work-setup-0.2.1.exe` | `b838074e4c941f23…` | MATCH |
| `.exe.blockmap` | `443c732a7c4365b0…` | MATCH |
| `latest.yml` | `f9ddbab8961d0ec7…` | MATCH |

三项 MATCH 才等于「发出去的就是本机这份」，此前三条缺的正是这一环。

### 7.5 核对脚本的反例测试

核对脚本按惯例做了反例：把线上 `latest.yml` 的 `size` 改 1 字节 → `SIZE_VS_LOCAL_EXE` 与 `ONLINE_YML_EQUALS_LOCAL_YML` 两条转红、退出码 1；还原后回到 `RESULT=OK`。解析器本身也踩过一次坑：列表项写作 `- url: ...`，不剥掉行首短横则 `/^url:/` 永不匹配、`url` 读成 `undefined` 而不报错 —— 与 `verify-pack.mjs` 那次缩进假设同源，**解析器的错都是静默的**。
