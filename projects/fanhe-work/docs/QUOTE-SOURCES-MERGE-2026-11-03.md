# 报价主类管理与两种合并（2026-11-03）

维护台（`/workbench` → 报价查价 → 价格与产品维护）这一屏加了三件事：

1. 顶部那排「主类」页签可以自己增删改了 —— 也就是说「数据来源」从代码里的三个字面量
   搬进了库；
2. 分类区可以**多选几个分类并成一个**；
3. 分类里的产品可以**把多条折成一条**。

三件事都在同一屏，但它们失败的代价完全不同（见下文各节），所以没有合成一个「批量
整理」入口。

---

## 一、主类为什么必须落库，以及哪些字段不许碰

原来 `QUOTE_SOURCES = ['sale', 'craft', 'hardware']` 是写死的常量，显示名、短名、条目号
前缀、排序全靠三张 `Record<QuoteSource, ...>` 常量表。想加一个「岩板外协」，得改代码、
发版、再教一遍人。现在这些都在 `quote_sources` 一行里。

**`code` 与 `ledger_prefix` 创建后不可改，界面上不给入口。**

- `code` 是每条产品业务键的第 0 段（`buildQuoteItemCode`）。改它等于把这一类下每一条
  的主键全换掉：图、审计、历史报价单同时失联，**而且不报错**。
- `ledger_prefix` 印在纸质台账上（`A037`），改了就与纸质表对不上号。

所以「编辑」只开放 `name` 与 `short`。给了入口再拦一层，比不给更不诚实。

**删除判据含 `archived`（在售 + 已下架 = 0）。** 产品现在**可以**删除（见第六节），所以
「这一类下面空了」是做得到的 —— 但只能靠逐条删或改主类，不能靠下架。判据由服务端算好
（`deletable` + `deleteBlockedReason`）下发，前端不自己判：前端只看得到 `itemCount`，
看不到 archived 那一半，自己判会在「产品全下架」时放行，而那一半的行还在库里。内置三类
永远删不掉（`sale` 还牵着导入器的文件名猜测与 `A/B/C` 号段）。

**来源字段的 JSON Schema 只校验形状。** 取值域已经在库里，而 Schema 是编译期常量、读
不到库。写成 `enum: [...QUOTE_SOURCES]` 的后果很具体：新建一个主类之后往里加产品一律
400「must be equal to one of the allowed values」，而那个值明明就显示在 tab 上。真实校验
在写路径上用 `sourceExists()` 做，缺来源回 `invalid_source`。

## 二、合并分类（多选 → 一项）

### 归集规则

- 被合并分类下的**所有产品整体改挂**到目标分类：`quote_items.category = to`。
  产品条目本身一条不少、编号不变。
- 目标分类不存在时新建，`sortOrder` 取源分类里最小的那个（合并后位置不跳到最后）。
- 源的 `quote_categories` 行删除 —— 它们已经是空壳。
- 写一条审计：`field = 'category'`，`old_value` 是源名字串，`new_value` 是目标名。

### 原数据是否保留

产品**全保留**。只删分类行本身（那张表只是「有哪些分类」的清单，删掉不影响条目）。
审计里留着「哪几个并到了哪」，事后能追。

### 校验与提示

| 情况 | 结果 | 提示 |
| --- | --- | --- |
| 勾选 < 2 条 | 400 `too_few` | 「至少选两个分类才能合并」 |
| 目标名为空 | 前端按钮禁用 | 「目标」占位符 |
| 目标名在源列表里 | **允许**，从源里剔除后作为结果 | 保留原名是最常见诉求 |
| 某个源已被别人删了 | 400 `not_found` | 整批失败，指名哪一个 |
| 来源不存在 | 400 `invalid_source` | 「可能在另一个窗口里被删掉了，刷新后再试」 |

**整批失败、不做部分成功**：三个源里有一个没了，「合了能合的」在界面上显示「合并完成」，
列表里却还剩一个同名分类 —— 操作员只会以为自己点错了再合一次，于是多一条审计。

---

## 三、合并产品（一个分类内多条 → 一条）

### 归集规则（`apps/api/src/quote/item-merge.ts` 文件头有同一份）

1. **名称 / 型号 / 规格 / 分类 / 备注 / 条目号**：一律取 `keep`，一个字不动。合并是「把
   别的行收进来」，不是「重新生成一条」。
2. **价格**：只在 `keep` 的价格为空（`priceKind === 'empty'`）时，从被折叠的行里**按条目号
   顺序取第一条有价的**。`keep` 本来有价就不动。**不做取平均、不做取最低** —— 事后没人
   解释得清这个价是怎么来的。
3. **商品图**：`keep` 没有图时，取第一条有图的那张，键照抄。
4. **被折叠的行**：只改 `status = 'archived'` 与 `dataset_version`，其余字段原样。

继承了什么会回传给界面（`inherited`），并单独进审计 —— 否则「合并完价格多出来了」看起来
像数据被改过。

### 原数据是否保留

**保留，只是下架。** 历史报价单上印着 `A037`，物理删掉那一行，报价单上的编号就查不到任何
东西。转 `archived` 后：搜索里不出现、维护台勾「含已下架」能看到、`POST /items/:code/status`
能单独上架回来。

### 校验与提示

| 情况 | 结果 | 前端表现 |
| --- | --- | --- |
| 勾选 < 2 条 | 400 `too_few` | 按钮禁用 + 「至少勾选两条才能合并」 |
| 没选「保留」哪一条 | — | 红字「还没有选「保留」哪一条」 |
| 保留条不在勾选里 | 400 `bad_target` | `canMerge` 已含 `selected.includes(keep)` |
| 跨分类 / 跨来源 | 400 `cross_category` | 跨分类合并本质是改分类，不是合并 |
| 勾到了已下架的条目 | 400 `inactive` | 只合并还在售的 |

就绪时按钮下方直接写清后果：「保留 1 条，下架 N 条（不删除，可单独上架回来）」。

---

## 四、边界与未做

- **两种合并不合并成一个按钮。** 合并分类 = 产品整体改挂、分类少一个、产品数不变；合并
  产品 = 同分类内多条收成一条、分类不变、产品数变少。放一个按钮里，用户没法确认自己点
  的是哪种。
- **不做撤销。** 分类合并删掉的那几行分类名只在审计里；产品合并不删数据，可以逐条上架
  回来。真要撤销，按审计逐条改。
- **主类顺序不可拖。** `sort_order` 已在表里，但界面没做拖拽 —— 主类个数是个位数，改顺序
  的需求还没出现过。
- **导入应用时来源必须已存在**，也走 `sourceExists()`。先建主类再导，顺序不能反。

## 五、判据（防止改回去）

- `apps/api/test/quote.test.ts`：新建主类能装产品且名字下发、乱填来源被拒、只剩已下架
  条目时不可删、多选只勾一个判 `too_few`、产品合并后 `rows.length === 3` 且价格继承、
  跨分类被拒。
- `apps/web/test/quote-source-merge.test.mjs`：三个写接口各接各的、删除两次确认、删除资格
  读服务端字段、多选合并 `picked.length >= 2` 才渲染、`canMerge` 三条件、写接口带口令头
  而读主类不带、七个组件不再使用 `QUOTE_SOURCES` 常量。

两处都做过反例注入（把判据改坏，确认断言真的报 FAIL 再还原）。

# 六、删除：分类与产品（同日第二轮）

用户看完上面这版后提的第二件事：分类区只有「新建分类」，没有删；产品只有「下架」，
没有删。两个删除都加了，但它们的安全边界完全不同。

## 6.1 删分类：只删得掉空的

入口：分类区每一行的操作列，`改名 / 合并 / 删除` 三个按钮并排。

- **判据 `count === 0`**（在售 + 已下架一起算）。删一个还有产品的分类，那些产品会挂在
  一个「列表里查不到、筛选栏里也没有」的名字下 —— 仍在库里、仍能被搜索命中，但界面上
  没有任何入口指向它们，连删都删不掉。
- **判断顺序：先看有没有产品，再看这一行在不在。** 分类名可以只出现在条目里而从没落过表
  （导入的数据就是这样），那种名字在维护台上照样是一行。先判 `row === null` 会回「找不到
  这个分类」，让人以为界面上那一行是假的。
- **拒绝用 409 `has_items`**，提示里写明下一步该做什么，而不是只说「不行」。
- **不 bump 数据集版本**：一条产品都没动，客户端的缓存价格仍然有效。
- **审计**：`field = 'category'`，`oldValue` 是分类名，`newValue` 为空串表示删除。
- **两次点击**，第一次把按钮换成「确认删除」。

前端在发请求**之前**先看行上的「N 条」：有产品就直接给一句人话，不等一个来回。服务端那道
409 仍然保留 —— 它挡的是「两个人同时操作」。

## 6.2 删产品：物理删除，但留整行快照

两个入口，都调 `POST /api/quote/items/delete`：

1. **产品与价格区**：与「下架 / 上架」并排的第三个按钮；
2. **分类区展开的产品列表**（点「N 条」）：每行右侧一个删除，那个列表原本只能看和合并。

与「下架」的分工：

| | 下架 | 删除 |
| --- | --- | --- |
| 行还在不在 | 在，`status = archived` | 不在，`quote_items` 里没有这一行了 |
| 历史报价单上的 `A037` | 查得到 | 查不到任何东西 |
| 能不能恢复 | 能，单独上架 | 只能照着审计里的快照手工重录 |

服务端的四件事：

- **先写快照再删**：`field = 'deleted'`，`oldValue` 是「名称 / 型号 / 规格 / 分类 / 条目号 /
  价格 / 状态」拼成的一行（截到 400 字，`old_value` 的列宽）。这是那条产品唯一还存在的
  记录。
- **图只在「这一条自己持有图」时才删**：条件写死 `imageKey === code` 并额外排掉
  `bindType = 'family'`。族键（`fam-<摘要>`）属于整个产品族，150 张图覆盖 499 条条目就是
  靠它 —— 按 `row.imageKey` 删会把同款其他行的图一起弄没，而且不报错，只是别的产品变空白。
- **跨主类拒绝**：`code` 属于别的主类时回 403 `wrong_source`。界面列表没刷新时会走到这里。
- **bump 数据集版本**：与下架一致，内容变了客户端就得重取。

## 6.3 两个入口为什么都留

「产品与价格区」里能看到已下架的条目（`includeArchived`），「分类区展开的产品列表」只看
在售（默认查询）。要删一条两年前下架的错行，只能在前者找到，所以那里必须有删除；而在
分类区里逐条清理刚导入的重复行时，展开就能删，不用来回切页签。

## 6.4 边界与判据

- **删完最后一条产品，分类还在**：行显示「0 条」，此时再去删分类才删得掉。这两个功能是
  一串的，不是二选一。
- **删的是主类下最后一条产品**：主类那一行从「不可删」变成「可删」（`deletable` 重算），
  主类管理条刷新后按钮行为跟着变。
- 判据：`apps/api/test/quote.test.ts` 的「删除分类 / 删除产品 / 跨主类被拒」三条；
  `apps/web/test/quote-delete.test.mjs` 七条（两次确认、有产品先拦、删完清勾选、
  删完刷新父子两级、接口是 POST 且带口令、变更记录两个新字段的文案）。
- 反例注入 9 次全按预期 FAIL，其中一次暴露了测试自身的漏洞：`onChanged` 的断言原来从
  函数开头切到文件末尾，而整个文件里 `onChanged` 还出现在 props 解构与合并那条路径上，
  等于什么都没钉住 —— 已改成只截 `remove` 这一个函数。

# 七、来源配色：只能有一个出处（同日第三轮）

用户看着截图指出：左边「来源」栏里「板式工艺收费」的圆点是**青绿**，右边结果表同一批行的
「板式工艺」标签是**暗褐**。两处都「有颜色」、页面不报错、控制台干净 —— 只有并排看才发现
对不上。

## 7.1 根因：同一件事写了两份，只改了其中一份

主类能自建这一轮，把筛选栏的来源色改成了「按 code 哈希取模分配」（`quoteSourceColor()`），
理由是原来那张 `Record<QuoteSource, string>` 对新主类返回 `undefined`，圆点变透明。

但 `QuoteResultTable.tsx` 里**还留着一份写死的表**：

```ts
const SOURCE_COLOR: Record<QuoteSource, string> = {
  sale: 'var(--m-teal)',
  craft: 'var(--m-amber)',
  hardware: 'var(--m-blue)',
}
```

于是同一个主类在两处的颜色由两套规则分别决定：

| 主类 | 左栏（哈希） | 表格标签（写死表） | 结果 |
| --- | --- | --- | --- |
| `craft` 板式工艺收费 | `--m-teal` 青绿 | `--m-amber` 暗褐 | 对不上（截图那次） |
| `sale` 销售查价系统 | `--m-purple` 紫 | `--m-teal` 青绿 | 也对不上，只是没人并排看 |
| 新建的第六个主类 | 有颜色 | `undefined` → 只剩默认边框 | 像「没归类」的普通文字 |

这类 bug 的麻烦之处在于**它不抛异常**。颜色是个辅助信息，滚动时没人核对；而一旦有人拿
颜色当「这两条是不是同一个主类」的判据（这就是画圆点的用途），错误的信息比没有信息更坏。

## 7.2 修法：颜色只留一处定义，三处都调它

- `apps/web/src/lib/quote-display.ts` 的 `quoteSourceColor(code)` 成为**唯一出处**。
- 内置三值先命中一张固定表（`sale` 青、`craft` 褐、`hardware` 蓝）—— 这三组配色是静态稿
  定的、用了一个多月，不该因为「换成哈希」而整体换一遍；哈希只负责自定义主类。若让哈希
  全权决定，`sale` 会落到紫、`craft` 会落到青，等于一次性把用户记住的对应关系全打乱。
- `QuoteResultTable.tsx` 删掉写死表，改调 `quoteSourceColor(item.source)`。
- 三处画来源色的地方现在全部是这一个函数：`QuoteFilters`（左栏圆点）、`QuoteResultTable`
  （表格标签的文字与边框）、`QuoteEntryCard`（详情浮层圆点）。

## 7.3 判据

`apps/web/test/quote-source-color.test.mjs`（8 条）：

- 接线：三处各调各的位置都必须出现 `quoteSourceColor(...)`，且结果表里不许再出现
  `SOURCE_COLOR[` 这种按来源名索引的取色写法；组件里不许再出现颜色字面量（配色要留在
  `quote-display.ts`）。
- 行为：内置三值返回静态稿的配色；同一个 code 两次调用同色且不为空；自定义主类有颜色。

反例注入 3 次，每次都命中对应断言后还原：

| 注入 | 应挂的断言 | 实测 |
| --- | --- | --- |
| 结果表恢复写死表 | 第 2、3、5 条 | 2、3、5 全挂 |
| `quoteSourceColor` 去掉内置固定表（全走哈希） | 第 6 条 | 6 挂 |
| 左栏改回按 code 手写三元色 | 第 1、5 条 | 1、5 挂 |
