# 后台编辑口令：维护台里的设置入口（2026-11-03）

这一轮在「价格与产品维护」页加了一个**只有超级管理员能看见**的口令设置入口。

为什么要加：口令原本只能从 `PriceGateDialog` 里设，而那个弹窗对超管**根本不会出现** ——
`QuotePanel` 的判断是「`access.direct` 就直接开维护台」，超管走直入路径，于是
「设 / 改口令」这件事在界面上没有入口，只能靠调接口。这是一条被直入逻辑绕掉的缺口。

---

## 一、位置与可见性

位置：维护台标题行的右侧，`后台编辑口令` 按钮，在「关闭」左边。

可见性判据是**角色**：

```ts
const isOwner = access !== null && access.role === ROLE_CODES.OWNER
```

为什么不用 `access.direct`：服务端两者现在等价（`direct` 就是
`role === 'owner'` 算出来的），但语义不同 —— `direct` 回答「能不能写价格」，
这里要回答「谁是唯一能设这把锁的人」。将来给 admin 开直写价格时，用 `direct` 做判据
会把「改口令」的权限一起放宽，而且**没有任何提示**。

按钮与展开条各挂一层 `isOwner`。别人看到按钮只会点开再被拒，等于给了一个坏消息的入口。

## 二、交互：行内展开，不再套一层弹窗

维护台自己已经是满屏 Dialog。里面再开 Dialog 要额外处理焦点陷阱、Esc 归属、两层遮罩，
而这一条只有三个控件 —— 摊开比叠起来省事，也不会出现「关错层以为没保存」的错觉。

展开条里：`新口令` / `再输一次` / `显示` / `设置口令`（或 `更新口令`）/ `收起`，
下面一行说明后果。**收起即卸载**（`{secretOpen && isOwner && <QuoteSecretPanel … />}`），
状态跟着清空 —— 不写 `useEffect` 重置，那一版在重开的第一帧会先闪上一次的错误文案，
而且会撞 `react-hooks/set-state-in-effect`。

## 三、校验

| 规则 | 前端 | 服务端 | 提示 |
| --- | --- | --- | --- |
| 非空 | `canSubmit` 要求 trim 后 ≥ 下限 | `checkPasswordShape` | 按钮禁用；输入框下方「至少 6 位」 |
| 长度 6–64 | 读 `QUOTE_LIMITS.PASSWORD_MIN/MAX` | 同一常量 | 同上 |
| 两次一致 | `normalizedConfirm === normalized` | —（服务端只收一个值） | 「两次输入不一致」 |
| 首尾空格 | 提交前 `trim()` | `normalizePassword()`（设口令、轮换、解锁三处） | 静默规整 |
| 纯空格 | trim 后长度 0，撞下限 | 同 | 「至少 6 位」 |

**长度下限从 8 改成 6**，依据是用户 2026-11-03 的原话「长度要求 6 位数以上就 OK」。
这是店里几个人共用的一把操作口令、不是账号密码，太长会被写在便利贴上。放宽半径不等于
放弃护栏：真正的防线是连续错 5 次锁 15 分钟，以及改口令时版本 +1 让所有旧令牌当场失效。

**为什么长度不交给 JSON Schema**：schema 拦下时响应是 Fastify 的默认形状
（`body/password must NOT have fewer than 6 characters`）—— 英文、带字段路径，出现在
这个面板里很突兀。schema 只留 `minLength: 1` 与 `maxLength`（防超长请求体），真实长度由
`checkPasswordShape` 判，给中文「口令长度需在 6–64 位之间」。

**首尾空格为什么要规整**：这是手输 + 复制粘贴得来的一串字，首尾空格肉眼不可见。不规整会
长出「设的时候粘贴带了一个尾随空格、解锁时手打没带」这类故障 —— 界面说「口令不正确」，
而人对着自己记的那串字怎么看都是对的。中部空格保留，口令可以是词组。

## 四、提示

| 场景 | 文案 |
| --- | --- |
| 首次设置成功 | 「口令已设置。之后其他账号要改价，都必须先输入它。」 |
| 更新成功 | 「口令已更新（第 N 版）。其他设备上已打开的维护权限立刻失效，需要用新口令重新解锁；你这台因为超管直入不受影响。」 |
| 权限不足（403） | 「只有超级管理员能修改后台编辑口令。当前账号没有这个权限。」 |
| 状态过期（409） | 服务端原话 + 「（界面上的状态可能已经过期，收起后重开一次再试）」 |
| 其他失败 | 服务端 `message` 原话 |

403 单独给一句话，是因为它要回答「我为什么不能改」，而不是复述「需要维护权限」。
409 的补白针对真实边界：两个标签页时，这里的 `hasSecret` 可能是别人改之前的旧值。

## 五、生效方式

- 版本 +1：`quoteAccessSecret.version` 自增。
- **所有旧解锁令牌当场作废**：`setAccessSecret` 在事务里把 `quoteUnlockSession.revoked`
  全置 true，且 `secretVersion` 比对本来就能挡住它们。
- 超管本人不受影响：他走的是直入路径（`direct`），不查令牌。
- 其他人：手上 30 分钟的有效期作废，下次写价格时服务端返回 403，界面提示「口令已失效」。
- 界面刷新：保存成功调 `onSaved()` → `QuoteMaintPanel.onChanged` → `refreshMeta` +
  `refreshAccess`，标题上的徽章从「超级管理员 · 免口令」等状态按新数据重算。

## 六、与现有功能的关系

- 只新增了标题行的一个按钮与一个条件渲染的分支，四个分区（分类 / 产品与价格 / 批量导入 /
  变更记录）一个都没动。
- 改口令不写 `quoteRevision`：那是价格与产品的变更记录，口令属于准入，混在一起会让
  「谁改了什么价」里出现一行与价格无关的东西。
- `PriceGateDialog` 里原有的「设置 / 修改口令」路径保留 —— 非超管看不到这个面板，而
  从价格门进来的 owner 仍然有他那条路。两条路走的是同一对接口（POST / PUT）。

## 七、判据与反例

`apps/web/test/quote-secret.test.mjs`（11 条）：入口判据是角色、按钮与展开条各挂一层、
收起即卸载、长度取常量不写死、`PASSWORD_MIN === 6`、两次一致进 `canSubmit`、
`normalizePassword` 三处都走、schema 不判长度、create/rotate 分开、成功文案与 `onSaved`、
失败分三种说法。

`apps/api/test/quote.test.ts` 新增 4 条：5 位被拒（且是中文）/ 6 位通过并能解锁、
纯空格被拒、首尾空格双向都能对上、非 owner 连轮换也做不了。

反例注入 7 次，**其中两次没抓到，都暴露了测试自身的问题**：

| 注入 | 结果 |
| --- | --- |
| 入口改成对所有登录用户可见 | 第 1 条 FAIL ✓ |
| 用 `access.direct` 当判据 | 第 1 条 FAIL ✓ |
| `canSubmit` 去掉两次一致 | 第 6 条 FAIL ✓ |
| 去掉 `onSaved()` | 第 10 条 FAIL ✓ |
| schema 改回 `minLength: PASSWORD_MIN` | 第 8 条 FAIL ✓ |
| 解锁不 `normalizePassword` | **第一次全绿** → 见下 |
| 删掉 `password !== ''` | **全绿** → 见下 |

**发现一：`password !== ''` 是条冗余条件。** 它拦的是「纯空格」，但纯空格在
`normalizePassword` 之后就是空串、长度 0，下限那条已经挡住了。删掉它，行为不变 ——
所以这是一个**没有作用的护栏**，留着会让人以为防线在那一行。已删，并把「纯空格被拒」
钉在行为测试上（不依赖某个具体条件）。

**发现二：空格用例只写了一个方向。** 原来只测「设置时带空格、解锁不带」，而注入「解锁
不 trim」时输入本来就没有空格，前后结果一样 —— 全绿。真正的故障在反方向（设置不带、
解锁带）。已改成双向各测一次，重做注入后第 38 条如期 FAIL。
