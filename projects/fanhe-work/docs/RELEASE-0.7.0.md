# 版本迭代方案 `0.7.0`

一版**把删除做成真删除**的迭代。0.6.0 把价格维护扩成操作台，能改价、能合并、能删；这一版补的是删除之后的收尾：客户与订单可以删，报价库三张表之间补上外键，删主类时不再留下「查价页看得见、维护台够不到」的条目。附带把客户详情的订单金额做成合计行，成交金额拆成五项可填、两项自动算。

## 一、为什么是 `0.7.0`

| 候选 | 判断 |
| --- | --- |
| `0.6.1`（补丁） | 不合适。客户与订单可删除、归属筛选、金额合计都是用户可见的新能力 |
| `0.7.0`（次版本） | **采用**。新能力 + 升级需额外动作（两个迁移、重建 api 镜像、重打安装包） |
| `0.6.0` 原地重打 | 不合适。这一版动了两张核心表的外键与订单金额的算法，同号重发会让「装的是哪一份」无法判断 |

按项目既有的 0.x 约定，「破坏性变更」指**升级需要额外动作**。本版额外动作见 §3.1。

## 二、内容

### 2.1 客户与订单可删除

| 决定 | 原因 |
| --- | --- |
| 物理删除加级联，只在审计留痕 | 用户明确要求「删了就没了」。软删会让客户列表越用越脏，且筛选每一处都要记得排除已删行 |
| 删客户要两个权限点 | 删掉一个客户会连带删掉他名下全部订单，只凭 `record.write` 授权过宽 |
| 删订单只要 `order.write` | 订单是客户的子项，改动范围限于一条记录 |

### 2.2 订单金额拆成五项可填、两项派生

`computeOrderSettlement` 是唯一算法：实收 = 定金 + 预付款 + 已收尾款 − 手续费，未收尾款 = 合同 − 前三项。`received_fen` 与 `unpaid_fen` 降级为派生列，写入路径必须经它，任何地方手填都会在下一处读取时被覆盖。

客户详情顶部的合计行走 `summarizeOrderAmounts`，口径与单条一致：**派生两项逐单算完再相加**。先合手填五项再调结算函数，缺合同的单会拿别人的合同去减，欠款少算且界面上看不出来。

### 2.3 归属筛选

`owner` 参数进 `buildCustomerWhere`，七处统计共用这一份条件，支持「我的」「未分配」「指定设计师」「指定销售」。`unassigned` 的判据是两栏都空（设计师与销售都没填）。下拉选项来自响应里的 `owners`，只受范围约束、不受其余筛选影响。

### 2.4 报价库的外键与孤儿清理

`quote_items.source` 与 `quote_categories.source` 补上指向 `quote_sources.code` 的外键，`ON DELETE RESTRICT`。

此前这两列只是字符串，删主类与写条目各走各的路径。测试里直接按名字删主类行、条目按主键前缀删不掉，于是每跑一轮就留一条孤儿。查价左栏直接从 `quote_items` 聚合分类、不校验主类，那些分类照常显示；维护台顶部页签只渲染 `quote_sources` 里的行，永远匹配不上。结果就是「这一项改不了、也找不到」，而库里、日志里都没有任何报错。当天清查时库里有 41 条这样的残留。

四处一起修：

1. 迁移先清残留再落约束（判定只有一条：source 不在主类表里）。
2. `listCategories()` 只列主类表认得的来源，判据收成 `filterKnownCategorySources` 纯函数。主类表为空时不过滤，避免迁移没跑时把筛选栏整列清空。
3. 测试 `after()` 按本轮创建的主类 code 清理，不再依赖条目主键前缀。
4. `makeSortFixture` 的残留清理补上分类行，否则外键会让它删不掉主类。

### 2.5 删除语义统一

| 入口 | 清理范围 |
| --- | --- |
| 删产品 | 条目行、它自己持有的图（`imageKey = code` 且非 `family`）、整行快照进审计 |
| 删分类 | 分类行（要求分类下条目为 0，含已下架） |
| 删主类 | 分类行、主类行（要求条目为 0） |

## 三、影响与风险

### 3.1 升级时必须做的动作

1. **跑迁移**。自 0.6.0 起新增 2 个：`20261104120000_add_customer_order_settlement`、`20261104140000_add_quote_source_foreign_keys`。第二个迁移会**删掉库里所有 source 不在主类表的条目与分类**，这是有意的：那些行在界面上本来就没有入口。升级前建议先备份一次 `quote_items` 与 `quote_revisions`。
2. **重建 `api` 镜像并 `--force-recreate`**。外键与 Prisma Client 都在镜像里。
3. **重打并分发安装包**。前端改动是构建产物，不打新包装的是老界面。
4. **不需要重跑 `db:seed`**。本版没有新增权限点，`permissions` 维持 24 行。

### 3.2 会被用户感知的变化

- 客户与订单上出现删除入口，点了要确认两次。
- 客户列表多一个归属筛选。
- 客户详情的订单列表上方多一行金额合计，缺合同的单会标「未计入」。
- 订单编辑里定金、预付款、已收尾款、手续费、合同金额五项可填，实收与未收两项不再手填。
- 查价左栏不再出现改不掉的分类。维护台删主类时，如果还有条目，会明确告诉你有多少条。

### 3.3 仍然存在的风险

| 风险 | 现状 |
| --- | --- |
| 族图（`fam-*`）在引用它的条目全删后不会自动清 | 图行没有外键指向条目，批量回收需要单独一次扫描。体量小，暂不处理 |
| `meta.itemCount` 是导入快照，删产品后不重算 | 与版本号同一条判断：价格没变就不改版本。删完条目后这个数字会偏大 |
| 空分类行在删完最后一条产品后保留 | 分类是维护台里可见、可点删除的实体，不属于够不到的残留。自动清会误删用户刚建的空分类 |
| 审计快照永久保留 | 这是删除与「什么都不留」的唯一区别。有人拿旧报价单来问「这条当时是什么」，翻审计能答上来 |
