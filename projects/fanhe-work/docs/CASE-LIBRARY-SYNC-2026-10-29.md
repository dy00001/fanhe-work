# 案例库：文件夹整理与两级图片缓存

> 2026-10-29 初版。承接 `docs/CASE-GALLERY-FEASIBILITY-2026-10-28.md`（封面层落地）。
> 本文覆盖两块：**首页品类图集的文件夹整理 + 云端同步**，以及**缩略图本地缓存 + 原图按需加载**。
> 结论摘要：文件夹与归属关系已服务端化，跨设备靠修订号自动拉齐；缩略图落在用户自己选的
> 文件夹里，原图始终按需走网络。

## 一、结论

| 需求 | 做法 | 代价 / 边界 |
| --- | --- | --- |
| 点品类框直接弹窗看图 | `CaseLibraryDialog`，一个弹窗装下图集与放大层 | 旧的「大图 + 左右翻 + 底部缩略条」`CaseAlbumDialog` 已删除 |
| 点图放大、再点缩小 | 放大层是弹窗内的覆盖层，整层可点 | 不新开窗口，不拦截浏览器手势 |
| 建 / 改名 / 删文件夹 | `POST|PATCH|DELETE /api/cases/folders` | 品类内重名 409；单品类上限 30 个 |
| 图片跨文件夹移动、多选批量 | `PUT /api/cases/placements` | 一次最多 200 张；只允许同品类 |
| 归属实时保存 | 每次写都落库，并把**整份快照**回传给前端 | 牺牲一点带宽换「前端不必推算增量」 |
| 跨设备自动一致 | 修订号 + 四个拉取时机（打开 / 聚焦 / 20s / 写完） | 不是实时推送，最坏延迟 20 秒 |
| 缩略图先到本地 | 打开品类时同步 320px WebP 到用户选的文件夹 | 需要一次用户手势授权 |
| 原图按需加载 | 点开大图时才请求那张 1000px 图 | 断网时大图打不开（缩略图仍可看） |
| 本地路径可配置 | File System Access 的目录选择器 | 浏览器不给绝对路径，界面只能显示文件夹名 |

## 二、交互流程

### 2.1 看图

```
首页品类框（CaseGallery 横滑卡）
  └─ 点击 → CaseLibraryDialog 打开，落在「全部」筛选
        ├─ 网格：缩略图（4:3），一行显示当前筛选下的全部图片
        ├─ 点某张 → CaseLightbox 覆盖层，按需请求原图
        │     ├─ 点图片本身 → 关闭
        │     ├─ 点空白处   → 关闭
        │     └─ Esc        → 关闭（捕获阶段处理，不被内层吞掉）
        └─ 关闭弹窗
```

放大层整层可点，是有意的：用户点「图片外面」和「图片上面」在心理上都是「看完了」。
只有一处例外——加载失败时会出现一个「重试」按钮，它自己 `stopPropagation`。

### 2.2 整理

整理是**弹窗内的一个模式**，不是另一个页面：

```
弹窗头部 ── [整理]  ──────────────→ 头部变成 [完成]
                                        │
文件夹条 CaseFolderBar                   │
  全部 | 未归档 | 我的文件夹… (+)         │
  文件夹上的 ⋯ → 重命名 / 删除            │
                                        ▼
网格进入选择态：每张图左上角出现复选框
底部浮出操作栏：已选 N 张 · 全选本组 · 退出整理 · 移动到 ▾
```

- **进入整理才出现复选框**。平时网格是纯看图，不显示任何可勾选的痕迹。
- 「移动到」是一个下拉菜单，列出本品的全部文件夹外加「移出文件夹（未归档）」。
- 提交后立即退出选择态并回到原筛选位置，不弹确认框——移动是可逆的，再搬回去就行。
- **删除文件夹要确认**：它会让里面的 N 张图全部回到「未归档」，这一句写在确认文案里，
  而不是笼统地问「确定删除吗」。

### 2.3 状态提示

弹窗标题下方那行字按优先级只显示一件事：

```
正在同步缩略图 12/30  →  保存中…  →  正在加载…  →  空（不占位）
```

失败信息走弹窗顶部的横幅（红底、可关闭），不与这行抢位置。

## 三、数据结构

### 3.1 共享包：`packages/shared/src/case-library.ts`

规则的唯一出处。前后端都从这里取，避免「前端允许 24 字、后端允许 32 字」这类分叉。

| 名称 | 内容 |
| --- | --- |
| `CASE_CATEGORY_IDS` | 13 个品类 id，与小节 2 的目录一一对应 |
| `CASE_LIBRARY_LIMITS` | `FOLDER_NAME_MAX 24`、`FOLDERS_PER_CATEGORY_MAX 30`、`ITEM_ID_MAX 64`、`BATCH_MAX 200` |
| `CaseFolder` | `{ id, categoryId, name, createdAt }` |
| `CasePlacement` | `{ itemId, folderId }` |
| `CaseLibrarySnapshot` | `{ revision, folders[], placements[] }` |
| `caseCoverItemId(categoryId)` | `` `${categoryId}-cover` ``，品类封面在同一个 id 空间里 |

两个容易踩的点：

1. **`isValidCaseFolderName` 自己先归一化再判长度**。要求调用方先 `trim` 的版本在
   `'   '` 上返回 `true`（长度 3、去空白后 0），单元测试当场抓到。校验函数不能假设
   别人已经做过前置处理。
2. **`caseItemIdBelongsTo(itemId, categoryId)` 只比前缀**。图片本身不入库，服务端没法
   查「这张图属于哪个品类」，前缀是唯一可用的判据——因此 itemId 的命名规则
   （`<categoryId>-<n>` / `<categoryId>-cover`）成了接口契约的一部分，写进注释。

### 3.2 服务端：三张表

迁移 `20261029140000_add_case_library`。

```
case_folders              id(uuidv7) / user_id / category_id / name
                          created_at / updated_at / deleted_at
                          @@index([user_id, category_id, deleted_at, created_at])

case_item_placements      user_id + item_id  ← 复合主键
                          folder_id (nullable, onDelete: SetNull) / created_at

case_library_states       user_id ← 单列主键
                          revision int default 0
```

三个设计决定：

- **图片本身不入库**，只存「归属」。素材是随前端产物发布的静态文件，一次入库反而要
  维护同步。好处是新增图片零迁移；代价是服务端无法校验「这张图真的存在」，只能校验
  「id 前缀属于这个品类」。
- **稀疏覆盖**：没有归属行＝未归档。因此「移出文件夹」是 `deleteMany`，不是写
  `folder_id = null`。少一种表示，就少一处「两行都表示未归档」的歧义。
- **删除文件夹是软删 + 归属行物理删**。文件夹名要能被重新使用（软删行与唯一性不打架，
  这一点有专门的用例），而归属行没有历史价值——它记录的是「现在在哪」，不是「曾经在哪」。

### 3.3 客户端缓存：`CaseCacheMeta`

存在 IndexedDB 的 `fanhe-case-assets` / `kv` 里，两个键：

| 键 | 值 | 为什么这样存 |
| --- | --- | --- |
| `directory` | 目录句柄本身 | 句柄可结构化克隆，这是持久化目录选择的唯一办法 |
| `meta` | `{ version, files: {id:{bytes,at}}, lastSyncedAt }` | `version` 是图片集指纹；`files` 是删除依据 |

**不存绝对路径**：浏览器不给，给了也不该存（换机器就失效）。

## 四、云端同步

### 4.1 修订号是唯一的「变了没有」

`case_library_states.revision` 每次写操作在**同一个事务**里自增：

```
BEGIN
  建/改名/删文件夹 或 写/删归属
  UPSERT case_library_states SET revision = revision + 1
  读快照
COMMIT
返回 { library: snapshot }
```

于是「revision 变了 ⇔ 有数据变了」在数据库层面成立，客户端可以只做一次整数比较就
决定要不要重绘。没有这层保证，就只能靠深比较数组，而深比较在网络返回的数据上做，
既慢又容易漏（比如两个文件夹互换名字）。

代价：**每个写接口都回传整份快照**。一次「移动 3 张图」的响应包含该用户的全部文件夹
与归属，量级是几 KB。这是刻意换来的简化——前端不做增量应用，就不存在「客户端推算的
新状态与服务端不一致」这一类最难查的 bug。

### 4.2 四个拉取时机，收敛到同一个 effect

| 时机 | 实现 | 解决什么 |
| --- | --- | --- |
| 弹窗打开 | `enabled` 变 true | 首屏 |
| 窗口重获焦点 | `window.addEventListener('focus')` | 从别的程序切回来 |
| 标签页重新可见 | `document.visibilitychange` | 焦点一直在窗口内时 `focus` 不触发 |
| 每 20 秒 | `setInterval` | 两个窗口并排摆着，没有焦点变化可依赖 |
| 写完一次 | `runWrite` 的 `finally` | 让回传快照之外的字段也归位 |

五个入口都只是 `setReloadToken(v => v + 1)`，真正拉取的是同一个 effect。两个细节：

- **写操作在飞时跳过拉取**（`busyRef.current > 0`）。否则一次轮询正好撞在乐观更新与
  服务端确认之间，会把刚做的动作抹回去。
- **revision 相同就不 `setSnapshot`**。不开这个判断，弹窗开着每 20 秒会闪一下。

### 4.3 冲突处理

| 服务端返回 | 含义 | 前端行为 |
| --- | --- | --- |
| 409 `duplicate_name` | 同名文件夹是别的设备刚建的 | 回滚 + 补一次拉取，让用户看到真实列表 |
| 409 `folder_unavailable` | 目标文件夹已被别的设备删掉 | 同上 |
| 404 | 文件夹已不存在 | 同上 |
| 409 `folder_limit` | 本品类已有 30 个 | 只提示，不重取（重取也不会变） |
| 400 | 名字空白 / 跨品类图片 | 只提示 |

分流在 `lib/case-library.ts` 的 `caseSaveExit(error)`：`'conflict' | 'gone' | 'retry'`。
`retry` 类不回滚重取，因为状态没变，重取只是白跑一趟。

**没有离线队列。** 写失败就回滚 + 提示重做。理由写在 `use-case-library.ts` 的文件头：
离线期间攒下的操作一旦与服务端冲突，正确的合并结果只有用户自己知道；与其猜，不如让他
重做一次。

### 4.4 写操作的乐观边界

只有「移动」给了乐观快照。建、改名、删都要等服务端——新 id 是服务端分配的，新名字
可能撞重名，猜不出来。移动的目标是确定的，本地先画出来能让点击立刻有反馈。

## 五、两级图片加载

素材是两套尺寸，同一张图两个地址：

| | 缩略图 | 原图 |
| --- | --- | --- |
| 案例图 | `public/cases/thumbs/<id>.webp`，320px 宽 / q70 | `public/cases/album/<id>.webp`，1000px 宽 / q74 |
| 品类封面 | `public/cases/<categoryId>.webp`（与 `src` 同一份） | 同左 |
| 体积 | 43 张案例缩略图合计 293,692 字节（约 287 KB），13 张封面另计约 320 KB | 43 张合计 1.8 MB |
| 何时取 | 打开品类时整批同步到本地文件夹 | 点开大图时那一张 |
| 谁兜底 | 本地文件 → 网络 → 内置图 | 浏览器 HTTP 缓存 |

品类封面**只有一份文件**：`caseAssetFiles()` 里 `thumb === src`，它既当封面的缩略图用，
也当放大图用。这是有意的——封面本来就小，再压一版 320px 没有意义，而两张文件会让
「换封面」变成两处要一起改。缓存条目因此是 **13 + 43 = 56 条**，不是 43 条。

**为什么不把原图也缓存下来**：一张 40 KB 左右，43 张 1.8 MB，而用户一次只看一张。
全量缓存换不来可感的体验提升，却会让「同步」变成一次明显的批量下载。

`CaseAssetFile`（`lib/case-catalog.ts`）：

```ts
type CaseAssetFile = {
  id: string          // <categoryId>-<n> 或 <categoryId>-cover
  categoryId: string
  thumb: string       // 320px
  src: string         // 1000px；品类封面的 thumb 与 src 相同
}
```

13 张品类封面 + 43 张案例图 = 56 个条目，其中封面的 `thumb === src`，所以它在缓存目录
里只落一份文件。

## 六、缓存与失效

### 6.1 版本指纹

```ts
CASE_ASSET_VERSION = fingerprint(caseAssetFiles())   // FNV-1a，8 位 hex
```

指纹的输入是「id + 两条地址」的序列。改图、换图、增删图都会让它变；改文件名也会。
它不读文件内容——缩略图只有几 KB，但为一次校验去读 56 个文件不值得。

### 6.2 同步计划是幂等的

```ts
planSync(items, meta, version)
  version 不一致 → { toWrite: 全部, reset: true }   // 整批重写
  version 一致   → { toWrite: meta 里没有的, reset: false }
```

- **不比对单张文件的内容哈希**。判断依据是「文件在不在 + 版本一致」，出错的方向只有
  「多写了几个文件」，而多写几个文件不会错。
- `reset: true` 时 meta 的 `files` 会被清空重建，因为旧条目可能对应已经换过的图
  （同一个 id、不同内容），留着它会让那张图永远显示旧版。
- 同步是**逐张串行**的：Chromium 的目录句柄读取本身就是串行的，并发发起不会更快，
  反而会把一次失败放大成一批失败。进度条因此是真实的逐张进度。

### 6.3 什么时候失效

| 事件 | meta 怎么变 | 旧文件怎么处理 |
| --- | --- | --- |
| 版本指纹变化 | 整批重写，`files` 重建 | 覆盖同名文件；不再被引用的旧 id 文件留着 |
| 换目录 | **清空 meta**（等同重同步） | **不删**。那是用户的文件系统 |
| 点「清除缓存」 | 清空 meta | 只删 meta 里记录过的 id |
| 同步中途失败 | 不落 meta | 已写的几张留着，下次接着补（幂等） |

**换目录不迁移、只重同步。** 迁移要把文件拷到新目录再删旧的，而旧目录里可能还有
用户自己的东西；「清空 meta + 重写一遍」的观感与迁移一致，实现却只有一条路径。
旧目录里的文件不删——我们只在用户明确要求「清除缓存」时删自己写过的那些。

### 6.4 清缓存绝不按扩展名扫

目录里放一个标记文件 `.fanhe-case-cache.json`，写入了它才认为这个目录是「我们的缓存
目录」。清理时只删 meta 里记录的 id。用户完全可能把目录指到桌面或某个已有资料的
文件夹上，一次「清理缓存」把别人的图删掉是灾难性的。

## 七、路径配置与校验

### 7.1 为什么是目录选择器，不是路径输入框

用 File System Access API 的 `showDirectoryPicker()`。选它而不是「输入一个路径字符串
交给主进程去写」，是因为**浏览器里与桌面外壳里是同一套代码**：外壳是 Chromium 44，
两者都支持。路径字符串方案只有外壳能用，浏览器里那条路要么不存在、要么得再写一套
IndexedDB 缓存——同一份缓存逻辑有两个实现，最终一定会分叉。

固有限制：**浏览器出于隐私不给绝对路径**，只给文件夹名。因此设置页显示的是
「文件夹名」，不是 `D:\梵禾\案例图`。这是 API 的限制，不是省事。

### 7.2 校验分三步，只有第三步真有效

| 步骤 | 做法 | 能证明什么 |
| --- | --- | --- |
| 1. 能力 | `typeof window.showDirectoryPicker === 'function'` | 浏览器支持（Safari / Firefox 不支持） |
| 2. 权限 | `handle.queryPermission({mode:'readwrite'})` | 访问被允许，**不代表现在可写** |
| 3. 写探针 | 往目录里写 `.fanhe-case-cache.json` | **唯一能证明可写的动作** |

第 3 步是重点：只读挂载、被别的程序占用、磁盘满，都在写入那一刻才暴露。选完目录
先写一个几十字节的探针，写不进去就当场判为不可用，并把可能残留的半个文件删掉。

权限过期（浏览器重启后很常见）走 `requestPermission`，**必须在用户手势里调用**。
放在 effect 里调只会拿到 `denied`，而那个 `denied` 看起来像「用户拒绝了他根本没见过的
弹窗」——所以设置页与图集在授权过期时只显示一句「重新授权」，绝不自动弹。

### 7.3 设置页（`/system/settings/preferences`）

```
本地缓存
  状态        可用 / 未设置 / 需要重新授权 / 浏览器不支持 / 目录不可用
  文件夹      <名称>（浏览器不提供绝对路径）
  已缓存      56 张 · 约 600 KB
  上次同步    2026-10-29 14:02
  资源版本    a1b2c3d4
  [选择或更换文件夹] [重新授权] [立即同步] [清除缓存]
```

## 八、降级处理

### 8.1 缓存的五档状态

| `status` | 触发条件 | 界面 | 图片从哪来 |
| --- | --- | --- | --- |
| `unsupported` | 无 `showDirectoryPicker` | 灰字说明，按钮全禁用 | 网络 |
| `unset` | 还没选过目录 | 「未设置」+ 选择按钮 | 网络 |
| `ready` | 句柄在、权限 granted、探针通过 | 显示文件夹名与用量 | 本地优先，缺的回落到网络 |
| `permission` | 句柄在、权限过期 | 「需要重新授权」 | 网络 |
| `unavailable` | 探针失败 / 目录被删改名 / 磁盘满 | 显示原因 | 网络 |

**每一档都能正常看图。** 最差的一档等于「没有这个功能」——与加缓存之前的体验一致。
一条会让人「什么都看不见」的缓存还不如没有。

### 8.2 网络异常

| 场景 | 表现 |
| --- | --- |
| 缩略图同步中途断网 | 逐张失败即停，已写的保留，`status` 不变（目录没坏，只是这轮没写完），横幅提示原因 |
| 缩略图已在本地、原图请求失败 | 网格照常显示；放大层出现「加载失败 + 重试」 |
| 快照拉取失败 | 保留上一次成功的快照，标题下显示失败原因；下一次轮询自动恢复 |
| 写操作时断网 | 回滚 + 提示；`caseSaveExit` 归为 `retry`，不触发重取 |

放大层的 `LightboxImage` 有 `loading | ready | failed` 三态，失败重试靠 `key={attempt}`
重新挂载 `<img>`。容器固定 `h-[min(60vh,640px)]`，避免加载完成时版面上跳。

## 十、已知边界

1. **同步不是实时的**。最坏延迟 20 秒（轮询间隔）。真要做实时推送得加一条长连接，
   当前规模（单人、两设备）不值得。
2. **服务端不知道图片是否存在**。图片不入库，只能靠 id 前缀做品类校验。前端 `album()`
   生成的 id 就是这一契约的唯一来源。
3. **换目录不删旧文件**。省事，也可能留下一份没人管的副本——用户能自己删，这比我们
   猜「他是不是不要了」更安全。
4. **`showDirectoryPicker` 需要用户手势**。这也是为什么设置页有三个按钮而不是一个
   自动流程：每个动作都得有他按下去的那一下。
