## 一、结论

| 问题 | 判断 |
| --- | --- |
| 案例区能否接真实图片 | 可以。`CaseSlot.cover` 字段已预留，接线点只有一处 |
| 能否按目录全量映射 | 不必按目录。`案列/分类清单.csv` 已完成 1672 条人工判读，按文件名可关联 |
| 全量图片能否进前端产物 | 不能。2.78 GB 对 1.1 MB 的 `dist`，量级差 2500 倍 |
| 推荐做法 | 人工选图 + 标准化工序生成 800×468 WebP 封面，约 1.5 MB，随 `dist` 分发 |
| 最大风险 | 仓库 `visibility: public` 且公网隧道可达，客户家实景原图不得入库 |
| 九品类是否都有素材 | 齐。但 `酒柜` 只有 2 张，可选空间极小 |

## 二、现状架构

### 2.1 组件划分

```
pages/WorkbenchPage.tsx        按 pathname 分派，根路径落在 HomePage
  └─ pages/HomePage.tsx        三段纵向排列，案例展示是第一段
       └─ components/home/CaseGallery.tsx
            ├─ lib/case-catalog.ts                  数据源（唯一）
            └─ components/home/CaseGalleryDialog.tsx  「全部品类」窗口内容
```

`CaseGallery` 承担五件事：区块头（标题、副题、入口按钮）、横滑条四等分卡、
四种输入方式（圆钮、滚轮、拖拽、键盘）、两端状态判定、把 `Dialog.Root` 提到区块
外层以便入口按钮作为 `DialogTrigger`。

### 2.2 数据结构

| 字段 | 类型 | 当前值 | 说明 |
| --- | --- | --- | --- |
| `CaseCategory.id` | `string` | 9 个英文 id | 稳定标识，作列表 key |
| `CaseCategory.name` | `string` | 9 个中文名 | 界面显示 |
| `CaseCategory.cases` | `readonly CaseSlot[]` | **全部空数组** | 案例库尚未建立 |
| `CaseSlot.id` | `string` | 无实例 | 不从标题推 |
| `CaseSlot.categoryId` | `string` | 无实例 | 冗余存一份，便于独立查询 |
| `CaseSlot.title` | `string` | 无实例 | 空串表示未录入 |
| `CaseSlot.cover` | `string \| null` | 无实例 | `null` 表示封面待补 |

九品类 id 与名称：`cabinet` 橱柜、`wardrobe` 衣柜、`bookcase` 书柜、
`shoe-cabinet` 鞋柜、`wine-cabinet` 酒柜、`door-set` 套装门、`tv-cabinet` 电视柜、
`sideboard` 餐边柜、`wall-panel` 护墙板。

### 2.3 映射关系

当前存在的是「品类 → 卡片位」一对一映射，**没有「图片 → 卡片位」这一层**。

| 界面位置 | 数据来源 | 数量 | 尺寸约束 |
| --- | --- | --- | --- |
| 首页横滑条 | `CASE_CATEGORIES` 顺序 | 9 张，一屏露 4 张 | `aspect-[400/234]`，四等分栅格 |
| 全部品类弹窗 | 同一份 `CASE_CATEGORIES` | 9 张，三列三行 | 同上，逐项照抄横滑条样式 |

两处渲染的都是「占位图标 + 封面待补」的固定块，`category.cases` 被完全忽略。
**把 `cases` 填满，界面也不会变。** 组件本身必须改，这一点决定了工作量性质，
不能按「改一份配置」估。

### 2.4 调用流程

```
渲染 CaseGallery
  → 同步 import CASE_CATEGORIES（编译期常量，无网络请求）
  → map 出 9 个 div，每个渲染占位块
  → 点击「全部品类」→ Radix Dialog 打开 → 同一份数据再 map 一次
```

全程无 `fetch`、无加载态、无错误态、无权限判定。它是首页三段里唯一
**不会失败**的一段。接真实接口后这三条性质全部会变。

### 2.5 静态资源通路

| 通路 | 位置 | 能力 |
| --- | --- | --- |
| Vite `public/` | `apps/web/public/` | 构建时原样拷进 `dist`，当前仅 `brand/` 124 KB |
| nginx（容器） | `COPY --from=build /repo/apps/web/dist` | 托管 `dist` 全量文件 |
| 桌面端本地服务 | `apps/desktop/src/server.ts` 托管 `resources/web` | MIME 表已含 `.jpg/.jpeg/.png/.webp/.gif` |
| API 静态服务 | 无 | `apps/api` 未安装 `@fastify/static`，无任何静态路由 |
| 上传接口 | 无 | 全仓库无文件上传端点 |

三条通路都指向同一结论：**能被访问的只有 `dist` 里的东西**。`dist` 当前 1.1 MB。

### 3.1 结构发生过一次重组

### 3.6 素材质量

复核后修正初版判断。分类池里**专业摄影与随手拍混在一起**：

- 专业水准的一类存在。实测电视柜候选第 1 名为暖色木饰面电视墙全景，光线均匀、
  构图完整、无杂物，可直接作为作品集封面。
- 随手拍的一类同样存在。橱柜原图可见油壶、垃圾桶、水杯、门贴，为竣工记录照，
  裁切后柜体完整性受损。
- `实木案例/` 的 57 个 TIF 为印刷级扫描件，色彩空间不一定是 sRGB，转 WebP 可能偏色。

判断：**素材足以支撑首页案例展示，前提是逐张过目筛选，不能按目录整批搬。**
分类清单解决了「属于哪个品类」，没有解决「够不够好看」，后者只能人工判定。

## 四、可行性与风险

### 4.1 三条结构性矛盾

**矛盾一：分类维度只剩一条有效轴。** 目录里出现了 `现代简约`、`中古`、`铝木门`
这类风格层，但判读结果是 1654 比 4，风格维度实质上是空的。界面若加风格筛选，
筛出来几乎全是现代简约，等于加了一个不产生信息的控件。

**矛盾二：构图与卡片比例冲突。** 卡片 400:234 为横构图，素材以 3:4 竖构图为主。
两条解法各有代价：改卡片比例会牵动横滑四等分与下方 Bento 的对齐关系；裁切则会
削掉柜体上下。第三条路是裁切前允许人工指定纵向焦点，代价是映射表从纯脚本产物
变成需要人工复核的工件。

**矛盾三：体积与分发通路冲突。** 唯一可用通路是 `dist`。2.78 GB 原图不可能进
`dist`，即使只放 200 张原图也有数百 MB，会让安装包与 nginx 镜像同步膨胀。

### 4.2 风险清单

| 级别 | 风险 | 说明 | 缓解 |
| --- | --- | --- | --- |
| 高 | 客户隐私外泄 | 仓库 `private: false`（已核验 `visibility: public`），公网隧道 `work.fanhe.dpdns.org` 可访问。素材含客户家实景 | 原图**绝不入库**，只入重编码封面；入册前逐张过目；必要时打码 |
| 高 | 素材库结构不稳定 | 同一天内目录被重排，`酒柜` 从 0 张变 2 张，`案列` 池被拆散 | 映射以文件为单位记录来源路径，不依赖目录约定；构建脚本幂等 |
| 中 | 酒柜素材仅 2 张 | 九品类里可选空间最小，容易出现两格几乎同款 | 补拍，或该格保留占位；不要用别的品类顶替 |
| 中 | 竖图裁切丢主体 | 见 3.5 实测 | 映射表支持 `focus` 字段，默认居中，人工可改 |
| 中 | 组件必须改，不能只填数据 | 两处渲染都忽略 `cases` | 明确把组件改造列入工作量 |
| 中 | 风格轴已无信息量 | 1654 比 4 | 一期只做品类轴，风格筛选单独立项再评估 |
| 低 | TIF 与 MP4 无法直接显示 | 57 个 TIF、19 个 MP4 | 构建工序只取 JPG 与 PNG，TIF 转码后另存 |
| 低 | 产物体积增长 | `dist` 1.1 MB 增至约 2.6 MB | 可接受，封面统一 WebP q78，单张限 60 KB |
| 低 | 文件名无意义 | 哈希名与 `IMG_xxxx`，无标题无客户信息 | 标题一律留空串或人工填，不自动推断 |

### 4.3 实测体积依据

取 6 张不同品类样图，居中裁 400:234 后缩至 800×468，存 WebP q78：

| 源文件 | 源大小 | 封面大小 |
| --- | --- | --- |
| 橱柜 1276×1702 | 131 KB | 24 KB |
| 衣柜 1080×1439 | 331 KB | 9 KB |
| 书柜 3120×4160 | 4403 KB | 62 KB |

## 五、方案

### 方案 A：受控封面随 `dist` 分发（推荐，一期）

1. 新建 `apps/web/public/cases/<categoryId>/<NN>.webp`，只放封面，不放原图。
2. 新建 `tools/cases/manifest.json`，记录「源文件相对路径 → categoryId → 顺序 →
   标题 → 可选 focus」，这是唯一需要人工确认的工件。源路径按文件记，不按目录约定。
3. 新建 `tools/cases/build-covers.mjs`，读 manifest，用 sharp 裁切、缩放、转 WebP，
   输出到 `public/cases/`。脚本只在素材更新时手动跑，不进门禁。
4. `lib/case-catalog.ts` 填 `cases`，`cover` 由 `null` 变为 `/cases/...webp`。
   `CASE_CATEGORIES` 仍是编译期常量，页面依然无网络请求、无三态、无权限。
5. 改两个组件。横滑条取每品类首张封面渲染 `<img loading="lazy">` 加品类名；
   弹窗按品类分组铺该品类全部封面。无封面时保留现有占位块，样式一字不改。

**优点**：零迁移、零接口、零鉴权改动；不新增权限点，因此不必重建 `migrate` 与
`api` 两个镜像，避开旧镜像返回旧权限清单导致整组静默消失的那个坑；浏览器端与
桌面端天然一致，因为两端都读 `dist`；首屏无额外请求。

**缺点**：换图必须重新构建与发版；图片无法从界面维护；`dist` 从 1.1 MB 增至约 2.6 MB。

### 方案 B：入库 + 接口 + 静态托管（二期）

新增 `Case` 与 `CaseImage` 两张表（第 12 个迁移）、`GET /api/cases` 读接口、
上传接口与体积类型校验、`@fastify/static` 或对象存储、`ops.case.read` 权限点。

必须预先知道的代价：新增权限点要重建 `migrate` 与 `api` 镜像并重跑 `db:seed`；
owner 走代码常量 `[...ALL_PERMISSIONS]` 而不查库，旧镜像只返回旧清单，前端
`filterNavigation` 按 `module.` 过滤会让整组静默消失且零报错。前端还要引入三态，
首页第一段从此会失败。

**适合**：需要从界面传图、按客户归属管理、远程维护素材。

### 方案 C：直接读本机目录（否决）

三条独立原因：

1. 桌面端渲染进程来源是 `shellOrigin`（回环本地服务，`server.ts` 托管
   `resources/web`），只能读 `dist` 内文件，读不到 `E:\BaiduSyncdisk`。
2. 浏览器端经隧道访问时，页面跑在阿阳的机器之外，只能请求服务端。
3. 即便在桌面端加自定义协议绕过，浏览器端覆盖不到，会形成两套行为。

另外路径含中文与空格，盘符会在 `E:` 与 `F:` 之间变，与「受控文件禁止写死盘符」
的既有约定冲突。

### 三案对比

| 维度 | A 静态封面 | B 入库 | C 读本机 |
| --- | --- | --- | --- |
| 迁移 / 接口 / 权限改动 | 无 | 3 项全有 | 无 |
| 换图成本 | 重新发版 | 界面操作 | 无 |
| 首屏是否可能失败 | 否 | 是 | 否 |
| 两端行为一致 | 是 | 是 | 否 |
| 2.78 GB 原图是否可用 | 否 | 否，需另存对象存储 | 是 |
| 本期工作量 | 小 | 大 | 不可行 |

## 六、执行步骤（方案 A）

1. **人工选图**。审阅页已生成在 `.tmp/cases-review/index.html`，按品类各列 12 张
   候选，上半部是按 400:234 裁切的真实效果，下半部是原图缩略，点选后底部生成编号
   清单。判据是构图完整、无生活杂物、裁切后柜体主体不残缺。
2. **写 manifest**。`tools/cases/manifest.json`，字段为
   `{ source, categoryId, order, title, focus? }`。`source` 相对素材根，
   `categoryId` 必须属于九品类。
3. **写构建脚本**。`tools/cases/build-covers.mjs`，能力固定为裁切到 400:234、
   缩至 800×468、转 WebP q78、输出 60 KB 以内、跳过 TIF 与 MP4。
4. **填数据**。`lib/case-catalog.ts` 的 `cases` 由 `[]` 变为真实数组，
   `cover` 变为 `/cases/...webp`。
5. **改组件**。`CaseGallery.tsx` 与 `CaseGalleryDialog.tsx` 各加一条分支。
6. **补测试**。在 `apps/web/test/case-catalog.test.mjs` 增加字段不变量：
   `id` 唯一、`categoryId` 存在于品类表、`cover` 以 `/cases/` 开头、
   `cases` 顺序与 `order` 一致。另加一条文件存在性断言，逐个读取 `cover` 指向的
   实际文件，不存在即失败。这条断言必须做反例测试，塞一个不存在的路径确认它真的
   报错，再恢复。
7. **过门禁**。`test → lint → typecheck → format:check`，在 `projects/fanhe-work`
   下跑且 DB 容器在跑。新增的 `.ts` 首次 `format:check` 必挂，先跑 `--write`，
   再查 `grep -c $'\xef\xbf\xbd'` 确认无乱码。图片是二进制，不要交给 prettier。
8. **验收**。首页横滑条九格全部有图且酒柜两格不重样；弹窗按品类分组；`dist`
   体积增长不超过 2 MB；断网时首页第一段照常显示。

## 七、需要先决策的三件事

1. **一期是否只做品类轴**。风格维度实测 1654 比 4，加风格筛选等于加一个不产生
   信息的控件。建议不做，单独立项再评估。
2. **酒柜只有 2 张怎么处理**。补拍、只放 1 张、或保留占位，三种都合理，
   但不能拿别的品类的图顶替。
3. **是否需要排除部分素材**。`安装照片回传/` 364 张我建议不进案例展示，
   它们是交付凭证，与营销素材不是同一种东西。涉及隐私判断的部分我不代做决定。

### 挑图这件事踩了一个坑，值得记下来

第一版按「清晰度、对比度、亮度、分辨率」机械排序，取每品类前 4。结果最靠前的一批是
**施工中的毛坯空房**：墙面平整、曝光均匀、边缘锐利，三个指标全部拿高分，但画面里没有
成品柜体。同批里还混进了施工垃圾、工人、茶几上的桌面截图。

根因是纯几何指标分不出「拍得好」与「拍的是空房子」。改判据后仍不够：把饱和度与高光占比
加权之后，24 张里有 6 张可用，剩下还得靠眼睛。最终采用两段式：

1. 脚本粗筛（尺寸、比例、别太糊、别太暗、平均哈希去重），每品类出 8 至 20 张候选并拼成审图；
2. 逐张看图挑选，挑中的按编号回填。

**参数化的自动挑选在这个素材库上不成立。** 交付物是手机随手拍与专业作品混在一起的，没有
一个可测量的量能把「竣工实景」和「施工中」分开。

### 从候选里删掉的三张

- 套装门有一张是「大片白墙加一道灯带」，构图干净但没有可辨识的门，删。
- 阳台柜前两张是同一空间的仰拍与平视，重复，留一张。
- 铝木柜有四张里两张都是酒瓶酒柜，同质，留一张。

结果就是酒柜 1 张、阳台柜 2 张这类不对称。**张数不齐比拿别的品类的图顶替更诚实。**

### 数据层为什么用生成函数

43 条路径若手写一遍，必然出一次「橱柜卡配了衣柜的图」这类串行错误，而它在界面上表现成
「看起来都挺合适」，肉眼很难发现。`case-catalog.ts` 里用 `album(categoryId, count)` 按张数
生成，少一个可写错的字段；测试再拿生成出来的路径去磁盘上找，两个方向都闭上。

传错张数不会静默通过：文件找不到，第 5 条断言直接 FAIL。

### 测试加了两条，方向相反

第 6 条是**反向**断言：磁盘 `album/` 目录里不允许有清单之外的图。改了张数却忘了删旧图，
不会有任何界面症状，但那个文件会一直躺在仓库里，让「一共多少张」这类人工统计失去意义。

新断言都做了反例测试：手动塞一张 `zzz-orphan.webp`，确认第 6 条确实 FAIL，再删除。不做
这一步，无法排除「断言写错了但一直通过」。
