# T7-04 团队协作下的开发端隔离与版本发布流水线

> 设计稿，2026-10-13。本文只做方案设计，不含代码改动。
> 与 `docs/T7-03-RELEASE-COMPATIBILITY.md` 的分工：T7-03 论证「旧版本为何会在迭代中失效」并给出目标形态；T7-04 把它落实为可执行流程，回答环境怎么分、代码怎么走、包怎么发、用户怎么点、出事怎么回。
> 现状依据全部来自仓库内文件，逐条给出位置。

## 一、结论摘要

1. 当前项目只有两套环境，dev 与 prod，且二者跑在同一台机器上、共用同一个数据库命名卷。**这是「开发迭代影响使用人」的结构性根源**，与 bug 无关，靠加大测试力度无法解决。
2. 需要新增一套 staging。它不是可选项，是隔离机制的支点：让新版在真实的客户端形态与真实的网络路径上被验收，同时与使用人手上的数据和生产入口完全分离。
3. 服务端零停机的最小改造点已经存在。`apps/web/deploy/nginx.conf` 的 upstream 写的是 compose 服务名 `api`，而 `cloudflared` 的路由指向 `http://web:80`、配置在 Cloudflare 侧。因此切换 api 不影响 Tunnel，只需在网络别名与 nginx 两层做文章。
4. 客户端手动更新需要改一个开关并同步文案，改动集中在 `apps/desktop/src/main.ts` 第 443 行。状态机（`update.ts`）与顶栏按钮（T7-02b）无需重做。
5. 数据库没有真正的回滚。这一条必须写进流程，用 expand-contract 迁移纪律换取「应用可回滚而 schema 不必回滚」。
6. 全文分四期落地，第一期不需要写代码。

## 二、需求拆解与依赖关系

用户的四个需求不是并列关系，前一条是后一条的前提。

| 需求 | 必须回答的问题 | 前置依赖 |
| --- | --- | --- |
| 开发端与使用端隔离 | 开发动作如何不触碰生产数据与生产入口 | 环境划分、数据库分卷 |
| 测试与打包发布流程 | 一个版本从提交到可分发，要过几道关、每道关的判据是什么 | 隔离（否则测的是被污染的环境） |
| 部署到正在使用的环境 | 新服务端如何接管正在服务的入口 | 蓝绿切换点、迁移纪律 |
| 用户端手动更新交互 | 用户何时被提示、点什么、能否拒绝 | 更新通道、最低支持版本闸门 |

依赖链是单向的。隔离没做好就做流水线，测出来的结果不可信；流水线没固定就做蓝绿，切换的是未经检验的产物。

## 三、现状勘察与结构性缺口

以下每条都有对应的仓库位置。

### 缺口 1：开发机即生产机

`.env.compose` 的注释记着 Tunnel 与域名的对应关系，`cloudflared` 容器不绑任何宿主端口（`docker-compose.yml` 第 236 行附近明确写了「刻意没有 ports」），外部流量由 Cloudflare 边缘经出站连接送进 `web:80`。这意味着源站就是这台开发用的机器。开发期间重启容器、断网、跑迁移，全部直接作用在使用人可见的域名上。

### 缺口 2：开发期与生产共用同一个数据库卷

`docker-compose.yml` 第 245 至 247 行，卷名为 `fanhe-work-pgdata`，不随盘移动。而 `apps/api/.env` 的 `DATABASE_URL` 指向 `127.0.0.1:5432/fanhe_work`，也就是这台机器上的同一个 PostgreSQL 实例。

后果有三层。开发期执行 `pnpm db:deploy` 会把迁移应用到生产库；开发期的测试数据落在生产库；开发期改坏的表结构与生产共存。

### 缺口 3：镜像无版本标识，服务端无法按版本回切

`docker-compose.yml` 的 api 服务只有 `build: {context, dockerfile, target}`，没有 tag。每次 `up -d --build` 都用 `latest` 语义重建，一旦新版有缺陷，没有「上一个版本的镜像」可切。第 166 行还写死了 `container_name: fanhe-work-api`，单实例标识固定，第二个实例无法并存。

### 缺口 4：端口段被 dev 与 prod 共用

`apps/api/src/config/env.ts` 第 24 行默认 `PORT ?? '8787'`，`apps/web/vite.config.ts` 第 73 行 Vite 在 5173，而 `docker-compose.yml` 第 188 行把 api 映射到 `127.0.0.1:8787`、第 212 行 web 映射到 `127.0.0.1:8080`。两套环境靠同一端口段互斥运行。这解释了为什么 staging 现在起不来，也与 T7-02 修的「origin 漂移导致设置丢失」同源。

### 缺口 5：打包链路不重建前端产物

`apps/desktop/package.json` 的 `dist` 脚本只跑 `sync-version.mjs && tsc && electron-builder`，而 `electron-builder.yml` 的 `extraResources` 把 `../web/dist` 原样投进 `resources/web`。改了前端忘了先 build web，会打出带旧界面的新版本安装包。工作记忆记载 v0.1.0 与 v0.1.1 两个包就带着 11:34 的旧产物，直接导致 T6-03b 的宿主分派没进客户端。

### 缺口 6：无自动化门禁，无回滚脚本

仓库内没有 `.github/workflows`，质量门禁（lint、typecheck、format:check、四包单测、浏览器 e2e、外壳冒烟）全部依赖人工按顺序执行。`tools/checks/db-backup.mjs` 说明已有备份意识，但没有任何回滚脚本与回滚判据。

### 缺口 7：迁移与应用启动强绑定

`docker-compose.yml` 第 195 至 198 行，api 依赖 `migrate` 的 `service_completed_successfully`。这条约束的正确性没有疑问，它保证 api 不会在建表完成前接请求。代价是迁移耗时全部计入停机窗口，且迁移与应用同批发布，破坏性迁移会直接作用于旧客户端。

## 四、模块一：开发端与使用端的隔离机制

### 4.1 隔离的七个维度

隔离要一次定义全，漏一个维度就会从那个维度漏出去。

| 维度 | dev | staging | prod |
| --- | --- | --- | --- |
| 数据库实例 | 本机 PostgreSQL，独立库名 | 独立命名卷 | 现有 `fanhe-work-pgdata` |
| 端口段 | web 5173 / api 8787 / db 5432 | web 8081 / api 8788 / db 5433 | web 8080 / api 8787 / db 5432 |
| 对外入口 | 无，仅回环 | `staging.` 前缀域名 | `work.fanhe.dpdns.org` |
| 签名密钥 | `apps/api/.env` 的 JWT_SECRET | `.env.staging` 独立一份 | `.env.compose` 现有那份 |
| 数据 | 开发数据，可随时重置 | 种子或脱敏快照 | 真实数据 |
| 镜像标识 | 不产出镜像 | `版本-rc.N` | 正式版本号 |
| 证书与信任根 | 不签名 | 与 prod 同证书 | 与 prod 同证书 |

三个环境共用同一张签名证书与同一个 Tunnel 容器，这两处刻意不分。原因在第六章与第十章说明。

### 4.2 dev 环境的硬边界

dev 就是开发者本机的 `pnpm dev`。隔离要求四条。

1. **数据库必须独立库名或独立实例。** 当前共用 `fanhe_work` 库，这是缺口 2 的直接来源。最低成本的改法是改 `apps/api/.env` 的 `DATABASE_URL` 指向 `fanhe_work_dev`，用同一实例的两个库。要更彻底就起一个只给 dev 用的容器。
2. **dev 的迁移不得应用到生产库。** 由第 1 条自然保证。
3. **dev 不得监听非回环地址。** 已成立，`env.ts` 第 71 行默认 `HOST ?? '127.0.0.1'`，Vite 也显式绑 `127.0.0.1`（`vite.config.ts` 第 68 至 72 行有说明，绑 IPv4 回环是为了避开 Windows 上 `localhost` 解析到 `::1` 的坑）。这条要保持并被断言。
4. **dev 签发的令牌在 prod 无效。** 已成立，`.env.compose` 的注释明确记着两份密钥刻意不同，理由是复用会让本机签发的令牌在对外环境有效。

### 4.3 staging 环境（新增）

staging 是整套方案的支点，它的定位是：**与 prod 同构、与 prod 同网络路径、与 prod 数据分离**。

形态上增加一个 `docker-compose.staging.yml`，与 prod 的编排同源，差异只有四处。

- 项目名与容器名前缀带 `staging`，避免与 prod 的 `container_name` 撞名。
- 卷名改为 `fanhe-work-pgdata-staging`。
- 端口换到 8081 / 8788 / 5433。
- 环境文件用 `.env.staging`，JWT_SECRET 独立生成。

入口的接法需要说明。当前 Tunnel 只有一条 hostname 路由指向 `http://web:80`，路由配置在 Cloudflare 侧。为 staging 加一条 `staging.work.fanhe.dpdns.org -> http://web-staging:80` 的 Public Hostname 即可，**不需要新增 cloudflared 容器，也不需要重启现有容器**。这是选 Cloudflare Tunnel 而非自建反向代理的一个实际好处：增加一条入口是 Cloudflare 侧的配置动作，与正在运行的服务完全解耦。

staging 的数据来源两条路可选。默认用 `db:seed` 兜底（`apps/api/src/db` 的种子按 code 做 upsert，幂等，重跑安全，第 14 行注释有说明）。要做真实数据量的验收时，从 prod 导一份脱敏快照，脱敏规则至少覆盖账号标识与业务内容字段。

### 4.4 隔离生效的机械判据

隔离不能靠「我觉得分开了」，要能被机械验证。以下五条都可执行。

1. 启动 dev 后，prod 数据库的活动连接数不增加。
2. 在 dev 上执行一条迁移，prod 的 `_prisma_migrations` 表记录数不变。
3. 停掉 prod 的全部容器，dev 功能完全可用。
4. `staging.` 域名返回的页面加载的 api 来自 staging 容器（用 `/api/version` 的指纹区分）。
5. dev 与 prod 的 JWT_SECRET 不同，dev 签发的访问令牌在 prod 得到 401。

第 4 条需要一个前置条件：让 `/api/version` 能区分环境。当前它返回 `version` / `builtAt` / `commitSha` / `fingerprint`（`apps/api/src/version/manifest.ts`），其中 `builtAt` 恒为空串、`commitSha` 恒为 `unknown`。加一个环境标识字段即可，成本一行。

### 4.5 一处必须说不的：staging 不用生产数据做开发

staging 存在之后，最容易出现的滑坡是把生产数据导入 staging 给开发当调试素材。这件事的风险有三层：真实客户内容进入一个门禁更松的环境；脱敏不彻底则等于把生产数据复制到第二个地方；一旦 staging 入口可被公网访问，等于扩大了暴露面。因此数据导入必须走脱敏流程并留记录，不允许直接 `pg_dump | pg_restore`。

## 五、模块二：版本功能的测试与打包发布流程

### 5.1 六道门禁与它们的判据

门禁是一条单向漏斗，前一关不过不进入下一关。判据必须机械，「看起来没问题」不能作为通过条件。

| 关 | 内容 | 通过判据 | 防住什么 |
| --- | --- | --- | --- |
| 1 静态检查 | `pnpm lint`、`pnpm typecheck`、`pnpm format:check` | 三条全部零退出 | 类型与风格问题流入后续环节 |
| 2 单元测试 | `pnpm test` | 四包全绿，基线 shared 108 + api 232 + web 116 + desktop 142 | 逻辑回归 |
| 3 契约快照 | 新增 | 响应结构快照未变 | 破坏性字段变更 |
| 4 迁移安全审查 | 新增 | 迁移中无 `DROP`、无 `SET NOT NULL`，或已确认旧客户端退场 | 旧客户端在新 schema 上失效 |
| 5 浏览器 e2e | 现有 150 项 | 全通过，且跑在 staging 而非开发机 | 环境差异掩盖的问题 |
| 6 外壳冒烟 | 现有 | PASS | 内置服务与反代链路断裂 |

第 3、4 关是 T7-03 约束 1 与约束 2 在本流程中的机械判据。第 5 关的环境从 dev 改成 staging 是本节的关键调整：e2e 必须跑在与 prod 同构的编排上，否则验证的是 dev 的形态。

有一处辩证需要说明。增加门禁会拉长单次发布周期，团队规模小的时候这个成本很实感。但门禁数量与发布频率是替代关系，叠加关系不成立。**在单人维护的阶段，宁可减少发布次数，也不要用跳过门禁换取更快发布**，原因在于跳过门禁的代价是生产故障，而故障排查与补救的时间成本远高于门禁执行时间。等发布频率上升、门禁真正成为瓶颈时，该做的是用 CI 并行化，删关卡只会把成本转移到线上。

### 5.2 打包纪律四条

1. **先构建前端，再打包外壳。** 顺序是 `pnpm --filter @fanhe/web build` 然后 `pnpm --filter @fanhe/desktop dist`。这是缺口 5 的全部对策，建议把两步写进同一个发布脚本，留给记忆的空间越少越好。
2. **版本号只改仓库根一处。** `sync-version.mjs` 在打包时同步到 `apps/desktop/package.json`。预发布版本用 `0.2.0-rc.1` 形态，`packages/shared/src/version.ts` 第 110 至 119 行已规定预发布号排在正式版之前。
3. **签名前自检，换证书单独安排发布。** 发版前跑 `signing:check`，确认证书身份与上一版一致。换证书等于换信任根（T6-03d 已查明），必须单独一次发布，与功能发布合并会同时打断更新链路与版本推进。
4. **产物只从 `release/` 取，并记录 sha256。** 打包后执行 `verify:pack` 与 `verify:sign`，前者第六节会比对产物指纹与签名身份档案。

### 5.3 发布动作序列

一个版本从代码就绪到可分发，共十步。

1. 更新仓库根 `package.json` 的 `version`，提交并打 git tag。
2. 全量构建 shared、api、web。
3. 跑第 1、2、6 关。
4. 打安装包，产出 NSIS 安装程序、`latest.yml`、blockmap。
5. 签名，跑 `verify:pack` 与 `verify:sign`。
6. 构建镜像并打双 tag：正式版本号与 `版本号-rc.N`。前者给 prod，后者给 staging。
7. 部署到 staging，跑第 3、4、5 关。
8. 在 staging 上用真实安装包做完整验收，覆盖登录、核心业务流程、更新链路。
9. 发到 GitHub Release。注意 `electron-builder.yml` 的 publish 产出的是草稿（`draft: true`），需再 PATCH 把 draft 置 false 才公开。
10. 通知使用人可在客户端内更新。

第 6 步的双 tag 是回滚能力的前提，对应缺口 3。第 9 步的时机不能提前：一旦 draft 置 false，旧版本客户端就会检查到新版本并弹提示，而此时服务端可能尚未切稳。

## 六、模块三：将新版本部署到正在使用的环境

### 6.1 先把议题澄清：「推送到正在使用的端口」有三种解读

这句话在字面上有歧义，三种解读对应三套不同的技术动作，需要分别回答。

**解读 A，新版本服务端如何接管正在对外提供服务的入口。** 也就是域名 `work.fanhe.dpdns.org` 背后的 `web:80` 与它反代的 api。这是「部署」的本义，6.2 节回答。

**解读 B，如何把新版本交付到使用人正在运行的那个客户端进程。** 这是「推送」的本义，6.4 节回答。

**解读 C，不更换端口号的前提下替换监听进程。** 即热替换。这条要单独说明为什么不做。api 容器的 `ENTRYPOINT` 是 tini 加 `node dist/index.js`（`apps/api/Dockerfile` 第 143 至 145 行），替换监听进程必须重启容器内的 node 进程。要做到「端口不中断地换进程」，需要进程内的零停机重启能力（socket 交接或主进程重载），对一个 Fastify 单进程应用来说，引入这套机制的复杂度远超它在一个单用户团队里的收益。**结论是解读 C 不做，用蓝绿替换在上一层达到同样的用户可感知效果。**

### 6.2 解读 A 的解法：蓝绿替换，切换点在 nginx upstream

先看现有链路，这是整个方案成立的基础。

```
使用人 → Cloudflare 边缘 → cloudflared 容器（出站长连接，无入站端口）
                              → web:80（nginx 静态托管 + /api 反代）
                                  → api:8787（compose 服务名）
```

三个关键事实。

- `cloudflared` 的路由配置在 Cloudflare 侧（`.env.compose` 注释说明了这一点），容器里只有一个 Token。改动 api 不影响 Tunnel。
- `apps/web/deploy/nginx.conf` 的 upstream 写的是 `server api:8787`，用的是 compose 服务名，容器 IP 变化由 Docker DNS 兜住。
- nginx 在 reload 时会重新解析 upstream 的主机名（该文件第 22 至 24 行的注释已经点出这个时机：nginx 启动时解析一次，IP 变了要重启才生效）。

因此零停机的切换点应放在「`api` 这个网络别名指向哪个容器」上。具体动作分五步。

1. 构建带版本 tag 的新镜像。
2. 起绿色 api 容器（`api-green`，同镜像），配好独立 container_name，等待它自己的 healthcheck 通过。
3. 把 compose 网络里的 `api` 别名从蓝色容器移到绿色容器：`docker network disconnect` 后 `docker network connect --alias api`。
4. 在 web 容器内执行 `nginx -s reload`，让它重新解析 `api` 到绿色容器的 IP。
5. 蓝色容器延迟五分钟再停，用于兜住第二步中尚未结束的长连接与可能的快速回滚。

窗口分析。第 3 步到第 4 步之间只有毫秒级；nginx reload 是不中断的，已建立的连接继续由旧 worker 服务到自然结束。用户可感知的中断接近于零。

前置改造两处，都不大。`docker-compose.yml` 第 166 行的 `container_name: fanhe-work-api` 要去掉或改成带颜色后缀，否则第二个实例无法并存；api 服务缺少能用于「绿色是否就绪」判定的 healthcheck 表达式（`apps/api/Dockerfile` 第 143 行有一条 CMD 形式的健康检查，但它打的是 `/api/` 而非 `/api/health`，建议显式指向 `app.ts` 里已注册的 `GET /api/health`）。

需要说明这处设计的一处妥协。nginx upstream 写死主机名加 reload 的方案，牺牲了 keepalive 的连续性（reload 后到旧 IP 的复用连接会失效），换来的收益是不引入服务发现组件。对单机单用户的规模，这个取舍是划算的。若将来 api 实例数超过两个，应改用 `resolver` 加变量的动态解析，那时再评估。

### 6.3 解读 A 的另一半：数据库迁移独立执行

服务端零停机的前提是数据层不阻塞。对应缺口 7 与 T7-03 约束 2，三条要求。

1. **迁移从 api 的启动依赖中解绑。** 保留 `migrate` 服务，但把执行迁移变成发布流水线里的一个显式步骤，由发布人触发并能观察耗时，代替 api 每次重建时的被动等待。
2. **迁移必须对当前线上代码向后兼容。** 用 expand-contract 两步走：发布 N 只做加法（加可空列、加新表、并发建索引），发布 N+1 及以后才做减法（删列、收紧约束）。判据是任一次发布的迁移里出现 `DROP` 或 `ALTER ... SET NOT NULL` 时，必须能回答「旧客户端现在还在跑吗」。
3. **执行迁移前必须有一次可用的备份。** `tools/checks/db-backup.mjs` 已存在，应作为迁移前的一道强制检查。

### 6.4 解读 B 的解法：分发模型，用户端主动拉取

客户端的分发走 electron-updater 加 GitHub Releases，这条链路 T6-03 已经打通并两次发版验证。本方案要补的是三点。

- **推送的语义是「可用」而非「强制到达」。** 服务端能做的只是把新版本放到客户端能发现的位置，装不装由用户决定。这一点与模块四直接衔接。
- **业务通道与更新通道完全解耦。** 服务端不可用时，更新检查仍能工作，反之亦然。T6-02 的版本比对已按非关键路径处理，`apps/web/src/lib/version-check.ts` 第 32 至 34 行记着这件事。
- **历史资产不删除。** GitHub Release 上每个版本的安装包是降级的唯一途径，清理资产等于放弃回滚能力。

## 七、模块四：用户端手动更新的交互设计

### 7.1 复用已有的状态机与按钮，不要重做

T6-03b 与 T7-02b 已经把两件事做好了，本节只描述如何把它们接进本流程。

- 状态机在 `apps/desktop/src/update.ts`，`UpdatePhase` 有八个状态，三条不变量（`downloaded` 不被抹掉、`error` 保留 version、`progress` 不编造 version）都有对应用例。
- 可见性判断在 `buildDesktopUpdateView`（T7-02b 抽出的纯函数），四种可见形态 `checking` / `downloading` / `ready` / `failed`，加一个不渲染的 `hidden`。
- 「有更新」按钮已从账号菜单挪到顶栏与头像同一行，因为菜单要先打开才看得见，而「有新版本」是用户不会主动去找的事。

所以本模块的净增量只有三处：一个开关、一个确认框、一个闸门字段。

### 7.2 交互时序

| 时刻 | 触发条件 | 界面表现 | 用户可做的动作 |
| --- | --- | --- | --- |
| T0 启动 | 打包态且非冒烟模式 | 无 | 无 |
| T1 检查中 | 启动后自动检查 | 按钮显示检查态 | 无 |
| T2 发现新版 | `update-available` | 按钮出现，「有新版本 vX」 | 点击查看版本说明 |
| T3 下载中 | `download-progress` | 按钮显示百分比 | 可继续正常工作，可点「稍后」 |
| T4 已就绪 | `update-downloaded` | 按钮变成「重启更新到 vX」 | 点击安装，或忽略 |
| T5 安装中 | 用户确认后 | 应用退出并替换 | 无 |
| T6 重启后 | 新版本启动 | 按钮消失，菜单显示新版本号 | 无 |

T4 之后用户不点时的行为，是本次需求的真正分歧点，写进 7.4 节。

### 7.3 三个必须坚持的设计点

1. **下载与安装分离。** 下载在后台完成，安装必须由用户点击触发。这是「由使用人手动选择是否更新」的直接实现。
2. **安装前有一次确认。** 点击「重启更新」后弹一次确认框，说明后果（应用会重启、当前页面会关闭）。理由是一个会退出应用的按钮不应一次点击就生效，这与 `update:install` 的 IPC 已经用 `isReadyToInstall` 做守卫是同一层考虑。
3. **服务端维护态要能与网络故障区分。** 服务端返回 503 时前端应显示「服务端正在更新，请稍候」，显示真实的网络错误。这个区分靠 `apps/web/deploy/nginx.conf` 第 88 至 90 行的 `proxy_connect_timeout 5s` 保住快速失败，再靠前端分类处理 503。T7-03 第 2 步已列出。

### 7.4 关键分歧：`autoInstallOnAppQuit` 到底设 true 还是 false

这是本方案里唯一需要产品决策的点，且两种选择都有真实理由，值得把论证写全。

**设 true（维持现状）的理由。** `apps/desktop/src/main.ts` 第 396 至 401 行的注释说得很清楚：桌面工具会被开一整天，用户不会主动去想有没有新版，退出时自动装能保证版本实际推进。文案「已可更新到 vX，重启后生效」正是建立在这个开关之上。

**设 false 的理由。** 与本次需求「由使用人手动选择是否更新」直接冲突。退出即装意味着用户在一次正常关机时被动换了版本，他可能正打开着一个页面，重启后发现界面变了而没有心理准备。

**我的判断是设 false，但要补一个补偿设计。** 单纯的 false 会让版本推进停滞，而停滞又反过来拉长兼容窗口（T7-03 第七节论证过这个张力）。补偿设计有两条。

- **T4 状态要持续存在且可见。** 用户忽略一次，下次启动按钮还在，不会退化成「没有提示」。`update.ts` 的不变量 1 已经保证 `downloaded` 不被后续 `checking` / `not-available` 抹掉，这条基础已经在了。
- **闸门兜底。** 当版本过旧到会影响正常使用时，才允许打断业务。见 7.5。

配套的文案要同步改。「重启后生效」这句话在开关为 false 时是一句空话，用户重启之后仍是旧版且不会再有提示。改成「新版本已下载，点此重启更新」。

### 7.5 强制更新闸门

闸门解决 7.4 的补偿问题，它是唯一允许打断业务的手段。

服务端在 `/api/version` 增加 `minimumClientVersion` 字段。这个接口已经存在、无门禁、且刻意设计成登录前可用，`apps/api/src/version/manifest.ts` 第 186 至 198 行的注释记着理由：客户端太旧以致什么都跑不起来时，这条提示本身不能要求先登录。

客户端在 T0 到 T1 之间读它，本地版本低于门槛时进入「必须更新」态。行为分三级，逐级加重。

| 级别 | 触发条件 | 表现 |
| --- | --- | --- |
| 提示 | 有新版 | 顶栏按钮 |
| 强调 | 低于 `recommendedClientVersion` | 按钮常显，关闭后仍再现 |
| 阻断 | 低于 `minimumClientVersion` | 业务操作前弹一次性说明，引导去更新 |

门槛的调整必须与发版解耦，它是一次独立的配置动作，可随时回退。**提高门槛的判据只有一条：确认旧客户端在新服务端上会持续失败。** 不能因为「想让别人都用新版」而提高门槛，那是把产品诉求伪装成兼容性约束。

### 7.6 文案清单

| 场景 | 文案 |
| --- | --- |
| 检查中 | 正在检查更新 |
| 发现新版 | 有新版本 v0.2.0 |
| 下载中 | 正在下载 v0.2.0（45%） |
| 已就绪 | 新版本 v0.2.0 已下载，点此重启更新 |
| 安装确认 | 安装新版本将重启梵禾 Work。当前打开的页面会关闭，未保存的草稿会保留。 |
| 必须更新 | 当前版本已不再受支持，请更新到 v0.2.0 后继续使用 |
| 服务端维护中 | 服务端正在更新，请稍候重试 |
| 更新失败 | 检查更新失败，稍后将自动重试 |

「未保存的草稿会保留」这句需要先核实再采用。仓库有 `apps/web/src/lib/note-draft.ts`，说明纪要存在本地草稿机制，但草稿的持久化时机与重建后的可恢复性需要确认。若不能保证，文案必须改为「未保存的内容将丢失」，不能给用户一个无法兑现的承诺。

## 八、各阶段操作流程、触发条件与判据

五个阶段串成一条主线，每阶段给出触发条件、操作、通过判据与失败出口。

### 阶段 1 功能开发

- **触发条件**：需求确认，接进某个里程碑。
- **操作**：在 dev 环境开发，数据库用独立库，端口 5173 / 8787。每日提交。
- **通过判据**：第 1、2 关在本地通过。
- **失败出口**：不进入阶段 2。dev 环境可随时重置，不影响任何人。

### 阶段 2 集成与打包

- **触发条件**：功能在 dev 自测完成，提交合并。
- **操作**：执行 5.3 节的第 1 至 6 步。全量构建、六道门禁、打双 tag 镜像、打安装包、签名、`verify:pack` 与 `verify:sign`。
- **通过判据**：六道门禁全绿；产物指纹与签名身份档案一致；镜像双 tag 均已推送。
- **失败出口**：修复后回到阶段 1。**此阶段尚未触碰 prod 与任何使用人，回退成本为零。**

### 阶段 3 staging 验收

- **触发条件**：阶段 2 全部通过。
- **操作**：部署 `版本-rc.N` 镜像到 staging（独立 compose、独立卷、独立端口、独立域名）。在 staging 上跑契约快照、迁移安全审查、浏览器 e2e。用真实安装包装一台机器做端到端验收，覆盖登录、核心业务流程、更新链路。
- **通过判据**：e2e 全通过；真实安装包能装能登能更新；`/api/version` 的环境标识为 staging。
- **失败出口**：回阶段 1。staging 数据可丢弃， prod 完全不知情。

### 阶段 4 生产发布

- **触发条件**：阶段 3 全部通过，且选在使用低频时段，并已预告。
- **操作**：按序执行六步。
  1. 发布前跑 `tools/checks/db-backup.mjs`，确认有可用备份。
  2. 执行数据库迁移（expand 阶段，只做加法），观察耗时。
  3. 按 6.2 节做蓝绿替换。
  4. 切流后观察五分钟，`/api/health` 与错误率。
  5. 把 GitHub Release 的 draft 置 false。
  6. 通知使用人可更新。
- **通过判据**：`/api/health` 连续正常；核心流程抽查可用；旧版本客户端仍能完成核心操作（这一条是 T7-03 约束 1 的现场验证）。
- **失败出口**：立即执行回滚，见第九章。

阶段 4 的第 5 步必须在第 3 步之后。一旦 draft 置 false，正在运行的旧客户端就会检查到新版本并弹提示，而此时服务端可能还没切稳。

### 阶段 5 客户端更新

- **触发条件**：阶段 4 的第 5 步完成。
- **操作**：无人工操作。使用人各自的客户端在下次启动时检查到新版，后台下载，顶栏出现按钮。
- **通过判据**：规定时间内多数客户端完成更新；低于 `minimumClientVersion` 的实例数归零。
- **失败出口**：个别客户端更新失败由用户重试或手工下载安装包；普遍失败则撤下该 Release（改回 draft 或删除资产）并回滚服务端。

## 九、回滚策略

### 9.1 分层看待回滚，各层的时效不同

| 层 | 回滚手段 | 时效 | 是否需要用户操作 |
| --- | --- | --- | --- |
| 服务端应用 | nginx upstream 切回蓝色容器 | 秒级 | 否 |
| 服务端配置 | 还原 `.env.compose` 与 Tunnel 路由 | 分钟级 | 否 |
| 客户端版本 | 用户手工下载旧版安装包覆盖安装 | 由用户决定 | 是 |
| 数据库 schema | 不可回滚，只能前向修复 | 视脚本而定 | 否 |
| 数据库数据 | 备份恢复 | 有丢失窗口 | 否 |
| 签名证书 | 不可回滚，必须重签并让用户重装信任根 | 长 | 是 |

### 9.2 服务端回滚

蓝绿结构下，应用层回滚就是把 `api` 网络别名切回蓝色容器再一次 `nginx -s reload`。前提是**蓝色容器在切流后延迟五分钟才停**，这五分钟就是回滚窗口。若超过五分钟才发现问题，需要重新拉旧镜像起容器，时间变为分钟级，这正是一定要保留双 tag 镜像的理由。

配置层回滚要求每次改动 `.env.compose` 或 Cloudflare 侧的 Tunnel 路由前留档。`JWT_SECRET` 的改动要单独归类：轮换它会让全部现有刷新令牌失效，等于让所有使用人重新登录一次，这是一次影响全员的动作，必须单独安排并提前通知。

### 9.3 数据库回滚：明确它不存在

这一条必须写死，因为「回滚」这个词最容易被误用成包含数据库。

expand-contract 纪律带来的性质是：**发布 N 的迁移对发布 N-1 的代码是兼容的**。因此回滚应用到旧版本代码时，schema 不需要跟着回滚，旧代码在新 schema 上仍能正常运行（新增的列不用它，新增的表不碰它）。这就是整套方案能用应用层回滚覆盖大部分故障的原因。

代价与边界同样要清楚。

- 已执行的 DML（数据变更）无法随应用回滚撤销，需要写前向修复脚本。
- 一旦进入 contract 阶段（删列、收紧约束），旧代码就不再兼容，**此时应用不可回滚到上一版**。所以 contract 必须在确认旧客户端全部退场之后执行，判据是门栏字段与客户端的版本上报。
- 最后的兜底是备份恢复，但它有丢失窗口（上次备份到故障之间的数据）。`tools/checks/db-backup.mjs` 因此是迁移前的强制步骤，可选项不成立。

### 9.4 客户端回滚

electron-updater 只向上不向下，所以降级只有一条路：让用户手工下载旧版安装包覆盖安装。这要求三件事同时成立。

1. GitHub Release 的历史资产不删除。
2. 旧版安装包与当前的签名身份一致。**换证书之后，旧安装包的签名者与新的受信根不匹配**，降级链路会断。这是签名证书必须单独安排发布的又一个理由。
3. 用户知道去哪下载。因此降级通知必须带上直链。

触发客户端降级的判据应当从严：只有新版出现阻断性缺陷（如登录失败、数据无法保存）时才通知降级。界面类问题不值得让全员走一遍手工降级。

### 9.5 回滚决策判据

满足任一条即触发回滚，不需要等到用户投诉。

- `/api/health` 连续三次非 200。
- 任一核心流程（登录、纪要、事件）在切流后抽检失败。
- 旧版本客户端出现大面积 5xx。
- 签名验证 `Status !== 0`（Valid），此时更新通道整体失效，必须先修证书。
- staging 验收阶段任何一条 e2e 失败。

## 十、注意事项与已知限制

1. **单机承载三套环境的资源开销。** dev 加 staging 加 prod 同时运行会占用可观的 CPU 与内存。若机器吃紧，退路是 staging 按需启停，不用时常开，但绝不能用 prod 顶替 staging。
2. **Tunnel 路由改动在 Cloudflare 侧，不会即时全局生效。** DNS 与边缘有缓存。给 staging 加域名后要实测可达，不能只看控制台显示已保存。
3. **`fanhe-work-pgdata` 是命名卷，不随盘移动。** 换机时数据迁移要单独演练（工作记忆已记：数据在宿主机命名卷，不随盘移动）。
4. **端口段分配要固化成文档。** 5173 / 8787 / 5432 给 dev，8081 / 8788 / 5433 给 staging，8080 / 8787 / 5432 给 prod。dev 与 prod 在 api 端口上重叠，两者本来就不能同时运行，这个事实要写清楚，否则将来同时启会得到难以理解的连接错误。
5. **预发布版本号的比较规则已就绪但要用对。** `compareVersions` 规定 `0.2.0-rc.1` 排在 `0.2.0` 之前，所以 rc 版本不会骗过「已是最新」的判断。
6. **门禁数量与发布频率是替代关系。** 见 5.1 节末的说明。
7. **`minimumClientVersion` 与 `recommendedClientVersion` 是两个独立旋钮。** 前者是兼容性底线，后者是产品偏好，不要为了推广新版而动前者。
8. **闸门信息的暴露面。** `/api/version` 返回更多可推导信息时要重新评估，该文件第 196 至 198 行已把这个复查起点留好了。
9. **本方案不含多机房与跨区容灾。** 蓝绿是单机内的可用性方案，源站仍是单点。T5-05 的访问策略风险（用户已决定维持现状并接受）不因本方案改变。

## 十一、实施顺序

四期推进，每期有明确的独立价值，任一期停下都不破坏已获得的部分。

| 期 | 内容 | 独立价值 | 依赖 |
| --- | --- | --- | --- |
| 一期 | dev 数据库独立库名；发布前先 build web 写进脚本；镜像打双 tag；发布前强制备份 | 立即消除缺口 2、3、5 的当前风险 | 无 |
| 二期 | `autoInstallOnAppQuit` 改 false 并同步文案；加安装确认框；前端区分 503 与网络故障 | 用户拿到更新选择权，服务端短窗口不再表现为「断网」 | 无 |
| 三期 | staging 环境（独立 compose、卷、端口、Tunnel 路由）；契约快照与迁移安全审查两道门禁；e2e 迁到 staging | 新版在与 prod 同构处被验收，发布前能发现绝大多数问题 | 一期 |
| 四期 | 服务端蓝绿改造（container_name 解绑、healthcheck 显式指向 `/api/health`、脚本化别名切换）；迁移与 api 启动解绑 | 服务端发布零停机 | 三期 |

四期各自的落地文档与代码改动需另立任务，本文只定方案与顺序。

## 十二、验证方式

1. **隔离可验**：4.4 节的五条机械判据。
2. **发布可验**：任取一个 rc 版本，从阶段 2 走到阶段 4 全程记录各步骤耗时，形成基线。往后每次发布与基线比对，异常慢的步骤就是风险点。
3. **零停机可验**：阶段 4 的蓝绿过程中，用一个脚本持续请求 `/api/health` 与一个核心业务接口，记录失败数与最大中断时长。当前这个数据不存在，所以「到底断多久」今天只能靠感觉。
