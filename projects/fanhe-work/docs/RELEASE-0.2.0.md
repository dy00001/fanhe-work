# 版本迭代方案 `0.2.0`

> 基线：`v0.1.6`（`76cf82a`，2026-10-18 发布）
> 范围：`v0.1.6..HEAD`，8 个提交、**176 个文件、+20,551 / −362 行**
> 结论：**次版本号 +1**（`0.1.6` → `0.2.0`）。理由见第六节。

本版是一件事的两个半面：**把千牛 / 生意参谋的经营数据接进梵禾 Work**（新增一个模块、四张表、三个权限点、七个入口），以及**让这份数据每天能自己长出来**（日增原始响应 → 契约 → 入库）。顺带把首页「全部品类」弹窗从 27 个占位案例位收敛成九品类网格。

## 一、运营看板：从占位项到一个模块

改动前，运维信息平台分组只有一个 `planned: true` 的「数据看板」和三个「功能开发中」。现在它是七个具名入口。

### 1.1 信息架构

- 侧栏七项：数据大屏 `/ops/dashboard`、交易分析 `/ops/trade`、商品分析 `/ops/items`、流量分析 `/ops/flow`、服务体验 `/ops/service`、推广投放 `/ops/ads`、内容运营 `/ops/content`。导航清单 18 → **21 项**，预留槽位 11 → 8 项。
- **七项共用同一个页面组件**，由 `item.code` 决定渲染哪一块。侧栏高亮由 `navPath` 派生，因此「点左侧 → 地址变 → 右侧换 → 高亮跟随」是同一个事实，不需要额外的选中态变量去同步。
- 路由分派用 `isOpsNavCode(code)` 而不是七条 `===`。七项写成一串 `if` 之后，新增第八个入口时很容易漏一支，而漏掉的表现是「点进去看到占位页」—— 界面不报错，只是内容不对。
- 状态全部写进地址栏（`p` / `from` / `to` / `shop`）。刷新不丢、链接可分享、后退符合直觉；代价是每次点击重建 URL，但这里只有六个区间档与五个店铺，成本可忽略。

### 1.2 数据模型（为什么是四张表，不是十张）

原方案（`docs/QIANNIU-OPS-INTEGRATION-2026-10-19.md` §4）设计了十张表，假定「商品 / 渠道 / 客服 / 推广」都有逐日序列。实际拿到的数据里，**只有支付金额、访客、支付买家、商品访客四项是逐日真值**，其余（商品排行、渠道结构、地域、搜索词、跳失率、停留时长）接口只给 30 天整段值。

按原设计建十张表，其中五张会长期是空表 —— 而空表比没表更糟：后来接手的人会以为「这里本该有数，只是还没采」，实际是「这个粒度平台不提供」。于是收敛成两类事实表：

| 表 | 存什么 | 关键约束 |
| --- | --- | --- |
| `ecom_daily_metrics` | 只存可加量（金额 / 访客 / 买家 / 商品访客） | `@@unique([shopId, statDate])`；金额单位是分（Int），单日上限约 2147 万元，超过说明上游把元当成分传了 |
| `ecom_dimension_snapshots` | 整段维度，**带自己的窗口** | `@@unique([shopId, dimType, statFrom, statTo, dimKey])`；同一批商品在两个窗口各有一份，不能互相覆盖 |
| `ecom_shops` | 店铺维度 | `code` 稳定（`fanhe-main`），不用店铺 id —— id 会随重建变化 |
| `ecom_collect_runs` | 采集批次 | 「昨天为什么没数」唯一能回答的地方 |

业务日是 `Date` 不是 `Timestamptz`：生意参谋按东八区切日，跨时区换算会把 10 月 1 日的单子算到 9 月 30 日，而这类错位只在月初月末暴露。

**空 ≠ 0**：0 是「当天确实没有」，空是「那一天没采到」。补 0 会让日均被系统性拉低，而且从数字上看不出来。

### 1.3 权限

新增 `ops` 段三个权限点，**页面准入与金额可见分开**：

| 权限点 | 作用 | owner | admin | member / viewer |
| --- | --- | --- | --- | --- |
| `ops.shop.read` | 进入七个入口、看非金额指标 | ✓ | ✓ | ✗ |
| `ops.finance.read` | 看金额类指标（GMV、客单价、商品支付金额） | ✓ | ✓ | ✗ |
| `ops.collect.read` | 看采集批次与数据新鲜度 | ✓ | ✓ | ✗ |

ADMIN 的三项**逐条列出、不写 `ops.*`**：通配会把将来新增的金额类权限一并给它，而「能不能看钱」不该由一次顺手改动决定。授权分布实测：owner 15 / admin 12 / member 6 / viewer 3。

核心用法是**不给角色、给账号**：`user_permissions` 单独授予 `ops.shop.read` 即可让某个人看到非金额部分，页面与接口两处都会按这个判断。

### 1.4 读模型的口径

KPI 有三档来源，界面上必须显示徽标，不允许默默混用：

- **整段（period）**：查询区间恰好等于某个快照窗口时，用平台给的整段去重值（访客 3,890 而不是逐日求和的 4,038 —— 同一个访客在不同日子来两次，逐日求和多算一次）。
- **逐日（daily）**：区间被改成其他跨度时，退回逐日求和，卡片副标题写明「跨日重复访客会重复计入」。
- **推算（derived）**：转化率、客单价这类由前两者相除得到，随区间重算。

金额裁剪（没有 `ops.finance.read` 时删掉金额字段）**必须在权限判断之后**，不能写在取数路径上。首版就是写在取数路径上，结果管理员也看不到商品与渠道金额，而 KPI 正常 —— 只测 KPI 的用例全绿。

### 1.5 五店

主店 `fanhe-main` 有真实数据；`s2`–`s5` 由 `pnpm db:ops-shops` 建为「已登记、无数据」的占位行。未接入店标「待接入」、金额显示「—」、迷你柱不画零柱；切过去看到的是同一套布局的空态 —— 布局与交互与有数据的店一致，这是「占位处理」的具体含义，也是「不填演示数字」的落点。

## 二、日增链路：让看板每天有今天的数据

改动前最大的欠账是：`run-daily.ps1` 跑完只落原始响应，**「跑完采集」不等于「看板有今天的数据」**，而且中间没有任何报错提醒。

```
run-daily.ps1  →  data/daily/<日期>/  →  export-daily-ingest.mjs  →  ops-daily-<日期>.json  →  pnpm db:ops-import
   （采集，不解析）      （17 页原始响应）        （解析 + 覆盖率报告）        （契约，窗口 = 1 天）        （写入，幂等）
```

### 2.1 适配器

`tools/collector/scripts/export-daily-ingest.mjs`（516 行）。三条纪律：

- **缺就是缺。** 页面没采到、字段没回（清单标 `thin: true`）一律写 `null` 或不写这一行，绝不补 0。
- **不猜结构。** 只解析逐个验证过的文件名与字段。接口换个壳子，宁可报「这个文件没认出来」，也不去递归找「名字里带 uv 的字段」—— 猜出来的数最危险，因为它看起来是对的。
- **一个数只认一个来源。** 支付金额以 `flow-overview.payAmt` 为准（30 天窗口下它与交易明细逐日求和**完全相等**，108,000 元，实测）；`getTendency` 若同时采到只用于对账，不一致就打印「待确认」，不静默取其一。

退出码 `0` 齐全 / `2` 有块缺失 / `1` 无法产出（目录不对、日期与目录名不一致、认不出总览）。第 3 步给出的覆盖率报告逐块说明「几行 / 来源文件 / 为什么没有」。

### 2.2 连带改动：快照选择

日增写的是 **1 天窗口**的维度快照，而读模型原来按 `statTo` 取最新 —— 日增一上线，「近 30 天」的商品榜就会被最新一天的前 5 名顶掉。数字本身没错，但它回答的不是用户问的问题，而且页面上不会自己说明。

改为按「与查询区间重叠天数最多」挑（`apps/api/src/ops/date.ts` 的 `pickSnapshotIndex`）：重叠优先 → 同分取更晚的 `to` → 再同分取更晚的 `from` → 全不相交才退回最新。7 项单测，第一条就是「取最新会选错」的反例。

### 2.3 单日视图暴露的三处缺陷

1. 地址里只写 `from` / `to` 时**静默回到近 30 天** —— 手拼的分享链接会显示一个既不是链接里那个、也没有任何提示的区间。新增 `resolvePreset()`。
2. 单日查看声称「这段时间没有可画的逐日数据」—— 实为只有一格，画不出线。改为四项读数 + 一句原因。
3. 全零序列的柱状图纵轴标成 **`¥0.01`**（`seriesCeiling` 的兜底值 1 分被直接格式化）。全零时标 0。

## 三、首页「全部品类」收敛

弹窗原来展示 27 个占位案例位加 10 个筛选芯片。那些案例位没有真实信息可看，把首页横滑条全量放大铺出来，反而冲淡了「主页先看 4 张、还有 5 张」的本意。

- 弹窗主体改为 3×3 的九品类网格，卡片样式与主页横滑条逐项对齐（`aspect-ratio 400/234`、`rounded-2xl`、`color-mix` 双层底、品类名 16/500/24 居中）。
- `case-catalog.ts` 保留 `cases: readonly CaseSlot[]` 的类型但不填数据（当前空数组），删除只为「占位 27 个案例位」服务的 `SLOTS_PER_CATEGORY` / `buildCategory` / `ALL_CASE_CATEGORIES` / `countCaseSlots` / `filterCaseCategories`。案例库建立时把 `CASE_CATEGORIES` 换成一次查询结果即可。
- 单测按新口径重写：保留「九品类齐全、顺序固定、id 唯一非空」，新增「id 必须是英文小写带连字符」「name 无前后空白与隐式字符」，删除关于占位案例位与筛选行为的旧不变量。

## 五、影响与风险

### 5.1 升级时必须做的动作

| 动作 | 不做的后果 |
| --- | --- |
| 应用第 8 个迁移 + 重跑种子 | 接口 500 / 权限判定不到新点 |
| 容器部署**同时重建 `migrate`** | 旧镜像的种子按旧清单摘掉新授权：重跑 `db:seed` 时日志「移除授权关联 6」→ 管理员访问看板 403，而 `permissions` 表里三个新点在 |
| 重打桌面安装包 | `app.getVersion()` 读打包内 `package.json`，客户端仍自称 `0.1.6`，更新通道反复提示有新版 |
| 全新部署跑 `pnpm db:ops-shops` | 五店并列只有一家店的卡片（不报错，看起来像数据缺失） |

### 5.2 行为变化（会被用户感知）

- 成员与访客**看不到**运营看板了（此前占位入口对所有已认证用户可见）。
- `/ops/slot-1..3` 三条地址不再存在，旧书签落「页面不存在」。
- 首页「全部品类」从 27 个案例位变成九品类卡；原本在弹窗里按品类筛选案例的路径没了。
- **多日区间的访客数会从 3,890 变成 4,069**（口径从整段去重退回逐日求和）。金额不变。这不是增长。

### 5.3 仍然存在的风险

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 服务 / 推广 / 内容三块没有真实数据 | 三个入口只有待接入清单 | 页面明写「缺什么、在哪个后台、卡在第几批」，不编数字 |
| 渠道块常缺（当天只采到总览） | 流量页的渠道排行为空 | 适配器报告里点名「未采到渠道树」，可按天重采 |
| 日增未接入计划任务 | 需要人工接两步，忘了看板就不更新 | RUNBOOK 第一节写成四步并给了判据；下一步接计划任务 |
| 角色级手工授权会被种子重置 | 有人手工给角色加过权限，升级后消失 | 账号级授权（`user_permissions`）不受影响；文档已写明 |
| 未跟踪的设计文档未纳入版本控制 | 换机/协作时丢失 | 见第七节，由负责人决定是否入库 |

## 六、版本号：`0.2.0`

| 候选 | 判断 |
| --- | --- |
| `0.1.7`（补丁） | 不合适。新增了完整的业务模块、四张表、三个权限点，不是修修补补 |
| `0.2.0`（次版本） | **采用**。功能级新增 + 数据库迁移 + 权限面变化，且升级需要明确动作 |
| `1.0.0` | 不合适。服务/推广/内容三个板块仍无数据，日增未接计划任务，此时打 1.0 会把「未完成」说成「稳定」 |

按 SemVer 的 0.x 约定，次版本号可以带破坏性变更；本版的三条「需额外动作」（迁移、重打安装包、权限重置）都写进了 `CHANGELOG.md` 的升级须知。

## 七、发布步骤与状态

顺序不能变：**先定版本号并提交 → 再构建前端 → 最后打包**。版本号必须在构建前端之前定下来，否则安装包里烧的是旧版本号（v0.1.2 的教训）。

| 步骤 | 状态 |
| --- | --- |
| 1. 根 `package.json` 版本 `0.1.6` → `0.2.0`，`apps/desktop` 由 `sync-version.mjs` 同步 | 本轮已完成 |
| 2. `docs/RELEASE-0.2.0.md` 与 `CHANGELOG.md` | 本轮已完成 |
| 3. 四道门禁（test / lint / typecheck / format:check） | 本轮已跑：912 项 0 失败 |
| 4. `pnpm --filter @fanhe/web build` | **待执行** |
| 5. 删 `apps/desktop/release/win-unpacked` 后 `pnpm --filter @fanhe/desktop dist` | **待执行**（U 盘上不删会撞安全删除守卫 ETIMEDOUT） |
| 6. `verify:sign` + `verify:pack` | **待执行** |
| 7. 发布三项核对（未认证 by-tag 200、线上 `latest.yml` 逐字节一致、线上 exe 的 sha512 与声明 MATCH） | **待执行** |

第 4 步之后本版才算「可发布」；第 5–7 步需要在能联网且证书在机的环境里做。
