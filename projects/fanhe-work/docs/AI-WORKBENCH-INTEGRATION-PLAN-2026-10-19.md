# 梵禾 Work AI 工作台集成方案
## 方向、架构与预期形态

> 版本：方案稿 v1，2026-10-19
> 范围：仅做方案规划与效果描述，不修改任何代码
> 依据：`EVOFLOW-ARCH-REUSE-2026-10-19.md`、`NOMIFUN-EVOFLOW-SYNTHESIS-2026-10-19.md`
> 现状基线：梵禾 Work 0.1.6，Electron 44 + Fastify 5 + Prisma 7.10 + PostgreSQL + React 19 + Vite 8 + Tailwind 4

---

## 0. 摘要

**定位判断。** 梵禾 Work 当前做的是两件具体的事，把人送到工作现场（启动 QQ、千牛并自动填表），以及把人做过的事记下来（纪要、事件）。AI 工作台的正确切入点在这两件事的中间，即接管"从决定要做，到程序开好、账号登好、事情记下"这段重复劳动。通用问答是副产品，接管动作才是主线。

**形态判断。** 不做悬浮聊天框，也不做独立 App。做成"一个一级导航模块 + 全站可唤起"的双入口。模块承载完整能力（会话、任务、技能、设置），唤起入口承载"随手问一句、顺手让它做"的轻交互。前者解决深度，后者解决频次。

**架构判断。** 沿用 NomiFun 的两宿主思想，把 Agent 运行时放在 Fastify 服务端进程内，Electron 只做本地工具执行器与渲染宿主。这条路径不增加安装包体积，不引入第二语言栈，密钥不出服务端，与梵禾既有的多用户、权限、审计体系天然对齐。

**一句风险提示。** 梵禾与两个参考项目最大的结构性差异是多用户。NomiFun 是单用户本地优先，EvoFlow 的组织能力与本地数据分离。梵禾必须自己回答"这是谁的助手、技能归谁、工具能操作谁的电脑"，这个答案会贯穿全部设计，不能留到实现阶段再补。

## 1. 设计前提

方案建立在四条对梵禾现状的判断上，每条都影响后续取舍。

### 1.1 底座已经够用，缺的是执行层

梵禾现有 13 张 Prisma 模型、6 组 Fastify 路由、完整的认证与权限体系、Electron 内置静态服务加 `/api` 反代、稳定的 origin 策略、electron-updater 通道。这些恰好是 AI 工作台最贵的部分（身份、多租户、分发、更新）。缺的只有执行层。

这条判断决定了方案基调，即补齐执行层，不动地基。

### 1.2 多用户是硬约束，不能简化

梵禾的 `User` / `Role` / `Permission` / `UserPermission` / `AuditLog` 五张表构成了完整的多租户骨架。AI 工作台必须嵌进这套骨架，避免在旁边另起一套。

具体含义有三条。会话归属到人，默认私有。技能归属到组织，按角色授权。工具调用写入 `AuditLog`，可追溯。这三条与 NomiFun 的单用户模型直接冲突，需要自行设计。

### 1.3 桌面工具的可用性是动态的

这是梵禾独有、两个参考项目都没有的问题。Agent 能否启动千牛，取决于"那台电脑此刻是否在线、是否装了千牛、当前是否已登录"。工具清单不能是静态注册表，必须是运行时上报。

这条判断会引出一个专门模块，即桌面能力广播。

### 1.4 已有两处可复用的"现场知识"

`launch-login-click.ts`（1,011 行）沉淀了坐标、窗口标题、前台校验、偏差阈值等真实客户端知识。`credential-vault.ts`（539 行）沉淀了凭据边界（只从 stdin 读、不经 IPC）。这两处是梵禾相对两个参考项目的真实壁垒，AI 工作台应当把它们包装成工具，而非重写。

## 2. 整体集成思路

### 2.1 一句话定位

**一个能替你开程序、记事情、跑流程的同事，长在你已经在用的工作台里。**

### 2.2 三条主线

方案不追求"什么都能聊"，而是围绕三个可验证的业务动作展开。

| 主线 | 用户动作 | Agent 承担 | 价值可测性 |
|---|---|---|---|
| 接管启动 | "把今天要用的都开起来" | 按序启动、等待就绪、填表登录、报告结果 | 高，成功率可直接统计 |
| 沉淀记忆 | "记一下，明天跟进这个客户" | 抽取事实、归类、到期提醒、关联历史 | 中，取决于召回质量 |
| 组织技能 | 管理员写一次，全员复用 | 加载 `SKILL.md`、按角色可见、按场景注入 | 中，取决于技能质量 |

三条主线之外的能力（文档处理、数据分析、图片生成）作为技能扩展，不进入首期核心。

### 2.3 对两个参考项目的取舍

不整包移植任何一方。按"形态、契约、实现"三层分别取材。

| 层 | 取自 | 具体内容 | 理由 |
|---|---|---|---|
| 形态 | NomiFun | 两宿主一前端、本地信任令牌、应用托管五段式、会话四事实 | 与梵禾底座同源，改造成本最低 |
| 契约 | EvoFlow | AG-UI 事件词表、工具七档分层、技能 `SKILL.md` 格式、沙箱四方法 | 纯规范，无体积与许可成本 |
| 契约 | NomiFun | 四类执行策略、IDMM 保守决策原则、进程身份三元校验 | 生产级 Agent 的必要约束 |
| 实现 | 梵禾自研 | Agent 循环、工具注册表、桌面桥、审批门 | 语言栈唯一可行选择 |

许可证层面已在前序报告论证。EvoFlow 为 PolyForm Noncommercial，只能作为设计参考。NomiFun 为 Apache-2.0，可合法深入代码，但本方案仍建议自研实现，理由是语言栈不匹配（Rust 对 TypeScript）与契约密度过高。

## 3. 目标架构

### 3.1 分层

```
┌─────────────────────────────────────────────────────────────┐
│ 渲染层  React 19                                              │
│   智能助理页 · 全局唤起 · 工具卡 · 运行现场 · 审批弹层           │
└───────────────┬─────────────────────────────┬───────────────┘
        HTTP    │                             │  WebSocket
┌───────────────▼─────────────────────────────▼───────────────┐
│ 宿主层  Electron 44 主进程                                    │
│   静态托管 · /api 反代 · /ws 反代 · 本地工具执行器 · 能力上报     │
└───────────────┬─────────────────────────────────────────────┘
                │ 反向代理（同一 origin）
┌───────────────▼─────────────────────────────────────────────┐
│ 服务层  Fastify 5                                            │
│   既有：auth · launch · notes · events · system-users         │
│   新增：agent-session · agent-run · agent-tools · agent-skills│
│         agent-mcp · agent-bridge · agent-policy              │
└───────────────┬─────────────────────────────────────────────┘
                │ Prisma
┌───────────────▼─────────────────────────────────────────────┐
│ 数据层  PostgreSQL                                            │
│   既有 13 表 + agent_* 新增 8 表 + skill 2 表                  │
└─────────────────────────────────────────────────────────────┘
```

关键设计是 `/ws` 走同一条反代通道。梵禾的 `server.ts` 已经证明"同一 origin 保住了 localStorage 与路由策略"，WebSocket 走同一 origin 可以复用登录态，不需要新的鉴权路径。代价是反代要处理 upgrade，这是一处明确的改造点。

### 3.2 服务端模块划分

新增 7 个模块，按职责边界划分，不按功能堆叠。

| 模块 | 职责 | 依赖 | 预估行数 |
|---|---|---|---:|
| `agent/session` | 会话、回合、事件、效果的持久化与投影 | Prisma | 1,200 |
| `agent/runtime` | Agent 循环，模型调用、工具调度、中断与恢复 | session、tools | 1,800 |
| `agent/tools` | 工具注册表、七档分层、参数校验、结果整形 | session、policy | 1,500 |
| `agent/skills` | `SKILL.md` 扫描、解析、启用态、提示注入 | 无 | 600 |
| `agent/mcp` | MCP 客户端池，stdio 与 HTTP 两种传输 | tools | 900 |
| `agent/bridge` | 桌面工具桥，能力清单、任务下发、结果回收、超时 | session | 1,000 |
| `agent/policy` | 审批门、副作用分类、角色白名单、审计写入 | 既有 auth | 700 |

合计约 7,700 行服务端代码，不含测试。

设计上有三处刻意的克制。

第一，`runtime` 不直接依赖 Prisma，只依赖 `session` 暴露的接口。这样运行时可以单测，且未来换存储不影响循环逻辑。

第二，`tools` 不包含任何具体工具实现，只做注册与调度。具体工具分三个来源注册，即内置工具（服务端能力）、桌面工具（经 bridge 代理）、MCP 工具（经 mcp 池）。

第三，`policy` 独立成模块，而非散落在各工具里。原因是审批逻辑一旦分散，新增工具时必然漏判，而漏判的后果是 Agent 未经确认执行了副作用操作。

### 3.3 桌面端模块划分

在 `apps/desktop/src/` 新增两个文件，改造两个文件。

| 文件 | 类型 | 职责 |
|---|---|---|
| `tool-bridge.ts` | 新增 | 接收服务端下发的工具任务，调用本地能力，回报结果 |
| `capability-report.ts` | 新增 | 启动时与变化时上报本机能力清单 |
| `server.ts` | 改造 | 增加 `/ws` 反代与 upgrade 处理 |
| `preload.ts` | 改造 | 暴露最小必要 IPC，严格白名单 |

`tool-bridge.ts` 的原则是"不新增能力，只暴露已有能力"。可暴露的动作限定为 `launch.start`、`launch.fill`、`window.focus`、`screen.capture`、`file.read` 五类，全部复用现有实现，不重写坐标或填表逻辑。

凭据相关的动作遵循既有边界，服务端只下发"用哪条配置执行登录"，不下发账号密码，凭据仍由 `credential-vault` 在本地解密并使用。

### 3.4 共享包

`packages/shared/src/` 新增 `agent.ts`，承载三类契约。

- 事件类型（对齐 AG-UI 词表，加上梵禾自定义事件）
- 工具描述（名称、档位、参数 schema、是否需审批、是否依赖桌面）
- 能力清单（桌面上报的可用程序、屏幕信息、在线状态）

放在共享包而非服务端，是因为前端要渲染工具卡、桌面要构造能力上报，三方必须用同一份类型。这与既有 `navigation.ts` 的"规则进共享包"约定一致。

## 4. 数据模型

新增 10 张表，沿用梵禾既有的外键与级联风格，不采用 NomiFun 的无外键契约。

| 表 | 关键字段 | 说明 |
|---|---|---|
| `AgentSession` | id, userId, title, agentKey, workspaceId, createdAt, archivedAt | 会话主体，归属到人 |
| `AgentTurn` | id, sessionId, seq, status, model, tokenIn, tokenOut, startedAt, endedAt | 一次用户输入到回复完成 |
| `AgentEvent` | id, turnId, seq, type, payload, createdAt | 流式事件落库，支持重放 |
| `AgentEffect` | id, turnId, toolCallId, kind, target, status, receipt, createdAt | 副作用回执，可回答"做没做成" |
| `AgentToolCall` | id, turnId, name, args, result, status, approvedBy, durationMs | 工具调用明细 |
| `AgentArtifact` | id, sessionId, kind, path, mime, bytes, createdAt | 产物（截图、文件、报表） |
| `Skill` | id, orgId, key, name, description, body, enabled, visibility | 技能正文与元数据 |
| `SkillBinding` | id, skillId, roleId | 技能按角色授权 |
| `AgentApp` | id, orgId, name, kind, command, cwd, env, status | 应用托管定义（P2） |
| `AgentAppRun` | id, appId, userId, params, status, startedAt, endedAt | 应用运行实例（P2） |

四事实模型的必要性值得单说。若只有消息表，Agent 执行完一次"启动千牛并登录"后，系统无法回答三个问题：这次操作到底做没做成、失败在哪一步、重试会不会重复副作用。`AgentEffect` 就是为这三个问题存在的。它不追求 NomiFun 那种全链路栅栏，只在副作用工具上启用，成本可控。

## 5. 关键改造点

八处，按改动面排序。

| # | 位置 | 改造内容 | 难点 | 工作量 |
|---|---|---|---|---:|
| 1 | `apps/api/src/app.ts` | 注册 7 个新路由组 | 需在既有 `registerAuthSupport` 之后、权限中间件之前插入 | 1 人日 |
| 2 | `apps/desktop/src/server.ts` | 增加 `/ws` 反代与 upgrade | Node `http` 的 upgrade 事件需手工转发，不能只靠 `http-proxy` | 2 至 3 人日 |
| 3 | `packages/shared/src/navigation.ts` | 新增一级项「智能助理」与四个子路由 | 导航是唯一事实来源，需同步 `permissions.ts` 与 `nav-icons.ts` | 1 人日 |
| 4 | `apps/api/prisma/schema.prisma` | 新增 10 张表与迁移 | 与既有 13 表的外键风格保持一致 | 2 人日 |
| 5 | `apps/desktop/src/preload.ts` | 暴露工具桥 IPC | 必须白名单化，沿用"凭据不经 IPC"的既有约束 | 1 人日 |
| 6 | `apps/web/src/routes.tsx` | 挂载助理模块路由 | 现有 `MODULE_SUB_ROUTES` 需扩展为多段 | 0.5 人日 |
| 7 | 权限体系 | 新增 6 个权限点 | 需进 `ALL_PERMISSIONS` 与角色默认值 | 1 人日 |
| 8 | 审计 | 工具调用写入 `AuditLog` | 需定义事件类型与脱敏规则 | 1 人日 |

第 2 项是全案技术风险最高的一处。梵禾的桌面壳刻意只绑回环、按候选端口依次试以保住 origin。WebSocket 走同一通道意味着 upgrade 必须由 `server.ts` 自己转发，`http-proxy` 的默认封装在部分 Node 版本上会丢掉 `Sec-WebSocket-*` 头。这一处必须先做技术验证，再排后续工期。

## 6. 最终用户可感知的形态

这一节是方案的核心。前面所有架构选择，都要落到"用户看到什么、点什么、得到什么"。

### 6.1 信息架构变化

侧栏新增一个一级项，位置在「首页」之后、「资产」之前。

```
首页
智能助理          ← 新增
资产
搜索
客户信息平台  ▾
运维信息平台  ▾
设计信息平台  ▾
其他        ▾
```

四个子页。

| 地址 | 内容 |
|---|---|
| `/assistant` | 对话（默认） |
| `/assistant/tasks` | 任务中心 |
| `/assistant/skills` | 技能库 |
| `/assistant/settings` | 模型、工具、审批偏好 |

首页保持三段式不变。原因是一键启动的 4×2 Bento 是原型对齐的结果，插入第四段会打乱节奏。改为在主卡上加一个"让助手安排"的次按钮，把入口交给需要的人。

### 6.2 核心界面

**智能助理页，三栏布局。**

```
┌────────────┬─────────────────────────────────┬──────────────┐
│ 会话        │  对话流                          │ 运行现场      │
│ 240px      │                                 │ 320px 可收起  │
│            │  ┌───────────────────────────┐  │              │
│ 今天        │  │ 用户：把今天的都开起来      │  │ 本次运行      │
│  开程序      │  └───────────────────────────┘  │ ● 启动千牛    │
│  客户跟进    │  ┌───────────────────────────┐  │ ● 等待就绪    │
│ 昨天        │  │ 助手：好的，按顺序来        │  │ ● 填表登录    │
│  整理纪要    │  │                           │  │ ○ 启动 QQ     │
│            │  │ ▸ 工具 启动千牛   2.4s 成功 │  │              │
│ [+ 新会话]   │  │ ▸ 工具 等待就绪   3.1s 成功 │  │ 产物          │
│            │  │ ▸ 工具 填表登录   1.2s 成功 │  │ 截图 3 张     │
│            │  │                           │  │              │
│            │  │ 千牛已登录，接下来开 QQ     │  │              │
│            │  └───────────────────────────┘  │              │
│            │  ┌───────────────────────────┐  │              │
│            │  │ 输入框              [发送] │  │              │
│            │  └───────────────────────────┘  │              │
└────────────┴─────────────────────────────────┴──────────────┘
```

三栏各自解决一个问题。左栏解决"我上次说到哪了"，中栏解决"现在在做什么"，右栏解决"它到底做了什么"。右栏是梵禾相对普通聊天产品的关键差异，因为 Agent 会真的去操作电脑，用户需要看得见。

**工具调用卡，折叠态与展开态。**

折叠态一行，包含图标、工具名、耗时、状态点、展开箭头。展开态显示参数（脱敏后）、返回摘要、产物缩略图、以及"重试"与"查看详情"。失败时整行变红并自动展开，附一句人话解释，例如"千牛窗口没找到，可能还没启动完成"。

**审批弹层。**

当 Agent 要执行副作用操作时，中栏底部升起一条确认条，不弹模态框。理由是模态框会打断阅读，而确认条可以边看上下文边决定。

```
┌──────────────────────────────────────────────────────┐
│ 助手想在你的电脑上执行：                                │
│   启动 千牛 并使用「店铺A」账号登录                      │
│                                                      │
│ 影响：会打开一个窗口，并用已保存的凭据自动填表            │
│ 可撤销：是，关闭窗口即可                                │
│                                                      │
│              [ 拒绝 ]  [ 允许一次 ]  [ 总是允许 ]       │
└──────────────────────────────────────────────────────┘
```

三档授权的设计意图是降低长期摩擦。首次全部询问，用户信任后可以对同类动作选择"总是允许"，该选择记入个人偏好而非全局配置。

**任务中心。**

用于长任务。左侧任务列表，右侧选中任务的步骤时间线。

```
┌──────────────────┬────────────────────────────────────┐
│ 进行中 2          │  批量上架 30 个商品                  │
│ ● 批量上架        │  ─────────────────────────────      │
│ ● 客户资料整理     │  ✓ 读取表格        12s              │
│                  │  ✓ 校验必填项      3s  2 条缺失      │
│ 已完成 5          │  ▶ 逐个上架        18/30 运行中      │
│ ○ 昨日纪要归档     │  ○ 生成汇总报告                      │
│                  │                                    │
│                  │  [暂停]  [跳过当前]  [终止]          │
└──────────────────┴────────────────────────────────────┘
```

暂停、跳过、终止三个干预按钮是必需品。长任务若不能干预，用户只会在第一次失败后放弃整个功能。

**技能库。**

卡片网格，每张卡显示名称、一句话描述、适用角色、启用状态。点开是 `SKILL.md` 的正文预览与编辑。管理员可新建，普通用户只读。

这里承载的是"组织能力沉淀"这条主线。一个运营写清楚"如何处理售后工单"，全组都能用上，这是 AI 工作台对组织最有价值的产出。

**全局唤起。**

顶栏右侧一个入口，加全局快捷键。唤起后是一个 560px 宽的浮层，顶部自动带上当前页面上下文（例如"你正在看：客户进度 / 张三"），下面是一个输入框与最近三条会话。

这个入口解决频次问题。用户不会为了问一句"这个客户上次说到哪"而跳转到助理页。

### 6.3 三条典型流程

**流程一，早晨开工。**

用户打开梵禾，首页一键启动区显示"上次你开了千牛和 QQ，要现在开吗"。点"让助手安排"，跳到助理页，Agent 依次启动、等待就绪、填表登录，每步在右栏亮起。全部完成后中栏给一句总结，并在纪要区自动生成一条"今日开工"记录。

用户可感知的变化是，原来要点三次、等三次、手动确认两次，现在点一次，剩下的看进度。

**流程二，随手记。**

用户在客户进度页看到一条信息，按快捷键唤起，输入"记一下，李四那边周五前要给报价"。

浮层回复"已记下，周五上午提醒你"，并在右上角给一个可撤销的提示。后台把这条写入纪要并关联到李四的客户记录。周五上午，梵禾发一条站内通知。

用户可感知的变化是，原来要切到纪要页、新建、选客户、填日期，现在一句话。

**流程三，批量任务。**

用户说"把这张表里的 30 个商品上架到千牛"。

Agent 先读表、校验必填项、报告"2 条缺价格"，等用户补完再继续。然后逐个上架，每完成一个在右栏打勾。中途某个失败，任务暂停并询问"第 12 个失败，重试还是跳过"。

用户可感知的变化是，原来需要人盯着重复操作 30 次，现在只在异常处介入。

### 6.4 交互约定

沿用梵禾既有规范，不新造。

| 约定 | 来源 |
|---|---|
| 空、加载、错误三态统一用 `StateView` | 既有 `components/StateView.tsx` |
| 工具卡与按钮取 `components/ui/` 现成组件 | 既有 shadcn 令牌体系 |
| 亮暗跟随全局，不单独设主题 | 既有 `lib/theme.ts` |
| 流式输出用打字机节奏，不用整段替换 | 新增，参照 EvoFlow 的块级增量 |
| 断线后自动重连并补齐事件，给"已恢复"提示 | 新增，参照 NomiFun 的事件序号 |
| 所有 AI 生成内容标注来源与时间 | 新增，审计需要 |

最后一条值得强调。AI 工作台会产生大量"看起来像事实"的内容。若不标注来源，用户会把模型生成的推测当成系统记录。建议在每条 AI 消息的元信息里带上模型名、时间、引用的数据条数，折叠在"详情"里。

## 7. 分期与里程碑

每期都以"用户能感知到什么"为验收标准，而非"代码写完没有"。

### P0 能对话，能看过程（17 至 25 人日）

用户能看到：侧栏多了「智能助理」，能新建会话、流式对话、看到工具调用卡（此时只有服务端只读工具）、断线能恢复、历史能翻。

技术上完成：会话四事实、Agent 循环、WS 通道、事件投影、基础工具注册表。

不包含：桌面工具、审批、技能、任务。

### P1 能动手，能授权（18 至 28 人日）

用户能看到：Agent 能真的启动程序并登录，动手前会问一句，可以选"总是允许"，失败会解释原因，操作写进审计。

技术上完成：桌面工具桥、能力上报、审批门、副作用回执、技能加载器、MCP 客户端。

这一期是产品质变点。从"能聊"到"能替我做"，用户留存的分水岭在这里。

### P2 能跑长任务，能沉淀能力（33 至 52 人日）

用户能看到：任务中心、步骤时间线、暂停与干预、技能库管理、批量任务、应用托管（可选）。

技术上完成：DAG 调度、计划状态机、技能管理界面、应用托管五段式。

### 里程碑建议

| 里程碑 | 判据 |
|---|---|
| M1 内部可用 | P0 完成，团队 5 人日常使用一周无阻断问题 |
| M2 灰度 | P1 完成，选 2 个真实岗位试用，启动成功率达到 90% |
| M3 全量 | P2 完成，技能库有 3 个以上被真实使用的技能 |

## 8. 风险与依赖

### 8.1 外部依赖

| 依赖 | 必要性 | 风险 | 备选 |
|---|---|---|---|
| 模型供应商 | 必需 | 价格波动、限流、合规 | 双供应商热备 |
| PostgreSQL | 已有 | 无 | 无 |
| WebSocket 反代 | 必需 | Node upgrade 转发不稳定 | 改用 SSE 加轮询补事件 |
| 桌面在线 | P1 起必需 | 用户关机时本地工具不可用 | 明确提示"该操作需要本机在线" |
| 向量检索 | 可选 | 引入 embedding 成本与延迟 | 首期用关键词检索 |

### 8.2 风险清单

| 风险 | 等级 | 影响 | 规避 |
|---|---|---|---|
| WS 反代不稳 | 高 | P0 直接受阻 | 第 1 周做技术验证，失败则退到 SSE |
| 权限与工具白名单双重判定错位 | 高 | 越权执行 | 判据只留一处，工具注册表读角色，不在前端判 |
| 凭据被 Agent 读取 | 高 | 安全事故 | 工具层只接受"用哪条配置"，不接受凭据本身 |
| 副作用误操作 | 高 | 业务损失 | 副作用工具默认需确认，白名单化本地动作 |
| 上下文成本失控 | 中高 | 单次对话成本不可预测 | 设 token 上限、结果截断、大内容外置 |
| 多租户数据串号 | 中高 | 严重 | 所有查询强制带 userId 或 orgId，加集成测试 |
| 技能质量参差 | 中 | 用户失望 | 技能需审核后上架，标注作者与版本 |
| 概念通胀 | 中 | 代码难维护 | 只保留五个概念：会话、回合、工具调用、技能、任务 |
| 团队能力错配 | 中 | 交付质量下降 | 服务端团队负责循环与工具，前端只做协议消费与渲染 |

### 8.3 一条需要提前想清楚的问题

**Agent 的"身份"是什么。** 它用谁的权限执行工具？三个选项。

其一，用发起人的权限，越权即失败。安全但保守，管理员无法让助手代做自己无权的事。

其二，用服务账号，拥有超集权限。灵活但危险，审计会失去"谁授权"这一环。

其三，用发起人权限，但对特定工具要求二次授权。这是推荐方案，兼顾安全与可用。

这个问题必须在 P1 之前定下来，因为它决定 `AgentToolCall` 表要不要记 `approvedBy`、审计日志怎么写、以及前端审批条的文案。

## 9. 验收标准

方案是否成功，用四条可测指标判断，不用"感觉好用"。

| 指标 | 定义 | 目标 |
|---|---|---|
| 启动成功率 | Agent 完成"启动并登录"的比例 | 不低于 90% |
| 干预率 | 需要用户手动纠正的会话占比 | 不高于 20% |
| 任务完成率 | 长任务无需人工接管跑完的比例 | 不低于 70% |
| 首响时延 | 用户发送到首个 token 的时间 | 不高于 1.5 秒 |

若 P1 结束时启动成功率低于 70%，说明工具层的现场知识不足，应当回到坐标与窗口识别上补，而非继续加功能。

## 10. 结论

三句话。

**第一，这个方案的价值不在"加了 AI"，而在"接管了两段重复劳动"。** 启动与记录是梵禾用户每天真实发生的动作，Agent 在这两处的收益可以被直接测量。通用问答的收益无法测量，也不构成产品差异。

**第二，架构上唯一的硬选择是运行时放服务端，其余都是可调的。** 放服务端的代价是本地工具需要回传通道，收益是密钥安全、体积不变、多端可用。这个交换在梵禾的语境下是划算的，因为梵禾本来就是服务端产品。

**第三，两个参考项目提供的是形态与契约，不提供实现。** 梵禾真正需要自研的部分约 7,700 行服务端代码加 1,500 行桌面代码，规模可控。真正难的部分是现场知识与权限设计，而这两块恰好是梵禾已经有的。
