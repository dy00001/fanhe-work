## 三、两条独立链路

访问该远端存在两条互不共享凭据的链路。

| 维度 | 链路 B 本地 git | 链路 A WorkBuddy 连接器 |
| --- | --- | --- |
| 端点 | `github.com` HTTPS | `api.githubcopilot.com/mcp/` |
| 凭据 | 细粒度 PAT，经 GCM 存储 | 服务端代持，GitHub 侧不可见 |
| 权限 | 读写 | 只读 |
| 可读范围 | 授权范围内的全部仓库 | 仅公开仓库 |
| 适用场景 | 日常提交与推送 | 助手经 API 读取仓库内容 |

链路 B 的凭据配置在 `~/.gitconfig`，属逐机逐用户，换机后必须重新配置。

链路 A 的凭据由 WorkBuddy 服务端代持。GitHub 账户侧查不到对应的 GitHub App 安装，也没有对应的 OAuth 授权记录，用户手上没有可调整的设置项。其可读范围由仓库可见性决定。

## 四、换机与故障排查

1. 换机后先跑 `infra\portable\ws-doctor.ps1` 检查工作区完整性。
2. 重新配置 `~/.gitconfig` 的 `credential.helper` 与代理项。
3. 用 `git ls-remote --heads origin` 验证读权限。
4. 用 `git push --dry-run origin main` 验证写权限，该命令走完整认证流程而不实际写入。
5. 连接器侧读取该仓库失败时，先确认仓库可见性是否为公开，这是连接器可读的前提。

## 五、本次核验记录

核验时间 2026-10-11 14:20。

| 测试项 | 结果 |
| --- | --- |
| 本地读远端 | 通过，返回 `refs/heads/main` 与 `refs/heads/dev` |
| 本地写远端 | 通过，推送区间 `ea119ab..e5a1953` |
| 连接器身份识别 | 通过，账号 `dy00001` |
| 连接器读仓库根 | 通过，返回 7 个条目 |
| 连接器查仓库元数据 | 通过，`private` 为 `false` |
| 连接器写仓库 | 未通过，`403 Resource not accessible by integration` |

三点结论。

第一，连接器由不可读转为可读，原因是仓库可见性变更。12:55 与 13:38 两次实测均返回 404，14:20 实测可正常读取仓库根目录。同期该仓库的可见性由私有改为公开，两项事实互相印证。

第二，连接器只读公开资源，读取能力与可见性绑定。仓库设为公开是连接器可读的前提，代价是仓库全部内容对全网可见。若仓库改回私有，连接器将重新返回 404。

第三，连接器的写入被拒，且在 GitHub 侧无法调整。该 token 由 WorkBuddy 服务端代持，账户侧无 GitHub App 安装，也无对应 OAuth 授权，没有可操作的权限项。可行的处置有两条，一是接受只读，写入由本地 git 承担；二是在 WorkBuddy 连接器管理中断开并重连，观察授权流程是否提供权限级别选择。

写权限对当前目标是可选项。日常提交与推送由链路 B 承担，链路 A 只用于助手读取远端内容。
