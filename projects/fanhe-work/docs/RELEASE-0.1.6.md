# 版本迭代方案 `0.1.6`

本版三件事：把更新通道从「查到就自己下」改成用户可掌控的四步流程，把下载过程从一句「正在下载」做成带大小、速度与剩余时间的详情面板，并给首页「全部品类」接上真正可点开的案例窗口。

## 一、更新流程改为四步

要求是四步：发现新版挂红点、用户点击才下载、下完静默处理并提示、确认后重启完成更新。改动前只有第三步成立。

- `autoDownload` 由 `true` 改为 `false`。原实现的「检测到即下载」让「等你点」这个状态在状态机里没有位置，视图层只能把它塞进 `downloading`，红点也就无从存在。三处缺口是同一件事的三个断面。
- 新增 `update:download` IPC。它**不等下载结束就返回**，一次约 112 MB 的包会让渲染进程的 `await` 悬上几分钟；进度仍走 `update:status` 轮询。该入口只在 `available` 与 `error` 两态接受，已下完再下是浪费，`idle` 时下载会被上游以「Please check update first」拒绝。
- `available` 从 `downloading` 拆成独立一态，带红点、按钮文案「立即更新」、**不给百分比**。给 `0%` 会让人以为已经在下。
- `ready` 点按钮先开确认对话框。原来直接调 `quitAndInstall`，会吞掉正在填的表单。
- 红点判据是「**有待办动作**」而非「有新版」：`available` 与 `ready` 挂，`downloading` 与 `failed` 不挂。`downloading` 不挂这条写进了用例，它最容易被「顺手都加上」破坏。
- 检查、下载、安装至此各自一个入口，`checkForUpdates` 只检查，不下载、不安装。

## 二、下载过程可视化

要显示已下载与总大小、百分比、实时速度、已用时间、预计剩余时间，并在完成、失败、暂停时给出明确状态。

- 数字全部在渲染进程之外算。速度平滑、剩余时间、停住判定都是纯函数，放进组件就只能靠真机发版复现，而这类缺陷的表现是「读数看起来正常但是错的」。
- 速度用相邻两次事件的 `Δ字节 / Δ时间` 计算，再与上一拍做指数平滑（系数 0.35）。采样间隔小于 200 ms 不重算，分母太小会把速度放大成几十 MB/s。字节数没涨时不立刻归零，按衰减走几拍，避免一次卡顿把速度打到 0 再弹回来。
- 剩余时间有四种「不知道」，一律显示 `—`：速度未知、速度为 0、总大小未知、估算超过 24 小时。写「剩余 0 秒」比「不知道」糟糕得多。已下满时 `0 秒` 是确定值，正常显示。
- `electron-updater` 不区分「慢」与「停」，停住只能按时间判：最后一次进度超过 3 秒。停住时不再显示速度，改为「已暂停 · 已用 00:18 · 等待网络恢复」，进度条转琥珀色。已下满但未收到完成事件不算停住。
- 轮询在内容不变时保留同一状态引用，已用与剩余时间不会自己走。hook 里加了一个只在下载阶段开启的每秒时钟，空闲时不跑。
- 窄条常驻顶栏，点开看详情。面板宽度 `min(20rem, 100vw − 1.5rem)`，右对齐，小屏不顶出视口。

## 三、首页「全部品类」窗口

截图里的入口原本是 `href="#"` 的静态文字，落地时保持成不可点的 `span`，于是首页最像入口的元素反而点不动。

- 入口改为真按钮，悬停文字加深、箭头右移 2px，键盘可聚焦。点击打开一个窗口，九个品类与各自案例位全量铺开。
- 新增 `apps/web/src/lib/case-catalog.ts`：九品类 × 三案例位。标题留空、封面为 `null` 是刻意的占位，不编客户名与方案名。品类带稳定 `id`，案例带 `categoryId`，将来换成一次查询即可接真实数据，卡片结构与筛选逻辑不用动。
- 窗口顶部一排品类筛选（`aria-pressed`），默认「全部」。切换时内容区滚回顶部，避免用户落在空白处误以为该品类没有案例。
- 选择窗口而不是新增路由。关掉即落回原位，首页横滑位置与滚动位置都在；跳转会把人带走，返回还得重新导航。
- `Dialog` 根放在区块外层，入口用 `DialogTrigger`。Radix 依赖触发器注册的 ref 完成两件事：打开时挂 `aria-expanded` / `aria-controls`，关闭后把焦点还给按钮。根写在弹窗组件内部时功能都对，唯独焦点落回 `body`。
- 案例内容仍无数据源（`docs/NEXT-TASKS-2026-10-12.md` 的 U-01 未结），卡面显示「封面待补」与「品类案例 01」这样的序号。

## 五、版本与发布

- 仓库根版本 `0.1.6`，`apps/desktop/package.json` 由 `sync-version.mjs` 同步。
- 发版顺序固定三步：先提版本号并提交，再 `pnpm --filter @fanhe/web build`，最后 `pnpm --filter @fanhe/desktop dist`。版本号必须在构建前端之前定下来，否则安装包里烧的是旧版本号（v0.1.2 的教训）。
- 打包前手工删 `apps/desktop/release/win-unpacked`，U 盘上安全删除守卫会 ETIMEDOUT。
- 发布前跑四道门禁与 `verify:sign` + `verify:pack`，发布后核对未认证 by-tag 200、线上 `latest.yml` 与本地逐字节一致、线上 exe 的 sha512 与 `latest.yml` 声明一致。
- **本版的正向验证需要旧版机器**：在装有 0.1.5 的机器上点更新到 0.1.6，观察四步流程与进度面板的真实外观。这一步只能在发布之后做。
