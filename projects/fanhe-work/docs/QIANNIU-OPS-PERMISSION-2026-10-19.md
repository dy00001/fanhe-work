# 千牛运营数据权限管理设计

> 版本：v1，2026-10-19
> 归属：`QIANNIU-OPS-INTEGRATION-2026-10-19.md` 第 7 节的展开
> 前提：梵禾已有 Role / Permission / RolePermission / UserPermission 四张表与完整的账号级配置界面

---

## 0. 结论

**不新增任何权限表。** 梵禾现有的权限基建已经覆盖了角色授权、账号级授予与拒绝、逐请求校验、管理界面这四件事，运营数据需要的只是七个权限点加一条字段裁剪规则。

**金额必须单独授权。** 这是本设计的核心判断。把 GMV、客单价、退款金额一起塞进 `ops.shop.read`，等于强迫 owner 在「给助理看数据」和「让助理看到钱」之间二选一。拆成一个独立对象之后，助理能看单品卖得好不好，看不到卖了多少钱，这个组合在实际使用中才是可用的。

**裁剪必须发生在服务端。** 前端不渲染金额列只是体验，任何人改一个请求就能拿到完整数字。梵禾既有的守卫文档已经把这条写死，运营数据要照办。

## 1. 现有基建的四个能力（已核实）

读代码确认的事实，不是推断。

| 能力 | 实现位置 | 对运营数据的意义 |
| --- | --- | --- |
| 最终权限 = 角色权限 ∪ 账号授予 − 账号拒绝 | `auth/guard.ts` 的 `resolvePermissions`，合并规则在 `mergePermissions` | 可以给某个人单独开一项，也可以单独收一项 |
| 拒绝优先，`UserPermission.granted` 是布尔而非「存在即授予」 | `schema.prisma` 的 `UserPermission` 注释 | 收回权限是精确操作，不用把人降级 |
| owner 短路返回全部权限，账号级覆盖对它无效 | `resolvePermissions` 首行 | owner 不会被锁在门外 |
| 每个请求都查库，权限不写进令牌 | `resolveAuthContext` 注释明确写了「不做缓存」 | 撤权在下一次请求就生效，不必等令牌过期 |

第四点值得单独强调。财务类数据的撤权要求是「立刻」，容不下「最迟十五分钟后」。这条保证已经存在，设计上不要引入任何缓存破坏它。将来若要优化，正确做法是给角色加版本号并在变更时递增，设一个 TTL 只会把时效问题藏起来。

管理界面也已经有了。`UsersPage` 的「配置权限」对话框从 `/api/system/permissions` 拉取权限清单逐项勾选，用 `diffPermissions` 把勾选结果翻译成相对角色默认的增量。**新增权限点之后，这些点会自动出现在对话框里，界面零改动。**

## 2. 权限点设计

七个，全部三段式，模块段统一为 `ops`。

| 权限点 | 保护什么 | OWNER | ADMIN | MEMBER | VIEWER |
| --- | --- | --- | --- | --- | --- |
| `ops.shop.read` | 页面准入与非金额指标 | 有 | 有 | 默认无 | 无 |
| `ops.finance.read` | 金额类字段（GMV、客单价、退款额、推广花费） | 有 | 有 | 默认无 | 无 |
| `ops.shop.export` | 导出 CSV | 有 | 有 | 无 | 无 |
| `ops.lead.read` | 线索列表与详情 | 有 | 有 | 默认无 | 无 |
| `ops.lead.write` | 编辑线索阶段与流失原因 | 有 | 有 | 无 | 无 |
| `ops.collect.read` | 采集批次、失败原因、对账告警 | 有 | 有 | 无 | 无 |
| `ops.collect.run` | 手动触发采集 | 有 | 无 | 无 | 无 |

三个刻意的选择。

**MEMBER 默认全无。** 店铺 GMV 与客单价属于经营机密，默认开放给全体成员，代价是泄露；定保守，代价只是一次授权操作。默认值定错方向，事后无法补救。

**ADMIN 不给 `ops.collect.run`。** 手动采集会占用本机浏览器并可能触发平台风控，同一时刻只应有一个人能按下这个按钮。给 owner 独有，避免两个人同时点导致会话冲突，也避免出问题时说不清是谁触发的。

**导出单列。** 查看是留在系统内，导出是把数据带出去，两者的泄露面差一个数量级。共用一个权限点会让「只想让人看」变成「也允许拿走」。

## 3. 金额为什么是一个独立对象

三段式的第二段是「对象」。`ops.finance.read` 表达的是「ops 模块下 finance 这个对象的读权限」，与 `ops.shop.read` 平级，语义是干净的。

### 3.1 典型授权组合

| 角色画像 | 授权 | 看到什么 |
| --- | --- | --- |
| 老板本人 | 全部 | 全部 |
| 店长 / 合伙人 | `ops.shop.*`、`ops.finance.read`、`ops.lead.*`、`ops.collect.*` | 全部，可导出，可看采集状态 |
| 设计助理 | `ops.shop.read` | 单品表现、流量结构、转化率；金额列显示「无权限」 |
| 客服主管 | `ops.shop.read`、`ops.lead.read`、`ops.lead.write` | 询单与线索，不含金额与推广 |
| 外部顾问 | `ops.shop.read` | 短期只读，看完即撤 |

设计助理那一行是这套设计存在的理由。全屋定制的助理需要知道哪款柜体点击高、加购多、转化好，但不需要知道公司这个月卖了一百二十八万。一个权限点分不开这两件事。

### 3.2 依赖规则

`ops.finance.read` 必须与 `ops.shop.read` 同时生效。单独给前者没有意义，页面根本进不去，而它的表现是「导航里能看到数据看板，点进去 403」，排查方向会先落到路由上。

实现方式是在保存账号权限时校验一次：提交后算出的有效权限里若有 `ops.finance.read` 而无 `ops.shop.read`，拒绝并返回 `invalid_permission_dependency`。这条校验放在服务端，界面上的勾选框只是提交内容。

### 3.3 与通配符的关系

`ops.*` 覆盖全部七个点，包括金额。给 ADMIN 配 `ops.*` 会连带授予 `ops.finance.read`。若希望 ADMIN 看不到金额，授权必须逐组写 `ops.shop.*`、`ops.lead.*`、`ops.collect.*`，不能图省事写 `ops.*`。这一条要写进 `ROLES` 的注释，否则后来者一定会顺手改成通配。

## 4. 服务端裁剪的实现

### 4.1 投影，不做二次过滤

所有返回金额的查询结果统一过一层投影函数。

```
projectMoney(rows, canReadFinance) → { rows, masked: string[] }
```

无权限时金额字段置 `null`，同时把被遮的字段名放进响应的 `masked` 数组。前端依据 `masked` 渲染「无权限」占位，不要用「字段是否为 0」来判断。

**0 与 null 必须区分。** 当天确实没有成交，GMV 是 0；没有权限时 GMV 是 null。两者在界面上都显示成「0」或「—」的话，用户会把「看不到」理解成「没卖出去」，而这个误解会直接影响经营判断。

### 4.2 聚合查询也不该算

无 `ops.finance.read` 时，聚合 SQL 里干脆不选金额列，避免先算出来再丢掉。两个理由。算力不是主要考虑，日志与慢查询记录才是，金额会随查询语句进入日志表，那等于绕过了权限。同理，导出走同一个投影函数，不做第二套实现，否则迟早有一处漏掉。

### 4.3 前端的分工

前端的判断只有一个用途，决定渲染什么占位。它拿的是 `/me` 返回的权限点，与后端同源。**任何以「前端已经隐藏」为由省略后端校验的写法都不可接受**，这一点梵禾的守卫注释已经写明，此处重复一次是因为财务数据的后果更重。

## 5. 数据范围（店级）

现阶段只有一家店，不做店级授权。`EcomShop` 全局共享，任何持有 `ops.shop.read` 的人看到的都是同一家店。

但有一件事现在就要做。**所有查询接口强制带 `shopId` 参数，即使只有一个店。** 服务端校验该店存在且启用，再从库里取数。不做这一步，将来加第二家店时，每一处查询都要回头补条件，而漏掉一处就是串店，这类错误不会报错，只会让数字看起来奇怪。

店级授权的触发条件是以下任一条出现。加盟店或代运营场景、一个账号只能看指定店、需要按店分别授权。

届时新增一张 `EcomShopAccess`（userId × shopId，可选 `canReadFinance`），查询层在 `shopId` 之外再注入一层用户可见店列表过滤，其余不动。这个方案现在不建表，只在文档里留位置，避免为尚未出现的需求付出维护成本。

## 6. 权限变更的生效路径

服务端已经做到逐请求查库，撤权在下一个请求生效。前端会滞后，它持有的是上次 `/me` 的结果。

处理方式是 403 兜底。`lib/ops.ts` 在收到 403 时触发一次 `/me` 刷新并重新渲染，同时给一句「权限已变更，页面已刷新」。不做 WebSocket 推送，理由是权限变更频率极低，为它引入一条长连接通道不划算。

有一个边界要写清。用户正停留在看板上，owner 在这时撤掉了他的 `ops.finance.read`。页面上的金额不会自己消失，直到他下一次操作触发请求。这属于可接受的行为，但需要在验收里明确，避免被当成 bug。

## 7. 审计

三类事件写入 `AuditLog`，复用 `audit/audit.ts` 的 `recordAudit`。

| action | 触发 | detail 建议 |
| --- | --- | --- |
| `permission.update` | 账号权限保存 | 变更前后的权限点差集、操作者、目标账号 |
| `ops.export.create` | 导出 CSV | 区间、行数、是否含金额、文件名 |
| `ops.collect.manual` | 手动触发采集 | 目标业务日、触发结果、耗时 |

`permission.update` 属于现在就该补的。账号权限目前可配但未见审计写入，而运营数据让这件事的敏感度上升了一个量级。补审计不需要新表，`AuditLog` 的字段够用。

采集器的自动采集不写审计。它属于系统动作，每次跑都记一条会让审计表变成采集日志。采集的可观测性由 `EcomCollectRun` 承担，两者分工不同。

## 8. 管理界面

### 8.1 现在就能用的

账号级权限配置已经完整。新增七个权限点后，`/api/system/permissions` 会多出七行，`UsersPage` 的对话框中自动出现，`diffPermissions` 的增量逻辑对新增点同样成立。**这一侧零改动。**

### 8.2 缺口与取舍

`/api/system/roles` 只读，角色权限矩阵的可写路由与界面都还没做。四个内置角色的授权完全由代码里的 `ROLES.grants` 定义，种子脚本做差集同步。

建议 P1 不做角色矩阵，靠账号级覆盖满足个性化。理由有两条。十人以内团队，四个角色的划分够用，改角色权限的真实需求远低于给某个人加一项。做矩阵页要引入自建角色、角色与用户的关系校验、内置角色不可删的约束，工作量与收益不成比例。

P2 再评估。触发条件是出现「某个岗位需要一套与现有四个角色都不同的权限组合，且这个岗位上有多个人」。

### 8.3 一个必须记住的部署步骤

新增权限点后，**必须重跑一次种子**（`apps/api/src/db/seed.ts`，可重复执行）。

漏掉这一步的失败方式是静默的。`permissions` 表里没有 `ops.*` 的行，`role_permissions` 里自然也不会有关联，于是 ADMIN 拿到的是空集合，界面上表现为「权限明明配了却不生效」。看起来像权限算法的 bug，实际是种子没跑。

这个脚本对角色授权做差集同步，会删除「代码里没有定义」的关联。因为目前没有自建角色，这个行为是安全的。将来支持自建角色后，种子脚本已经用 `knownRoleCodes` 做了保护，不会碰自定义角色。

`UserPermission` 里的账号级覆盖不受种子影响，重跑不会清掉。

## 10. 验收

除了常规的四道门禁，本设计有三条必须做的反例测试。按既有方法论，不做反例的断言只是恒真的装饰。

**反例一，金额裁剪。** 用一个只有 `ops.shop.read` 的账号请求 `/api/ops/overview`，断言响应里 GMV 为 `null` 且 `masked` 含 `gmvFen`。再把该账号的 `ops.finance.read` 加上，断言变成数字且 `masked` 为空。两次断言都要真跑，不能只看第二次。

**反例二，拒绝优先。** 给一个 ADMIN 角色的账号单独写一条 `ops.finance.read` 的 denied 行，断言它看不到金额，尽管角色自带这个权限。这一条验证的是 `mergePermissions` 的优先级在运营数据上真的生效。

**反例三，未跑种子。** 在测试库里先不跑种子，断言 ADMIN 拿不到任何 `ops.*` 权限，页面落到无权限。这条不是测代码，是测部署文档的准确性，防止下一个人以为权限是代码直接生效的。

另外两条正向验收。

- 撤权即时生效。A 账号停在看板上，owner 撤掉其 `ops.shop.read`，A 下一次请求返回 403 并提示刷新，不需要等令牌过期。
- 导航可见性。持 `ops.shop.read` 的 MEMBER 能在侧栏看到「数据看板」，持 `personal.*` 的 MEMBER 看不到。

## 11. 风险

| 风险 | 等级 | 表现 | 应对 |
| --- | --- | --- | --- |
| 只做前端隐藏 | 高 | 界面看不到，请求能拿到 | 投影函数在服务端，导出复用同一函数 |
| 忘记跑种子 | 中高 | 权限配了不生效，像算法 bug | 写进部署清单，验收里做反例三 |
| ADMIN 授权写成 `ops.*` | 中 | 管理员看到金额，与预期不符 | `ROLES` 注释写明，代码评审时专门看一眼 |
| 0 与 null 混淆 | 中 | 用户以为当天没成交 | 响应带 `masked`，前端据此渲染占位 |
| 前端权限缓存过期 | 低 | 撤权后界面仍显示旧按钮 | 403 兜底刷新，验收里明确这一边界 |
| 店级授权被提前设计 | 低 | 多建两张用不上的表 | 只在查询层强制带 `shopId`，表等需求出现再建 |
