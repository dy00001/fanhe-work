## 零、先给结论

三条判断先摆出来，后面的章节都在为它们提供依据。

**第一条，把「外壳」与「内容」解耦，是本项目唯一不可妥协的架构原则。** 桌面外壳只承担三件事，加载界面、启动本机进程、读写本机资源。界面、业务逻辑、数据三者由独立服务提供。实验版让外壳指向本机服务，网络版让同一个外壳指向 Cloudflare 域名。用户提出的「本地更新后其他端口拉取更新」在这个结构下几乎不需要额外开发，服务器更新完成即全端生效。

**第二条，前期的真实成本在工具链与介质，不在 UI。** Tauri 需要 Rust 工具链与编译产物，Electron 需要 Chromium 二进制与海量 `node_modules` 小文件。当前介质是 32GB U 盘，随机 IO 弱且有写入寿命限制。因此建议实验版先以「浏览器加本机服务」的形态推进，界面与业务全部验证完毕之后再套壳。套壳可以后置，返工不可接受。

**第三条，「一键登录」的能力边界必须提前划定。** 微信、QQ、千牛均未提供公开的多账号自动登录接口。可靠且合规的做法是管理账号入口并一键唤起对应客户端实例，凭据输入与扫码交由官方客户端自身完成。把「自动填充账号密码」写进需求，会引入账号风控与合规风险，建议不纳入本期范围。

## 一、需求解构与三个结构性矛盾

用户提出的需求表面上是功能清单，实际包含三处内在张力。先把它们拆开，方案才不会在中期推倒重来。

### 1.1 桌面端与网络版的目标冲突

桌面端的价值在于离线可用与系统集成，其中「一键登录 QQ、微信、千牛」必须调用本机进程。网络版的价值在于集中分发与多端一致。若把工作台做成纯远程 Web 页面，远程页面要调用本机能力就会撞上浏览器的同源与权限边界。若把它做成纯本地安装包，分发通道又退回传统软件更新，与「网络版」的直觉不符。

**解法是区分控制面与数据面。**

| 平面 | 内容 | 位置 | 演进方式 |
| --- | --- | --- | --- |
| 控制面 | 界面、业务数据、账号与权限、审计 | 服务端 | 实验版本机，网络版 Docker |
| 数据面 | 外部软件启动、本机文件、本机登录态 | 客户端本地代理 | 始终留在客户端 |

客户端内置一个仅监听回环地址的本地代理，界面通过它触达本机能力。这样同一套界面既能本地运行，也能远程运行。

### 1.2 一键登录的合规边界

三家客户端都没有对外开放的多账号自动登录接口。网络上流传的多开手段依赖客户端内部参数或进程互斥量的绕行，稳定性由客户端版本决定，且部分手段会被安全软件判定为异常行为。

稳妥定位是「账号入口管理加一键唤起」。工作台记录每个账号对应的客户端实例配置，点击即启动对应实例，扫码或密码输入交给官方客户端。这条边界需要在需求阶段就与用户确认，避免后期返工。

### 1.3 可移动介质与桌面工具链的冲突

工作空间的既有约定要求受版本控制的文件不出现盘符，且全部写入落在工作空间内部。桌面端工具链与这条约定存在摩擦。

| 工具链 | 体积特征 | 与 U 盘的冲突 |
| --- | --- | --- |
| Rust（Tauri 依赖） | 工具链约 1.5GB 起，`target/` 可达数 GB | 编译产生海量小文件写入，随机 IO 弱时极慢，且消耗闪存寿命 |
| Node（Electron 依赖） | 安装后约 250MB，`node_modules` 数万小文件 | 同样是小文件密集，但可接受 |
| 浏览器二进制 | 约 150MB | 已有 `ELECTRON_CACHE` 重定向，可控 |

**结论是源码与配置留在 U 盘以保证可移动性，重型构建产物不留在 U 盘。** 工作空间的 `ws-env.ps1` 已经重定向了 `CARGO_HOME`、`RUSTUP_HOME`、`ELECTRON_CACHE`、`ELECTRON_BUILDER_CACHE`，尚缺 `CARGO_TARGET_DIR` 一项，建议补齐（见第十一章）。

## 二、技术选型

### 2.1 客户端外壳

| 维度 | Electron | Tauri 2.x |
| --- | --- | --- |
| 安装包体积 | 约 92MB（macOS DMG） | 约 8MB |
| 安装后体积 | 约 250MB | 约 22MB |
| 冷启动 | 约 1.4s | 约 0.6s |
| 空闲内存 | 约 140MB | 约 45MB |
| 更新机制 | `electron-updater`，生态成熟，文档密集 | 官方 updater 插件，负载小，配置更简 |
| 本机能力 | Node 全生态，原生模块即插即用 | Rust 侧能力更强，Node 模块需要绑定或旁路进程 |
| 主要成本 | 运行时体积与内存 | Rust 学习曲线，编译开销，WebView2 平台差异 |

数据来源为 TechKis 2026 年 5 月的同构应用实测对照（https://techkis.tech/insights/tauri-vs-electron-binary-ram-autoupdate ）。

**推荐 Tauri 2.x，但把套壳动作后置到阶段四。** 理由有三。其一，本项目界面是典型的中后台形态，不依赖 Node 原生模块，Tauri 的生态短板不构成障碍。其二，本机能力只需「启动一个进程」与「读取一个路径」，Rust 侧几十行即可覆盖，不需要引入 Node 旁路进程。其三，体积与内存优势在弱介质与低配机器上会被放大。

若用户不接受 Rust 的学习成本，Electron 是完全可以接受的退路，代价是安装包与内存开销增加约一个数量级。

### 2.2 前端框架与 UI 库

前端采用 **React 19 + TypeScript + Vite**。选择理由是生态规模与本项目所需的组件（富文本编辑、拖拽排序、虚拟列表、图表）在 React 侧可选方案最多。

UI 库的选择见第四章，需要用户决策后再定。

### 2.3 后端与数据层

| 层 | 实验版 | 网络版 | 选择理由 |
| --- | --- | --- | --- |
| 服务进程 | Node + Fastify | 同左，进 Docker | 与前端同语言，接口层可共享类型 |
| ORM | Prisma | 同左 | 双方言支持，SQLite 与 PostgreSQL 切换成本低 |
| 数据库 | SQLite（文件） | PostgreSQL（容器） | 实验版零运维，网络版支持并发与备份 |
| 缓存与会话 | 内存 + 签名 JWT | Redis（可选） | 实验版不引入额外组件 |

关键约束是**从第一天起就用 Prisma 的 migration 管理表结构，且不写任何 SQLite 专有语法**。这是让阶段五迁移成本从「重写数据层」降到「改一行连接串」的前提。

### 2.4 更新分发通道

| 方案 | 机制 | 适用 |
| --- | --- | --- |
| 远程界面直载 | 外壳加载服务端地址，服务器更新即全端生效 | 网络版主通道 |
| 资源包增量更新 | 客户端比对清单中的版本与哈希，差异则拉取 | 需要离线可用的场景 |
| 安装包自动更新 | Tauri updater 或 `electron-updater` | 外壳自身升级 |

Tauri 的 updater 插件强制要求签名校验，官方文档明确说明该校验无法关闭（https://v2.tauri.app/plugin/updater/ ）。`electron-updater` 的 `generic` provider 可指向任意静态文件服务器，通过 `latest.yml` 与 `*.blockmap` 实现差分下载（https://www.electron.build/docs/features/auto-update/ ）。

**推荐组合是「远程界面直载为主，资源包清单为辅」。** 日常功能更新只改服务端，客户端下次启动即最新。外壳自身升级走安装包通道，频率低，可以接受手动触发。

### 2.5 选型结论

```
外壳      Tauri 2.x（阶段四再引入，实验版先用浏览器）
前端      React 19 + TypeScript + Vite + 选定 UI 库
后端      Node + Fastify + Prisma
数据      SQLite → PostgreSQL
更新      远程直载 + 版本清单比对
部署      Docker Desktop + Cloudflare Tunnel
```

## 三、总体架构

两阶段使用同一份代码，差异只体现在配置中的服务地址。

**阶段 A 实验版**

```
浏览器 / 后续的桌面外壳
        │  http://127.0.0.1:8787
        ▼
   本机 Node 服务
   ├── 静态前端资源
   ├── REST API（账号、权限、纪要、事件）
   ├── 本机代理路由（启动外部软件）
   └── SQLite 数据文件
```

**阶段 B 网络版**

```
各端桌面外壳
        │  https://work.<域名>
        ▼
   Cloudflare（Tunnel + 访问策略）
        │
        ▼
   Docker Desktop 宿主机
   ├── 容器 web   静态资源 + 反向代理
   ├── 容器 api   Node + Fastify
   └── 容器 db    PostgreSQL
        │
        ▼
   Cloudflare Tunnel 出站连接，无需公网 IP
```

Cloudflare Tunnel 采用仅出站连接模型，`cloudflared` 从源站主动连向 Cloudflare 边缘，源站无需暴露入站端口（https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/ ）。

**本机代理在网络版中的角色**。当外壳加载远程界面时，「启动微信实例」这类请求由外壳内置的本地代理承接，不经过远程 API。远程 API 只返回该账号的启动配置，真正的进程创建发生在客户端。这条边界让网络版不必也无法远程操作任何人的电脑。

### 4.1 三个方向与取舍

这十款实际归入三个方向，选择方向比选择具体库更重要。

**方向一，现代极简（第 1、6 款）。** 以 shadcn/ui 为代表，组件以源码形式复制进项目，样式完全可控。视觉上限最高，容易做出「产品感」而非「后台管理系统感」。代价是需要自己维护组件规范，且团队需要熟悉 Tailwind。

**方向二，企业级中后台（第 2、3、4、5、7、9、10 款）。** 以 Ant Design 为代表，组件覆盖最全，中文文档最完善，权限与路由骨架现成。代价是视觉同质化严重，容易做成市面上随处可见的管理后台。

**方向三，桌面原生（第 8 款）。** Fluent UI 与 Windows 系统视觉一致，桌面应用的「原生感」最强。代价是 Web 生态与中文社区资料相对少，部分组件需要自行补齐。

### 4.2 推荐

**首选 Ant Design 5 配合 Ant Design Pro 的布局骨架。** 理由是本项目定位是业务工作台而非消费级产品，组件覆盖与开发速度的权重高于视觉差异化，且中文文档能显著降低后期维护成本。左侧导航、权限路由、面包屑这些骨架 Pro 已经提供，可以直接裁剪。

**次选 shadcn/ui。** 若用户希望界面有辨识度，且接受前期多投入约一到两周搭建组件规范，这是视觉上限最高的路线。

**备选 Fluent UI。** 若用户明确希望桌面端有 Windows 原生观感，选它。

需要说明的是，方向一与方向二并非互斥。可以用 Ant Design 承担复杂表单与表格，用 Tailwind 控制整体布局与间距，二者通过 CSS 变量对齐设计令牌。混合使用会增加规范维护成本，仅在用户对视觉有明确诉求时才建议。

## 五、主框架布局

左侧主导航是用户明确提出的排版基准，其余界面元素向它对齐。

**一级导航三项加占位项。**

| 序号 | 名称 | 状态 | 权限点 |
| --- | --- | --- | --- |
| 1 | 个人工作台 | 本期开发 | personal.* |
| 2 | 客户信息平台 | 占位，标记「功能开发中」 | customer.* |
| 3 | 运营信息平台 | 占位，标记「功能开发中」 | ops.* |

**布局规格。** 左侧导航固定宽度 224px，折叠态 64px，支持记忆用户的折叠偏好。顶部栏高度 56px，承载面包屑、全局搜索、账号菜单。内容区使用最大宽度约束而非通栏铺满，长文本可读性更好。二级导航在内容区左侧以内嵌形式出现，仅「个人工作台」本期需要。

## 六、个人工作台模块设计

### 6.1 板块一 一键登录软件通道

**功能范围。** 用户可维护若干「启动配置」，每条配置包含所属软件、显示名、本机可执行文件路径、启动参数、图标、排序序号。点击配置即启动对应客户端实例。支持同一软件配置多条以实现多账号。

**多账号实现路径。**

| 软件 | 多实例方式 | 稳定性 |
| --- | --- | --- |
| 微信 | 客户端内置多实例参数，快捷方式追加参数即可固定入口 | 依赖客户端版本，需在配置中记录版本要求 |
| QQ | 新版客户端支持账号切换，多实例需按客户端实际行为配置 | 中等 |
| 千牛 | 原生支持多账号登录 | 高 |
| 自定义 | 由用户填写可执行文件路径与参数 | 取决于用户配置 |

具体参数取值需要在本机实测确认后再固化进实现。检索过程中出现的相关说明均来自中文站点，与既定信源要求不符，未予采用，故此处按可复现的工程事实陈述，不标注文献引用。

**关键约束。** 启动配置中的可执行文件路径是本机绝对路径，与工作空间「受版本控制的文件不出现盘符」的约定冲突。处理方式是将其存入运行时数据库，数据库文件不纳入版本控制。这条规则必须写进项目约定，否则换机后会出现一批失效路径。

**安全边界。** 工作台不保存任何第三方账号的密码。若用户坚持要求免密登录，只能用操作系统凭据接口（Windows DPAPI 或 Electron `safeStorage`）加密存储，且需要在界面明确风险提示。本期建议不做。

**失败处理。** 路径不存在时给出明确提示并提供重新指定入口，不静默失败。

### 6.2 板块二 工作纪要

**功能范围。** Markdown 编辑与预览、标签分类、全文检索、置顶、按时间归档。

**交互要点。** 自动保存草稿，避免误关丢失。列表支持按标签与时间范围筛选。搜索覆盖标题与正文。

**数据模型。**

```
notes
  id, user_id, title, content_md, tags, is_pinned, created_at, updated_at
```

### 6.3 板块三 事件记录

这是用户描述最具体的一个板块，交互细节需要重点设计。

**列表视图。** 每行左侧为勾选框，中间为事件标题与标签，右侧为截止时间与优先级。未完成与已完成分两组展示，已完成组默认折叠。

**勾选切换。** 点击勾选框即把状态由 `todo` 切换为 `done`，同时写入完成时间与操作人。采用乐观更新，界面立即响应，请求失败则回滚并提示。切换后提供一个短暂的可撤销入口，撤销即恢复原状态并清除完成时间。

**已完成详情。** 已完成条目点击后打开详情面板，展示事件完整描述、创建时间、完成时间、从创建到完成的耗时、操作人，以及状态变更历史。

**数据模型。**

```
events
  id, user_id, title, description, status, priority, tags,
  due_at, completed_at, completed_by, created_at, updated_at

event_logs
  id, event_id, action, from_status, to_status, note, created_at
```

`event_logs` 是详情面板的数据来源，每次状态变更追加一行，不做原地修改。这个设计让「查看已完成事件的详情」有据可查，也为后续审计留出接口。

## 七、账号与权限分级

**认证方式。** 用户名加密码登录，服务端使用 Argon2id 哈希存储。会话采用短期访问令牌配合长期刷新令牌，刷新令牌只存哈希值，支持按设备撤销。登录失败按账号与 IP 双重限速。

**角色分级。** 建议内置四个角色，权限点按模块与操作二维展开。

| 角色 | 编码 | 权限范围 |
| --- | --- | --- |
| 超级管理员 | owner | 全部权限，含用户与角色管理、审计查看 |
| 管理员 | admin | 业务模块全部读写，可管理普通成员 |
| 成员 | member | 个人工作台全权，客户与运营平台按授权读写 |
| 只读访客 | viewer | 仅查看，不可写 |

**权限点命名。** 采用 `模块.对象.操作` 三段式，例如 `personal.event.write`、`system.user.manage`、`system.audit.read`。

**一条必须遵守的安全规则。** 权限校验只能在服务端执行，前端的菜单隐藏与按钮禁用只承担体验职责，不承担安全职责。若把权限判断只放在前端，任何用户改一个请求就能越权。这是权限系统最常见的失效方式，需要在代码评审中作为硬性检查项。

**首次初始化。** 数据库为空时，首次启动引导创建超级管理员账号，创建完成后该入口自动关闭。

## 八、数据模型汇总

| 表 | 用途 |
| --- | --- |
| users | 账号 |
| roles | 角色 |
| permissions | 权限点 |
| role_permissions | 角色与权限关联 |
| refresh_tokens | 会话与设备 |
| audit_logs | 关键操作审计 |
| launch_profiles | 一键登录启动配置 |
| launch_history | 启动记录 |
| notes | 工作纪要 |
| events | 事件记录 |
| event_logs | 事件状态变更历史 |

所有表均带 `created_at` 与 `updated_at`，软删除统一使用 `deleted_at`，避免物理删除导致历史断裂。

## 九、实施路线图

每个阶段都给出交付物与验收标准，未通过验收不进入下一阶段。

### 阶段零 项目初始化

**交付物。** `projects/fanhe-work/` 目录骨架、包管理与脚本约定、`ws-env` 补充 `CARGO_TARGET_DIR`、项目级约定文档。

**验收标准。** 从 `infra/portable/ws-run.cmd` 进入后可完成依赖安装与开发服务器启动，`ws-doctor.ps1` 扫描无硬编码盘符。

### 阶段一 账号与权限

**交付物。** 登录页、会话管理、角色与权限点、首次初始化流程、审计日志。

**验收标准。** 四种角色登录后可见范围符合预期，直接调用无权限接口返回 403，刷新令牌可撤销。

### 阶段二 主框架与 UI 骨架

**交付物。** 左侧导航、路由体系、主题令牌、三个占位页、错误与空状态页。

**验收标准。** 导航折叠状态可记忆，占位页正确显示「功能开发中」，界面与选定 UI 方案的设计令牌一致。

### 阶段三 个人工作台三板块

**交付物。** 一键登录通道、工作纪要、事件记录。

**验收标准。** 见第六章各节的交互要点，逐条对照。

### 阶段四 桌面外壳

**交付物。** Tauri 2 外壳、本机代理、外壳与服务地址的配置切换。

**验收标准。** 外壳加载本机服务与加载远程地址两种模式均可正常工作，本机代理可成功启动外部软件。

### 阶段五 服务端化

**交付物。** Docker Compose 编排、PostgreSQL 迁移、Cloudflare Tunnel 配置、访问策略。

**验收标准。** 外部网络可访问，数据库数据与实验版迁移一致，无公网入站端口暴露。

### 阶段六 更新通道

**交付物。** 版本清单接口、客户端版本比对、外壳安装包升级通道。

**验收标准。** 服务端发布新版本后，客户端重启即加载新版本，旧版本有明确提示。

## 十、风险清单

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 工具链写入量压垮 U 盘 | 编译缓慢，闪存寿命消耗 | 重型产物移出 U 盘，补 `CARGO_TARGET_DIR` |
| 启动配置写入版本控制 | 换机后路径全部失效 | 路径只存运行时数据库，纳入忽略规则 |
| 一键登录被判定为异常行为 | 第三方账号风控 | 只做唤起，不做自动填密，明确告知用户 |
| 权限只在前端校验 | 越权访问 | 服务端强制校验，代码评审硬性检查 |
| SQLite 与 PostgreSQL 语法差异 | 迁移返工 | 全程使用 ORM 抽象，不写方言专有语法 |
| 本地数据不随工作空间移动 | 换机后数据丢失 | 实验版接受并提示，网络版由服务端解决 |
| 更新包被篡改 | 供应链风险 | 启用更新签名校验，密钥独立保管 |
| 换机后本机代理失效 | 一键登录不可用 | 外壳启动时自检并给出重新配置引导 |

## 十一、工作空间落地细则

### 11.1 需要补充的环境变量

`ws-env.ps1` 与 `ws-env.sh` 已覆盖 Node、Rust、Electron 的缓存与主目录。唯一缺口是 Rust 的编译产物目录，默认会落在项目内并随 U 盘移动，体积可达数 GB。

建议在两个脚本的映射表各加一行。

| 变量 | 目标位置 | 用途 |
| --- | --- | --- |
| `CARGO_TARGET_DIR` | `.cache/cargo-target/` | Rust 编译产物，不随项目移动 |

这符合工作空间既有约定，即新增技术栈时只改映射表，不另写一套逻辑。

### 11.2 项目内目录约定

```
projects/fanhe-work/
├── apps/
│   ├── web/          前端
│   ├── api/          后端服务
│   └── desktop/      桌面外壳（阶段四引入）
├── packages/
│   └── shared/       前后端共享类型与常量
├── docs/             方案与决策记录
└── data/             运行时数据，不纳入版本控制
```

### 11.3 必须遵守的既有约定

1. 所有开发操作从 `infra/portable/ws-run.cmd` 或 `ws-run.sh` 进入，直接启动 IDE 不会继承环境重定向。
2. 受版本控制的文件中不出现盘符，需要根目录时使用 `WS_ROOT`。
3. 脚本中所有变量加引号，工作空间路径含空格。
4. `data/` 目录与数据库文件纳入忽略规则，它们逐机不同。
5. 跨 bash 与 Windows PowerShell 传递含中文路径的文本文件时，读取侧显式指定 UTF-8 编码。此坑在本工作空间已造成过一次误判，需要沿用既有教训。

## 十二、待决策事项

以下五项需要用户确认后才能进入阶段零。

1. **UI 方案选哪一款。** 影响阶段二的全部界面实现，建议在第四章的三个方向中先定方向再定具体库。
2. **前端技术栈。** 推荐 React。若倾向 Vue，第 5、7、9 款方案可用。
3. **桌面外壳。** 推荐 Tauri 2 并把套壳后置。若不愿引入 Rust，改用 Electron。
4. **实验版数据库。** 推荐 SQLite 单机文件。若希望实验版即支持多机同时访问，需要提前引入 PostgreSQL。
5. **一键登录的安全边界。** 是否接受「只做唤起，不做自动填密」。这一项直接影响合规风险，建议明确。
