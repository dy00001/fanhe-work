# 插件直采方案（评审稿）

> 2026-10-25。目标是把采集路线从「Edge 每店独立 profile + CDP 旁路录制」改为「浏览器插件直采 + 本机代理转发」，并由前端发起。
> 本文只写实现方案与评审要点，不含代码。

## 一、结论与三个硬约束

方案可行，但「前端直接指挥插件」在技术上不成立，必须走三段式：**前端 → 指令层 → 本机代理 → 插件**。

三个约束逐条说明，它们决定了架构形态，绕不过去。

**约束一，插件只认自己的调用方。** `background.js` 的身份校验是 `X-Dmp-Bridge: <插件 ID>` 自定义头，预检只放行 `chrome-extension://<ID>` 的 Origin。任何网页脚本都无法伪造这两者。所以插件不可能被前端直接调用，必须由本机一个进程按它的协议去拉任务、交结果。

**约束二，远程页面碰不到 `127.0.0.1`。** 桌面端安装版加载的是远端页面，origin 是 https 域名。这个页面 fetch `http://127.0.0.1:<port>` 会同时撞上混合内容拦截和 Chrome 的 Private Network Access 预检。插件桥自身已经处理了 PNA（响应里带 `Access-Control-Allow-Private-Network: true`），但那只对插件发起的请求有效，对普通网页无效。

**约束三，采集必须异步。** 现有 `/api/ops/shops/:code/sync` 返回 202 只置时间戳，代码注释写得很清楚：一轮采集几十秒起，HTTP 同步等待会把「慢」和「失败」混成一件事，而这两件事在界面上要给完全不同的提示。新方案沿用这个判断。

由此得到唯一合理的形态：前端发起一个任务，任务由本机代理执行，前端轮询任务状态。前端永远不直接等采集结果。

## 二、数据范围

按「能直接上」「补一条探测」「补三条探测」分三期。覆盖度是实测结论，不是估算。

### 第一期，现有命令直接可用

| 数据块 | 需要 | 能给 | 说明 |
|---|---|---|---|
| daily | 4 项 | 3 项 | 缺 `itemVisitors` |
| summary | 13 项 | 9 项 | 缺 `itmUv`、`bounceRate`、`itmAvgPv`、`newPayByrCnt` |
| item 维度 | 6 字段 | 6 字段 | `item-list` 与现有 `item_view_top` 是同一接口 |
| channel / area / keyword | 共 10 字段 | 0 | 无对应命令 |

第一期能撑起：KPI 四张卡里的三张、商品榜完整、结构指标九项。渠道榜、地域分布、搜索词三块会是空的。

### 第二期，补一条裸探测

`GET /flow/monitor/overview/overview.json` 一条接口同时补齐 `itemVisitors`、`bounceRate`、`itmAvgPv`、`newPayByrCnt`。补完 daily 到 4/4，summary 到 13/13，逐日与整段两块完整。

这一期是分水岭。**在它完成之前不能开自动上报**，原因见第七节的一致性风险。

### 第三期，补三条裸探测

`tree_platform_support`（channel）、`listAreas`（area）、`drainageSearch`（keyword）。三条都在 `sycm.taobao.com` 域下，插件白名单放行，用 `api` 命令可探测。风险是这三条没有经过作者验证，改版即断，需要自建校验。

`content` 维度日增本来就不上报，不在本期范围。

## 三、触发方式

四种，共用同一个任务模型。

| 方式 | 入口 | 说明 |
|---|---|---|
| 手动 | 前端按钮 | 单店单日，或指定日期区间补采 |
| 定时 | 本机代理内置调度 | 替代现有 Windows 计划任务，每店一个时间点，避开整点 |
| 事件 | 绑定完成后自动触发 | 沿用现有语义：绑定只写库，由代理发现后执行 |
| 补采 | 前端选日期区间 | 受 cc 系接口窗口限制，只允许 1/7/15/30 天 |

一个必须写进产品文案的限制：**同一时刻只允许一个采集任务**。插件桥是机器级一把锁，第二个任务会排队，界面上要显示「排队中」而不是「采集中」。

## 四、端到端流程

以桌面端手动触发为例。

```
① 前端（桌面端渲染进程）
    用户点「采集今天」
    → IPC 调主进程，不走 fetch

② Electron 主进程
    → POST http://127.0.0.1:47850/collect  { shop, date }
    ← 202 { taskId, status: "queued" }

③ 本机代理（新进程，常驻）
    任务入队，串行执行
    → 调 sycm-cli：run-tb.cmd sycm home-overview --date ... --raw --out ...
    每条命令 2 到 10 秒，十几条命令累计一到三分钟

④ 插件
    轮询 127.0.0.1:47831-47840 拿任务，在已登录页面里发只读请求，回传结果
    注意：这里有两层端口，代理与 CLI 之间是 47850，CLI 与插件之间是 47831 起

⑤ 本机代理
    原始响应落盘到本地目录
    转 ops-ingest.v1
    → POST /api/ops/ingest（本机开发态）
    或走 db:ops-import（容器态，回环校验不通过时降级）

⑥ 前端
    每 2 秒 GET /collect/<taskId> 拿进度
    成功后 invalidate 看板查询
```

远程浏览器场景下，①②换成：前端调 `POST /api/ops/shops/:code/sync` 置时间戳，代理轮询 `/api/ops/shops/pending` 发现任务。两条路径在③之后完全合流。

## 五、接口约定

### 5.1 新增：本机代理的 HTTP 接口

只监听 `127.0.0.1`，端口固定 `47850`（避开 8787 API、5173 web、9222 起 CDP、47831 起插件桥）。

| 方法 | 路径 | 入参 | 出参 |
|---|---|---|---|
| GET | `/health` | 无 | `{ ok, cliVersion, pluginOnline, loggedIn, busy }` |
| POST | `/collect` | `{ shop, date, scope? }` | `202 { taskId, status }` |
| GET | `/collect/:taskId` | 无 | `{ status, progress, steps[], result? }` |
| POST | `/collect/:taskId/cancel` | 无 | `202` |

鉴权：只接受带 `X-Fanhe-Agent` 自定义头的请求，值为本地生成的随机 token，写在 `%APPDATA%\梵禾 Work\agent.json`，桌面端主进程读取。理由与插件桥一致：自定义头会触发预检，普通网页伪造不了。

### 5.2 复用：现有 API 的三个端点

| 端点 | 用途 | 是否改动 |
|---|---|---|
| `POST /api/ops/ingest` | 数据入库 | 不改 |
| `GET /api/ops/shops/pending` | 远程场景的待办发现 | 不改 |
| `POST /api/ops/shops/:code/state` | 回写登录态与失败原因 | 不改 |
| `POST /api/ops/shops/:code/sync` | 远程场景置时间戳 | 不改 |

**契约不动**。`ops-ingest.v1` 的字段、单位、幂等语义全部保留。这是本次改造最重要的边界：换采集方式不换数据契约，前端与入库侧零改动。

### 5.3 任务状态机

```
queued → running → succeeded
                 → partial      （部分步骤失败，数据已入库）
                 → failed       （未入库）
queued → cancelled
running → cancelled
```

`partial` 是这次要新增的语义，现有 `EcomCollectStatus` 里已经有这个枚举值，不用迁移。

## 七、数据一致性与异常处理

### 7.1 幂等

按 `(shop, statDate)` 与 `(shop, dimType, statFrom, statTo, dimKey)` upsert，同一份 payload 反复提交结果一致，`revised` 只在值真的变了才为真。这条不需要改，`ingestOpsSnapshot` 已经实现。

### 7.2 部分成功会削数据，这是本次最大的风险

`ingest.ts` 的清行逻辑是按类型逐个处理：

- 某类型本次**一条都没上报**，跳过清理，库里旧行不动。
- 某类型**上报了**，按本次的 key 集合 `deleteMany notIn`。

推论一：第一期只报 item 和 summary，channel、area、keyword 因为完全没出现而安全。这条比直觉更宽容。

推论二：summary 本次上报 9 项，就会把同窗口的 summary 清到 9 项，丢掉 `itemVisitors`、`bounceRate`、`itmAvgPv`、`newPayByrCnt` 四项。每跑一次削一次，而这次运行仍然记 `succeeded`，事后没有痕迹。

**所以第一期上线时必须关掉自动上报，只允许手动试跑。** 等第二期补齐 13 项再开定时。这一条要写进上线检查表。

### 7.3 失败分类

现有分类基于 `collect-daily.mjs` 的退出码，与 sycm-cli 的语义直接冲突，必须重写映射。

| 情况 | sycm-cli 表现 | 新分类 | 界面提示 |
|---|---|---|---|
| 插件未装或未开 | 退出码 2，提示没连上插件 | `plugin_offline` | 打开 Chrome 并确认插件已启用 |
| 登录失效 | 退出码 2，提示登录失效 | `login_expired` | 在该浏览器里登录生意参谋 |
| 触发风控 | 退出码 3，响应含风控词 | `risk_stopped` | 人工完成验证，不要连续重试 |
| 子账号无权限 | 业务错误码 5008004 一类 | `no_permission` | 请主账号开通 |
| 接口改版 | 解析不到字段 | `schema_changed` | 需要更新适配器 |
| 网络中断 | 连续 2 次 HTTP 失败 | `network` | 检查网络后重试 |
| 机器级锁被占 | 排队提示 | `busy` | 显示排队中，不是失败 |

注意 `risk_stopped` 与 `login_expired` 的区分。现有实现把退出码 3 映射成登录失效，直接搬过来会让风控被提示成「去重新登录一个其实有效的账号」，这类误判在 10-20 已经踩过一次。

### 7.4 对账

三个手段，都已在库里，不用新增表。

1. `ecom_collect_runs` 记每次任务的行数、耗时、错误、`rawPath`。
2. `revised` 标记平台回溯改数，前端可以显示「今日数据已修正」。
3. 同一天的 `summary.visitors` 与逐日求和并存，差值就是跨日重复访客，这是已知且已记录的契约内差异。

### 7.5 代理进程的可靠性

代理是常驻进程，挂了就整条链路停。三件事要做：

1. 自启：随桌面端启动，或注册为用户登录启动项。不要用系统服务，服务账户拿不到用户的浏览器会话。
2. 心跳：每次处理任务写一次时间戳，前端能显示「代理离线 N 分钟」。
3. 单实例：端口被占用即认为已有实例在跑，第二个实例直接退出。现有 `sync-shops.mjs` 用 `--watch` 常驻，没有做单实例保护，这次要补。

## 八、评审要点

### 8.1 必须先定的三件事

**第一，复用第三方 sycm-cli 还是自研插件。** 这是最大的架构选择，两条路的代价完全不同。

| | 复用 sycm-cli | 自研插件 + 自研 CLI |
|---|---|---|
| 工期 | 一到两周 | 一到两个月 |
| 覆盖度 | 55 命令，含单品下钻、客服对话 | 从零开始，先做基础几页 |
| 风险 | 第三方版本变动、协议不保证稳定、作者可能收费或停止维护 | 全部自己扛，改版要自己跟 |
| 多店 | 受机器级锁限制，只能串行 | 可设计成多实例 |
| 退出码与错误语义 | 需要适配层翻译 | 自己定义 |

我的判断：短期复用，把 sycm-cli 当成一个「采集后端」，我们只做适配与调度。同时在适配层做隔离，让将来换掉它时前端与契约不受影响。这个隔离的关键就是 5.2 那条「契约不动」。

**第二，多店并行要不要保留。** 现在四家店可以并行跑，插件方案下必须串行。单店一轮约一到三分钟，四家店串行就是四到十二分钟。如果能接受，方案成立；如果不能接受，就要回到自研插件。

**第三，历史数据怎么办。** 现有 `data/daily/` 下已有的原始响应和 `csv30` 基线，是继续用 CDP 补采，还是接受「某一天之前是旧口径、之后是新口径」。建议在 `ecom_collect_runs` 的 `trigger` 里加一个值区分，不改表结构。

### 8.2 里程碑

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| M1 | 本机代理跑通，手动触发单店单日，只入 daily 与 item | 前端点一次按钮，两分钟内看到 KPI 与商品榜更新；`ecom_collect_runs` 有记录 |
| M2 | 补 `overview.json` 裸探测，summary 到 13 项 | 逐日 4/4、summary 13/13；重跑两次 `revised` 为 0 |
| M3 | 开定时任务，替代计划任务 | 连续三天自动采到，无人工干预；失败时界面有明确分类 |
| M4 | 补三条维度探测 | 渠道榜、地域、搜索词有数据，且与后台对得上 |
| M5 | 下线 CDP 链路 | 旧脚本移入 `legacy/`，计划任务注销，profile 目录归档 |

### 8.3 验收要能证伪

沿用项目既有方法论，每条都要有反例。

- 断网跑一次，确认状态是 `failed` 而不是 `succeeded` 加空数据。
- 手动退出插件，确认提示是 `plugin_offline` 而不是 `login_expired`。
- 故意只上报 9 项 summary，确认库里 summary 从 13 项被削到 9 项，以此证明 7.2 的风险真实存在，再据此确认「M2 之前不开定时」这条约束有效。
- 同一天连跑两次，确认 `revised` 为 0、行数不翻倍。
- 让第二个任务在第一个运行时提交，确认返回排队状态而不是报错。

### 8.4 待决事项

1. 代理进程的形态：独立 exe，还是随桌面端主进程一起跑。独立 exe 更简单，但要处理升级。
2. 代理与 API 的传输：容器化之后回环校验会拒，现有代码已经降级到 DB 直连。新代理要不要沿用这条降级路径，还是给代理单独发一个可跨边界的 token。
3. 采集范围要不要扩到千牛后台。插件 `SITES` 里登记了 `myseller.taobao.com`，但 CLI 没装千牛模块，拿不到包。
4. 客服对话要不要入库。`fetch-recent` 能拿完整聊天正文，但涉及买家隐私，且契约里没有对应维度。

## 九、一句话总结

方案成立，形态是「前端发任务、本机代理执行、插件取数、契约不变」。真正的成本不在采集，在三件事：补齐那 4 个字段之前不能开自动上报、多店必须串行、以及长期依赖一个第三方工具的版本稳定性。
