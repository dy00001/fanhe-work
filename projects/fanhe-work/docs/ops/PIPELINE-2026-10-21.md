# 运营数据链路：三段职责、衔接判据与改动记录

> 2026-10-21。本文回答三个问题：抓取、更新、推送各拥有什么事实；三段靠什么接起来；本轮改了什么、怎么验的。
> 上一轮的静态评审在 `REVIEW-2026-10-21.md`，本文是它的执行结果与边界定义。

## 一、三段各拥有什么事实

判断一段代码该不该管某件事，用一条标准：**这件事的真相只有它能看见吗。** 只有它能看见，就归它管；别处也能看见，就别在这里再定义一遍。

| 环节 | 输入 | 输出 | 它唯一拥有的事实 | 它明确不负责的事 |
| --- | --- | --- | --- | --- |
| 抓取 `collect-daily.mjs` | 已登录的浏览器会话 | `data/daily/<业务日>/<页>/<序号>_<接口>.json` 与 `_manifest.json` | 这一天、这个页面、这些接口的**原始响应** | 去重、合并、历史拼接、数值对不对 |
| 更新 `export-daily-ingest.mjs` + `ingest.ts` | 原始响应 | 入库契约 JSON、库里的 `ecom_*` 四表 | **口径**：哪一列算金额、哪个窗口算整段、同窗口重采怎么覆盖 | 页面为什么没发请求、浏览器登录态还在不在 |
| 推送 `routes/ops.ts` + 前端 | 库 | 界面上的数 | **可见性**：权限裁剪、区间锚定、缺失怎么呈现、什么时候重取 | 数据是否完整（只负责如实呈现缺失，不负责补齐） |

三条推论，本轮都落到了代码里：

**抓取端不该判断"数据够不够用"。** 它只知道回了几个接口，不知道这些响应能不能被认出来。上一轮把"体量够"当成"内容对"，渠道页 2 个文件、字节数达标、判定不薄，而关键接口从未触发。现在它只记录事实（`missing` 字段），判断交给校验器。

**更新端不该猜测"页面为什么空"。** 它只看文件。分不清"目录空"与"文件名对不上"时，它给出的建议必然是错的：前者要重采，后者改匹配规则就行，重采一百遍也是同样的文件名。现在它把三种原因分开说。

**推送端不该假装数据完整。** 缺失就是缺失，显示「—」，并在新鲜度上如实说"数据截止到某时"。它不能靠"上一份数据还在内存里"把界面填满。

## 二、三段靠什么接起来

三个契约，每个都有明确的失败模式。

### 2.1 原始目录契约（抓取 → 导出）

```
data/daily/2026-10-19/
  _manifest.json          这一天采过哪些页、每页落了哪些文件、是否偏薄
  flow-overview/02_new_guide_trend_overview.json
  item-rank/09_cc_item_view_top.json
  ...
```

约定：目录名是业务日；一级子目录名是模块名；文件名里带接口特征。**导出层按"模块名 + 文件名正则"定位数据**，所以文件名本身就是契约的一部分。

失败模式：接口改了名，或页面换了请求。此时目录里有文件、字节数够，导出层却匹配不到。本轮把这种情况单独识别出来了（见 3.5）。

### 2.2 入库契约（导出 → 更新）

结构见 `DATA-CONTRACT.md`。三条硬约束：

- `window.from === window.to === 目标业务日`（日增恒为一天）
- `daily` 恰好 1 行，`daily[0].date === 目标业务日`
- 缺块写 `null`，不补 0

失败模式：响应里的 `statDate` 与目标日不一致。此时窗口合法、行数正常、金额看着合理，入库之后每一层校验都会通过，只有对着生意参谋的原始页面才看得出不对。本轮把它从"降退出码但照写文件"改成"写文件前直接拒绝"。

### 2.3 读模型契约（更新 → 推送）

`OpsDashboardResponse` 带两个 flag：`flags.covered`（覆盖区间）与 `flags.masked`（哪些金额被裁掉了）。界面靠这两个渲染空态与裁剪提示，不自己推算。

失败模式：接口返回 200 但表不存在（`P2021`）、权限点缺失导致 403。前者是部署问题，后者是镜像问题，都不是前端能修的，前端只负责把原因显示出来。

## 三、本轮改动

### 3.1 维度清理不再退化成全删（`apps/api/src/ops/ingest.ts`）

原写法 `dimKey: { notIn: keys.length === 0 ? [''] : keys }` 读起来像"没有要保留的就清空"，实际是把"这个类型今天没采到"当成"这个类型今天空了"。上午采到渠道 5 行、下午重采时渠道页偏薄只回了商品榜，上午的渠道金额就被删掉，而这次运行仍记 `succeeded`。

改法：本次一条都没上报的类型直接 `continue`，一行不清。

反向断言防修过头：如果某类型这次上报了、但里面少了某个对象（商品下架），那个对象**必须**被清掉。否则下架商品会永远留在榜上。这条写在 `ops-ingest.test.ts` 里。

### 3.2 `partial` 真正产出（同文件）

`OPS_COLLECT_STATUSES` 里一直有 `partial`，展示层连文案都写好了（「部分成功」），写入端却只产出 `failed` / `succeeded`。于是"逐日拿到了、维度全没拿到"这种最常见的半截采集被记成成功：看板上商品榜一片「—」，运行记录却是绿的，而人只会去看运行记录。

判据取"逐日与维度有一方为空"，不按维度类型逐个要求。`keyword` 与 `content` 在当前授权下本来就采不到，按类型要求会让每天都变成 `partial`，一个天天出现的告警等于没有告警。

`partial` 也更新 `lastCollectedAt`：这次确实采到了东西，界面据此显示"数据截止到某时"是对的。

### 3.3 响应日期错位直接拒绝产出（`export-daily-ingest.mjs`）

原来是 `failures.push(...)` 加退出码 2，文件照写。而文件里 `window` 用的是目标日，数值却属于另一天，紧接着打印的 `pnpm db:ops-import` 会把它入库到错误日期。

现在写文件前 `exit 1`。结构性错误不能降级成"待确认"，因为它的下游动作不可逆。

### 3.4 运行记录移出事务（`ingest.ts`）

原来店铺 upsert 与 `running` 运行记录都在事务里，事务一抛异常就整批回滚，包括那条运行记录。结果是"采集中断"在库里完全不可见：没有记录、没有错误、没有时间点，运维只能看到"今天没有新数据"，而这条现象和"今天没采"长得一模一样。

现在店铺与运行记录先落地，事务失败时补写 `failed` 并记录原因。代价是失败的批次也会留下店铺行，这是对的：一次失败的采集确实发生在这家店上。

### 3.5 导出层区分三种"读不到"（`export-daily-ingest.mjs`）

| 原因 | 打印 | 该做什么 |
| --- | --- | --- |
| 目录不存在 / 目录里没有 json | `采集这一页没落盘` | 重采 |
| 有 json 但文件名不匹配 | `没有一个匹配 /pattern/，这个接口要么没被触发，要么文件名变了` | 补采集规则或改匹配规则，**重采没用** |
| 文件匹配上了但里面没有可用行 | `读到了，但里面没有可用行` | 页面结构变了，或这一页确实为空 |

同时把报告里的"来源"列从手写字符串改成由扫描记录派生，避免"未采到 xxx"与实际文件名走偏。

### 3.6 采集端记录关键接口缺失（`collect-daily.mjs` + `lib/required-endpoints.mjs`）

`isThin` 只看文件数与总字节。渠道页 2 个文件、字节数达标，于是"不薄"，而渠道树接口从未触发。

新增 `REQUIRED_ENDPOINTS`：每页声明必须拿到的接口特征，落盘记录里匹配不到就记进 `missing`，打印时单列一行"缺接口"。判定表放在 `lib/required-endpoints.mjs`，采集端与校验端共用同一份，避免"采集按 A 判、校验按 B 判"。

**只记录、不改退出码。** 把它算成偏薄会让日增每天都红，告警就废了。缺口的可见性交给校验器。

### 3.7 跨段校验器 `verify-daily.mjs`（新增）

拿 manifest 与导出契约做交叉断言。它不重采、不写库、不改文件，只回答"这一天的三段接得上吗"。

核心是**跨段一致性**：采集端说这一页拿到了东西，导出端就必须有对应维度的行。两段各自都能自证清白，只有交叉看才看得见断裂。

三级严重度是整个脚本的关键：

| 级别 | 含义 | 退出码 |
| --- | --- | --- |
| 阻断 | 会让**错的数据**进库：窗口错位、逐日日期不符、维度 0 行 | 1，不许入库 |
| 缺口 | 数据少了一块但剩下的都对：偏薄页、接口没触发、采集说拿到了导出却认不出 | 2，可入库 |
| 提示 | 已知缺口，看一眼即可 | 0 |

划分依据：缺失的数据会显示「—」，人看得见；错的数据显示得和真的一样，人看不见。所以只有"会写错"才值得挡下来。挡下所有缺口会让日增永远跑不完。

### 3.8 落库校验 `ops-verify.ts`（新增）

前两道只管到契约为止。文件写对了、契约合法、窗口一致，仍然可能在入库这一步悄悄失真：事务回滚、状态记错、行数对不上、维度只写了一部分。这些在库里都不报错，看板只显示「—」。

它读库回验四件事：批次状态（`failed` / `running` 都算失败）、逐日行与契约字段一致、维度键全部在库、`lastCollectedAt` 不为空。给了 `--contract` 就逐项比对。

### 3.9 管道 `run-pipeline.ps1`（新增）

五步串起来，每步的退出码决定是否继续：

```
1 collect  →  0 继续 / 2 记为缺口继续 / 3 登录态失效直接停
2 export   →  0 继续 / 2 记为缺口继续 / 1 停
3 verify   →  0 继续 / 2 记为缺口继续 / 1 停（不许入库）
4 import   →  0 继续 / 其它停
5 verify DB → 0 通过 / 1 整体失败
```

整体退出码：0 干净、2 数据已入库但有缺口、1 中断。

三个实现细节值得记下来，都是踩过的：

- `tsx` 必须经 `node_modules\.bin\tsx.cmd` 启动。直接 `node ...\tsx\dist\cli.mjs` 会在普通 node 下跑，TS 加载器没注册，`import './x.js'` 全部 `ERR_MODULE_NOT_FOUND`（磁盘上只有 `.ts`）。
- 函数里调子进程必须 `| Out-Host`，不能用 `| Out-String`。函数体内未被捕获的输出会成为返回值的一部分，`$code` 变成"子进程输出 + 退出码"的数组，所有 `-eq` 比较都失效。
- 脚本开头设 `[Console]::OutputEncoding = UTF8`，否则子脚本的中文在日志里是乱码，而失败原因正好写在中文里。

### 3.10 推送段：超时、静默重取、新鲜度流动

| 问题 | 改法 | 落点 |
| --- | --- | --- |
| 请求没有超时，网络半通时界面永久停在加载态 | `RequestOptions.timeoutMs`，运营三个读接口设 15 秒 | `lib/api.ts` |
| 桌面壳反代没有上游超时 | GET/HEAD 设 20 秒，超时返回 504；写请求不设（备份可能到分钟级） | `apps/desktop/src/server.ts` |
| 切回标签页不重取，挂着一天的窗口一直显示昨天的数 | `visibilitychange` 时静默重取，**不进指纹**，界面不回到加载态 | `lib/use-ops-dashboard.ts` |
| 静默重取失败会把已经显示好的数据换成错误态 | 已有同指纹的 ready 数据时保留旧数据，靠新鲜度标签表达"这份是几点的" | 同上 |
| 新鲜度标签的"现在"冻在渲染那一刻 | `useNow()` 每分钟推进一次 | `lib/use-now.ts` |
| 每次切回都完整拉一遍几十 KB | 三个读接口加 `ETag` + `Cache-Control: private, max-age=0, must-revalidate`，内容没变返回 304 | `routes/ops.ts` |

`max-age=0` 是刻意选的，不是 `max-age=60`：后者在 60 秒内直接吃本地缓存，"刚采完数据、刷新页面"会看到旧数。每次回源验证、内容没变就 304，既保住即时性又省掉重复传输。`private` 必须有：响应里是带登录态、且经过权限裁剪的金额。

**不上 SSE / WebSocket。** 一天变一次的数据不值得三套长连接逻辑：断线重连、心跳、服务端连接数、桌面壳反代的兼容性。切回来重取加 304，成本接近零，收益接近全部。

## 四、三段协同的验收方式

一条命令验完整条链路：

```
powershell -ExecutionPolicy Bypass -File tools\collector\scripts\run-pipeline.ps1 -Target 2026-10-19
```

跳过采集、只验后四步：

```
powershell -ExecutionPolicy Bypass -File tools\collector\scripts\run-pipeline.ps1 -Target 2026-10-19 -SkipCollect
```

本轮实测（10-19 真实数据）：

```
2/5 export    导出：维度 38 行（summary 13 / area 10 / keyword 10 / item 5）
3/5 verify    通过 5 / 提示 2 / 缺口 2 / 阻断 0   → 可入库
4/5 import    逐日 1 行，维度 38 行，被改写天数 0，252 ms
5/5 verify DB 通过 7 / 警告 0 / 失败 0
整体          DONE with gaps  → 退出码 2
```

反例也做了，确认断言不是恒真的装饰：

| 反例 | 期望 | 实测 |
| --- | --- | --- |
| 把契约的 `window.to` 改成次日 | 阻断 | 阻断，退出码 1 |
| 把契约的 `visitors` 改成 999 | 落库校验失败 | `逐日字段与契约不一致（访客：契约 999，库里 67）`，退出码 1 |

| 退回二值状态 | `partial` 两条断言变红 | `fail 2` |
| 关掉 304 分支 | ETag 命中那条变红 | `fail 1` |
| 把 POST 也算进读超时 | 写请求那条变红 | `fail 1` |

### 验证覆盖到什么程度

这一栏单独列出来，是因为「跑过了」与「验过了」不是一回事。

| 改动 | 验证方式 | 结论 |
| --- | --- | --- |
| 维度清理、三态状态、运行记录在事务外 | 6 项集成用例，两条反向断言各做一次反例 | 验过 |
| `verify-daily.mjs` | 10-19 真实数据；篡改窗口反例 | 验过 |
| `ops-verify.ts` | 10-19 真实数据（含 `--contract` 逐项比对）；篡改访客反例 | 验过 |
| `run-pipeline.ps1` | 实跑五步，退出码 2；导入与落库校验均执行 | 验过 |
| ETag | 4 项路由级用例：拿到 ETag、命中 304、过期 ETag 仍 200、内容变化后旧 ETag 失效 | 验过 |
| 反代读超时 | 2 项用例：卡死上游得到 504；POST 在同样条件下仍完整回包 | 验过 |
| 前端 `timeoutMs` | 浏览器实测：慢服务延迟 20s，客户端 15s 上限 | 验过，见 4.1 |
| `useNow` 与 `visibilitychange` 静默重取 | 浏览器实测：定时器推进计数、切标签前后请求记录 | 验过，见 4.2 |
| ETag（浏览器侧） | 浏览器实测四跳，含两条反例 | 验过，见 4.3 |

上表全部验过。原先标为缺口的 `timeoutMs`、`useNow`、`visibilitychange` 三项，在 10-21 下午用临时探针页在真实浏览器里补齐 —— 这三项的失败形态都是「界面不刷新」或「超时不触发」，只看代码和 typecheck 判断不了。

### 4.1 请求超时（`timeoutMs`）

做法：起一个探针服务，`/api/ops/dashboard` 收到请求后**先不写响应体**，20 秒后才回 —— 复现的是「响应头回来、响应体一直不来」这条半通路径，而不是单纯的连接超时。前端用临时 `.env.local` 把 `VITE_API_BASE_URL` 指过去，探针页直接调真实的 `opsDashboardRequest`。

| 观察点 | 结果 |
| --- | --- |
| 对照组 `/api/ops/health`（立即返回） | 成功，11 ms —— 慢的是服务端，不是代码 |
| 被测 `/api/ops/dashboard` | **15005 ms** 后失败，`code=timeout`、`status=0`、文案「服务器超过 15 秒没有响应」 |
| 服务端日志 | `08:33:38.287 收到请求` → `08:33:53.286 客户端在响应写出前断开` |

服务端那条「断开」是关键：它证明请求是被真的掐掉的，而不是 Promise 提前返回、连接继续挂着。这正是 `api.ts` 注释里写的 abort 与 race 的差别，本轮实测确认走的是 abort。

### 4.2 `useNow` 与切标签重取

做法：探针页挂 `useNow(1000)` 并把当前时刻渲染出来，同时挂 `useOpsDashboard` 用 `PerformanceObserver` 记录所有 `/api/ops/` 请求。

| 观察点 | 结果 |
| --- | --- |
| 时钟推进 | 30 秒内推进 30 次，时刻持续变化（若退化成渲染时取一次，会永远停在初始值） |
| 切到别的标签再切回 | 请求记录从 7 条增至 9 条，每次回到前台都多一条 dashboard 请求 |
| 切回时的界面状态 | hook 状态始终是 `ready`，没有回到 `loading` —— 静默成立 |

间隔取 1 秒只是为了在观察窗口内看到变化；被验的是「定时器挂载并驱动重渲染」，不是 60 秒这个数值。

### 4.3 ETag 在浏览器里真的命中 304

做法：探针页用应用自己的 `withAccessToken` 拿 access token（不碰口令），对同一个接口发四跳。

| 跳 | 请求条件 | 期望 | 实测 |
| --- | --- | --- | --- |
| ① | 不带条件 | 200 + 有 etag | 200，`etag=W/"7VwST6FD..."`，`cache-control=private, max-age=0, must-revalidate` |
| ② | 带正确 etag | 304 | **304** |
| ③ | 带错误 etag | 200 | 200（反例成立，不是恒 304） |
| ④ | 再不带条件 | 200 | 200（反例成立，不是请求过就 304） |

**这一项第一次是失败的**：四跳全 200、响应里既没有 `etag` 也没有 `cache-control`。原因不是代码 —— 是容器里跑的 api 还是 15:40 的镜像，而 ETag 是 16:20 才写进 `routes/ops.ts` 的。重建 api 镜像（18 秒）之后四跳立刻符合预期。教训：**接口行为类改动在容器里验证前必须先 `--build`**，判据不是「容器起来了」，而是「响应头里有 etag」。

四道门禁：test 924 项 0 失败（api 263、web 253、desktop 289、shared 119）、lint、typecheck、format:check 全部通过。api 从 259 增至 263 是新增的 4 项 ETag 用例，desktop 从 287 增至 289 是新增的 2 项超时用例。

## 五、已知缺口（不修，但要看得见）

### 5.1 渠道树接口从未被触发

`flow-shopsource` 页面在浏览器里只发出 `getCurrentTime` 与 `shop_source_overview_v4` 两个请求，渠道树那个接口一次都没有出现过。`data/csv30/flow-shopsource/02_flow_shop_source_tree_platform_support__data.csv` 存在，说明数据本身拿得到，但那是 CSV 下载路径，不是网络抓取路径。

后果：日增永远不会更新渠道维度，看板渠道榜停在最近一次全量回填的值。`verify-daily.mjs` 把它标为**提示**而不是缺口，因为它不会自己好。

修法有两条，都需要在真实浏览器里试：给这一页补一次交互（点开渠道分组），或者直接构造那个接口的请求。本轮没有登录态，无法验证，所以没有动采集逻辑。

### 5.2 `running` 没有过期判定

事务失败且补写 `failed` 也失败时，运行记录会停在 `running`。界面显示「采集中」并配告警色，不会无声无息，但它不会自己过期。判"多久算超时"要跟着采集耗时分布走，属于另一件事。

### 5.3 多店接入前的两处单店假设

`latestCoveredDate()` 不带 `shopId`，五店都有数据后默认区间锚点会错位。维度快照只能"最接近"匹配，查近 7 天时选中的是 30 天快照，商品榜实际是 30 天的榜。两者都在单店下无害，多店前必须改。

### 5.4 计划任务的运行身份

采集依赖已登录的图形会话，服务账户跑不起来。这条决定 `run-pipeline.ps1` 能不能挂计划任务，需要人来定。
