### 3.1 数据与迁移

**数据库用容器提供，数据落在宿主机命名卷 `fanhe-work-pgdata`，不随介质移动。** PostgreSQL 的随机 IO 很重，而工作空间在闪存 U 盘上，既慢又有写入寿命限制。代价就是换机后数据库不在，需要重新 `up` 一次或从备份恢复。这是刻意的取舍，写在 `docker-compose.yml` 的注释与 README 里。

**排序规则在建库时固定为 ICU 的 `zh-CN`，不是默认的 `C`。** `C` 排序按 UTF-8 字节序比较，对中文相当于按码位排，列表里的中文姓名不会按拼音顺序出现。实测差别：ICU `zh-CN` 给出 `陈 < 李 < 王 < 张`，`C` 给出 `张 < 李 < 王 < 陈`。这一项事后更改需要重建数据库。

**Prisma 钉在 7.10.0，两个包必须同版本，不要用 `@latest`。** `prisma` 的 `latest` 标签当前指向 8.0.0-rc，而 `@prisma/client` 的 `latest` 是 7.10.0，用 `@latest` 会把 CLI 拉到 RC 上与客户端错开。

**Prisma 7 的三处硬性差异**：SQL 提供方强制要求驱动适配器（PostgreSQL 用 `@prisma/adapter-pg` + `pg`）；连接串与迁移配置移到 `prisma.config.ts`；`.env` 不再自动加载，需自己 `import 'dotenv/config'` 且置于首行。

### 3.2 认证与令牌

**访问令牌与刷新令牌分工明确，不混用。** 访问令牌是 JWT（HS256，默认 15 分钟），无状态、不查库、不可撤销，所以必须短命；刷新令牌是不透明随机串（32 字节），只存 SHA-256 哈希、可撤销。把访问令牌也做成有状态的等于每个请求查一次库，把刷新令牌也做成 JWT 的等于放弃撤销能力——两种退化都会让设计里最有价值的那一半消失。

**刷新令牌用 SHA-256 而非 Argon2。** 密码是低熵的，必须用慢哈希抵抗离线爆破；刷新令牌是 256 位随机串，不存在「猜」的余地，慢哈希只会让每次刷新白付几十毫秒。用哈希的目的只有一个：拖库者拿到的是摘要，不能直接拿去用。

**登录失败只有一种响应。** 账号不存在 / 密码错误 / 被停用 / 被锁定全部返回同一句话，且都执行一次哈希校验以填充时间（用模块加载期现算的假哈希）。少了时间填充，响应耗时的稳定差别就足以枚举用户名。

**轮换的判定与写入必须在同一事务内**，并先用 `SELECT ... FOR UPDATE` 锁行。否则两个并发请求会各自签发一份新令牌，一次登录裂成两条都有效的链，而流程不报任何错。

**重放检测按时间区分并发与泄露。** 撤销原因为 `rotated` 且落在宽限期（`REFRESH_ROTATION_GRACE_SECONDS`，默认 10 秒）内算并发，只失败不撤链；超出算泄露，按 `familyId` 整链撤销。

**撤销分 `session` / `device` / `all` 三层，默认最小范围。** 写库用带 `revokedAt: null` 条件的 `updateMany`，登出幂等。**撤销不会让已签发的访问令牌立即失效**，最多再活一个有效期。

### 3.3 限速

**账号与 IP 两个维度各挡一类攻击，缺一不可。** 账号维度挡不住用户名枚举（不存在的用户名不产生计数），IP 维度挡不住换 IP 的分布式爆破。

**登录尝试单独建表 `login_attempts`，不复用 `audit_logs`。** 两者保留策略相反：审计长期保留，限速计数只需覆盖一个窗口且超期必须清理。

**被限速的请求不做哈希校验，也不写记录。** 否则限速本身成为放大器。

**限速返回 429 并带 `Retry-After`，是唯一对外可见的失败原因**，其余失败共用 401。

**窗口是滑动的，记录保留期必须显著长于窗口**（默认 7 天对 15 分钟），否则记录在滑完前被删、计数偏小、限速提前失效。清理挂在写入路径上，不引入定时任务。

### 3.4 授权

**权限点的唯一事实来源是 `packages/shared/src/permissions.ts`。** 服务端校验与前端菜单可见性引用同一份常量。命名固定三段式 `模块.对象.操作`。

**通配符的吃法取决于位置，错了不报错：**

| 写法                | 含义                                     |
| ----------------- | -------------------------------------- |
| `personal.*`      | 末尾 `*` 吞掉剩余全部段，覆盖 `personal.note.read` |
| `personal.*.read` | 非末尾 `*` 只匹配一段，只匹配 `personal.<对象>.read` |

一律让 `*` 吞掉剩余段，只读角色会静默拿到写权限。**展开只在种子阶段做一次，运行时 `hasPermission` 只做精确匹配**，不接受模式串。

**认证与授权分成两个 preHandler**：`requireAuth` 只认证，`requirePermission(code)` 认证加校验。401 与 403 的区别对客户端有意义。

**授权每次查库，不做缓存。** 权限点不放进访问令牌，否则撤权要等令牌过期才生效；TTL 缓存会把这条保证退化成「最多延迟 N 秒」且延迟取决于是否命中，排查时看不出来。真要优化就给角色加版本号。

**同一趟查询顺带读 `status` 与 `deletedAt`**，账号被停用或删除后已签发的访问令牌立即失效。

### 3.5 首次初始化

**判据是「存在任意 owner 账号」，不过滤状态与软删除。** 否则「先让 owner 不可用、再走初始化入口给自己建一个」就成了一条完整路径。代价是 owner 被全部删除后入口不会重新开放，恢复走 `pnpm db:create-owner`。

**并发初始化用 `pg_advisory_xact_lock` 串行化**，因为条件「owner 角色至多一个账号」跨行，普通唯一约束写不出来。哈希放在事务外算。

**账号标识规则的唯一实现是 `packages/shared/src/account.ts`。** `normalizeUsername` 用 `toLowerCase` 而非 `toLocaleLowerCase`（后者在土耳其语环境把 `I` 变成 `ı`）。归一放在应用层，库侧只留唯一约束。登录侧拆两个值：提交的原值写 `login_attempts`，归一后的值用于查询。

**恢复通道与 HTTP 入口共用同一份实现**，差别只在 `requireUninitialized` 这一个开关。密码只从环境变量读，不走命令行参数——参数会留在 shell 历史与进程列表里。

### 3.6 审计

**写入入口是 `apps/api/src/audit/audit.ts` 的 `recordAudit`，动作码词表在 `packages/shared/src/audit.ts`。**

**写入失败不能让主流程失败，但也不能静默。** 一次登录不该因为审计表出问题而登不进来；而记录缺失意味着「出了事却查不到痕迹」，与没出事一样糟。`recordAudit` 因此吞掉异常并出声，而不是向上抛。

**不许写入密码、令牌明文或哈希。**

**`actorId` 与 `actorName` 同时写。** 外键是 SetNull，账号删除后 `actorId` 置空，没有这份快照就答不出「谁做的」。

**四类不写**：被限速的登录、首次初始化被拒绝的那次（同属「被拒的请求不产生任何写入」）、重复登出（幂等，没撤销任何东西等于没有事件）、`user_unavailable`（合法客户端每次刷新都撞上，只有噪声）。

**失败的登录不填 actor。** 只在账号存在时才填，等于让 `actor` 列变成「账号存不存在」的旁路判据。

**动作码不拆成功与失败**，用 `result` 列区分。

### 3.7 测试

**用 Node 内置运行器，不引第三方框架。** `node --test <目录>` 在 Node 22 上不行（目录参数会被当成模块加载并报 `Cannot find module`），要用无参数的 `node --test` 自动递归扫描。

**api 测试必须串行（`--test-concurrency=1`）。** `setup.test.ts` 的判据是「全库没有 owner」，属全局单例状态，而 `permission.test.ts` 需要建一个 owner 角色的账号；并行时对方建的 owner 会落在判定与断言之间。

**每个用例用独立来源地址**（RFC 5737 的 TEST-NET 段），避免限速计数互相污染。测试数据统一带 `zz_test_` 前缀。

**`@fanhe/shared` 是构建型包**，`typecheck` 与 `test` 脚本都需前置 `pnpm --filter @fanhe/shared build`。

### 4.1 迁移目录名的字典序与应用顺序相反（已核验，无需处理）

`prisma/migrations/` 下两个目录，字典序是：

```
20261010082118_login_rate_limit   ← 字典序在前
20261010150103_init               ← 字典序在后
```

而 `_prisma_migrations` 里记录的应用顺序是 `init` 先、`login_rate_limit` 后。**两者相反。**

看起来像隐患：`login_attempts` 表与它的枚举定义在 `login_rate_limit` 里，如果 `init` 引用了它，按字典序应用就会失败。

**实测结论：不会失败，因为两个迁移互相独立。** `login_rate_limit` 只建自己的枚举与表，不引用 `init` 的任何对象；`init` 也不引用 `login_attempts`。

核验方式（在一个临时空库上跑完整链）：

```
建库 → prisma migrate deploy → 7 张业务表齐全 → prisma migrate status 报 up to date
     → pnpm db:seed → 11 权限点 / 4 角色 / 29 授权关联
```

两个迁移按字典序依次应用，全部成功，结果与主库一致。**结论：不需要重命名目录，也不需要调整任何东西。** 之所以记录下来，是因为将来新增迁移时若出现依赖关系，同样的「字典序与时间序不一致」就会变成真问题——那时要检查的不是 Prisma 的排序，而是新迁移是否引用了时间上更晚的对象。

> 待确认的成因：`init` 的目录名时间戳是 15:01:03，但它的 `applied_at` 是 07:09:27 UTC；`login_rate_limit` 的目录名是 08:21:18，`applied_at` 是 08:21:18 UTC。两组值对不上同一套时区解释，具体是当时手工创建还是时区混用，已无从追溯。不影响结论。

## 七、换机必做步骤

工作空间是 U 盘上的可移动目录，多台电脑轮换使用。**大部分内容随介质移动，但有几样不在介质上。** 下面按顺序列出。

### 7.1 先确认介质状态

如果换机时是整个目录拷过去的（不是 `git clone`），那么 `node_modules/`、各 `dist/`、`.workbuddy-ai/`、`.cache/` 都在，可以跳过 7.3 与 7.4。

如果是 `git clone` 或只带了受版本控制的文件，则必须走完 7.2 至 7.5。

### 7.2 数据库（不在介质上，必须重建）

**PostgreSQL 数据在宿主机命名卷 `fanhe-work-pgdata`，不随介质移动。** 新机器上数据库是空的。

```bash
# 1. 从工作空间入口进入（不能跳过，否则环境重定向不生效）
cd <工作空间根>
. ./infra/portable/ws-env.sh          # PowerShell 用 . .\infra\portable\ws-env.ps1
cd projects/fanhe-work

# 2. 准备连接串
cd apps/api
cp .env.example .env
#    编辑 .env，填 JWT_SECRET：
#    node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))"
cd ../..

# 3. 启动数据库并等到健康
docker compose up -d --wait

# 4. 建表与写种子
pnpm db:deploy
pnpm db:seed
pnpm db:ping
```

`pnpm db:ping` 会打印表与各表行数。预期：`permissions` 11、`roles` 4、`role_permissions` 29、`users` 0。

**然后走首次初始化**：启动服务后访问前端，按引导创建超级管理员（T1-08 的入口）。如果 owner 已被删除、入口不开放，用 `pnpm db:create-owner` 恢复（密码从环境变量读）。

**这条路径已实测。** 2026-10-10 在一个临时空库上跑过完整链：`migrate deploy`（两个迁移按字典序应用）→ 7 张业务表齐全 → `migrate status` 报 up to date → `seed` 写入 11 / 4 / 29。结果与主库一致。

### 7.3 依赖（不在介质上）

```bash
cd projects/fanhe-work
pnpm install
```

**必须经入口执行**，否则依赖会落到宿主机磁盘而不是工作空间的 `.cache/pnpm-store`，换机后状态就散了。检查方式：`node_modules/.modules.yaml` 里的 `storeDir` 应形如 `<工作空间根>/.cache/pnpm-store/v10`。

**预留时间按分钟到十分钟量级。** 瓶颈在网络链路而非源站，单次元数据请求要十几到几十秒。装一次 Prisma 相关的依赖大约需要 20 分钟，属预期范围，用后台任务跑。

安装时会有 `ignored build scripts` 提示，可以忽略——`onlyBuiltDependencies: []` 是刻意的。

### 7.4 构建产物（不在介质上）

```bash
pnpm --filter @fanhe/shared build      # 共享包是构建型，必须先建
pnpm db:generate                        # 生成 Prisma 客户端到 apps/api/src/generated/prisma
```

`pnpm build` 与 `pnpm typecheck` 都会自动跑 `prisma generate`，所以直接跑这两个也可以。但 `@fanhe/shared` 的 `dist` 缺失会让 api 报「no exported member」——根脚本的 `typecheck` / `test` / `db:seed` 都前置了 shared 的构建，直接调 api 内的脚本则不会。

### 7.5 状态文件与记忆

- `infra/portable/state/root.json` 逐机不同，**不需要**拷贝。入口首次运行时会按新机器重建，检测到根变化或主机变化会触发一次修复与健康检查。
- 健康检查随时可跑，只报告不修改：`infra\portable\ws-repair.ps1 -CheckOnly`
- `.workbuddy-ai/` 如果没随介质过来，本交接文档（`docs/HANDOFF-2026-10-10.md`）与 `docs/DEVELOPMENT-PLAN.md` 的第九章仍然完整覆盖了进度与判断，够继续开发。

### 7.6 验证环境

```bash
pnpm test              # 期望 shared 27 项 + api 85 项 = 112 项全绿
pnpm lint
pnpm typecheck
pnpm format:check
```

api 测试需要数据库可达，不可达时相关用例会跳过并在文件顶层打印告警。**跑完核对表行数**——`users` / `audit_logs` / `login_attempts` / `refresh_tokens` 应回到 0 行。

浏览器级验证需要额外起两个服务，且库必须处于未初始化状态：

```bash
ACCESS_TOKEN_TTL_SECONDS=60 pnpm dev:api   # 一个终端，有效期压短才能观察到续期
pnpm dev                                    # 另一个终端
pnpm --filter @fanhe/web test:e2e           # 库已初始化时会拒绝并打印重置命令
```

它会创建一个 `zz_e2e_owner` 账号，跑完需按脚本头部注释里的 SQL 清理。

### 7.7 换机后一定要记得的三件事

1. **入口。** 所有开发操作经 `infra/portable/ws-run.*` 或点源 `ws-env.*`，否则环境重定向不生效。
2. **路径含空格。** 工作空间路径 `fanhe Work` 含空格，脚本里所有变量必须加引号。
3. **编码。** bash 写 UTF-8 无 BOM，PowerShell 5.1 的 `Get-Content` 无 BOM 时按系统 ANSI 代码页解码。跨这两个环境传递含中文的清单文件时，读取侧必须显式 `-Encoding UTF8`。

## 八、当天发现并修正的缺陷

列在这里是因为它们都不报错，或者报出的位置具有误导性。

| 缺陷                           | 表现                                                          | 根因                                                                  | 修法                                     |
| ---------------------------- | ----------------------------------------------------------- | ------------------------------------------------------------------- | -------------------------------------- |
| 权限通配符展开                      | 种子报 17 条授权而设计应为 29，流程不报错、退出码 0                              | 非末尾 `*` 被当成吞掉剩余段                                                    | 区分末尾与非末尾两种吃法，补回归测试                     |
| `pg_advisory_xact_lock` 反序列化 | 首次初始化接口必然 500，`Failed to deserialize column of type 'void'` | 该函数返回 `void`，Prisma 驱动适配器无法反序列化                                     | 套一层子查询取整型常量。`typecheck` 与 `lint` 都发现不了 |
| 入口脚本无条件 `cd` 到根              | 项目移入 `projects/` 后命令在错误目录执行且不打印提示                           | 历史遗留的强制 `cd`                                                        | 保留调用者目录，仅当在空间外时回退到根                    |
| `DOCKER_CONFIG` 重定向          | `docker compose` 变成未知命令，`desktop-linux` 上下文消失只剩裸 `default`  | 该变量指向空目录，而那里存的是上下文与凭据                                               | 从重定向表中移除                               |
| api 测试并行                     | `setup.test.ts` 偶发失败，报库不干净但直接查库却干干净净                        | `permission.test.ts` 建的 owner 落在判定与断言之间                             | `--test-concurrency=1`                 |
| 审计测试残留 12 行                  | 门禁全绿但库里留有记录                                                 | 直接调 service 的测试 ip 为 NULL；`inject` 默认 `remoteAddress` 是 `127.0.0.1` | 前者在删账号前按 `actorId` 清理，后者显式给 `TEST_IP`  |
| 端到端断言依赖落地模块                | 再次登录后等待「权限点」文案超时，表现像登录失败                                  | T2-03 路由化后登出不改写地址栏，深链接决定再次登录落到哪个模块                            | 判据改为等「已登录外壳挂上」（账号菜单），与落地模块无关，见 9.23 |
| 端到端浏览器 profile 落在 U 盘        | 不报错。脚本注释称「放在系统临时目录」，而 `.tmp/` 下已积下两份共 45MB profile           | 工作空间把 `TEMP`/`TMP` 重定向到 U 盘上的 `.tmp/`，而 `os.tmpdir()` 读的正是这两个变量      | 改从 `LOCALAPPDATA` 推（不在重定向表中），非 Windows 退回 `os.tmpdir()`，见 9.25 |

**两条贯穿性教训：**

- **跑完不算验证，数字对得上才算。** 凡是「展开」「派生」一类逻辑，落库后要拿预期数量核对。
- **断言全绿不等于没有残留。** 数据库行的核对是另一步，不做就发现不了。

## 九、当天修正的文档偏差

核对过程中发现 `README.md` 两处与代码不符，已一并修正：

1. **入口脚本的行为描述过时。** 原文说「入口脚本会把当前目录切回工作空间根，所以传入的命令必须自带 `cd`」。该行为已在提交 `479bd83` 修正为「保留调用者目录，仅当在空间外时回退到根」，README 未同步。
2. **迁移清单不完整。** 原文只提了首个迁移 `20261010150103_init`。实际有两个迁移，且目录名字典序与应用顺序相反（见 4.1）。
