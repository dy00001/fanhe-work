## 一、项目整体目标与技术栈

### 1.1 目标

**梵禾 Work** 是一个桌面端个人工作台，用来管理软件启动通道、工作纪要、事件记录。走「账号权限 → 主框架 → 三板块业务 → 桌面外壳 → 服务端化 → 更新通道」七阶段路线，另计划外新开阶段七（账号与权限管理）。

设计上有两条贯穿全项目的判断值得留意，它们解释了大量看起来「过度设计」的地方：

- **权限定义跟着代码走，不跟着某台机器的数据走**。所以 `db:seed` 幂等并挂进了 migrate 容器，每次部署自动跑一遍，自动跑它又不会在任何环境留下默认口令账号。
- **服务地址可切**。同一个前端既能被 Electron 外壳内置服务反代，也能指向局域网或公网服务，所以 `apps/web` 从头到尾一行未改。

### 1.2 技术栈（实测自 package.json 与 schema）

## 三、核心模块与相互依赖

### 3.1 依赖方向（单向，无环）

```
                    packages/shared  ← 唯一被两端共享的构建型包
                   （11 个模块，不依赖任何运行时框架，不引入数据库客户端）
                            │
              ┌─────────────┴─────────────┐
              ↓                           ↓
        apps/api                    apps/web
     Fastify + Prisma            React + Vite
              │                           │
              └───────── HTTP ────────────┘
                            ↑
                    apps/desktop（Electron 主进程）
              · 内置静态服务，把 /api 反代到服务地址
              · agent.ts 经 import() 动态加载 api 的 TS 源码（一行未改）
              · update.ts 为不 import electron 的纯函数状态机
```

### 3.2 各模块职责

**packages/shared**（11 个模块，108 项测试）
跨进程类型与「两边必须严格一致」的字面量集合。`permissions.ts` 含 12 个权限点与通配符匹配（`personal.*` 与 `personal.*.read` 语义不同，段数不等即拒）；`navigation.ts` 是导航与路由的唯一事实来源；`version.ts` 提供版本比较四态 `same/outdated/ahead/unknown`。设计原则写在包头注释里：只放两边都要用的东西，塞进来会让它变成杂物间。

**apps/api**（39 条接口，226 项测试）
`app.ts` 负责组装：先挂认证容器，再 `initPermissionCatalog(ALL_PERMISSIONS)` 显式注入权限清单，最后注册各路由。有一处值得注意的取舍——把 Fastify 的 `removeAdditional` 改为 `false`，理由写在注释里：默认行为会静默丢掉 schema 未声明的字段，调用方会以为某字段生效而它从未被读取。

模块划分：auth（登录、双令牌、限速、权限中间件、账号管理）、launch（配置 + 历史 + 本机唤起代理）、note、event（含 event_logs 流水）、audit、version、setup。数据面 13 个 model，按「实体表带软删除 / 关联表只带 createdAt / 流水表只增不改」三条规则区分。

**apps/web**（97 项测试 + 149 项浏览器 e2e）
分层清晰且可离线验证：`lib/api.ts` 只拼地址不认会话 → `lib/session.ts` 的 `withAccessToken` → 各模块文件负责会话感知、拆信封、按错误码分流。展示规则（分组、逾期、时间转换、取值转文案）全部下沉到 `*-display.ts` 纯函数，因此不开浏览器也能测。`routes.tsx` 的路由表由 `NAV_ITEMS` 派生而非另写一份，两层嵌套路由保证切模块时不重挂外壳，侧栏折叠状态与滚动位置不丢。

**apps/desktop**（99 项测试 + 3 个验收脚本）
主进程职责：内置静态服务、配置持久化（落工作区 `.config/fanhe-work/service.json`）、启动自检、更新通道。`update.ts` 与 `diagnostics.ts` 都刻意做成不 import electron 的纯函数状态机，把「一串事件过来之后界面该说什么」与 Electron 解耦，从而可断言那些只能靠真发一版才能验的问题。

**infra/portable**
工作空间机制的唯一入口。所有包管理必须经 `ws-run.cmd`，裸跑 pnpm 会静默把 store 落到宿主机磁盘。

### 3.3 一个值得称道的实现细节

T6-03c 的自签证书必须同时装进 `CurrentUser\My` 与 `CurrentUser\Root`。病根在于 electron-updater 只在 `Status === 0`(Valid) 时才比对发布者，而 `TrustedPublisher` 只抑制弹窗、不让信任链变可信，导致每一次更新都被拒。作者用「同一个包、逐字节不变、只把自签根移出 Root」做对照实测：移除 → `阶段=error`，加回 → `阶段=downloaded`。因变量只有信任根而结果翻转，这才是「签名校验生效」的证据。

### 5.2 仍然成立的问题（已 grep 到源码）

**① 改密不会让已签发访问令牌失效（安全向）**
`users.passwordChangedAt` 在 `user-admin.ts` 两处被写入，但 `auth/tokens.ts` 的载荷仍只有 `sub / role / iat / exp`，从未读它。改密后旧的访问令牌在有效期内继续可用。

**② 账号名创建后不可改（功能缺口）**
`updateManagedUser` 的 `UpdateUserInput` 只有 `displayName / department / roleCode / status`，**没有 username 字段**。旧遗留项写的「改名复用 `normalizeUsername`」随 T7-01 改造已不再适用，当前状态是账号名根本改不了。若将来要做，改名必须走归一后查冲突，否则会撞唯一约束。

**③ 16 个占位导航项 `module: null`（实测数量精确吻合）**
这 16 个占位模块对已认证用户一律可见，权限点只管 `system` 与 `personal` 两段，将来模块增多时管理界面无法按模块分组展示。

**④ T5-05 访问策略暂缓（暴露面最大）**
`work.fanhe.dpdns.org` 任何拿到地址的人都能打开页面。业务接口与数据仍受登录保护，暴露在登录之前的是页面与静态资源。

**⑤ 浏览器 e2e 在 UI 落地对齐后未重跑**
上次实跑 149 项是在 UI 集成之后，7-13 的设计稿对齐改动（字体栈、悬停规则、滚动条）之后未重跑。
