# T7-03 版本迭代期间的可用性与手动更新方案

> 设计稿，2026-10-13。本文只做分析与方案设计，不含代码改动。
> 关联：`docker-compose.yml`、`apps/desktop/src/update.ts`、`apps/desktop/src/main.ts`、`apps/desktop/src/server.ts`、`apps/api/src/version/manifest.ts`、`apps/web/src/lib/api.ts`、`apps/desktop/electron-builder.yml`、`docs/T6-03-UPDATE-CHANNEL.md`。

## 零、结论摘要

1. 用户观察到的「断网、无法正常使用」是**四类故障的合并症状**，其中两类发生在发布窗口内且会自愈，另外两类发生在发布之后且不会自愈。把四者当成一个「网络问题」去找，必然找不到。
2. 根本原因是一次「版本迭代」同时改动了三个本应独立的层：服务端运行时、数据库结构、客户端产物。而服务端是**单实例替换式部署**，没有兼容契约，于是每次发布都必然产生一个「新服务端 + 旧客户端」或「没有服务端」的窗口。
3. 可行方案是**三条通道解耦加一条兼容契约**：服务端发布通道对客户端透明，客户端更新通道对业务透明，兼容仲裁通道负责在契约被撑破时强制收口。
4. 「由使用人手动选择是否更新」这一需求可以直接落地，改动点集中在 `autoInstallOnAppQuit` 与提示文案。但它会引入一个内在张力，见第七节，需要靠「最低支持版本」闸门兜底。
5. 建议分五步落地，第 0 步不需要写代码。

## 一、「断网」的六种机制

把症状按时间轴拆开，机制与判据如下。前两条属于「迭代期间」，后四条属于「迭代之后」。

### 1. 发布窗口内的连接中断（秒级到分钟级，自愈）

证据在 `docker-compose.yml`。api 服务是 `restart: unless-stopped`，执行 `docker compose up -d --build` 时，Docker 会停掉旧 api 容器再起新容器。这个窗口内所有到 `127.0.0.1:8787` 的连接被拒绝。

客户端侧的放大效应在 `apps/desktop/src/server.ts`。外壳内置服务把 `/api` 反代到 `serviceUrl`，`proxyToService` 里的 `fetch` 一旦失败，异常冒泡到 `handleRequest` 的 `catch`，返回 502 加一段纯文本「内置服务处理失败」。渲染进程拿到的是一个没有结构化错误体的 502，前端把它归一成 `ApiError`。用户看到的是操作失败，而不是「服务端正在更新」。

### 2. 迁移窗口（分钟级，自愈，但可能显著更长）

`docker-compose.yml` 里 api 依赖 `migrate` 的 `condition: service_completed_successfully`。这条约束本身是对的，它的代价是**迁移耗时全部计入停机窗口**。PostgreSQL 在大表上加列带默认值、加索引、改类型，都可能持有表锁。项目当前 13 张表、数据量小，窗口短；一旦有真实数据量，窗口会非线性增长。

### 3. 接口契约不兼容（持续，不自愈）

这是「软件不能用了」的真正主因。证据是 API 路径**没有版本前缀**，全部是 `/api/notes`、`/api/auth/me`、`/api/launch/profiles` 这样的形态，集中在 `apps/web/src/lib/api.ts` 一处调用。

一旦服务端升级做了以下任何一件事，旧客户端会持续失败：

- 响应字段改名或结构变化，旧客户端的解析逻辑落空。
- 新增必填请求字段，旧客户端提交被 AJV 拒绝（`app.ts` 已把 `removeAdditional` 改回 `false`，所以是明确拒绝而非静默丢弃）。
- 权限点集合增删，旧客户端持有的令牌权限不足，大面积 403。
- 令牌或会话语义变化，旧客户端进入 401 循环。

关键特征是**用户重启客户端也不会好**，因为问题在服务端侧。

### 4. 前端产物与外壳版本错配（持续，不自愈）

证据在 `apps/desktop/electron-builder.yml` 的 `extraResources`，它把 `../web/dist` 原样投进 `resources/web`。而 `apps/desktop/package.json` 的 `dist` 脚本只跑 `sync-version.mjs && tsc && electron-builder`，**不重建 web**。

这意味着「改了前端但忘了 `pnpm --filter @fanhe/web build`」会打出一个带旧界面的安装包，而且版本号是新的。工作记忆记载 v0.1.0 与 v0.1.1 两个包就带着 11:34 的旧产物，直接导致 T6-03b 的宿主分派没进客户端。这类故障的表现是「更新完了，但界面没变」，用户很容易误判成「更新失败」。

### 5. 隧道与网络层（秒级到分钟级）

`cloudflared` 用固定镜像 tag `cloudflare/cloudflared:2025.8.1` 且没有配置文件，正常 `up -d` 不会重建它。但只要出现 `--force-recreate`、改动 `command`、或改动 `.env.compose` 里的 Token，它就会被重建，Tunnel 需要重新与边缘建连，公网域名短暂返回 502 或 1033。

### 6. 签名信任根变化（持续，不自愈）

这一条与「断网」无关，但与「迭代之后客户端不能更新」直接相关，所以列入。`electron-builder.yml` 的注释与工作记忆都记着同一个判据：electron-updater 只在 `Status === 0`（Valid）时才比对发布者，自签根逐机导入 `CurrentUser\Root`，换证书等于换信任根，已装机器上没有新根，整段比对被跳过，每次更新被拒。**换签名证书不能与发新版安排在同一次迭代。**

## 二、根因

一次「版本迭代」当前同时改动了三件互相独立的事：

| 层 | 载体 | 变更频率 | 是否必须与客户端同步 |
| --- | --- | --- | --- |
| 服务端运行时 | api 容器镜像 | 每次发布 | 否 |
| 数据库结构 | `migrate` 容器 | 有数据模型改动时 | 否，但受兼容性约束 |
| 客户端产物 | NSIS 安装包 | 每次发布 | 是，但可以滞后 |

问题出在最后一行与第一行的关系上。客户端产物必须与某个服务端版本匹配，而它**无法被服务端单方面替换**，只能靠用户安装。当前系统缺少三样东西来承接这个事实：

1. **没有兼容契约**。API 无版本前缀，也没有「服务端承诺兼容上几个客户端版本」的书面约定。
2. **没有迁移纪律**。迁移与应用代码同批发布，且允许破坏性变更。旧客户端在新 schema 上运行，属于「未经声明的兼容」。
3. **没有仲裁机制**。当契约被撑破时，系统没有手段告诉用户「你必须升级」，只能表现为功能莫名失效。

结论：**当前的设计把「服务端可以随时升级」和「客户端必须同步升级」这两件事绑在了一起，而后者在物理上不可能即时完成。**

## 三、方案整体思路

核心是把耦合拆开，变成三条互不阻塞的通道，再加一条仲裁通道。

### 通道 A：服务端发布通道（对客户端透明）

目标：发布新版服务端时，旧客户端要么感知不到，要么只感知到一次短暂的重试。

三条要求。

1. **迁移与应用解耦，且迁移必须对当前线上代码向后兼容。** 迁移单独执行，执行期间旧代码仍能正常读写。这一条把「迁移耗时」从停机窗口里移出去。
2. **应用层零停机。** 新实例先起、健康检查通过、再切流量、旧实例延迟下线。单机形态下用两个 api 容器加 nginx upstream 切换即可实现，无需引入编排系统。
3. **不可用时给出明确的维护语义。** 服务端返回 503 加 `Retry-After`，外壳反代把上游的 503 原样透出（当前 `proxyToService` 已经透传状态码，这一条无需改动），前端识别 503 并显示「服务端正在更新，请稍候」，与真正的网络故障区分开。

### 通道 B：客户端更新通道（对业务透明）

目标：更新动作与用户当前正在做的事互不干扰，且安装时机由用户决定。

四条要求。

1. **更新源独立于业务通道。** 当前已是 GitHub Releases（`electron-builder.yml` 的 `publish` 段），保持。检查更新失败必须静默，不得弹窗、不得阻塞启动。
2. **检查与下载非阻塞。** `main.ts` 的 `wireAutoUpdater` 当前在启动后调一次 `checkForUpdates`，方向正确，保持。
3. **安装动作由用户点击触发。** 这是本次需求的核心。当前 `autoUpdater.autoInstallOnAppQuit = true`（`main.ts` 第 443 行），语义是「用户下次退出应用时自动装上」。这与「由使用人手动选择是否更新」冲突，需要改。
4. **已就绪状态必须持久可见。** `update.ts` 的状态机已有不变量 1（`downloaded` 不被后续事件抹掉），顶栏按钮由 `buildDesktopUpdateView` 决定可见性（T7-02b 已做）。这条基础已经在，只需把「自动装」改成「确认后装」。

### 通道 C：兼容仲裁通道

目标：当用户长期不更新、兼容窗口被撑破时，系统有明确且唯一的收口手段。

1. `/api/version` 扩展出 `minimumClientVersion` 字段。这个接口已经存在、无门禁、且刻意在登录前可用（`apps/api/src/version/manifest.ts` 的注释说明了这一点），是承载该字段的现成位置。
2. 客户端启动时读它。低于门槛则进入「必须更新」态，顶栏按钮变成不可忽略的提示，业务功能给出明确说明而非静默失败。
3. 服务端记录请求携带的客户端版本，用于判断「旧版本客户端是否已全部退场」，从而决定何时可以做收缩类迁移。

### 为什么不直接做 API 版本化

这是需要辩证看待的一处取舍。把路由改成 `/api/v2` 是业界的彻底方案，它的代价同样真实：两套路由注册、两套类型定义、两套契约测试、以及跨版本的会话与权限模型对齐，全部要并行维护。

本项目的具体条件是：单用户内部工具、只有一个自研客户端、客户端数量可控、服务端与客户端同仓库同发布节奏。在这个条件下，**「N-1 兼容加契约快照测试」比「双版本路由」的成本低一个量级，且能被门禁机械拦住**。等到出现第三方集成方或客户端数量不可控时，再引入版本前缀，那时的迁移成本远低于现在。

## 四、关键约束

### 约束 1：旧版本可用性

服务端承诺兼容**上一个**客户端版本（N-1）。具体含义是：新增字段一律可选或有默认值；不删字段、不改字段语义；不新增必填请求字段；权限点只增不减。

### 约束 2：迁移必须是扩展收缩两步走

- **扩展阶段**（随发布一起）：只加。加可空列、加新表、加新索引（PostgreSQL 用 `CREATE INDEX CONCURRENTLY`）。旧代码不受影响。
- **收缩阶段**（滞后至少一个发布，且确认旧客户端已退场）：删旧列、删旧表、收紧约束。

判据可以机械检查：**任何一次发布的迁移里出现 `DROP` 或 `ALTER ... SET NOT NULL`，就必须能回答「旧客户端现在还在跑吗」。**

### 约束 3：更新推送与业务解耦

更新检查走 GitHub Releases，与 `/api` 通道无任何依赖关系。这一点当前已经成立，需要保持并加一条断言防回归：**服务端不可达时，更新通道仍能正常工作。**

### 约束 4：手动确认更新的流程

需要明确的流程如下。

1. 客户端启动后静默检查。
2. 有新版本则后台下载，顶栏出现进度按钮。
3. 下载完成进入「已就绪」，按钮文案从进度变成可点击的「重启更新」。
4. 用户点击才安装并重启。用户不点，则本次会话不受影响。
5. 用户正常退出应用时**不自动安装**。这是与当前行为的唯一实质差异。
6. 版本过旧、低于 `minimumClientVersion` 时，提示从「可更新」升级为「必须更新」，此时才允许打断业务。

第 5 条需要权衡。当前「退出即装」的设计理由是「桌面工具会被开一整天，用户不会主动去想有没有新版」（`main.ts` 注释原话）。改成手动后，用户可能长期不点。这正是第七节要讨论的张力，而闸门（第 6 条）是它的解药。

### 约束 5：回滚能力

- 服务端镜像打版本 tag，保留上一版，能一键切回。
- 数据库迁移若不可逆，必须准备前向修复脚本，不能假设「回滚 = 反向迁移」。
- GitHub Release 上的历史资产**不删除**，否则回滚的客户端下载不到对应版本。

### 约束 6：签名身份稳定

换签名证书等于换信任根，会打断已装机器上的整条更新链路。因此**签名证书的轮换必须单独安排一次发布，不与功能发布合并**。`signing:check` 与 `verify:pack` 第六节的身份比对是这条约束的机械判据。

### 约束 7：前端产物必须在打包前重建

这是最容易被忽略、代价却最直接的一条。打包链路不重建 web，所以「先 `pnpm --filter @fanhe/web build` 再打包」必须成为发布清单里的硬步骤，而不是靠记忆。

🔴 **2026-10-14 补充：光有这一步不够，而且「靠纪律」已经被证伪了。**

这条纪律**被执行过**，`v0.1.2` 还是带出了陈旧产物 —— 因为漏掉的不是「有没有重建前端」，而是**更靠前的一步**：前端产物的版本号是**构建期**从仓库根 `package.json` 文本替换进去的，所以**版本号必须在重建前端之前就定下来**。实际发生的是前端 22:41 构建（版本号还是 `0.1.1`），版本号 22:57 才提到 `0.1.2`，安装包 22:54 打出 —— 用户装完 `0.1.2`，菜单那行显示 `v0.1.1`。

正确的三步顺序是：**先定版本号 → 再 `pnpm --filter @fanhe/web build` → 最后 `dist`**。

而「必须成为硬步骤，而不是靠记忆」这句话，正确做法不是把它写得更醒目，而是**让它不再依赖记忆**：现在有两道机械判据 —— 打包前 `scripts/check-web-build.mjs`（`dist`/`dist:dir` 的第一步，不符即拒绝打包）、打包后 `verify-pack.mjs`「二·补二」。判据是产物**自报的版本号** == 仓库根版本，**不含需要随发版维护的常量**，因此不会在下次发版时静默失效。详见 `docs/WORK-STATUS.md` 4.1.18。

## 五、落地步骤

### 第 0 步：发布纪律（零代码，立即生效）

1. 发布前按**三步**执行：**先定版本号（改仓库根 `package.json` 并提交）→ `pnpm --filter @fanhe/web build` → 打包**。第一步必须早于第二步，理由见约束 7。**现在有机械判据兜底**：`pnpm --filter @fanhe/desktop check:web`（`dist`/`dist:dir` 已内置为第一步）。
2. 服务端发布时只重建受影响的容器，避免连带重建 `cloudflared`。当前 `ws-compose.cmd` 会把参数透传给 `docker compose`，因此可以显式指定服务名。
3. 发布安排在低使用时段，并提前告知使用人。

这一步不解决根本问题，但能把故障概率降到最低，且今天就能做。

### 第 1 步：客户端改为手动确认更新

改动集中在两处。`main.ts` 的 `autoUpdater.autoInstallOnAppQuit` 由 `true` 改为 `false`；`update.ts` 的状态机不需要改，它已经支持「已就绪等待确认」。文案需要同步修改，`main.ts` 第 396 至 401 行的注释明确写着「重启后生效」这句话成立的前提就是那个开关为真，改开关必须改文案。

`--update-probe` 探针本来就显式关掉了这个开关（`main.ts` 第 543 行），改动后它与正常路径一致，探针代码可以简化。

### 第 2 步：客户端容忍服务端短暂不可用

在 `apps/web/src/lib/api.ts` 的 `request` 层加分类处理：识别 503 与网络层失败，配合退避重试（例如 1 秒、3 秒、7 秒三次），并对 503 显示「服务端正在更新」的明确提示。这一步让通道 A 的短窗口对用户不可见。

### 第 3 步：迁移纪律与契约快照测试

1. 在 `DEVELOPMENT-PLAN.md` 或独立文档里把约束 2 写成发布检查项。
2. 加一条契约快照测试：把当前 API 的响应结构固化成快照，任何破坏性变更会让测试变红。这条测试的价值在于它把「兼容性」从一个口头约定变成门禁能拦住的断言。

### 第 4 步：最低支持版本闸门

在 `/api/version` 响应里加 `minimumClientVersion`，客户端读取并据此决定是否进入强制更新态。这个字段的来源可以是服务端配置，也可以与 `package.json` 的版本号做算术。

### 第 5 步：真正的零停机

起两个 api 容器，nginx upstream 指向它们，切换时先起新的、健康检查通过、`nginx -s reload`、旧容器延迟下线。这一步成本最高，建议在前四步稳定运行后再做。

## 六、注意事项

1. **`service_completed_successfully` 这条依赖是窗口的放大器。** 它保证正确性，代价是 api 启动被迁移时长绑定。解耦迁移是通道 A 的第一条要求，理由在此。
2. **外壳的 502 与真正的网络故障在界面上无法区分。** 当前 `handleRequest` 的兜底返回 502 纯文本，前端只能归一成 `ApiError`。第 2 步要解决的就是这个可观测性问题。
3. **`index.html` 必须每次回源。** `server.ts` 的 `sendFile` 已经对 `index.html` 设 `no-store`，其余资源设长期缓存。这条在发版链路里是必要的，改动缓存策略前要意识到它与「发版后外壳加载旧入口」直接相关。
4. **菜单里的版本号是构建期常量。** 更新成功后菜单仍显示旧号，判据必须用 `app.getVersion()`。这一点会干扰「用户以为自己没更新成功」的判断。
5. **客户端与服务端版本号是两套。** `/api/version` 读的是仓库根 `package.json`（`manifest.ts` 的 `readProductVersion`），桌面端版本在 `apps/desktop/package.json`，两者由 `sync-version.mjs` 在打包时同步。设计闸门时要明确用哪一个。
6. **单机单实例没有真正的零停机能力。** 第 5 步的前提是有地方跑第二个实例。在开发机上这一点成立，但要占用额外端口与内存。
7. **「用户不更新」是常态而非异常。** 任何依赖用户主动行为的机制，都要假设用户会长期不动，因此闸门不是可选项。

## 七、辩证：方案的代价与内在张力

这个方案有一个无法通过工程手段消除的矛盾，值得写清楚。

**手动确认更新与兼容窗口天然冲突。** 用户越是有权不更新，旧版本停留的时间就越长，服务端需要维护的兼容面就越大。极端情况下，兼容窗口会被用户行为无限拉长，最终要么被迫放弃兼容（旧版本突然失效），要么被迫冻结服务端演进。

三条缓解路径，各有代价。

- **加长兼容窗口**：服务端维护 N-2、N-3 的兼容，成本随 N 增长，且每多一个版本就多一套要测的组合。
- **加闸门强制更新**：把「自愿」变成「限期自愿」。代价是它削弱了本方案的核心诉求，用户在某一天会被强制打断一次。
- **加快客户端更新成功率**：把闸门触发频率降到最低。这是最值得投入的方向，而它依赖第 1 步的提示设计与第 2 步的可用性。

我的判断是三者都要用，但重心放在第三条。手动确认更新的真正价值在于「把打断的时机交给用户」，而闸门的存在保证了这种自由有一个明确的边界。**用户获得的是「什么时候更新」的选择权，而非「是否永远不更新」的权利。** 这一点应当在产品文案与内部约定里同时讲明，否则将来第一次触发强制更新时会被理解为「说好的手动呢」。

另一处需要警惕的是**方案的复杂度本身**。第 5 步的蓝绿部署、第 3 步的契约快照、第 4 步的闸门，每一项都增加维护面。对一个单用户内部工具而言，第 0 至 2 步已经能解决绝大部分实际困扰，第 3 至 5 步应当按实际痛感逐步引入，而非一次性上齐。

## 八、验证方式

1. **窗口可测**：发布期间用脚本持续打 `/api/health`，记录失败请求数与非零耗时，量化窗口长度。当前没有这项数据，所以「断网多久」目前只能靠感觉。
2. **契约可测**：契约快照测试（第 3 步）是兼容性的机械判据。
3. **更新链路可测**：`--update-probe` 已能把整条更新链路变成可离线重复的断言（`main.ts` 第 530 行起）。改完 `autoInstallOnAppQuit` 后要重跑它。
4. **旧版本可用性可测**：保留一个旧版客户端安装包，每次服务端发布后用它跑一遍核心流程。这是唯一能直接验证约束 1 的手段。
