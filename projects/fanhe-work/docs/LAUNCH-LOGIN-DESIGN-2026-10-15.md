# 梵禾 Work「一键登录」两个新需求的设计分析

> 日期：2026-10-15　范围：`projects/fanhe-work` 桌面端「一键启动」板块
> 前置：`docs/LAUNCH-OPTIMIZE-2026-10-15.md` §2.1~§2.9（均已实施）
> 本文是**设计分析**，不含代码改动。落地前需先对 §10 的四条未决项拍板。

---

## 0. 结论先行

| 问题 | 结论 |
|---|---|
| 能不能做 | **能，但要分层做，且必须承认「自动填密码」这一层天然脆弱。** |
| 密码存哪 | **主进程 `safeStorage`（Windows 下即 DPAPI）加密后落 `userData`**，绝不进服务端数据库、绝不进共享包。 |
| 密码怎么给脚本 | **脚本从子进程 stdin 读**，不用 `-EncodedCommand`（base64 在命令行里可被 WMI 读到）。 |
| 怎么填 | **`SendInput` + `KEYEVENTF_UNICODE` 走纯键盘序列（账号 → Tab → 密码 → Enter）**，不用剪贴板、不用 UIA 定位控件、不用 CDP 注入。 |
| 微信侧 | 只做「配几个拉起几个 + 把 N 个扫码窗排开」，**一个键都不敲**（沿用现有 `wechat: false`）。 |
| QQ/千牛多账号 | **同一个客户端必须串行**（拉起 → 等登录窗 → 填 → 等窗关闭 → 再拉下一个），不能并发。 |
| 最大风险 | **账号风控**（滑块/短信/限登）与「**把密码打进已登录的主界面**」。前者要靠「默认关闭 + 不盲目重试」，后者要靠「确认这确实是登录窗」的判据。 |
| 既有边界 | 共享包里那句「工作台不保存任何第三方账号的密码」**不需要推翻** —— 把「工作台」限定为**服务端/工作空间**，本机凭据库不在其内。这条边界要改写得更精确，而不是删掉。 |

## 1. 需求拆解与现状盘点

### 1.1 两条需求各自要的是什么

**需求一（微信）**：微信是扫码登录，不做账号密码。配置 N 个微信启动项 → 一次动作拉起 N 个微信登录窗，各自出二维码，用户挨个扫。

拆出来是三件事：
1. 一次动作触发 N 条配置（**已有**：`launch:runMany` / `runLaunchProfiles`，§2.2）。
2. 真的起来 N 个**独立进程**（**不是现成的**：微信有单实例互斥量，连点只会激活已有窗口 —— 现有代码注释已承认这一点）。
3. 让用户能顺利扫到 N 个码（**没有**：N 个窗口散在任务栏里，用户要自己找）。

**需求二（QQ / 千牛）**：支持账号密码登录。客户端自带的「记住密码 + 自动登录」只能记一个账号，多账号做不到。要在配置页新增账号密码记录（**仅本地**），多账号时用内置脚本在相应位置自动填写并登录。

拆出来是五件事：
1. 配置页有账号/密码字段（**没有**）。
2. 密码有本地加密存储（**没有**，但 `credential.ts` 已有同构实现可参照）。
3. 密码能从主进程安全地送到脚本（**没有**）。
4. 脚本能定位登录窗并填对位置（**没有**，现有脚本只会敲一个 Enter）。
5. 多账号时不串台（**没有**，且这是最容易出错的一环）。

### 1.2 现有代码已经给了什么（逐文件）

| 文件 | 已有的能力 | 缺口 |
|---|---|---|
| `apps/desktop/src/launch-login-click.ts` | `shouldClickLogin(software)` 软件级开关；`clickLoginAfterLaunch(software, pid)` best-effort；`buildLoginClickScript(pid)` 用 `EnumWindows` + `AttachThreadInput` + `SetForegroundWindow` + `keybd_event(0x0D)` 把登录窗带到前台敲 Enter | 只敲 Enter；**spawn 后立即执行，窗口往往还没出现**（文档里已记为「实测恒 `no-window`」）；没有填表能力 |
| `apps/desktop/src/main.ts` `scheduleLoginClick` | spawn 成功后 fire-and-forget，结果只进日志，绝不阻断启动结果 | 无等待、无重试、无凭据 |
| `apps/web/src/lib/credential.ts` | WebCrypto AES-GCM + `extractable:false` 密钥入 IndexedDB，密文 + IV 入 localStorage；三条硬约束（明文不落盘 / 密钥读不出来 / 凭据不出本机） | **跑在渲染进程**，主进程读不到；文件里已自陈「阶段四应换成主进程 `safeStorage`」 |
| `apps/api/src/launch/agent.ts` | `RUN_DEDUPE_WINDOW_MS = 3000`，**按 `profile.id` 去重**（不是按软件）；`buildLaunchEnv()` 剔 `NODE_OPTIONS`/`ELECTRON_*` | 无登录概念 |
| `packages/shared/src/launch.ts` | `LaunchProfile` 明确**没有密码字段**；注释写「工作台不保存任何第三方账号的密码……免密只能走 OS 凭据接口（Windows DPAPI 或 Electron safeStorage），属阶段四之后的事」 | 这条边界现在**到了该被触发的时刻** |
| `apps/web/src/components/launch/LaunchProfileDialog.tsx` | 五个字段：软件 / 显示名 / 可执行文件路径（+一键检测）/ 启动参数 / 图标；`validate()` 全部用共享包规则 | 无账号密码字段 |
| `apps/desktop/src/config.ts` | 建立了「工作区 `.config/fanhe-work/` 放跟着工作空间走的配置」这条约定，并**明确说凭据不跟着走** | 凭据该落在哪已有结论（`userData`） |
| `apps/desktop/src/launch-registry.ts` | 已有从注册表推主程序路径的能力（读 `DisplayName`/`InstallLocation`/`DisplayIcon`） | 与本次无关，但说明「读注册表」在本项目是被允许且已实现的手段 |

### 1.3 三处既有边界与冲突（必须先裁决）

**冲突一：共享包说「不保存密码」，新需求要求「保存密码」。**

共享包原话是「**工作台**不保存任何第三方账号的密码」。这句话里「工作台」的所指需要收窄：

- 它**不该**指「这台电脑上的客户端」—— 本机凭据库是明确被它许可的（原话紧接着就写了「免密只能走 OS 凭据接口（Windows DPAPI 或 Electron safeStorage）」）。
- 它**该**指「服务端 + 共享包 + 版本控制里的任何东西」。

**裁决**：不推翻这条边界，而是把它改写得更精确 ——「工作台（服务端 / 共享包 / 数据库）不保存任何第三方账号的密码；本机凭据库只存 OS 加密后的密文，且**只在本机解密**」。据此：
- **共享包零改动**（不加密码字段）。
- **数据库零迁移**（不加密码列）。
- 配置与凭据的关联**用本地映射**（见 §3.2），不引入 `credentialId` 列。

**冲突二：密码一旦过 IPC，就进了渲染进程。**

渲染进程是 `apps/web/dist` 里的 JS，同源 XSS 就能读。`credential.ts` 的注释已经把这条说清楚了：「一次同源 XSS 就能调用它解密……阶段四的 Electron 外壳落地后，应把本文件的实现换成主进程的 `safeStorage`」。

**裁决**：**密码永不出主进程**。渲染进程只负责「提交时把用户刚输入的明文交给主进程加密保存」与「显示掩码后的账号」；**读取路径上，明文只在主进程内存在**（主进程解密 → 拼脚本 → 走 stdin → 子进程用完即弃）。渲染进程拿不到任何已存密码。

**冲突三：现有 §2.4 的时序是错的（spawn 后立刻点）。**

文档已记：「当前登录点击在 spawn 后立即执行、客户端窗口往往尚未出现，实测恒 `no-window`」。填表要求窗口存在且**已可交互**，比敲 Enter 更苛刻。这条必须先修，否则新需求无从落地。

**裁决**：把后置动作从「spawn 后立刻 fire-and-forget」改成「**等窗口出现 → 判定是登录窗 → 执行 → 判定结果**」的四段流水线（见 §5.1），并给整条流水线设总超时。

## 2. 整体实现思路与技术选型

### 2.1 三层切分

```
┌─ 配置层（服务端 DB + 共享包，零改动）
│   LaunchProfile：software / name / executablePath / args / icon / sortOrder
│   —— 只描述「启动什么」，不描述「用谁的账号」
│
├─ 凭据层（本机，主进程独占）
│   CredentialVault：profileId → { account, password }
│   磁盘 = safeStorage 密文；明文只存在于主进程内存
│   —— 只描述「这条配置该填什么」
│
└─ 执行层（本机，主进程 → PowerShell 子进程）
    spawn → 等登录窗 → 填表 → 判定 → 记录
    —— 只描述「怎么把凭据放进那个窗口」
```

三层各自的失败互不牵连：凭据层坏了（换机解不开）只降级成「只唤起不填表」；执行层坏了只降级成「用户手动输一次」。**这是整套设计的核心韧性来源**，也是它比「把密码塞进 `args`」高明的地方。

### 2.2 技术选型表（含「考虑过并否决」）

| 环节 | 选型 | 理由 / 否决理由 |
|---|---|---|
| 凭据加密 | Electron `safeStorage`（Windows = DPAPI） | 密钥由 OS 托管，**渲染进程根本拿不到密钥**；`credential.ts` 与共享包两处都已预告这条路径。 |
| 凭据落盘位置 | `app.getPath('userData')/credentials.enc` | 与 `config.ts` 已确立的语义一致：「凭据不随工作空间移动」。放 U 盘上只会得到「文件在、解不开」的困惑。 |
| 凭据传输 | 新增 IPC `credential:status` / `credential:save` / `credential:delete` | 与既有 `launch:*` 通道同构；**没有 `credential:get`（读明文）这个通道**，从接口层面杜绝渲染进程拿到已存密码。 |
| 输入手段 | `SendInput` + `KEYEVENTF_UNICODE` | 纯键盘序列，**不认坐标、不认控件文字**，与 §2.4 敲 Enter 的思路一脉相承，最能抗客户端改版；且能输入中文/特殊字符（`keybd_event` 只能发 VK 码，打不了非 ASCII）。 |
| ~~剪贴板粘贴~~ | **否决** | 密码会落进系统剪贴板，被其它程序读、被 `Win+V` 剪贴板历史持久化。用 `KEYEVENTF_UNICODE` 可以完全绕开。 |
| ~~UIA 定位控件后 SetValue~~ | **否决（保留为探针项）** | QQNT 是 Electron 应用，UIA 拿到的往往只是一个 WebView 节点、「空树」，内部输入框在渲染进程里不可见（社区共识）。且依赖客户端开启无障碍。**脆弱度高于键盘序列**，不值当。 |
| ~~CDP / `--remote-debugging-port` 注入~~ | **明确否决** | 要改客户端的启动参数、等于给第三方进程开一个本机任何程序都能连的控制通道。这已经越过了「唤起并辅助输入」的边界，进入「控制他人进程」的范畴，且有合规风险。 |
| ~~驱动级模拟（DD 虚拟键鼠）~~ | **明确否决** | 需要装内核驱动、绕过反作弊/反外挂体系，性质同上。 |
| 多实例 | 按软件分策略 + **一次性探针** | 千牛原生支持多开（双击快捷方式即新窗口新账号，社区资料一致）；微信需互斥量绕过类技巧；QQNT 待探针。**不硬编码假设，探针结果落盘**。 |

### 2.3 端到端时序（QQ / 千牛，多账号串行）

```
用户点「一键登录全部」
  │
  ├─ 取配置列表（服务端），按 software 分组
  │
  ├─ 微信组：并发 spawn 全部 → 等各自登录窗出现 → 把 N 个窗口平铺排开 → 结束
  │
  └─ QQ / 千牛组：逐条串行
       for profile of group:
         spawn(profile)                    ← 已有 runShellLaunchProfile
         waitForLoginWindow(pid, 15s)      ← 新增：轮询 EnumWindows 找属于该 pid 的可见窗
         if 未出现 → 记 outcome=no-window，跳到下一条
         confirmIsLoginWindow(hwnd)        ← 新增：判定「这确实是登录窗」（§5.4）
         if 不确认 → 只敲 Enter（退回 §2.4 行为），记 outcome=unverified
         解密凭据（主进程内）
         if 无凭据 → 只敲 Enter，记 outcome=no-credential
         fillLoginWindow(hwnd, account, password)   ← 新增：纯键盘序列
         等待登录窗消失（最多 20s）
         if 消失了 → outcome=success
         else → outcome=maybe-captcha（**不重试**，交还用户）
```

**关键：串行的不是 spawn，是整条流水线。** 理由见 §6.2：单实例客户端下「并发 spawn」的结果是第二个请求只把第一个窗口激活，于是第二条凭据会被打进第一个账号的窗口。

## 3. 配置页面的字段与数据结构设计

### 3.1 表单字段（现状 + 新增）

`LaunchFormValues` 现有五个字段，新增一个**条件字段组**：

| 字段 | 显示条件 | 控件 | 说明 |
|---|---|---|---|
| 软件 | 恒显示 | 按钮组（已有） | — |
| 显示名 | 恒显示 | Input（已有） | — |
| 可执行文件路径 | 恒显示 | Input + 一键检测（已有） | — |
| 启动参数 | 恒显示 | Textarea（已有） | — |
| 图标 | 恒显示 | 图标选择（已有） | — |
| **登录方式** | 恒显示，**只读** | 一行文字 | 微信 → 「扫码登录，无需密码」；QQ/千牛 → 「账号密码」；自定义 → 「不自动登录」 |
| **账号** | `software ∈ {qq, qianniu}` | Input | 编辑态显示掩码（`138****8888`）+「显示完整账号」按钮 |
| **密码** | `software ∈ {qq, qianniu}` | Input `type=password` + 显示/隐藏 | **编辑态恒为空**，placeholder 写「已保存（留空则不修改）」；旁边一个「清除已保存密码」按钮 |
| **登录后自动填表** | `software ∈ {qq, qianniu}` | 开关 | 默认开。关掉则只唤起 + 敲 Enter（退回 §2.4） |
| **说明行** | 有账号字段时 | 一行小字 | 「密码经本机系统加密后保存在这台电脑上，不会上传。」 |

**为什么要「编辑态密码框恒为空」**：一旦把已存密码回填到 `<input value>`，明文就进了 DOM，devtools、React DevTools、任何同源脚本都能读到 —— 那等于把 §1.3 冲突二的裁决作废。空 + placeholder 是唯一正确的做法。

**为什么「登录方式」是只读的**：它由 `software` 决定，不构成一个独立选择。做成可选项只会多出「选了微信又要求填密码」这种无意义组合。

**为什么「自动填表」开关放在单条配置上而不是只按软件**：现有 `shouldClickLogin` 的注释已经预告了这个扩展点（「将来若要把开关下放到单条配置，只改这一个函数」）。但**为了零迁移**，建议第一版仍按软件级默认值（qq/千牛开、微信/自定义关），单条覆盖作为后续 —— 见 §10 未决项。

### 3.2 数据结构

**共享包 / 数据库：零改动。** 不加密码字段、不加 `credentialId` 列。

配置与凭据的关联用**本地映射**：

```ts
// apps/desktop/src/credential-vault.ts —— 主进程内部结构
type StoredCredential = {
  account: string
  password: string
}

// 磁盘格式（明文外壳，密文内核）
type CredentialVaultFile = {
  v: 1
  items: {
    profileId: string          // 与 LaunchProfile.id 对齐（uuid，跨机稳定）
    label: string              // 用户可见的提示，取配置显示名，非机密
    blob: string               // base64(safeStorage.encryptString(JSON.stringify(StoredCredential)))
    updatedAt: string
  }[]
}
```

**为什么用 `profileId` 做键而不是给配置加一列**：
- `LaunchProfile.id` 是服务端生成的 uuid，跨机稳定，天然适合做本地映射的键。
- 加一列 `credentialId` 意味着：一次 Prisma 迁移 + 共享包契约变更 + 「这一列指向的本机凭据不存在」这个新状态要额外表达。而**用 `profileId` 做键时，同一个「不存在」状态自然表现为「本机凭据库里没有这一条」**，不需要任何新概念。
- 删除配置后本地留下孤儿条目是**无害的**（它永远不会被读到），在下次写库时顺手清理即可。

**为什么明文外壳里留 `label`**：它取自配置的显示名，而显示名本来就在服务端 DB 里，**不构成额外泄露**；它的用处是「换机后凭据解不开」时，还能告诉用户「这台机器上原本存着『QQ · 工作号』的密码」。若整个条目全加密，那种情况下用户只会看到一片空白。

### 3.3 新增 vs 编辑的提交流程

**新增**时 profile 还没有 id，所以顺序必须是「先建配置、再存凭据」：

```
handleSubmit(values):
  profile = values.login?.account
              ? await createProfile(values)          // 先拿到 id
              : await createProfile(values)
  if (values.login?.account && values.login?.password) {
     await bridge.credentials.save(profile.id, values.login.account, values.login.password)
  }
```

**失败处理**：配置已建、凭据存失败时**不回滚配置**，只在提示里说明「配置已保存，但密码没能保存到本机（原因）」—— 回滚会连带丢掉用户刚填的路径与参数，代价远大于收益。

**编辑**时分三种意图，必须用**显式信号**区分，不能靠「密码框为空」推断：

| 用户动作 | `login` 字段 | 行为 |
|---|---|---|
| 没动账号密码框 | 不传 `login` | 保持原凭据不动 |
| 改了账号或填了新密码 | 传 `{ account, password }` | 覆盖 |
| 点了「清除已保存密码」 | 传 `{ clear: true }` | 删除本机凭据 |

**为什么不能靠「密码框为空 = 不修改」推断**：用户改了账号却没重填密码时，「保持旧密码」会把旧账号的密码配到新账号上 —— 这是个静默的错误登录，比明确报错糟得多。显式信号是唯一稳妥的做法。

### 3.4 浏览器态降级

浏览器态没有主进程、没有 `safeStorage`。行为对齐既有 `launch:detect` 的 `agentAvailable=false` 模式：

- 账号/密码字段**照常显示但禁用**，旁边一行说明「自动登录需要桌面外壳」。
- 不假装「保存成功」，也不把密码写进 localStorage 充数（那会把安全等级拉回到 `credential.ts` 的水平，而它自己都说该换掉）。

## 4. 账号密码的本地存储与安全方案

### 4.1 存储位置与选型

**选型：主进程 `safeStorage`。** Windows 下它底层是 DPAPI（`CryptProtectData`），密钥派生自**当前用户的登录凭据**。

三个直接后果，都要在 UI 上如实表达：

1. **换机解不开**：把 `credentials.enc` 拷到另一台电脑或另一个 Windows 用户下，`decryptString` 会失败。
2. **换用户解不开**：同一台机器换个 Windows 账户登录，同样失败。
3. **同用户下的其它程序能解**：DPAPI 保护的是「文件被拷走」，不是「防本机恶意程序」。**这条边界必须在文档和 UI 里说清楚**，否则用户会以为它等价于密码管理器。

落盘路径 `app.getPath('userData')/credentials.enc`。**不放工作区 `.config/`**：`config.ts` 已经确立了「凭据不随工作空间移动」这条语义，把一份**换机必然解不开**的文件放在便携介质上，只会制造「文件明明在，为什么说没有」的困惑。

### 4.2 磁盘格式与「不可解密」状态

写入：

```
items.push({
  profileId,
  label,
  blob: safeStorage.encryptString(JSON.stringify({ account, password })).toString('base64'),
  updatedAt: new Date().toISOString(),
})
```

读取时**逐条**解密，不是整文件解密 —— 一条坏掉不该让整库失效：

```ts
function readVault(): { items: ResolvedItem[]; undecryptable: string[] } {
  // 单条 decryptString 抛错 → 该条进 undecryptable，其余照常返回
}
```

**「不可解密」是一个必须显式表达的状态**，不能静默当成「没有凭据」：两者对用户的含义完全不同 —— 前者要引导「请重新填写密码（换机/换用户后属正常）」，后者只是「你还没填」。UI 上表现为账号框的 placeholder 不同、提示文案不同。

`safeStorage.isEncryptionAvailable()` 返回 `false` 时（理论上 Windows 不会，但接口存在），**拒绝保存并明确告知**，不退回明文。

### 4.3 传输与 IPC

```ts
// preload 桥（新增）
credentials: {
  status: (profileIds: string[]) => Promise<{
    items: { profileId: string; state: 'saved' | 'undecryptable'; accountMasked: string | null }[]
  }>
  save: (profileId: string, account: string, password: string) => Promise<{ ok: boolean; detail?: string }>
  delete: (profileId: string) => Promise<{ ok: boolean }>
}
```

三条纪律：

1. **没有 `get`**：接口层面就不提供「读回明文密码」的通道。渲染进程能拿到的只有 `accountMasked`。
2. **账号默认掩码**：`138****8888` 这类形式，需要完整账号时由用户点「显示完整账号」再单独请求。这是把「明文暴露面」从「每次打开对话框」收窄到「用户主动要看的那一次」。
3. **`save` 的入参是用户当场输入的明文**，这是不可避免的一次穿越（用户总得把密码输进某个框），但它只走一次 IPC，且**只在主进程内存里落地**。

### 4.4 内存、日志、命令行三处泄露面

| 泄露面 | 风险 | 处置 |
|---|---|---|
| **命令行** | `powershell.exe -EncodedCommand <base64>` 会把 base64 放进进程命令行，`Win32_Process.CommandLine`（WMI）任何本机程序都能读到，而 base64 **不是加密** | **改用 stdin**：命令行只放**不含机密的固定脚本**，账号密码从子进程 stdin 读入 |
| **脚本块日志** | 企业环境可能通过 GPO 开启 PowerShell Script Block Logging，会记录**脚本内容** | 同上：脚本里不含机密，机密走 stdin，于是日志里只有代码 |
| **日志** | 排障日志一旦带上密码，就会进日志文件、进用户发来的截图 | 日志只记 `profileId`、掩码账号、outcome、耗时；**密码与完整账号一律不出现**；为此给 vault 加一个 `maskAccount()` 工具函数，日志处强制走它 |
| **Node 字符串内存** | JS 字符串不可清零，用完仍可能留在堆里直到 GC | **说明局限，不假装解决**。可做的是缩短生命周期：不缓存明文、用完立刻置 `null`、不做字符串拼接副本。 |

### 4.5 安全边界（防什么、不防什么）

**防**：
- 密码被上传到服务端（接口层面不存在这条路）
- 密码随工作区/U 盘移动（落 `userData`）
- 凭据文件被拷贝到别的机器后可用（DPAPI 机器+用户绑定）
- 渲染进程 / 同源 XSS 读出已存密码（无 `get` 通道）
- 密码出现在命令行、脚本日志、应用日志、剪贴板

**不防**（如实说明，不夸大）：
- 同一 Windows 用户下的恶意程序（DPAPI 对它透明）
- 内存转储（`procdump` 之类）
- 客户端自身被攻破
- 用户把密码填进 `args`（那是用户自主选择，与「工作台代管」是两回事 —— 沿用共享包原注释的这条区分）

## 5. 脚本与启动程序的交互方式与调用流程

### 5.1 后置流水线（新增四段）

现有 `scheduleLoginClick(software, pid)` 是「一步」；新的需要「四步」，且**每一步都可能失败且都不该阻断启动结果**：

```ts
async function runLoginPipeline(profile, pid, attempt): Promise<LoginOutcome> {
  // 1. 等窗口（新增）—— 现有实现缺的就是这一步，也是「恒 no-window」的根因
  const hwnd = await waitForWindow(pid, LOGIN_WINDOW_WAIT_MS)
  if (hwnd === null) return { kind: 'no-window' }

  // 2. 判定「这确实是登录窗」（新增，安全关键）
  if (!(await looksLikeLoginWindow(hwnd))) {
    // 不确定就不动。宁可只敲 Enter（§2.4 的老行为），也绝不往不确定的窗口里打密码。
    await pressEnter(hwnd)
    return { kind: 'unverified' }
  }

  // 3. 取凭据（主进程内解密）
  const credential = vault.read(profile.id)   // null | 'undecryptable' | { account, password }
  if (credential === null || credential === 'undecryptable') {
    await pressEnter(hwnd)
    return { kind: 'no-credential' }
  }

  // 4. 填表
  await fillLoginWindow(hwnd, credential.account, credential.password)
  const closed = await waitForWindowGone(hwnd, LOGIN_SETTLE_MS)
  return { kind: closed ? 'success' : 'maybe-captcha' }
}
```

**总超时**：整条流水线给一个硬上限（建议 45s），到点即放弃并记 outcome。没有上限的话，一个卡住的客户端会把串行队列后面的账号全堵住。

**永不重试**：`maybe-captcha` 就是终态。盲目重试提交密码是**触发风控的头号原因**，也是把「辅助输入」变成「暴力尝试」的那一步。

### 5.2 输入手段：`SendInput` + `KEYEVENTF_UNICODE`

`keybd_event`（现有脚本用的）**只能发虚拟键码**，打不出中文、打不出 `@`/`!` 这类需要 Shift 的字符（除非手动配 Shift 组合）。密码里几乎必然有这类字符，所以必须换 `SendInput`。

`KEYEVENTF_UNICODE` 直接把 **UTF-16 码元**作为字符注入前台窗口，**不经过键盘布局、不经过输入法**（这也是它能打中文的原因）。

序列（每一步之间 `Start-Sleep -Milliseconds 80~150`）：

```
聚焦并选中账号框（若客户端已预填上次账号）
  Ctrl+A            ← 清掉预填，避免「旧账号 + 新账号」拼在一起
  逐字符发账号
  VK_TAB (0x09)     ← 切到密码框
  Ctrl+A            ← 同样清预填
  逐字符发密码
  VK_RETURN (0x0D)  ← 提交（多数登录窗的登录按钮是默认按钮）
```

**为什么用 Tab 而不是找密码框**：Tab 是「账号 → 密码」这个通用布局里最稳定的连接关系，不依赖坐标、不依赖控件文字、不依赖 UIA 树可见。它与 §2.4「敲 Enter 最能抗改版」是同一条判断。

**已知弱点（要写进代码注释）**：若客户端在账号框与密码框之间插入了别的可聚焦元素（如「忘记密码」链接、协议勾选框），Tab 会跳到错误位置，于是密码被填进账号框。这就是 §5.4 那道确认判据必须存在的原因 —— 但**它也不能完全消除这个风险**，所以「默认关闭 + 明确告知 best-effort」是产品层面的必要配套。

**实现坑**：`INPUT` 结构体在 x64 下是 40 字节（`type` 4 字节 + 4 字节对齐填充 + 32 字节 union）。用 `Marshal.SizeOf(typeof(INPUT))` 传 `cbSize`，**不要写死数字** —— 写错时 `SendInput` 返回 0 且不报错，表现为「什么都没发生」，极难查。

### 5.3 脚本与机密的传递：stdin，不是 `-EncodedCommand`

现有 `buildLoginClickScript` 用 `-EncodedCommand` 传 base64(UTF-16LE)。**这条对不含机密的脚本无害，但绝不能用来传密码** —— base64 会被 `Win32_Process.CommandLine` 原样读出。

新脚本的形态：

```ts
// 命令行里只有这段固定脚本，不含任何机密
const SCRIPT = `
$ErrorActionPreference = 'Stop'
Add-Type @" ... P/Invoke: EnumWindows / AttachThreadInput / SendInput ... "@
$payload = [Console]::In.ReadToEnd() | ConvertFrom-Json
# ... 定位窗口 → 确认是登录窗 → 发键盘序列 ...
`
execFile('powershell.exe', ['-NoProfile', '-NonInteractive', '-Command', SCRIPT],
         { timeout: 45000, windowsHide: true }, cb)
  .stdin.end(JSON.stringify({ pid, account, password }))   // ← 机密只走这里
```

**为什么 `-Command` 而不是 `-File`**：`-File` 要求脚本先落盘，落盘就多一处泄露面（临时文件可能被别的程序读、可能残留在磁盘上）。`-Command` 让脚本只存在于内存。

**PowerShell 5.1 兼容**（沿用既有踩坑）：不用 `0u`/`0ul` 后缀、不用 `??`、不用三元 `?:`、不用 `-Parallel`。既有单测里那条「断言脚本不含 `0u`」的回归用例要继续保留，并扩展到新脚本。

### 5.4 「这确实是登录窗」的判据（安全关键）

**这是整套设计里最容易被忽略、后果最严重的一处。** 如果客户端处于「上次已登录、本次免登录直接进主界面」的状态，填表序列会把**账号和密码打进聊天输入框**，然后回车发出去 —— 这不是「功能没生效」，这是**把密码公开发送给了联系人**。

判据（**取交集，宁可漏判不可误判**）：

1. 窗口属于我们刚 spawn 的那个 pid（`GetWindowThreadProcessId`，既有能力）。
2. 窗口可见且**未最小化**（既有 `IsWindowVisible`）。
3. 窗口是**顶层窗口**且不是工具窗/消息窗（`GetWindowLong(GWL_STYLE) & WS_POPUP` 之类可作辅助）。
4. **窗口标题匹配已知登录标题白名单**（如包含「登录」「Log in」「Sign in」），或
5. 窗口内**通过 UIA 能找到一个 `ControlType=Edit` 且 `IsPassword=true` 的元素**（UIA 在 Electron 上常拿不到，所以这条是**加分项而非必需项**）。

**保守规则**：4 与 5 **至少满足一条**才认为「是登录窗」；两条都不满足 → 退回「只敲 Enter」。**绝不用「窗口大小/位置像登录窗」这种启发式** —— 它在客户端改版后会静默失效，而失效的后果是密码发到聊天框。

另需一条前置保护：**spawn 前后比对该软件已有的窗口集合**。若 spawn 后没有出现新窗口（说明客户端把已有窗口激活了），直接判定「已在运行，不填表」。这条同时解决了单实例客户端的串台问题（§6.2）。

## 6. 单账号与多账号场景的处理差异

### 6.1 单账号

一条配置、一份凭据。串行与否无关紧要，流水线一次跑完。**唯一要处理的是「已登录」状态**（§5.4 的那条前置保护）。

### 6.2 多账号：三条真实约束

**约束一：同一客户端的进程模型。**

- **千牛**：原生支持多开 —— 双击快捷方式即新窗口、新账号（社区资料一致）。因此 N 条配置 → N 个独立进程是可行的，**但填表仍必须串行**（见约束三）。
- **微信**：有单实例互斥量。现有代码注释已经承认：「重复点同一条……在微信这类有互斥量的客户端上只会激活已有窗口」。要真的起 N 个，需要互斥量绕过类技巧（常见做法是极短时间内连续 `start` 两次抢在互斥量建立之前）。**这类技巧不受官方支持，且明确有风控风险。**
- **QQ（QQNT）**：待真机探针确认。QQNT 自身提供「多账号登录/切换」，但那是**一个进程内的多账号**，不是多进程。

**约束二：凭据与窗口的配对。**

N 个登录窗同时开着时，**「哪个窗口对应哪份凭据」这件事没有可靠答案** —— 窗口没有可读的账号标识（那正是我们要填的东西）。因此：

> **多账号的唯一正确做法是「一次只开一个、填完再开下一个」。**

并发开 N 个窗口再逐个填，必然出现「凭据填错窗口」，而填错的后果是**把一个账号的密码打进另一个账号的登录框**（轻则登录失败，重则触发风控）。

**约束三：spawn 本身也要串行（对单实例客户端）。**

对单实例客户端，「并发 spawn」的结果是第二条只激活第一条的窗口。于是第二条的流水线会：
- 找不到属于它自己 pid 的新窗口（前置保护拦下）→ 记 `already-running`，不填。
- 若没有前置保护 → 把第二条的凭据填进第一个账号的窗口 → 串台。

所以：**对单实例客户端，串行的单位是「整条流水线」而不是「spawn」**。

### 6.3 串行 vs 并行：按「多实例能力」分流

| 软件 | spawn | 填表 | 依据 |
|---|---|---|---|
| 微信 | **可并发**（多实例能力由探针确认；确认不支持时串行 + 明确告知） | 不填 | 扫码登录，N 个窗口各自出码，并发不冲突 |
| QQ / 千牛 | **串行** | **串行** | 凭据与窗口的配对只能靠时序保证 |
| 自定义 | 沿用现有（不自动登录） | 不填 | — |

微信并发还有一处实际好处：**N 个二维码可以同时显示**，用户扫完一个扫下一个，不用等。

### 6.4 多实例能力探针

**不硬编码「微信支持/不支持多开」这类假设**，而是做一次性探针，结果落盘（`userData/launch-capability.json`）：

```
probeMultiInstance(software):
  记录启动前的 pid 集合（按可执行文件名）
  spawn 一次 → 等 3s → 记录启动后的 pid 集合
  Δ>0 → multi-instance 可用
  Δ=0 → 单实例
```

**为什么值得单独做探针**：① 客户端版本会变（微信 3.x 与 4.x、QQ 与 QQNT 的进程模型不同）；② 探针结果可以直接驱动 §6.3 那张表，不必改代码；③ 探针失败（超时、环境异常）时**退回最保守策略（串行 + 只唤起）**，不猜测。

探针只在用户首次为某软件配置第 2 条及以上的启动项时提示运行，不做后台静默探测（静默探测会真的启动客户端，那是有副作用的动作）。

### 6.5 微信侧：配几个拉几个 + 窗口排布

需求原话是「配置了几个微信启动项，脚本就拉起几个微信登录程序」。除了 spawn 本身，还有一个**体验上的关键补充**：

**把 N 个登录窗在屏幕上平铺排开。** N 个二维码窗口默认会叠在一起（同一个默认位置），用户要点 N 次任务栏才能扫到 N 个码。用 `SetWindowPos` 按网格排布（比如 2×2、3×2），用户一眼就能看到全部二维码，挨个扫完即可。

这条不涉及任何凭据，纯窗口操作，风险为零，但**它是「配几个拉起几个」这句话从「能跑」变成「好用」的分界点**。

### 6.6 与 3 秒去重窗口、`runMany` 的幂等口径对齐

三处需要明确对齐，否则会出现「配了 3 个微信，只起了 1 个」这种看起来像 bug 的行为：

1. **去重是按 `profile.id` 的，不是按软件的**（`agent.ts` 注释已明确）。因此 N 条配置 → N 次 spawn，**不会**被去重窗口合并。✅ 需求天然满足。
2. **但同一条配置在 3 秒内被点两次仍会被合并。** 「一键登录全部」按钮应该走 `runLaunchProfiles`（批量），**不是**循环调 `runLaunchProfile` —— 后者在同一 profile 上重复点击会被去重，行为不一致。
3. **批量接口不把整批当一个去重单位**（注释已明确：各条按 `profile.id` 各算）。这条要继续保持，新的串行逻辑**只影响后置流水线，不改 spawn 的去重语义**。

## 7. 关键实现细节清单

按落地顺序排列，每条都是「不做会出事」的：

1. **先修 §2.4 的时序**（等窗口 + 有限次重试），否则一切免谈。
2. **新脚本必须用 `SendInput`，不是 `keybd_event`** —— 后者打不出非 ASCII。
3. **`INPUT` 结构体 `cbSize` 用 `Marshal.SizeOf`**，不写死 40。
4. **机密走 stdin**，命令行只放固定脚本；脚本里不含任何机密。
5. **PowerShell 5.1 语法**：无 `0u`/`??`/`?:`/`-Parallel`。
6. **登录窗判定（§5.4）必须实现**，且「不确定就只敲 Enter」。
7. **spawn 前后比对窗口集合**，识别「单实例客户端把旧窗口激活了」。
8. **解密逐条、不整库**，坏一条不影响其余。
9. **`undecryptable` 与「没有凭据」是两个状态**，UI 文案必须不同。
10. **编辑态密码框恒空**，靠显式信号区分「不改 / 覆盖 / 清除」。
11. **日志强制走 `maskAccount()`**，并在单测里断言日志字符串不含测试密码。
12. **整条流水线有总超时**（45s），串行队列不能被一个卡住的客户端堵死。
13. **`maybe-captcha` 是终态，不重试。**
14. **`buildLaunchEnv()` 的净化继续生效**（虽然已证实不是 QQ 崩溃的原因，但仍是正确的卫生习惯，且新流程会启动更多客户端）。
15. **微信的窗口排布用 `SetWindowPos`**，纯窗口操作、零风险。

## 8. 潜在风险与注意事项

### 8.1 账号风控（最重要，且无法用技术手段消除）

**风险**：自动填密码 + 提交登录，在腾讯（QQ）与阿里（千牛/淘宝）的风控体系里，与「异常登录行为」的特征高度重合。可能的后果依次是：弹滑块/图形验证码 → 要求短信验证 → 设备锁 → 限制登录 → **账号封禁**。多账号串行登录时，同一台机器短时间内多次提交，会显著提高触发概率。

**必须做的事**：
- **默认关闭**。用户必须主动为某条配置开启自动填表。
- **首次开启时给一次明确的提示**，内容包含「本功能会代替你输入账号密码，可能触发客户端的安全验证；失败时请手动完成登录」。不要做成「点一下知道了」的轻量提示 —— 这是有可能导致账号损失的动作。
- **失败不重试**（§5.1）。
- **限制批量规模**：一次「一键登录全部」超过 N 条（建议 3）时提示用户确认。
- **绝不实现「失败后换密码再试」**之类逻辑。

### 8.2 安全

- **密码打进聊天框**（§5.4）：靠登录窗判定 + 保守规则防。这是唯一一个「做错了会造成真实泄露」的点，必须优先实现且必须真机验证。
- **命令行泄露**：靠 stdin（§5.3）。
- **剪贴板泄露**：靠 `KEYEVENTF_UNICODE` 完全绕开（§5.2）。
- **换机解不开**：靠 `undecryptable` 状态显式表达（§4.2）。
- **同用户下的其它程序可解**：DPAPI 的固有边界，如实说明（§4.5）。

### 8.3 稳定性与兼容

- **客户端改版**：登录窗布局、Tab 顺序、默认按钮都可能变。整套设计因此是 best-effort：**失败的表现必须是「没填进去、用户手动输一次」，绝不能是「填错地方」**。§5.4 的保守规则就是这条的落地。
- **窗口出现慢**：客户端冷启动可能要十几秒。等待上限给足（建议 15s），并采用轮询（200ms 一次）而不是固定 sleep。
- **窗口出现但内容未就绪**：窗口一出现就发键盘序列，可能打在还没绑定事件的输入框上。需要在「窗口出现」之后再加一个**稳定期**（窗口连续 N 次轮询保持同一 hwnd）再发。
- **输入法状态**：`KEYEVENTF_UNICODE` 通常绕过 IME，但仍需真机确认（尤其是拼音输入法激活时）。
- **非 BMP 字符**（emoji 类密码）：UTF-16 代理对要按两个码元依次发送。
- **DPI / 多屏**：纯键盘序列不依赖坐标，天然不受影响 —— 这是选它的附带收益。
- **杀软**：`SendInput` 到其它进程 + PowerShell 读 stdin 的组合，可能被某些安全软件标记。需要在目标环境验证。

### 8.4 产品与合规

- **第三方用户协议**：自动化登录第三方客户端，通常与对方的用户协议存在冲突。这不是技术问题，是**产品决策**，需要在交付前评估。
- **对客户交付时的告知义务**：应把「本功能会代替你输入账号密码、风险由你承担」写进功能说明，而不是只放在代码注释里。
- **不要把「自动登录」当作卖点宣传**，把它定位成「省一次手输的便利功能」。

## 9. 分阶段实施建议与验收

### 9.1 分阶段

| 阶段 | 内容 | 前置 | 风险 |
|---|---|---|---|
| **P0（已实施）** | 修 §2.4 时序（等窗口 + 稳定期复查）；微信的「配几个拉几个 + 窗口排布」 | 无 | 低。纯窗口操作，无凭据 |
| **P1** | 凭据层：主进程 vault（`safeStorage`）+ 3 条 IPC + 配置页账号密码字段 + `undecryptable` 状态 | 无 | 中。安全设计必须一次做对 |
| **P2** | 执行层：`SendInput` 填表 + 登录窗判定 + 串行队列 + 多实例探针 | P0、P1 | **高**。§5.4 与 §8.1 是主要风险源 |

**建议顺序**：P0 先做（它同时是 P2 的前置，且单独就有价值 —— 微信侧的全部需求在 P0 就能交付）。P1 与 P2 之间建议插一次**真机探针**（§9.2），因为 P2 的可行性取决于探针结果。

### 9.1b P0 已实施（2026-10-15）

用户就两条未决项拍板：**需要自动填表**（P2 在范围内），**微信桌面版在快速点击下确定可以多开**（微信侧按「并发拉起」实现，不做互斥量绕过）。

**落点**：窗口原语与「点一下登录」合并在 `apps/desktop/src/launch-login-click.ts`（原计划拆成 `launch-windows.ts`，合并的原因见该文件头的模块约束说明）；`main.ts` 的新增编排在 `runPostLaunchBatch`。

**具体做了四件事**：

1. **等窗口进脚本**（修「实测恒 `no-window」）。`buildWindowWaitBody` 是一段带超时的轮询循环：每 200ms 查一次属于目标 pid 的可见顶层窗，15 秒等不到才报 `no-window`；窗口出现后再等 500ms 稳定期并**复查**，只认「等完之后还在」的那一个。
   - 复查不是多余的：部分客户端会先闪一个启动窗再开登录窗，只找一次会把那个转瞬即逝的窗口当成登录窗。
2. **微信侧：等登录窗 + 网格平铺，一个键都不敲**。`launch:runMany` 后把 wechat 组的结果并发送入 `findProcessWindow`，拿到的句柄交给 `computeTileLayout`（纯函数，`ceil(sqrt(N))` 列、列数封顶 6）+ `tileWindows`。平铺用 `SWP_NOZORDER | SWP_NOACTIVATE`，**不动 z 序、不抢焦点**。
   - 少于两个窗口直接跳过：单个窗口没有排布可言，省掉一次无意义的 PowerShell 调用。
3. **QQ / 千牛串行点登录**（原来是并发）。串行的理由：并行的两条 Enter 会互相把对方窗口带到前台，后敲的那个落在已经处理过的窗口上，表现为「第二个账号没登录」。P2 把串行单位前移到 spawn 时，这里跟着改。
4. **日志补上等待时长**。`尝试=是 结果=launched 等待=2341ms`，这是判断 Enter 是否真的落到登录窗的唯一现场依据。

**微信「配几个拉几个」为什么不需要改 spawn**：`runShellLaunchProfiles` 用 `Promise.allSettled(raws.map(...))`，所有 spawn 调用在同一次 tick 内发起，等价于「快速连点快捷方式」；而 3 秒去重按 `profile.id` 各算，因此 N 条配置就是 N 次真实 spawn。用户确认这一形态在真机上成立。

**顺带发现并修正的两个真实缺陷**（都是本轮写测试时暴露的，不是历史遗留）：

- `parseWindowSendOutput` 原本先看 `sent` 再看 `reason`，于是一段自相矛盾的负载（`sent:true` 却说 `no-window`）会被判成「已发送」。改为**失败原因优先**。这与 `agent.ts` 里「报成功而没做事比明确失败难查得多」是同一条判断。
- PowerShell 的 `Add-Type` here-string 要求 `@"` 之后紧跟换行、`"@` 独占一行。把共享的 P/Invoke 源码 `.trim()` 掉首尾换行会让 `@"` 直接顶上 `using System;`，脚本在真机上解析失败，而本机单测完全看不到。现在显式不 trim，并有单测钉住 `@"\n` 与 `\n"@` 两个形态。

**新增的项目级约束（写进了源码注释，值得记住）**：`apps/desktop` 的单测是 `node --experimental-strip-types --test`，**只按字面解析 import 说明符**；而 CJS 产出的 TypeScript 要求相对导入写成 `./foo.js`。于是「一个 `.ts` import 另一个 `.ts` 且用 `.js` 后缀」这一生产正确的写法，会让单测整个文件报模块缺失。已验证：`main.ts` 用了整整十章 `.js` 后缀相对导入，而它恰恰是不被单测加载的那个文件；所有**被测**的 src 模块（`launch-icon.ts`、`launch-registry.ts`、`brand-icon.ts`）都是零相对导入、自包含。**后续新增外壳模块时，只要它有单测，就不能拆成互相 `.js` 导入的两个文件。**

**门禁**：desktop typecheck ✅、单测 **243/243** ✅（原 210，新增 `test/launch-login-click.test.mjs` 的 33 例：软件开关、等待参数注入、PS 5.1 纪律、here-string 形态、平铺布局 10 例、四个输出解析器、平台守门）；shared 108/108、web 184/184 无回归；新文件 eslint ✅、prettier ✅（同目录既有文件同样干净，因此这里不是既有红灯）。

**未验证的部分（必须在真机做）**：脚本语法在真机 PowerShell 5.1 上能否跑通、微信多开的实际实例数、登录窗在真机上的出现时长（§9.2 的命题 1、3、6、9）。

### 9.3 验收标准

- **功能**：单账号能自动填并登录成功；多账号串行不串台；微信 N 条配置起 N 个登录窗且排布整齐。
- **降级**：任一环节失败时，**启动结果不受影响**，用户看到的是「已启动，请手动登录」而不是报错或静默无反应。
- **安全**：单测断言日志不含密码；断言不存在 `credential:get` 通道；断言编辑态密码框初值为空。
- **门禁**：三包 typecheck 全绿；desktop / web 单测全过（新增用例覆盖 vault 的加解密往返、`undecryptable`、掩码、串行队列、登录窗判定、脚本不含机密与不含 PS7 语法）。
- **真机**：§9.2 的 10 条命题逐条有结论。

## 附：与既有文档的关系

- **§2.4「凭据与自动登录：只唤起 + 点登录，工作台不存密码（已定）」** —— 本文**修正**了这条。原决策的前提是「不存密码」，现在需求变了，因此「只唤起 + 点登录」升级为「只唤起 + 点登录 +（可选）本机凭据填表」。**§2.4 里「工作台不存密码」的结论仍然成立**，只是「工作台」的所指收窄为服务端/共享包（§1.3 冲突一）。
- **§2.4 未闭环的「等窗口 + 有限次重试」** —— 本文把它从「待定的设计取舍」提升为 **P0 必做项**，因为填表比敲 Enter 更依赖窗口存在。**P0 已于 2026-10-15 实施**（见 §9.1b），「实测恒 `no-window」这一项随之闭环。
- **§2.2「批量 run，独立 spawn，按需串行」** —— 本文的「按需串行」给出了具体判据（多实例能力），并指出**串行的单位是整条流水线而不是 spawn**。P0 已把 QQ / 千牛的「点登录」改成串行，P2 再把串行单位前移到 spawn。
