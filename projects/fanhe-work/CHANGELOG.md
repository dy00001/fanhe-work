# 变更日志

本文件记录梵禾 Work 的对外可感知变更。0.x 阶段版本号仍按 SemVer 解释，但**「破坏性变更」的含义是「升级时需要额外动作」**，不一定是接口不兼容 —— 例如必须跑一条迁移、必须重打安装包、手工加过的角色授权会被重置。

历史版本的详细方案见 `docs/RELEASE-<版本>.md`；更早的迭代过程见 `docs/WORK-STATUS.md`。

---

## [0.3.3] - 2026-10-24

一版**把运营面板补成能自己用**：谁能看到哪些店有规矩了，端口能自己填了，日增采完也会把状态写回来。

### 新增

- **店铺归属与可见性**：`ecom_shops` 加 `owner_id`。持 `ops.shop.bind` 的账号看到全部店铺，其余人只看「自己的 + 公共的」。**空值即公共**，现有 5 家店保持公共，不会因为这次改动对任何人消失。绑定入口自动把店记给操作人；面板上可直接改归属。
- **补登记端口**：端口为空的行可以直接填，不必解绑再绑定。解绑会把槽位的 `collect` 置 false、再绑定才置回 true，为填一个数字走一遍关闭再打开属于自造故障窗口。校验 1024 到 65535，端口被占时提示占用方代号。

### 修复

- **日增采完不回写平台**：宿主上有两个执行者（常驻轮询与 `run-daily.ps1`），后者采完不碰库，于是界面会同时说三件错事：「等待采集器」（待办没清）、「登录未校验」（登录态没记）、以及常驻任务停掉时的「采集器离线」——而数据其实每天在更新，这一条最误导人。现在成功的日增会清待办、记登录态、刷新心跳；失败不写，否则会把失败记成成功。

### 升级须知

1. **新增一条迁移**（`add_ecom_shop_owner`，共 11 条），`migrate` 镜像必须重建。列可空，现有店铺保持「公共」，不会因为这次改动对任何人消失。
2. **不需要重跑 `db:seed`**，权限点没动。
3. **必须重打安装包**：归属下拉与补登记端口在桌面端的前端产物里。
4. 服务端重建 `api` 与 `web`。
5. 采集器侧无变化，但日增脚本多了回写：手工采过之后也可以用 `scripts/report-synced.ps1 -Shop <code>` 补记。

## [0.3.2] - 2026-10-24

一版**修掉 0.3.1 里两处「按了没反应」**。两处都表现为界面毫无动静，而代码路径都在正常返回，属于最难自查的一类。

### 修复

- **「打开登录」点了不出窗口**。三层原因叠在一起：`-File` 配合隐藏窗口时脚本会在第一个 `Write-Host` 处静默结束（退出码 0、无输出、浏览器没起来）；不传 `-Keep` 时脚本检查完就关窗口；需要登录时脚本会 `Read-Host` 等回车，而这里 stdio 是 ignore，没有控制台。现改为 `-Command` 加输出重定向到日志、带 `-Keep -NoPrompt`，并按脚本约定的退出码翻译结果（0 已登录、3 待登录、其它为失败并附日志尾巴）。
- **常驻任务弹出一个关不掉的命令行窗口**。任务以交互式登录跑 `cmd.exe`，控制台就一直显示在那儿。现经 `run-hidden.vbs` 以窗口样式 0 启动，实测父进程 `MainWindowHandle=0`、无标题。不用「不管用户是否登录」那种方式，因为它不加载用户配置，DPAPI 与 Edge profile 都用不了，登录态会静默变成空。
- **启动失败被当成成功**。`spawn` 的错误是异步事件，原先只 try/catch 同步异常就返回成功，命令找不到时界面一片安静。现在等一小段时间确认没有立刻失败。

### 升级须知

1. 不需要迁移，不需要重跑种子。
2. **必须重打安装包**：三处修复都在桌面端主进程与采集脚本里。
3. 服务端只需重建 `web`（绑定提示文案），`api` 无改动。
4. 采集器侧改了 `shop-login.ps1`（新增 `-NoPrompt`），从磁盘读取，无需重装。

## [0.3.1] - 2026-10-24

一版**修掉 0.3.0 在真实环境里暴露的两个断点**。两处都不是逻辑错，是「装在哪台机器上」与「谁有权碰宿主机文件」没对齐。

### 修复

- **跨盘安装时「打开登录」永远失败**：桌面端定位 `shop-login.ps1` 只沿自己的安装目录向上找 `.ws-root`，安装目录在 D 盘、工作区在 E 盘时链条必然断，界面长期显示「当前安装没有采集器脚本」。现支持 `collector.json` 配置采集器根目录（安装态在 `%APPDATA%\梵禾 Work\`，开发态在工作区 `.config/fanhe-work/`），环境变量 `FANHE_COLLECTOR_ROOT` 可一次性覆盖，`root` 指向 `tools/collector` 或仓库根都认，每次现读、改完不用重启。
- **绑定后槽位永远要手工补**：API 在容器里看不到宿主机的 `shops.config.json`，绑定只能返回 `manual` 让人粘贴。现由宿主机常驻进程每轮按库里的 `code` / `name` / `collect_port` 补齐槽位（幂等，只在真的写了东西时打日志）。绑定提示随之改成「采集器下一轮补齐」。
- **没配 `OPS_INGEST_TOKEN` 时整条链路停摆**：守卫原先无条件要求密钥，而 DB 直连根本不需要它。现只在显式 `--transport http` 时要求。

### 升级须知

1. **不需要跑迁移**，仍是 10 条；不需要重跑 `db:seed`，权限点没动。
2. **必须重打安装包**：跨盘修复在桌面端主进程里。
3. 服务端重建 `api` 与 `web`：槽位补齐的 CLI 在 `api` 镜像里，绑定提示在 `web` 里。
4. 采集器的常驻任务会自动用上新逻辑（脚本从磁盘读），重启一次任务更稳妥。
5. 若安装目录与工作区不同盘，装完之后写一个 `collector.json` 指到 `tools/collector`（见 `docs/ops/SHOP-BINDING.md`）。

## [0.3.0] - 2026-10-24

一版**把运营链路接到人手上**。此前接入一家店要改配置文件、跑脚本、手工导入；现在在工作台里填四个字段，绑定之后由本机采集器自动同步，面板上能看到每一步停在何处、为什么停。

版本号取 0.3.0 而不是 0.2.2：本版新增的是用户可见的能力（店铺绑定面板、采集器状态、打开登录入口），且升级需要额外动作（两条迁移、重跑种子、重建镜像、重打安装包）。0.2.1 的判据是「0.3.0 不合适，因为那批改动不在安装包里」，这批恰恰在安装包的前端产物里，方向相反。

### 修复

- **停在 `running` 的采集记录会永远显示「采集中」**：进程在入库中途死掉、补写 `failed` 也失败时，库里会留下一条永远是 `running` 的记录。运维看到「正在采」就不会去查，而实际上那条记录早就死了。现按 `COLLECT_RUNNING_TIMEOUT_MS`（10 分钟）判定超时，徽标显示「采集中断」并转为告警色。**库里的 `status` 不改写** —— 那条 `running` 是审计事实，读路径上把它改成 `failed` 会让「补写失败」与「真的失败」在库里长得一样。阈值取 10 分钟的依据是实测入库耗时 0.107—0.200 秒（含一次 30 天回填），余量约 3000 倍。

### 新增

- **店铺绑定入口**：运营看板顶部新增折叠面板，填代号/名称/端口即可登记一家店，不必再手改 `shops.config.json` 与手工导入。绑定只做三件事：写 `ecom_shops`、尝试写采集槽位、置 `sync_requested_at`；采集仍由本机采集器执行。
- **绑定后自动同步**：采集器新增 `tools/collector/scripts/sync-shops.mjs`，轮询待同步的店、跑既有采集与入库、把登录态与失败原因回写到那条店铺记录。界面据此显示「等待采集器 / 同步失败 / 数据陈旧」，不必翻脚本日志。
- **采集器心跳**：店铺列表上方显示 `采集器在线` / `离线` / `从未启动`。心跳不设独立接口，拉待办这个动作本身就是存活证明，两种传输（HTTP 与 DB 直连）各写一次。
- **打开登录**：每行店铺可一键打开采集浏览器的登录窗口（桌面外壳走 IPC 起脚本，浏览器态复制命令，安装态提示手工执行）。

### 升级须知

1. **新增两条迁移，共 10 条**：`ecom_shops` 加 6 列绑定状态并新增枚举 `ops_login_state`，另加单行表 `ops_collector_heartbeats`。`migrate` 镜像必须重建。
2. **必须重跑 `db:seed`**。新增权限点 `ops.shop.bind`：不重跑时 owner 仍然有（走代码常量），但内置「管理员」角色没有该点 —— 表现是界面上看不到绑定入口，且没有任何报错。
3. **服务端重建 `api` 与 `web` 两个镜像**：绑定与心跳在 `api`，面板在 `web`。
4. **桌面端需重打安装包**才有「打开登录」的 IPC 通道。没重打的旧外壳里该按钮退化成复制命令，功能不缺失。
5. **采集器需要单独注册常驻任务**：`powershell -ExecutionPolicy Bypass -File tools\collector\install-sync-task.ps1`。脚本会建一个登录时启动、每分钟尝试拉起的计划任务（实例互斥，运行中不会重复启动）。不注册时绑定与列表都正常，只是不会自动同步，面板会显示「采集器从未启动」。
6. **容器化部署下同步走 DB 直连**。采集入口的回环校验在容器里看到的源地址是 docker 网关，HTTP 那条路必然 403；脚本会自动降级，不需要额外配置。

## [0.2.1] - 2026-10-21

一版**收口**：把运营链路的三段（抓取、更新、推送）各自的失败形态分开，让「看起来成功」不再能混过。看板本身没有新增板块，但此前几处会静默错的地方现在会报出来。

### 修复

- **区间锚点不认店铺**：默认「近 30 天」原先取全库最新一天，五店都有数据后，落后那家会被锚到别的店的末日，首屏多一段空白而接口全 200。现按所选店铺取锚点；五店并列那张表仍取全库最大，两个口径分开。
- **维度快照整类清空后仍记成功**：`statDate` 窗口内某类维度为零行时，原先仍执行 `deleteMany` 把旧行清掉，重跑一次就丢历史。现零行时不动库。
- **采集中断在库里完全不可见**：运行记录原先写在事务内，失败随事务回滚。现移出事务，失败补写 `failed`。
- **导出端日期错位降级成「待确认」**：文件写出后才发现 `statDate` 与实际不符，下游只能人工判断。现改为写文件前阻断，退出码 1。
- **店铺名四个写入点不一致**：库、采集配置、种子脚本、30 天回填脚本各写一份，改一处会被另一处覆盖回去。现统一为「梵禾」「雅素」「简作」。

### 新增

- **写入三态 `ok` / `partial` / `failed`**：逐日与维度一方为空记 `partial`，只有非 `failed` 才推进采集时间。
- **两个校验器**：`verify-daily`（采集产物与契约）、`ops-verify`（库与契约），加 `run-pipeline` 串五步，整体退出码 0/2/1 三级。
- **必采接口判定表** `required-endpoints`：采集端与校验端共用一份「每页必须拿到什么」，缺页单列打印但不改退出码。
- **三类「读不到」分开报**：目录空、文件名不匹配、匹配到但无行。
- **多店采集**：一店一份浏览器 profile（同 profile 切账号会顶着别人的名字入库且不报错），`--shop` 与目录所属店不一致直接退出，防串店。

### 优化

- **运营三接口 15s 请求超时**，反代 GET/HEAD 20s 上游超时返回 504，写请求不设超时。
- **三个读接口加 ETag**（`private, max-age=0, must-revalidate`），窗口切换命中 304 不再重传。
- **回到前台静默重取**：`visibilitychange` 触发一次刷新，不进数据指纹、失败保留旧数据。
- **新鲜度每分钟推进**：改由 `useNow` 定时推进，不再渲染时取一次就定格。

### 升级须知

1. **没有新增迁移**，仍是 8 个；不需要重建 `migrate` 镜像。
2. **必须重打安装包**。推送段改动落在反代与前端构建产物里，只更新服务端不会让已安装的客户端生效。
3. **服务端要重建 `api` 与 `web` 两个镜像**：锚点与 ETag 在 `api`，静默重取与新鲜度在 `web`。
4. 店铺名变了（「分店 2」「分店 3」→「雅素」「简作」）。只影响显示，历史数据按 `shop_id` 关联，不受影响。

## [0.2.0] - 2026-10-20

一个模块级的新增：**运营看板**。千牛 / 生意参谋的经营数据接进梵禾 Work，成为运维信息平台下的七个入口，并打通了「每日采集 → 入库 → 看板可见」的完整链路。首页「全部品类」弹窗同时收敿为九品类网格。

### 新增

- **运营看板模块（七个入口）**：数据大屏、交易分析、商品分析、流量分析、服务体验、推广投放、内容运营。侧栏点左侧换右侧整块看板，区间与店铺写进地址栏（可分享、可刷新、后退符合直觉）。
- **数据接入**：`ecom_shops` / `ecom_daily_metrics` / `ecom_dimension_snapshots` / `ecom_collect_runs` 四张表与四个枚举，一条迁移（第 8 个）。
- **五个接口**：`GET /api/ops/dashboard`（单店读模型）、`GET /api/ops/overview-shops`（五店并列带）、`GET /api/ops/health`（采集批次与新鲜度）、`GET /api/ops/shops`、`POST /api/ops/ingest`（回环 + 共享密钥写入）。
- **三个权限点**：`ops.shop.read`（进入看板）、`ops.finance.read`（金额类指标）、`ops.collect.read`（采集批次）。页面准入与金额可见分开授权。
- **采集器迁入**：`tools/collector/` 收下 30 天基线（17 个模块、67 张 CSV）、20 个采集与校验脚本、10 份口径文档与一份前端原型页面，作为后续持续开发的依据。
- **日增适配器**：`tools/collector/scripts/export-daily-ingest.mjs`，把 `data/daily/<日期>/` 的原始响应转成入库契约，并输出逐块的覆盖率报告。
- **回填入口**：`pnpm db:ops-import [契约 JSON 路径]`，与 HTTP 写入共用同一个 `ingestOpsSnapshot`。
- **五店并列与占位**：`pnpm db:ops-shops` 建 `s2`–`s5` 四家「已登记、无数据」的店，未接入店显示「待接入」与「—」而不是被隐藏。
- **涨跌色令牌** `--up` / `--down`（亮暗各一份，涨红跌绿），与「危险操作」的 `--destructive` 分开。

### 变更

- **导航清单 18 → 21 项**：运维信息平台由「1 个入口 + 3 个功能开发中槽位」改为七个具名入口，预留槽位 11 → 8 项。
- **「数据看板」改名为「数据大屏」并绑定 `ops` 模块**：此前它对所有已认证用户可见，现在需要 `ops.shop.read`。
- **首页「全部品类」弹窗**：从「27 个占位案例位 + 10 个筛选芯片」改为 3×3 的九品类网格，卡片样式与主页横滑条逐项对齐。`CaseSlot` 类型保留、当前为空数组，案例库建立时换一次查询即可接真实数据。
- **维度快照的选择规则**：从「取 `statTo` 最新」改为「取与查询区间重叠天数最多」，否则日增的单日快照会把「近 30 天」的商品榜顶成「最新一天 Top 5」。
- **区间档解析**：地址里只写 `from` / `to` 时按「自定义」理解，不再静默回落近 30 天。
- **区间锚点**：以库里最新一天为锚，不以「今天」为锚（采集是攒出来的，以今天为锚会让首屏多出几天空白）。
- **`docker-compose.yml` 增 `OPS_INGEST_TOKEN`**：默认空，为空时写入接口返回 503 并说明原因，读接口与页面不受影响。

### 修复

- **金额裁剪与权限脱钩**：首版把 `maskDimensionRows` 写在取数路径上，导致持有 `ops.finance.read` 的账号也看不到商品与渠道金额，而 KPI 正常 —— 只测 KPI 的用例全绿。现按权限判断，并补了「有权限时金额必须在」的反例。
- **起止颠倒的区间返回一屏空数据**：现在直接 400 并说明哪一端在前。
- **从 `/login` 登录成功后落进 404**：登录页不在路由表里，登录成功后地址仍是 `/login`；补了 `login` / `setup` 的兜底重定向。
- **没有金额权限时商品表仍显示空的「加购金额」列**：金额列改为各自判断，键被裁掉就整列不渲染。
- **没有采集权限时仍发一次注定 403 的请求**：按 `can()` 门控，面板改为直接渲染「无权限」说明。
- **单日查看声称「这段时间没有可画的逐日数据」**：实为只有一格、画不出线。改为给出四项读数并说明原因。
- **全零序列的柱状图纵轴标成「¥0.01」**：`seriesCeiling` 的兜底值 1 分被直接格式化。全零时标 0。
- **五店迷你柱被峰值压平**：柱高改按平方根压缩（仅这条 16px 装饰带），读数仍由悬停给出精确值。
- **内容来源访客在空集合时显示 0**：改为「待接入」，与「真的为零」区分。

### 优化

- 未接入的服务 / 推广 / 内容三个板块显示「缺哪几个数、在哪个后台、卡在第几批」，不给演示数字。
- 趋势图支持按指标切换，四指标折线可逐条开关；各曲线按自身峰值归一，只比趋势不比高低。
- 采集器整体加入 `.gitignore` / eslint `ignores` / `.prettierignore` 三处，保持与采集源字节一致。
- 运营看板配套文档：`docs/ops/README.md`（模块边界、权限、口径、欠账）、`docs/ops/DATA-CONTRACT.md`（上报契约）、`docs/ops/RUNBOOK.md`（每日采集、回填、故障判据）。

### 破坏性变更 / 升级须知

1. **必须应用第 8 个迁移并重跑种子**。容器部署时 `migrate` 服务也要重建：`build migrate api web` 三者一起。只重建 `api` / `web` 会让旧镜像的种子按旧权限清单把新增的 `ops` 授权摘掉（实测日志「移除授权关联 6」，随后管理员访问看板 403，而 `permissions` 表里三个新点在）。
2. **角色授权以代码为准**。重跑种子会删除手工加在**角色**上的额外授权（`user_permissions` 账号级授权不受影响）。给某个账号单独开运营看板请用账号级授权。
3. **`/ops/slot-1` `/ops/slot-2` `/ops/slot-3` 三条地址不再存在**（导航项删除），旧书签会落到「页面不存在」。
4. **成员与访客默认看不到运营看板**。此前占位入口对所有已认证用户可见，现在需要 `ops.shop.read`；管理员与 owner 默认已具备。
5. **桌面端必须重打安装包**。`app.getVersion()` 读的是被打包进去的 `package.json`，只改仓库根版本而不重打包，客户端仍会自称 `0.1.6`，更新通道会反复提示有新版。
6. **全新部署要跑 `pnpm db:ops-shops`**。五店并列依赖这四行占位记录；不跑也能用，但首屏只有一家店的卡片。

### 已知限制（不影响升级，但会影响读数）

- 服务 / 推广 / 内容三个板块**没有真实数据**，页面显示待接入清单。
- 日增的**渠道块经常缺失**：当天的 `flow-shopsource` 只采到总览、没有渠道树时，渠道排行会是空的，报告里会写明「未采到渠道树」。
- **多日区间的 KPI 会从「整段去重」退回「逐日求和」**：`period` 只在查询区间恰好等于某个快照窗口时生效。日增开始后 30 天区间与快照窗口错开一天，访客会从 3,890 变成 4,069（跨日重复访客被重复计），金额不变。这是口径切换，不是增长，KPI 卡上的徽标会标明。
- **日增未接入计划任务**：`run-daily.ps1` 不自动调用导出与入库，两步需人工（或计划任务）接着走。
