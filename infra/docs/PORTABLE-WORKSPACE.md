# 可移动工作空间机制

本文件说明 `fanhe Work` 工作空间存放在 U 盘上、需要在多台电脑之间轮换使用时的路径内聚与盘符自适应机制。机制已实现于 `infra/portable/` 目录并通过验证。

---

## 一、目标

机制要同时满足三个目标。

1. **写入内聚**。项目产生的全部文件，包含源码、依赖、构建产物、缓存、配置、日志与临时文件，物理位置都落在工作空间内部，不落到工作空间之外。
2. **盘符无关**。所有受版本控制的文件都不记录盘符。工作空间从 E 盘换到 F 盘或 G 盘之后，无需手工修改任何配置即可运行。
3. **可检测、可修复**。换机之后能够自动识别路径变化，并对少数在设计上必须内嵌绝对路径的生成物执行修复。

这三个目标之间存在张力，值得说明。真正的盘符无关要求配置里不出现盘符，而部分工具链会把绝对路径写进它生成的产物。机制的取舍是让源文件与配置保持盘符无关，把绝对路径限制在运行时生成、且可以重建的产物范围内，再用修复例程统一处理这批产物。

## 二、适用范围

### 2.1 覆盖范围

凡是通过 `infra/portable/` 入口脚本启动的进程，以及这些进程派生的子进程，其可写路径都被重定向到工作空间内部。

| 用途 | 环境变量 | 工作空间内位置 |
| --- | --- | --- |
| 进程临时目录 | `TMP` `TEMP` | `.tmp/` |
| 通用缓存根 | `XDG_CACHE_HOME` | `.cache/` |
| 通用配置根 | `XDG_CONFIG_HOME` | `.config/` |
| 通用数据根 | `XDG_DATA_HOME` | `.local/` |
| Python 虚拟环境 | `VIRTUAL_ENV` | `.venv/` |
| pip 缓存 | `PIP_CACHE_DIR` | `.cache/pip/` |
| 字节码缓存 | `PYTHONPYCACHEPREFIX` | `.cache/pycache/` |
| npm 缓存与全局前缀 | `npm_config_cache` `npm_config_prefix` | `.cache/npm/` `.local/npm-global/` |
| Yarn 缓存 | `YARN_CACHE_FOLDER` | `.cache/yarn/` |
| pnpm 仓库与主目录 | `npm_config_store_dir` `PNPM_HOME` | `.cache/pnpm-store/` `.local/pnpm/` |
| Gradle 用户目录 | `GRADLE_USER_HOME` | `.gradle/` |
| Maven 本地仓库 | `MAVEN_OPTS` | `.m2/repository/` |
| Rust 工具链与注册表 | `CARGO_HOME` `RUSTUP_HOME` | `.cargo/` `.rustup/` |
| Go 工作区与构建缓存 | `GOPATH` `GOCACHE` `GOMODCACHE` | `.go/` `.cache/go-build/` |
| 编译缓存 | `CCACHE_DIR` | `.cache/ccache/` |
| Docker 客户端配置 | `DOCKER_CONFIG` | `.docker/` |
| 浏览器与 Electron 二进制 | `PLAYWRIGHT_BROWSERS_PATH` `ELECTRON_CACHE` | `.cache/ms-playwright/` `.cache/electron/` |
| NuGet 包缓存 | `NUGET_PACKAGES` | `.nuget/packages/` |
| 日志 | `WS_LOGS` | `logs/` |
| 可选便携运行时 | 追加到 `PATH` 首位 | `runtime/` |

重定向以进程级环境变量实现，不修改宿主机的用户级或系统级环境变量，因此不会污染使用过的电脑。

### 2.2 不覆盖范围

以下几类内容无法由工作空间自身控制，需要单独约定，这是机制的边界。

1. **基础运行时本体**。Python、Node、JDK、Git 等解释器与工具链安装在宿主机上，它们属于宿主环境而非项目产物。工作空间提供 `runtime/` 目录作为可选的全自包含方案，把便携版运行时放入其中后入口脚本会优先采用。代价是体积增加与版本维护成本，需要按需权衡。
2. **操作系统行为**。页面文件、系统日志、Windows 更新、设备驱动与项目无关。
3. **IDE 自身**。VS Code 与 IntelliJ 的安装目录和用户级全局设置位于宿主机的 AppData。项目级设置可以放进工作空间，全局设置无法迁入。
4. **未经入口脚本启动的进程**。若某进程的父进程没有加载 `ws-env`，它不会继承重定向。这是机制最主要的边界，第三章的触发方式专门针对这一点做了处理。
5. **安全软件隔离区**。杀毒软件对可移动介质的扫描与隔离发生在文件系统之外。

## 三、自动适配的触发方式

机制采用三层触发，逐层兜底。

### 第一层 自定位，每次启动生效

所有入口脚本都用自身文件位置推导根目录，不出现任何硬编码路径。

| 环境 | 取根方式 |
| --- | --- |
| PowerShell | `$PSScriptRoot` |
| 批处理 | `%~dp0` |
| bash | `BASH_SOURCE` 配合 `cd ... && pwd` |
| Python | `Path(__file__).resolve().parents[...]` |

这一层使盘符变化对任何经过入口脚本的调用完全透明，不需要额外动作。

### 第二层 变化检测，换机后的首次启动触发

每次启动时，`infra/portable/ws-state.ps1` 把当次解析出的两个信号与 `infra/portable/state/root.json` 中记录的值比较，任一不一致即调用 `infra/portable/ws-repair.ps1`。

| 信号 | 判据 | 对应的实际情形 |
| --- | --- | --- |
| 根变化 | 解析出的根目录与记录值不同 | 盘符变了，例如从 E 盘换到 F 盘 |
| 主机变化 | 主机名与记录值不同 | 换了一台电脑，而盘符可能恰好相同 |

之所以要单独设立主机信号，是因为新电脑完全可能分配到与上次相同的盘符。此时根目录比较不出任何差异，而依赖宿主机路径的产物仍然可能失效，最典型的是 `.venv/pyvenv.cfg` 中记录的基础解释器路径。只比较盘符会漏掉这一整类情形。

修复动作按触发原因区分。

**根变化时**，额外重写生成物中残留的旧根路径，范围限定在 `.venv`、`.vscode`、`.idea`、`infra/portable/state` 之内，源码不在重写范围内。

**无论哪种原因**，都执行一次工具链健康检查。

1. 探测 `python`、`node`、`npm` 是否可用。探测时识别 Microsoft Store 的应用执行别名桩，避免把桩误报为可用解释器，同时跳过 PowerShell 的 `.ps1` 转发脚本，只认可直接启动的 `.exe`、`.cmd`、`.bat`。
2. 读取 `.venv/pyvenv.cfg` 的 `home`，验证记录的基础解释器在本机是否存在。缺失时明确提示该虚拟环境必须在本机重建，并给出重建命令。
3. 基础解释器存在时，用 `python -m venv --upgrade` 重建虚拟环境的控制台脚本转发文件。
4. 存在 `node_modules` 时，用 `npm rebuild` 重建 `.bin` 转发脚本与原生模块绑定。

状态文件 `root.json` 是这一层的唯一判据，也是机制唯一的持久化状态。它按设计不纳入版本控制，因为其内容天然逐机不同。当前状态结构版本为 2，除根目录外还记录主机名、用户名与系统版本。

健康检查可以随时单独运行，只报告不修改。

```powershell
infra\portable\ws-repair.ps1 -CheckOnly
```

两个入口对状态管理是同一份实现。PowerShell 侧由 `ws-env.ps1` 在进程内调用 `ws-state.ps1`，bash 侧由 `ws-env.sh` 以子进程方式调用同一个脚本，避免两套检测逻辑各自演化而失同步。

### 第三层 定位兜底，手工恢复用

当某个工具、快捷方式或历史记录仍指向旧路径时，`infra/portable/ws-locate.ps1` 会扫描全部已挂载卷，用工作空间根目录下的 `.ws-root` 标记文件定位。标记文件携带稳定标识，因此查找结果与盘符无关。

## 四、预期效果

1. **换盘符零改动**。工作空间从 E 盘变为其他盘符后，通过入口脚本启动的一切操作正常运行，无需编辑任何配置文件。
2. **换机一次自愈**。在另一台电脑上首次启动时，无论盘符是否变化，第二层触发都会自动完成一次工具链健康检查，并重建虚拟环境脚本与 Node 转发脚本。若换机后盘符恰好相同，主机信号仍能触发这次检查，这是单看盘符做不到的。
3. **失效可见**。基础解释器在本机不存在这类无法自动修复的情形，会在启动时明确报出，并给出重建命令，而不是在后续构建中以难以定位的错误形式暴露。
4. **可审计**。`infra/portable/ws-doctor.ps1` 扫描硬编码盘符、统计工作空间体积、并按基线对比宿主机外部缓存目录的增长，把不可见的泄漏变成可见报告。
5. **不污染宿主**。全部重定向都是进程级的，宿主机环境变量与全局配置不被修改。

需要明确的是，第五点只对经过入口脚本的进程成立。若在某台电脑上直接用普通方式启动 IDE，该 IDE 及其内置终端不会继承重定向，此时需要改从 `infra/portable/ws-run.cmd` 启动，或在 IDE 终端中先加载 `ws-env`。

## 五、需要规避的典型场景

### 5.1 介质本身的约束

当前 U 盘卷标为 `WORK`，文件系统已于 2026-10-10 整盘迁移为 NTFS，分配单元 4096 字节。迁移前为 exFAT，下述几条曾是该介质上的硬约束，现作为历史背景与「若再遇到 exFAT 介质」的应对保留，因为迁移只是改变了这块盘，并没有改变机制对文件系统的依赖方式。

1. **符号链接、junction 与硬链接**。exFAT 标准不含这些结构，依赖链接的工具会直接失败。NTFS 支持这些结构，但换机后由 ACL 记录的权限无法跨机解析，因此机制仍不依赖链接。若遇到 exFAT 介质，规避方式是让 pnpm 采用 hoisted 或 copy 形式的 node 链接器，避免 `mklink`，避免依赖 Git 符号链接。
2. **文件权限与访问控制列表**。exFAT 不提供。NTFS 提供，但其 ACL 记录的是创建主机上的安全标识符，换机后无法解析，跨机权限强制实际无效。因此写入内聚依然依靠环境变量重定向与审计脚本共同保证，不存在可跨机生效的强制技术兜底。审计脚本因此不是可选项。
3. **日志型事务**。基础 exFAT 不具备，Microsoft 把事务安全语义放在独立的 TexFAT 扩展中。NTFS 提供日志。无论哪种文件系统，都应使用系统安全弹出，并避免在安装依赖、构建等写密集操作进行中拔出。
4. **簇大小**。32GB 容量若按较大簇格式化，海量小文件场景会明显浪费空间，`node_modules` 是典型。当前 NTFS 采用 4096 字节分配单元，已按此考虑选择。

关于 exFAT 约束能否事后解除，只有整盘转 NTFS、在 exFAT 上叠加 VHDX 容器、或继续在工具层规避三条路，完整对比见 `FILESYSTEM-OPTIONS.md`，迁移步骤见 `NTFS-MIGRATION.md`。

### 5.2 路径与脚本

5. **路径含空格**。当前路径 `E:\fanhe Work` 含空格，所有脚本都必须给变量加引号。本次实施过程中就曾出现 bash 循环未加引号，把 `fanhe Work` 拆成两段，进而在 E 盘根目录生成游离目录的情况。该问题已定位、修复并复验。
6. **硬编码盘符**。这是可移植性的头号杀手，常见藏身之处包括 IDE 工程文件、`.sln`、`launch.json`、`.env` 与各类构建脚本。审计脚本会扫描这批文件并列出具体位置。
7. **Windows 260 字符路径上限**。U 盘路径叠加深层依赖目录容易超限。入口脚本已通过 `GIT_CONFIG` 注入 `core.longpaths=true`，其余工具需逐个确认。

### 5.3 包管理器与工具链

8. **全局缓存默认落在系统盘**。npm、pip、Gradle、Maven、Cargo、Go 默认把缓存与全局仓库写在用户目录，累积可达数 GB。机制已全部重定向，`ws-doctor.ps1 -Leak` 用于验证。
9. **Python 虚拟环境不可直接迁移**。`pyvenv.cfg` 与控制台脚本记录绝对路径。同一解释器下用 `--upgrade` 重建即可；解释器不同的电脑上需要重建虚拟环境。后一种情形机制无法自动修复，会由健康检查明确报出并给出命令。
10. **Node 的 `.bin` 转发脚本记录绝对路径**。换机后需 `npm rebuild` 重建，机制已自动执行。
11. **pnpm 的全局硬链接仓库与 exFAT 冲突**。需要关闭硬链接模式，改用复制模式。
12. **Docker 与 WSL 的数据不随工作空间移动**。守护进程运行在宿主机，镜像与卷位于宿主机磁盘。若项目依赖容器，需要单独规划数据迁移。

### 5.4 运行环境

13. **未经入口脚本启动**。IDE 若从普通快捷方式启动，其内置终端与任务不会继承重定向。规避方式是从 `infra/portable/ws-run.cmd` 启动 IDE，或在该 IDE 的终端中先加载 `ws-env`。
14. **临时目录被重定向的副作用**。少数安装程序假设临时目录位于系统盘且路径简短，重定向到含空格的 U 盘路径可能失败。遇到此类情况，可在单次会话中临时排除 `TMP` 重定向。
15. **杀毒软件实时扫描**。对可移动介质的实时扫描会拖慢构建，并可能隔离构建产物。可将工作空间加入排除列表。
16. **云同步目录**。若工作空间被 OneDrive 一类工具同步，会产生冲突副本。应排除同步。

## 六、日常使用

在 Windows 上，所有操作都从入口脚本进入，环境才会生效。

```bat
infra\portable\ws-run.cmd npm install
infra\portable\ws-run.cmd python -m pytest
infra\portable\ws-run.cmd -Shell
```

在 bash 或 Git Bash 中。

```bash
source infra/portable/ws-env.sh
./infra/portable/ws-run.sh npm install
```

换到新电脑之后的标准动作。

```bat
infra\portable\ws-run.cmd --version
infra\portable\ws-repair.ps1 -CheckOnly
infra\portable\ws-doctor.ps1
infra\portable\ws-doctor.ps1 -Baseline
```

第一条启动并触发自愈，第二条单独查看工具链健康检查结果，第三条确认没有硬编码盘符，第四条记录外部缓存基线，便于日后用 `-Leak` 比对。
